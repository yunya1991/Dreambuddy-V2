## 三、P0 阻断项（必须修订）

### B1｜把「已实现的校验」写成「未做」——L2-E09 / GAP-11 双重失真

**位置**：TECHNICAL_DESIGN §2.2 `L2-E09`（判 🟡「未做逐角色工具数硬校验」）、§6 `GAP-11`。

**事实**：`47-MCP管理系统/registry/scripts/validate_mcp_registry.py` 第 379–435 行**已经实现** worker_roles 校验：

- 引用的 `shell_id` / `tool` 必须存在；
- `0 < len(role_tools) <= max_tools_per_shell`（每角色上限，超限直接报 `E-... 超出每角色上限 ...（ADR-4）`）。

**影响**：把已有护栏报成缺口，会引导后续做重复建设；同时与本文 §3.2「硬约束 4」自相矛盾。

**修订要求**：`L2-E09` 改为 ✅ 并注明校验器文件 + 行号；删除 `GAP-11`，或改写为「角色池已校验，缺的是**角色清单与 34 Worker 实际花名册的一致性**」（若确有此缺口需给证据，否则删）。

---

### B2｜把「零实现」写成「部分可用」——cognition 裁决层

**位置**：TECHNICAL_DESIGN §2.1 `L2-K01` 表格外的说明、SPEC-56 §4.1 第 4 行「`cognition_signal.verdict` 🟡 裁决语义有，路线字段未落地」。

**事实**：全仓 `*.py / *.ts / *.tsx` 检索 `cognition_signal` **零命中**；该字段只存在于 [SPEC-v1.4](../34-前端应用训练系统/SPEC-v1.4-L0L1L2-路由边界与认知裁决.md) 的契约描述中。`l2_route` 同样零命中（这是预期的，但说明「裁决 → 路线」整条链都还停在文档层）。

**影响**：SPEC-56 §0 第 4 条「L2 与 L1 边界已可机器判定」成立，但「认知裁决已具备」不成立。这会误导 P1 排期（以为只差一个字段）。

**修订要求**：
- `cognition_signal` 状态改 ⬜，注明「契约已定义、实现为零」；
- SPEC §4.1 该行改为 ⬜，并把「裁决层落地」升为 GAP 并给优先级；
- §0 第 4 条改写为「L1 侧准入可机器判定；L2 侧裁决与路线**尚未实现**」。

---

### B3｜计数错误：IPC 命令 17 → 18；53 插件「3 个」→ 13 条

**位置**：TECHNICAL_DESIGN §1.1「dsh_frontend_bridge（IPC，17 条命令）」；§2.4 `L2-P02`「自有插件 3 个」。

**事实**：
- `dsh_frontend_bridge.py` 命令字典实为 **18** 条：8 个 `subagent.*` + `c-drive` + `c-drive.debate` + `synthesizer` + `orchestrator` + `orchestrator.status` + `knowledge.search` + `skill.index` + `user.memory` + `data.dal_query` + `shell.stats`。原 17 的成因是统计正则的字符集漏了下划线，把 `data.dal_query` 漏掉。
- `53-DSH插件模块/plugin_whitelist.yaml` 实测 **13 条 `status: "approved"`**，不是 3 个（「3 个」引自 11-13 的调研稿，已过期）。

**影响**：命令面是 L2-E 的对外能力边界，数错会直接影响壳与角色设计；插件数错会误导 53 的治理阶段判断。

**修订要求**：改为 18 与 13，并注明「实测日期 + 复跑命令」。

---

### B4｜状态过强：45 门禁标 ✅「生产接线」

**位置**：TECHNICAL_DESIGN §1.2 表格最后一行。

**事实**：`gate_45_adapter.py` 头注释写明 `submit_fn / poll_fn` **由调用侧注入**，生产应接 HTTP `:8790`、测试注入 fake；文件本身「不持网络与存储」。即：**适配器已就绪，生产注入点未见证据**。

**影响**：验收门禁 G-L2-4 的真实生效状态被高估，可能让 P2「转硬门」缺少前置条件盘点。

**修订要求**：改 🟡，备注「适配器就绪；生产注入点待核（需给出调用侧文件/行号才能回 ✅）」。同类问题：§1.2 中 25/26/27/28 的 🟡 也缺证据，应统一补「载体文件或降为 ⬜」。

## 四、P1 重要问题（影响可维护性，非阻断）

### B5｜缺机器可读能力清单，43 项能力只活在散文表格里

54 有 `capability_manifest.yaml`（48 出口、`visibility` 字段、可被校验），56 没有对应物。后果：
- GAP 与状态列无法被 CI 校验，「只改图标不改代码」无法拦截（违反本文 §0.6 规则 2）；
- L2 壳的 `capability_id` 与本文 `L2-*` 无映射，层级审计断链。

**建议**：P0 之后建 `56/config/l2_capability_manifest.yaml`，字段 `{id, name, layer, subloyer, carrier, exposure, status, evidence, gap}`，并加一条校验脚本。

### B6｜同一件事三种说法（E09 / GAP-11 / §3.2 硬约束 4）

§2.2 说未校验、§6 立 GAP-11、§3.2 又说已校验。修订 B1 后需全文扫一遍同类矛盾（尤其 K14 与 §4.1 表）。

### B7｜「C 层双实现」缺判据

`L2-K07` 称 `sacg_orchestrator` 与 `dreamos/core/compute` 双实现并存。事实成立（`agent.py:39` 导入 `GraphExecutor`），但**未说明谁是权威**：DreamOS 内核走 `core/compute`，34 侧走 `cdrive_v3_router`，两者服务对象不同。这不是「重复建设」，而是「两个宿主各有一套」。当前表述会让读者误判为技术债。

**建议**：改成「两宿主两实现，权威性按宿主切分；跨宿主一致性由 IF-2 OKR 契约保证」，并把「是否需要统一」列为 Q5 待决。

### B8｜IF-L2-1 与 Q1 冲突

SPEC §4.3 称「本文首次冻结 `L2Envelope` 字段集」，§7 Q1 又问「信封是否与 L0 `0.1` 合并」。**先冻结再问要不要合并**，顺序错误：若 Q1 选 A（合并），字段集定义位置就要变。

**建议**：Q1 提到 §4.3 之前作为「冻结前置决策」，或直接采建议值 A 并在 §4.3 注明「在 0.1 基础上扩展」。

### B9｜状态列缺代码位置，违反自定规则

本文 §0.6 规则 2 要求「状态变更必须附代码位置」，但 §2 中 `L2-G02/G04/G06/G07/P01/P02/P03` 多条只给目录名、无文件或行号；`L2-A02` 亦然。规则与执行不一致时，规则会立刻失效。

**建议**：逐条补最小证据（文件路径即可），否则降级为 ⬜ 并标「未核实」。

## 七、结论

- **方向正确**：五子层、唯一判据、只读边界、信封与 Mandate 三件套，都与既有 SSoT 一致，没有新造架构。
- **当前不可直接作为实施依据**：4 个 P0 中有 2 个是「虚实颠倒」（B1 低估已有护栏、B2 高估未实现能力），会让 P1/P2 排期整体偏乐观。
- **处置建议**：先按 R1–R6 修订文档（不改代码），复审通过后再开 P0-1（信封落地）。
