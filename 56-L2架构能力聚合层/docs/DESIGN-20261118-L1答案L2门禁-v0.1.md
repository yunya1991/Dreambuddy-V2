# DESIGN-20261118 — AI Agent 模式下 L1 答案的 L2 门禁与接管（v0.1）

> 状态：待评审
> 关联：`ASSESSMENT-20261118-架构总装与调度能力评测-v0.1.md` §12
> 范围：`3.1-FRONTEND` 的 `/api/agent/chat` 链路；不改 L1 Python 路由判定本身

---

## 1. 背景与目标

### 1.1 问题

用户打开 AI Agent 开关后，L1 确定性直答仍会先于模型执行并直接返回。实测两类错误：

- 「查询比特币价格」→ 行情卡（正确）
- 「分析比特币未来几天价格走势」→ 仍是行情卡 + 通用追问（错误；已由 D-12 的意图闸门部分修复，但只覆盖"分析类问法"这一种）

根因不是某一个正则，而是**没有任何机制检查"L1 答案是否真的回答了这个问题"**。

### 1.2 目标

在 `agent_enabled === true` 时，对每一条 L1 直答执行 L2 门禁：

1. **审核**：判断 L1 答案是否正确、完整、与数据一致；
2. **接管**：审核不通过时，在同一请求内由 L2（agent + 工具）重新回答；
3. **零回归**：关闭 AI Agent 时保持 L1 零 token 直答的既有体验。

### 1.3 非目标

- 不重写 L1 意图识别与路由（`l1_route_signal.py` 保持不变，D-12 闸门保留）；
- 不做"所有问题都转 L2 完整任务链"；
- 不做多模型投票 / 人工标注闭环（后续可加）。

## 3. 总体设计

```
用户消息
   │
   ├─ agent_enabled === false ──► L1 直答
   │                               └─ G1 规则门（仅拦截空答/占位）
   │                                     ├ pass ─► 返回 L1（零 token）
   │                                     └ fail ─► 返回"L1 无法回答，请开启 AI Agent"
   │
   └─ agent_enabled === true ───► L1 直答
                                   └─ G1 规则门
                                        ├ pass ─────────────► 返回 L1（打标 pass）
                                        └ uncertain/fail
                                              └─ G3 LLM 轻审（judge）
                                                   ├ pass ─────► 返回 L1（打标 reviewed）
                                                   ├ timeout ──► 返回 L1（打标 timeout，记录）
                                                   └ fail ─────► L2 接管（同路由重答，最多 1 次）
```

**核心原则**：G1 拦掉绝大部分确定性错误（零成本）；G3 只处理灰区；接管只发生一次。

## 4. G1 规则门（零 token，<10ms）

### 4.1 输入

```ts
interface GateInput {
  message: string;          // 用户原始问题
  intent: string;           // L1 返回的 intent（price_query / metric_series / ...）
  answer: string;           // L1 答案文本
  data?: unknown;           // L1 返回的结构化数据
  routeSignal?: { decision?: string; reasons?: string[]; route_confidence?: number };
}
```

### 4.2 规则清单

| ID | 规则 | 判定 |
|---|---|---|
| R1 | 空答 / 占位词（`暂无数据`、`未知`、`加载中`、`分析中`、`处理中`、`N/A`）出现在答案前 80 字 | **fail** |
| R2 | 意图-答案结构不一致 | **fail** |
| R3 | 实体不一致：用户问的实体（BTC/ETH/茅台…）未出现在答案中，或答案主标的与提问不符 | **fail** |
| R4 | 方向矛盾：问题显式含"跌/下跌/回调"而答案只讲上涨（或反之） | **fail** |
| R5 | 新鲜度：`price_query` 答案无时间戳，或时间戳距今 > 5 分钟 | **uncertain** |
| R6 | 覆盖度：问题含 ≥2 个可识别指标，答案缺失其中任一 | **uncertain** |

R2 按意图细分：

- `price_query`：必须同时含「数字价格」+「标的名称」
- `metric_series`：必须含「指标名」+「≥3 个数据点」或时间序列表述
- `data_insight` / `data_query`：必须含被问实体，且至少 1 个数值字段
- `artifact_query` / `doc_search`：必须含来源/引用标记

### 4.3 判定汇总

```
任一 R1/R2/R3/R4 → fail
否则任一 R5/R6  → uncertain
否则            → pass
```

### 4.4 实现约束

- 规则只做**模式匹配 + 实体抽取**，不调用模型；
- 实体词表复用 `market-data-adapter` 与 `entity_aliases.json`，避免第二套词表；
- 规则命中必须给出 `reasons`（如 `["R3:entity_mismatch", "R2:missing_price"]`），供接管 prompt 使用。

## 5. G3 LLM 轻审（灰区专用）

### 5.1 触发条件

仅当 `agent_enabled === true` 且 G1 判定为 `uncertain`（`fail` 不需要 LLM，直接接管）。

### 5.2 契约

- 模型：复用当前 agent 模型（`resolveAgentModel`）
- 参数：`temperature=0`，`maxTokens=200`，`timeout=8s`
- 输入：用户问题、L1 intent、L1 答案（截断 1500 字）、L1 结构化数据摘要（截断 800 字）、G1 reasons
- 输出（强制 JSON）：

```json
{
  "verdict": "pass | fail",
  "reasons": ["answer_does_not_address_question"],
  "missing": ["未来走势判断", "时间窗口"]
}
```

### 5.3 Judge 系统提示（要点）

1. 只判断两件事：**是否回答了用户的问题**、**是否与给定数据矛盾**；
2. 不评价文风、不补充新事实；
3. 允许的输出只有枚举值，禁止自由文本（防注入）；
4. 判定 `fail` 必须给出 `missing` 列表，供接管使用。

### 5.4 超时与异常

- 超时 / 解析失败 → 视为 `timeout`：**放行 L1 并打标**，不接管；
- 理由：门禁不可用时不阻断主链路（FAIL-OPEN），但必须记录，便于后续统计误放行率。

---

## 6. 接管协议（同路由重答）

### 6.1 注入内容

接管时在消息列表中追加一条系统级上下文（不作为用户消息展示）：

```
[L1 直答未通过门禁]
用户问题：{message}
L1 草稿：{answer}
未通过原因：{reasons}
缺失项：{missing}

要求：
1. 先使用可用工具核实数据，再回答；
2. 不要复述 L1 草稿；
3. 若工具取不到数据，明确说明"暂无数据"，禁止编造。
```

### 6.2 边界

- **最多接管 1 次**：接管后的回答不再进入门禁，标记 `l2_takeover=true`；
- 接管仍失败 → 返回接管结果 + `degraded=true`，不重试；
- 接管消耗的 token 计入同一次 usage 结算，前端可见。

## 7. 开关矩阵

| `agent_enabled` | G1 | G3 | 接管 | 用户可见 |
|---|---|---|---|---|
| `false` | 跑 | 跳过 | 不接管 | G1 fail → "L1 无法回答该问题，请开启 AI Agent" |
| `true` | 跑 | 灰区跑 | fail 时接管 | 响应头标注 gate 结果 |

> 说明：关闭状态下仍跑 G1，是为了避免把空答/占位直接返回给用户；但绝不产生 token。

## 9. 接口契约

```ts
// src/lib/l1-answer-guard.ts
export type GateVerdict = 'pass' | 'fail' | 'uncertain' | 'timeout';

export interface GateResult {
  verdict: GateVerdict;
  reasons: string[];
  missing: string[];
  gateMs: number;
  judgeMs?: number;
}

export async function reviewL1Answer(
  input: GateInput,
  opts: { allowJudge: boolean; judge?: (prompt: string) => Promise<string> },
): Promise<GateResult>;
```

`route.ts` 调用顺序：

1. `tryL1Direct` 命中；
2. `reviewL1Answer(..., { allowJudge: agent_enabled === true })`；
3. `pass` → `textUiResponse(answer, headers)`；
4. `fail` 且 `agent_enabled === true` → 走既有 agent 分支并注入接管上下文；
5. `fail` 且 `agent_enabled === false` → 返回显式提示，不返回错误答案。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Judge 与生产模型同源，自审偏袒 | 误放行 | 规则门优先；judge 必须做"数值一致性"核对 |
| 用户消息注入 judge prompt | 越权输出 | judge 输出仅接受枚举；输入用分隔符包裹并截断 |
| 过度接管 | L1 零 token 价值被抵消 | 接管率设 5% 告警阈值；按 intent 分桶观察 |
| 门禁超时 | 延迟抖动 | 8s 硬超时 + FAIL-OPEN 放行 + 打标 |
| 接管循环 | 成本失控 | 最多 1 次，硬限制 |

### 15.3 实施中的口径修正（相对 v0.1 初稿）

1. **R6 从 uncertain 改为 fail**：多指标只答一部分是客观缺失，交给 LLM 判反而增加延迟与不确定性。实测中该场景 judge 超时后放行了低质量答案，说明"该硬判的不能软判"。
2. **Judge 超时 8s → 15s**：该 provider 实测单次生成常超 8s；仍保留 FAIL-OPEN。
3. **新增 `AGENT_JUDGE_MODEL`**：审核可独立使用轻量模型；未配置时复用主模型。实测主模型延迟使 judge 频繁超时，这是当前门禁生效率的首要瓶颈。
4. **`L1_TIMEOUT_MS` 16s → 32s**：`/api/data/query` 脚本上限为 30s（含语义模型冷启动），内层 16s 会在冷启动时必超时，导致门禁根本没机会执行。这是实测发现的前置缺陷。

### 15.4 实测证据（本机 3001）

| 场景 | `x-l1-gate` | `x-l2-takeover` | 结果 |
|---|---|---|---|
| Agent 关 + 查询比特币价格 | `pass` | `false` | 返回 L1 行情卡（零 token） |
| Agent 开 + 查询比特币价格 | `pass` | `false` | 返回 L1 行情卡（未误接管） |
| Agent 开 + 多指标（L1 复合问法已交 L2） | 无（L1 未直答） | — | 直接进入 agent 推理 |
| Agent 开 + L1 答案含旧日期 | `timeout` | `false` | FAIL-OPEN 放行并打标（judge 延迟超限） |

### 15.5 已知限制

1. **Judge 延迟是主瓶颈**：主模型单次 >15s 时门禁退化为 `timeout` 放行；建议配置 `AGENT_JUDGE_MODEL` 指向低延迟模型。
2. **L1 冷启动 14~21s**：语义模型每次进程启动加载，导致首个请求接近超时。中长期应改为常驻服务或预热，否则门禁与 L1 都受影响。
3. **当前线上难构造"硬 fail 且 L1 直答"自然样本**：L1 自身的复合问法闸门已把多指标问法交 L2；接管路径主要由规则与单测保证，建议后续用录制的 L1 响应做回放测试。
