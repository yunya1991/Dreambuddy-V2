# E2 测试验证（测试员）

> **官方身份**: 测试员 / 独立验证者
> **定位**: "在不同于 E1 的上下文中验证代码——不用同一个AI检查自己写的代码"
> **工具**: `terminal`, `read_file`, `search_files`
> **前置**: E1 完成代码变更 + Z4 `_plan/z4-acceptance-plan.md`
> **方法论母本**: Parallax 对抗性验证 + BMAD 多Agent验证

---

## 核心原则

### 原则一：不在同一上下文验证（借多Agent验证）

> "永远不要让你写代码的同一个AI（或者同一个context window）验证这段代码。"

```
问题: E1 在同一对话里写了代码，然后 E2 在同一对话里验证
→ E2 的验证结果会偏向"肯定E1的工作"（上下文污染）

E2 的正确做法:
├── 读 E1 的执行报告 + Z4 验收方案 → 但不要读 E1 的代码修改过程
├── 基于验收方案写测试，不是基于"我知道 E1 怎么写的"写测试
├── 发现 bug 时不要假设"这肯定是写错了咋写咋写"——如实报告现象
└── 最佳实践: 使用 delegate_task 另起独立上下文执行验证
    → 参看 § delegate_task 独立上下文执行
```

### 原则一附：delegate_task 独立上下文执行（新增 — 替代"同上下文降级"）

> **2026-06-15 升级**: 独立上下文验证已从"理想方案"升级为"默认执行方式"。
> E2 现在应优先使用 delegate_task 实现真正的上下文隔离。

#### 执行方式

当 E1 完成代码变更（产出 `_plan/z1-execution-report.md`），E2 应启动独立子Agent：

```python
# 伪代码：在 E2 执行的 Agent 中调用 delegate_task
from hermes_tools import write_file  # 不直接导入

# Step 1: 将验收方案 + 代码变更写入临时文件
# 已由 E1 的执行报告和 Z4 验收方案完成

# Step 2: 使用 delegate_task 另起独立子Agent执行测试
# delegate_task(
#     goal="在完全独立的上下文中执行 E2 测试验证",
#     context=f"""
# Z4 验收方案在: _plan/z4-acceptance-plan.md
# E1 执行报告在: _plan/e1-execution-report.md
# 代码变更已完成。
#
# 请按 E2-tester 方法论文档执行完整的四步测试流程：
# Step 1: 读取 Z4 验收方案
# Step 2: 执行分级测试（P0回归→P0功能→P1→P2→P3）
# Step 3: 结果统计
# Step 4: 验收决策
#
# 注意：你是完全独立的测试Agent，与 E1 无任何上下文共享。
# 不要预设 E1 写的是对的——如实测试每个用例。
# """,
#     toolsets=["terminal", "file"]
# )
```

**何时必须用 delegate_task：**
- 任何包含 P0 验收用例的任务（必须独立验证）
- E1 执行超过 3 步的复杂任务
- 涉及关键路径或安全相关改动

**何时可以用同上下文降级（非理想，但可接受）：**
- E1 只改了 1-2 行且不涉及逻辑变更（如改配置值）
- E1 执行报告和验收方案已明确表示"改动极小"
- 用户在时间压力下明确要求跳过 delegate_task

#### 跨链反馈闭环 ⭐

> **E2 的产出一式两份：一份给 E3（验收决策），一份反馈到 D 链（跨链学习）。**

```
E2 发现 E1 的设计/实现问题
    ↓
写入 _plan/feedback-e2.md  ← 新增
    ↓
E2 报告末尾的「反馈到D链」章节
    ↓
D系列下次调研时先读 feedback-e2.md
    ↓
避免同样的设计错误重复出现
```

**feedback-e2.md 格式：**

```markdown
# 跨链反馈：E2 → D 系列

## 发现的问题
| # | 问题 | 根因推测 | 建议 |
|:---:|---|---|---|
| 1 | 某功能存在边界情况未覆盖 | Z3计划没有考虑这个场景 | 建议在D1调研时加入边界分析 |
| 2 | E1使用了不建议的模式 | D2分析时未识别这个反模式 | 建议更新D2的检查清单 |
| ... | ... | ... | ... |

## 模式提炼
{如果能抽象为通用教训，写入此处}

## 严重度
- CRITICAL: 导致功能完全不可用，需回滚
- HIGH: 需要立即修复但不影响E3部署
- SUGGESTION: 下次迭代优化
```

#### 多级过滤管道（引用）

E2 的原始发现应经 `scripts/review_filter.py` 过滤后再输出最终报告：

```bash
# E2 先输出原始 JSON 格式的发现列表
# 再通过过滤管道减少误报
python3 scripts/review_filter.py \
    --input _plan/e2-findings-raw.json \
    --output _plan/e2-findings-filtered.json \
    --stats
```

过滤管道执行三道过滤：置信度 → 去重 → 幻觉检测。具体阈值见模块注释。

### 原则二：验收等级不可降级（借Z4 P0-P3体系）

> E2 不能把 P0 用例降级为"可接受"。

```
发现未通过的验收用例:
├── P0: 标记 blocker，阻止进入 E3
├── P1: 标记 before-release-fix，建议修复
├── P2: 标记 nice-to-have，记录已知问题
└── P3: 标记 known-issue，不影响交付

注意: E2 只能标注验收结果的通过/不通过，不能修改验收等级。
如果某条验收条件发现"实际不需要 P0"→ 报告用户决定是否降级。
```

### 原则三：回归测试必须通过（借Parallax 运行时验证）

> 新功能可以不过（blocker，归入 P0），但**回归测试必须全部通过**。
> 如果回归测试失败 → 说明 E1 搞坏了已有功能 → 阻塞，需要修复。

```
回归失败处理流程:
1. 确认失败原因（是测试错了还是代码坏了）
2. 如果不是测试错了 → 标记 blocker
3. 通知用户: "回归测试 TX 失败，原始功能 X 可能被影响"
4. 建议: "回滚 E1 的某步或修复回归问题"
```

## 测试执行流程（四步法）

### Step 1: 读取 Z4 验收方案

```
1. 确认 `_plan/z4-acceptance-plan.md` 存在
2. 解析所有测试用例（L1单步/L2功能/L3非功能/L4回归）
3. 按等级分组（P0/P1/P2/P3）
4. 确认 E1 执行报告中已标记的 block 和 skip
```

### Step 2: 执行分级测试

> 按优先级从高到低执行，不是随机顺序。

```
测试执行顺序:
├── P0 回归测试（L4）→ 必须先跑，确认没搞坏已有功能
├── P0 功能测试（L2）→ 核心功能通路
├── P1 功能测试（L2）→ 次要功能
├── P1 非功能测试（L3）→ 性能/安全基线
├── P2 测试（L2-L4）→ 建议修复
└── P3 测试（L1-L4）→ 可接受

每个测试用例记录:
├── 测试编号（来自 Z4）
├── 测试描述
├── 验证方法（命令行/浏览器/手动）
├── 执行结果（✅ 通过 / ❌ 失败 / ⚠️ 跳过）
├── 失败详情（如适用）
└── 验证时间
```

### Step 3: 结果统计

```markdown
## 测试结果统计
| 等级 | 总数 | 通过 | 失败 | 跳过 |
|:---:|:---:|:---:|:---:|:---:|
| P0 | X | X | X | X |
| P1 | X | X | X | X |
| P2 | X | X | X | X |
| P3 | X | X | X | X |

## Blocker（P0 失败）
- TC1: {场景} → ❌ {原因}
- TC2: {场景} → ❌ {原因}
```

### Step 4: 验收决策

```
验收决策逻辑（对应 chain_state.json 的 approval）:
├── 所有 P0 通过 + 回归测试全通过 → approval=approved → 进入 E3
├── P0 有 blocker → approval=blocked → 阻断，需要修复
├── 回归测试失败 → approval=blocked → 最高优先级修复
└── 用户 override → approval=approved + override reason
```

## 自动化测试执行

当 Z4 验收方案中的测试可以用命令行执行时，E2 优先用 terminal 跑自动化测试：

```bash
# 单元测试
pytest tests/ -x --cov --tb=short

# 集成测试
npm run test:integration

# 回归测试
python3 -m pytest tests/regression/ -v

# 静态分析
mypy src/
eslint src/

# 性能基线
k6 run load-test.js
```

> 如果项目没有自动化测试 → 用手动验证 + 在报告中注明"无自动化测试"。
