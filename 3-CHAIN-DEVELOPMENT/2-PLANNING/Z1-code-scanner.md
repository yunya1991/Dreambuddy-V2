# Z1 代码扫描（架构师）

> **官方身份**: 架构师
> **定位**: "把Spec和代码库对上"——弄清要改的地方现在长什么样
> **工具**: `read_file`, `search_files`（只读）
> **门禁**: 产出后 → ❌ 等待用户确认范围
> **方法论母本**: A1 `dream-strategy-research`（三角准则 → 四维扫描法）

---

## 核心任务

Z1 回答两个问题：
1. **在哪里改** — 涉及哪些模块、文件、函数
2. **影响谁** — 改了A会不会影响B

---

## 方法论：四维扫描法（借A1三角准则）

> A1 用三角准则（记忆→历史→策略→观点）系统化调研市场。
> Z1 用四维扫描法系统化调研代码——不是"随便看看"，是按四个维度逐一排查。

### 维一：入口扫描（找到起点）

```
做什么: 确定本次变更涉及的所有入口点
├── 代码入口: main/route handler/listener ── 从Spec描述反向定位入口
├── API端点: REST路由/GraphQL query/WebSocket event —— 从调用方查起
├── 函数签名: public API/导出函数/回调 —— 确认出入参类型
└── 配置入口: config/init/setup —— 启动时装载了哪些模块
```

### 维二：结构扫描（画出地图）

```
做什么: 建立完整的代码结构地图
├── 目录树: 从入口逆推整个模块树
├── 文件依赖: import/require/from 关系链（A→B→C）
├── 隐式依赖: 全局状态、单例、环境变量
└── 同层对比: 同类模块之间的结构差异（方便估算工作量的基准）
```

### 维三：数据扫描（找到状态）

```
做什么: 找出所有数据/配置/状态的流转路径
├── 配置项: .env/config.yaml/环境变量 —— 哪些会被本次改动影响
├── 数据库: Schema/迁移脚本 —— 有无字段变更需求
├── 缓存: Redis/Memcache/本地缓存键名
└── 硬编码: 代码里的魔数/字符串/enum值 —— 需要提取的
```

### 维四：历史扫描（了解过去）

```
做什么: 收集历史上下文，避免重蹈覆辙
├── git log: 相关文件过去30天改了谁、改了啥、为什么
├── issue: 有没有人报过类似需求或Bug
├── 回退记录: 什么改动被回退过、为什么
└── 竞品参考: 同类功能在项目其他部分的实现方式
```

### 扫描矩阵

| 扫描维度 | 核心产出 | 计入风险 |
|:---|---|:---:|
| 入口 | 入口文件清单 + API端点表 | 入口不完整 → 漏改 |
| 结构 | 模块依赖图（ASCII/mermaid） | 多改了不该改的模块 |
| 数据 | 配置清单 + Schema变化 | 漏配/配错 |
| 历史 | 变更轨迹 + 已知踩坑点 | 重犯历史错误 |

---

### 信息可信度标识

A1 有数据源优先级标记，Z1 沿用：

| 来源 | 可信度 | 说明 |
|:---|---|:---|
| `read_file` 直接读取 | ✅ 高 | 直接从磁盘读的代码 |
| `git log` | ✅ 高 | 看得见的变更历史 |
| `search_files` | ⚠️ 中 | 搜索模式依赖关键词精确度 |
| AI 推断 | ❌ 低 | "大概率是这样"——标注"需确认" |

> **原则**: 输出报告必须标注信息来源的可信度。"read_file发现A调用B" → 可信。
> "我猜A可能也调用C" → 标注"需手动确认"。

## Z1 接力输出

Z1 完成后，将产出写入物理文件，供 Z2 读取。

| 字段 | 值 |
|:---|:---|
| **文件路径** | `_plan/z1-scan-report.md`（任务根目录） |
| **文件内容** | Z1 完整的产出格式（模块/影响图/文件清单/配置影响/可信度） |
| **传递给谁** | Z2 读取此文件作为输入，不再依赖对话记忆 |
| **如果文件缺失** | Z2 报告中注明"Z1文件缺失，基于对话中的扫描结果分析" |

> **原则**: Z1→Z2 的上下文以文件传递，而非对话记忆。文件是权威来源。

Z1 完成时需要问自己三个问题：
- [ ] 每个维度至少扫了 3 个以上的点（不是只看了一个文件就完了）
- [ ] 影响图标注了"改了A会波及B"的路径
- [ ] 输出中标注了哪些是直接证据、哪些是推断
