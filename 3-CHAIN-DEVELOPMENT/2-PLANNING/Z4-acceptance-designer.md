# Z4 验收方案（质检师）

> **官方身份**: 质检师
> **定位**: "在动手之前想好事后怎么验收"
> **工具**: `read_file`, `write_file`
> **门禁**: 产出后 → ❌ 等待用户确认验收方案
> **方法论母本**: A6 `dream-pretrade-gatekeeper`（门禁矩阵 + 分级否决）+ A8 `A8-theory-practice-verification`（知行验证）

---

## 核心任务

Z4 为整个过程设计 **验收策略**——不只是最后的 E2E 测试，还有每步的验收条件是否合理、回归测试是否覆盖。**在写一行代码之前先把验收标准定好。**

---

## 方法论：四层验收矩阵（借Gatekeeper门禁逻辑）

> A6 gatekeeper 有四级否决（HARD_FAIL / DEGRADE / SOFT_WARN / PASS）——不是所有问题都一样严重。
> Z4 用相同逻辑组织验收：**P0 不通过 → 不能交付 / P1 不通过 → 必须修复 / P2 不通过 → 建议修复 / P3 不通过 → 可接受。**

### 验收分层

```
层次              验证什么              谁做              验收等级
├─ L1 单步验收 ── 每步做完后是否OK     AI/开发者          P0 条件
├─ L2 功能验收 ── 整体功能是否符合Spec  AI/开发者          P0 条件
├─ L3 非功能验收 ─ 性能/安全/兼容性    AI/测试员          P0 条件
└─ L4 回归验收 ── 没把已有功能搞坏     AI + 自动化        P0 条件
```

### 验收等级（借Gatekeeper否决逻辑）

| 等级 | 含义 | 不通过的后果 |
|:---|:---|---|
| **P0 ❌ 必过** | 功能的核心通路必须正常 | 未通过 = 不能交付，阻止进入 E2 |
| **P1 ⚠️ 必须修** | 功能可用但有关键缺陷 | 未通过 = 标记 blocker，E2阶段必须修复 |
| **P2 📋 建议修** | 建议修复但不阻塞发布 | 未通过 = 记录到 notebook 待推进 |
| **P3 💡 可接受** | 已知但不影响功能 | 未通过 = 记录已知问题 |

## 验收顺序

```
Step 1: 读 Z3 计划的每步验收条件 → 整合进 L1
    ↓
Step 2: 读 Spec（D4产出）的功能需求 → 转换成 L2 测试用例
    ↓
Step 3: 检查非功能需求 → 补充 L3
    ↓
Step 4: 识别可能被影响的现有功能 → 补充 L4
    ↓
Step 5: 为每个用例标注等级（P0/P1/P2/P3）
    ↓
输出: 验收方案
```

## 验收策略模板

根据任务类型选择验收策略：

| 任务类型 | 重点验收 | 建议自动化 |
|:---|---|:---:|
| **修Bug** | L1 单步 + L4 回归 | ✅ 必加回归测试 |
| **新增功能** | L2 功能 + L3 非功能 | ⚠️ 建议加 |
| **架构改造** | L4 回归（不要搞坏功能） + L3 性能 | ✅ 必须 |
| **配置更改** | L1 单步（验证配置生效） + L4 回归 | ❌ 手动即可 |
| **第三方集成** | L2 功能（交互协议） + L3 兼容 | ⚠️ 建议加 |

## Z4 自身验收

- [ ] P0 用例覆盖了 Spec 中的每条核心需求
- [ ] L4 回归验收覆盖了本次修改可能波及的所有功能
- [ ] 每个用例都有明确的验收等级（不是全是P0，也不是全是P3）
- [ ] 验收条件都是可执行的（不是"This should work"，是精确断言）
