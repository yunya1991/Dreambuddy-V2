# 三链开发架构指南 (Three-Chain Development)

> 借鉴 6-TRADING A系列（矛盾论/三均准/推演验证）的**系统化方法论**，适配开发场景的**多阶段多Agent接力流程**。
>
> **核心理念**: 不把AI当快速代码生成器，而是当作有方法论约束的协作伙伴。
> **核心机制**: 多Agent接力 + 人工门禁 = 防止跳步。

---

## 架构总览

```
    用户需求
        │
    ┌───┴───┐
    │ 链路1  │  调研分析 → 方案推荐 → 用户选择方案
    │ D系列  │  ┌──────────────┐
    │        │  │ D1 深度调研  │ → 每步人工确认
    │        │  │ D2 分析诊断  │
    │        │  │ D3 推演验证  │
    │        │  │ D4 Spec合成  │
    │        │  └──────────────┘
    └───┬───┘
        │ 门禁1: 用户批准Spec
    ┌───┴───┐
    │ 链路2  │  实施规划 → 路径设计 → 用户确认计划
    │ Z系列  │  ┌──────────────┐
    │        │  │ Z1 代码扫描  │ → 每步人工确认
    │        │  │ Z2 范围划分  │
    │        │  │ Z3 路径设计  │
    │        │  │ Z4 验收方案  │
    │        │  └──────────────┘
    └───┬───┘
        │ 门禁2: 用户批准实施计划
    ┌───┴───┐
    │ 链路3  │  逐任务执行 → 验收 → 交付
    │ E系列  │  ┌──────────────┐
    │        │  │ E1 任务执行  │ → 每步可回滚
    │        │  │ E2 测试验证  │
    │        │  │ E3 部署交付  │
    │        │  └──────────────┘
    └───┬───┘
        │ 用户验收
        ▼
    交付完成
```

## 使用方式

| 场景 | 走什么链路 | 说明 |
|:---|:---|---|
| **极小改动**（<10行，如改个配置/修个单词） | 直接改，不走任何链 | 改完告知 |
| **简单问题**（"这段代码有什么问题"） | 只掉**一个** Skill（如 D2-analyst） | 单问题走单Skill，不启动全链 |
| **小任务**（"把这段代码重构一下"，<100行） | 链路3 直接执行 | 不需要调研/确认，直接做 |
| **中等需求**（"设计个新功能"，100-500行） | 完整三链接力 | D1→D2→D3→D4 → Z1→Z2→Z3→Z4 → 链路3 |
| **复杂需求**（"开发新模块"，>500行） | 完整三链接力 | 同上，每个门禁确认 |

> **阈值说明**: 行数是估算指标，不是硬性规则。关键是**影响面**——改一行配置影响全系统，应该走全链；改100行文档，直接改。
> 
> **不确定时**: 走完整三链接力。多花30分钟调研比"发现改错了重来"划算。

## 核心原则

### 1️⃣ 多Agent接力
每个阶段是不同的Agent身份：
- **D1-D4**（调研链）= 研究员、分析师、推演师、作者
- **Z1-Z4**（规划链）= 架构师、规划师、路径师、质检师
- **E1-E3**（执行链）= 工程师、测试员、运维

### 2️⃣ 人工门禁
每个Agent的产出后 **等待用户确认**，只有确认才进入下一阶段：
```
D1完成 → ❌ 用户确认"调研结论OK" → 进入D2
D2完成 → ❌ 用户确认"根因分析正确" → 进入D3
D3完成 → ❌ 用户选择"方案A/B/C" → 进入D4
D4完成 → ❌ 用户批准Spec → 进入链路2
...
```

门禁点是**天然节点**——AI产出报告后自然停止，用户反馈后手动触发下一Agent。

### 3️⃣ 矛盾论贯穿始终（借A0方法论）
- **D1 调查矛盾**: 代码里的"表面正常但实则有问题"的设计矛盾
- **D2 分析矛盾**: 约束条件之间的首对矛盾（快 vs 好，成本 vs 质量）
- **D3 推演矛盾**: 每套方案内在的权衡（理想 vs 可行）
- **D4 化解矛盾**: Spec中选择的方案如何统一矛盾

### 4️⃣ 工具隔离
每个Agent有固定的工具可见性，物理上禁止越权操作：

| 链路 | 允许工具 | 禁止工具 |
|:---|---|:---:|
| D1-D2（调研） | `read_file, search_files, web_search, web_extract` | `write_file, patch, terminal` |
| D3-D4（推演/Spec） | `read_file, write_file(.md only)` | `patch, terminal, cronjob` |
| Z1-Z4（规划） | `read_file, write_file(.md only)` | `patch, terminal` |
| E1-E3（执行） | 全工具 | 无 |

### 5️⃣ 单步可回滚
链路3中每个任务完成后可独立回退，不影响其他任务。

## 谁在做什么（Agent身份速查）

| Skill | 身份 | 核心动作 | 产出 | 门禁 |
|:---|:---|:---|---|:---:|
| **D1** | 调查官 | 代码现状/依赖/历史/外部方案调研 | 现状调查报告 | 确认调研OK |
| **D2** | 分析师 | 根因链/矛盾识别/方案矩阵 | 根因分析与方案矩阵 | 确认分析方向 |
| **D3** | 推演师 | 方案A/B/C三景推演/风险评估 | 多方案推演报告 | 选择方案 |
| **D4** | Spec作者 | 方案论证/Spec编写/验收标准 | 完整Spec文档 | 批准Spec |
| **Z1** | 架构师 | 模块依赖图/接口分析 | 代码结构图 | 确认范围 |
| **Z2** | 规划师 | 边界切割/依赖排序/回滚点 | 修改范围表 | 确认划分 |
| **Z3** | 路径师 | 步骤分解/验收条件/异常处理 | 实施计划 | 批准计划 |
| **Z4** | 质检师 | 测试策略/验收清单/回归预案 | 验收方案 | 确认方案 |
| **E1** | 工程师 | 逐任务代码实现 | 代码变更 | 验收单步 |
| **E2** | 测试员 | 测试执行/覆盖率检查 | 测试报告 | 验收测试 |
| **E3** | 运维 | 部署/发布/环境检查 | 部署确认 | 验收交付 |

## 映射关系：A系列 → D系列

| A系列（交易） | D系列（开发） | 借了什么 |
|:---|:---|---:|
| A1 深度调研（三角准则+矛盾论调查） | **D1** 深度调研 | 三角准则方法论、调研输出格式、数据源优先级 |
| A2 第一性原理（根因分析+矛盾识别） | **D2** 分析诊断 | 根因链分析、矛盾识别框架、方案矩阵格式 |
| A3 推演验证（多情景+三层索引） | **D3** 推演验证 | 方案A/B/C三景推演、风险评估、可验证假设 |
| A4 战略设计（战略合成+顾问评审） | **D4** Spec合成 | 方案选择论证、范围定义、验收标准 |

> **限制**: 只借方法论（思维方式/分析框架/输出格式），不借具体交易规则和代码。
