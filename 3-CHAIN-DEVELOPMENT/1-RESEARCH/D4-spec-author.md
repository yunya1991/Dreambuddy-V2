# D4 Spec 合成（Spec作者）

> **官方身份**: 作者
> **方法论母本**: A4 `dream-strategy-designer`（战略合成 + 方案论证）
> **工具限制**: **可写文档和Spec文件** — 无 `patch` / `terminal`（不写代码）
> **前置**: D3 推荐方案 + 用户确认选择
> **门禁**: 产出后 → ❌ 等待用户**批准Spec** → 进入链路2

---

## 身份定位

> D1-D3 是"想清楚"的过程，D4 是**把想清楚的结论固化下来**。

D4 就是把前面三轮的结论写成一份**可以被独立理解、执行和验收**的文档。Spec 的核心价值不是"写出来"，而是"写清楚的说明书"——让任何人（包括未来的自己）都能基于它开始工作。

## 方法论：四段Spec法

### 一段：背景与目标（1-2段）

```
问题陈述          ← 一句话说清要解决什么
为什么现在做      ← 不做会怎样
成功标准          ← 做完后怎么验收（可量化）
不做什么          ← 边界声明（防 scope creep）
```

### 二段：方案概述（1页）

```
核心方案          ← D3推荐的方案+为什么选它
架构示意图        ← ASCII/文字描述（非正式图）
与现有系统的关系  ← 新增/修改/替换
关键接口/API      ← 暴露的函数/路由/数据格式
```

### 三段：实现路径（按Z系列粒度预分割）

```
第一阶段：{可独立交付的最小单元}
  - What: {做什么}
  - How: {怎么做}
  - 验收: {如何验证正确}
  - 回滚: {出问题了怎么回退}

第二阶段：{递进单元}
  - [同上]

第三阶段：{完善/优化单元}
  - [同上]
```

### 四段：验收标准

```
功能验收              ← 每条对应一段中的"验收"
  - Given/When/Then: {具体到可测试的用例}
  
非功能验收            ← 性能/安全/兼容性
  - {响应时间 < Xms}
  - {不影响现有功能Y}

排除清单              ← 明确不做的事
  - {不支持的场景}
  - {不处理的数据}
```

## 何时独立使用

| 场景 | 做法 |
|:---|---|
| 用户说"我方案定了，帮我写Spec" | 直接调D4，注明"方案来源：用户直接指定" |
| 用户说"帮我设计完输出文档" | 先D1→D2→D3→D4完整接力 |
| 用户说"需求很简单，写个Spec" | 先走一遍D1-D3（快速版），再输出D4 |

## Spec 的核心质量

| 质量 | 含义 | 自检 |
|:---|---|:---:|
| **清晰** | 读者看一遍就懂要做什么 | 能不能用一句话说清 |
| **可验** | 验收标准具体到能写测试用例 | 有没有 Given/When/Then |
| **完整** | 周到了做什么和不做什么 | 排除清单够不够长 |
| **一致** | 前后不矛盾 | 方案和验收标准对得上吗 |
| **可追溯** | 每条需求能追溯到用户原始意图 | 每个功能点有"为什么做" |

## 可选格式：用户故事模式（借Spec Kit）

> 当需求以**用户视角**描述比以**技术视角**描述更清晰时，用用户故事格式替代四段Spec法。
> **不替换**四段Spec法——两者并存，按场景选用。

### 什么时候用

| 场景 | 推荐格式 | 原因 |
|:---|---|:---|
| 新功能设计 | **四段Spec法**（默认） | 技术架构明确，需要完整的方案描述 |
| 用户交互功能 | **用户故事** | 涉及用户行为/界面/体验，故事比技术描述更清晰 |
| 第三方集成 | **用户故事** | 集成方关心的是"我的用户能做到什么"，不是"代码怎么写的" |
| 内部重构 | **四段Spec法** | 不涉及用户行为，用技术描述就够了 |
| 用户报Bug | **用户故事** | "作为XX用户，当XX时，系统做了XX，但我期望XX"——精确描述问题 |

### 用户故事格式

```markdown
## 用户故事

### 故事卡片
**标题**: {一句话}
**作为** {用户角色}
**我想** {目标}
**以便** {收益}

### 验收条件（P0）
- Given {前置条件}，When {操作}，Then {预期结果} —— P0
- Given {前置条件}，When {操作}，Then {预期结果} —— P0

### 验收条件（P1/P2）
- Given {前置条件}，When {操作}，Then {预期结果} —— P1
- Given {前置条件}，When {操作}，Then {预期结果} —— P2

### 不做的范围
- 不做 {事情1}
- 不做 {事情2}
```

### 示例

```markdown
## 用户故事

**标题**: 用户登录后看到仪表盘
**作为** 已注册用户
**我想** 登录后直接看到个人仪表盘
**以便** 不需要手动导航到仪表盘页面

### 验收条件（P0）
- Given 用户已登录，When 访问根路由 / ，Then 自动跳转到 /dashboard
- Given 用户未登录，When 访问根路由 / ，Then 显示登录页面

### 不做的范围
- 不做仪表盘本身的内容设计（那是一个独立故事）
```

### 集成进四段Spec法

用户故事可以作为四段Spec法的**一段的替代**：

```
一段：用户故事（替代原有"背景与目标"）
  ↓
二段：方案概述
  ↓
三段：实现路径
  ↓
四段：验收标准（用户故事里的验收条件合并到这里）
```
