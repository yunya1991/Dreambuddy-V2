## §0 摘要

**行业已收敛的五条铁律**：

| # | 铁律 | 代表来源 |
|---|---|---|
| L1 | **指令有优先级**：宪法/系统 > 开发者 > 用户 > 工具返回的数据；数据永不升格为指令 | OpenAI Instruction Hierarchy、Claude's Constitution |
| L2 | **提示词分段结构化**：指令 / 上下文 / 输入 / 输出格式各自成块，降低歧义 | Anthropic XML tags、Gemini `<OUTPUT_FORMAT>` |
| L3 | **写清理由与目标，而不是堆步骤**；简短清晰的指令优于复杂框架 | Anthropic「解释动机」、GPT-5 指南「少用复杂提示词框架」 |
| L4 | **提示词是代码**：不可变版本、可寻址、评测门禁后才晋升、可回滚 | prompt registry / eval-gated promotion 实践 |
| L5 | **上下文要预算与接地**：显式规定取多少上下文、事实必须来自检索而非记忆 | GPT-5 `<context_gathering>`、Gemini grounding |

**我们直接采纳**：L1（做成宪法层）、L2（六层分段）、L4（注册表 + semver + 门禁）、L5（token 预算 + L0/L1 接地）。

**我们改造后采纳**：L3 只取「简洁 + 说明动机」，**不取**「让模型自己探索代码库」——L2 的上下文必须来自 L0/L1 事实，不接受自由探索式取证（与 56 G-L2-5 证据门禁冲突）。

**我们明确不采纳**：宿主侧自动 prompt 优化/自动热更新（违反 56 ADR-10 可回滚原则与 ADR-06 验收外部化）。

## §1 方法论与判据

- **范围**：三家一线模型厂商官方提示词指南 + LLMOps 社区在生产环境的版本化实践。
- **筛选判据**：① 是否对「多 Agent + 有工具 + 有硬红线」的编排形态有效；② 是否可机器判定（能写成门禁）；③ 是否与现有 56/47 契约冲突。
- **不采用的证据**：博客个人经验类，只在能交叉验证两家以上时引用。

## §2 Anthropic / Claude

| 实践 | 内容 | 对我们的价值 |
|---|---|---|
| XML 标签分段 | `<instructions>` / `<context>` / `<input>` 分块，避免指令与数据混淆 | 直接对应 P1 角色层 / P3 上下文层 / P5 工具层分段 |
| 解释动机 | 「不要让回复出现省略号，因为会被 TTS 朗读」优于单纯禁止 | 我们的红线（实盘永不 MCP）必须带**理由**，否则模型只会机械回避 |
| 说结果不说步骤 | 告诉模型「用户无邮箱导致校验崩溃」，而不是「打开 userService.ts 第 42 行加空值判断」 | 与 56 G-L2-7「发现权在 L1」天然一致：L2 只接目标与证据，不接越权的实现脚本 |
| 评测驱动迭代 | 先建成功判据与测试用例，再改 prompt | 支撑我们的 golden set 门禁（G-P-3） |
| Claude's Constitution | 存在一份**独立于系统提示的宪法层**，系统提示在其授权范围内生效 | 这是「源文件宪法」最直接的对标：宪法不是 prompt 的一部分，而是 prompt 的上位约束 |

**关键差异**：Anthropic 的宪法是模型训练期的对齐产物；我们的宪法是**工程侧可审计的上下文契约**——不进训练，只进每次调用的最高优先级段落，且每次出口必须回指版本。

## §3 OpenAI / GPT-5 / Codex

| 实践 | 内容 | 对我们的价值 |
|---|---|---|
| Instruction Hierarchy | 训练使模型识别 system > user > tool data 的优先级，抵御间接提示注入 | 直接成为宪法 §H5 与门禁 G-P-6（工具数据不得作为指令） |
| 简短胜于复杂框架 | GPT-5 相比旧模型不需要复杂 prompt 框架，短清晰指令效果更好 | 我们的六层结构必须是**薄层**：宪法恒定段 + 任务段精简，禁止层层堆砌 |
| 元提示 | 用模型改进自己的提示 | 只在 48 实验 + 45 门禁下允许（D2 技术涌现），不做自动上线 |
| 显式上下文获取预算 | `<context_gathering>` 规定「多快拿够上下文、并行化发现」 | 映射为 P3 上下文层的 `max_context_tokens` / 检索条数上限 |
| reasoning_effort 与提示耦合 | 低推理档位要配合更明确的探索边界说明 | 我们的 L2Envelope 已记录 `model`，应同时记录推理档位，否则同 prompt 跨档位不可复现 |
| Codex 系统提示分段 | 自主性指令 / 人格 / 工具指引 / 安全边界 / 输出契约 分节 | 与我们的 P1-P5 分段高度同构，可作章节骨架参考 |
| evaluator / tripwire | 计划必须带外部验收或硬失败触发 | 与 56 IF-7 `plan_handoff` 的 evaluator/tripwire 要求一致 |

**可迁移结论**：GPT-5 的「少即是多」是对我们最有价值的纠偏——六层结构如果每层都写长文，反而退化；**宪法层要厚（红线），任务层要薄（目标）**。

## §4 Google / Gemini

| 实践 | 内容 | 对我们的价值 |
|---|---|---|
| 提示分解 / 串联 | 一条指令一个提示；多步任务拆成链式提示 | 对应 L2 内部 P2 任务层按「修复/优化/研究/辩论」分模板，不写万能模板 |
| 结构化输出 | 明确 schema 与字段顺序 | 对应 P4 输出契约层，直接复用 56 的 5 个 JSON Schema 资产 |
| Grounding | 事实必须来自检索/工具，而非模型记忆 | 对应 P3 只允许 L0 事实 + L1 证据；对应 56「L0 给事实」口诀 |
| 系统指令 | 明确 role + 任务 + 约束三件 | 我们已有 32 辩论的「立场锁」实践，可推广为角色层规范 |

## §5 行业 LLMOps：提示词当代码

| 实践 | 共识做法 | 我们的映射 |
|---|---|---|
| Prompt Registry | 单一事实源；**不可变**、append-only、`name@version` 可寻址 | `registry/prompt_registry.yaml`，`prompt_id + semver` |
| 语义化版本 | MAJOR=破坏输出契约/行为；MINOR=新增能力；PATCH=措辞修正 | 直接采用；MAJOR 必须重跑全部 golden set |
| Golden Dataset | 不需要上万条，**20–50 条高价值必过用例** | P2 阶段每类任务 ≥20 例，复用 45 评测框架 |
| Eval-gated Promotion | draft → gated → active → deprecated；评测不过不得晋升 | 四态生命周期，与门禁 G-P-3 绑定 |
| 可回滚 | 每次晋升留 rollback token，可一键回退 | 与 56 ADR-10「无 unload 不开放写」同构 |
| 依赖检查 | prompt 之间、prompt 与工具/schema 版本有依赖矩阵 | 注册表 `depends_on`（prompt_id@range + tool_set 指纹） |
| 指纹 | 内容 sha256，用于 trace 对账 | `prompt_fingerprint`，写入 `L2Envelope.meta` |

**最重要的工程结论**：registry 不需要复杂，但必须**正确**——不可变、可寻址、有评测分。这三条我们缺一不可。

## §6 五条铁律 → 我们的落地映射

| 铁律 | 57 的落地物 | 与现有契约的接缝 |
|---|---|---|
| L1 指令优先级 | `PROMPT_CONSTITUTION` H0–H5 六层 + 12 条硬条款 | 补充 56 ADR-03 的 `meta`；防注入对应 G-P-6 |
| L2 分段结构化 | 六层架构 P0–P5（宪法/角色/任务/上下文/输出/工具） | P5 必须等于 56 IF-7 `tool_set` 快照（G-L2-11） |
| L3 简洁 + 动机 | 宪法厚、任务薄；每条红线附理由 | 与 56 §5「prompt 版本」治理要求对齐 |
| L4 提示词当代码 | prompt registry + semver + 四态 + golden set | 45 评测门禁、56 台账（RepairLedger） |
| L5 预算 + 接地 | `max_context_tokens` 硬上限；事实只来自 L0/L1 | G-L2-3 预算门禁、G-L2-5 证据门禁 |

## §7 冲突点与不可照搬项

| 业界做法 | 为什么不照搬 | 我们的替代 |
|---|---|---|
| 让 Agent 自主探索代码库取证 | 与 56 G-L2-5「结论须回溯 nodes[] 或 L1 只读事实」冲突；且 L2 对 L1 只读 | 取证必须由 L0 检索/L1 证据提供，prompt 里只允许声明「缺少证据 → 标 evidence=none」 |
| 自动 prompt 优化并热更新 | 违反 ADR-10 可回滚、ADR-06 验收外部化；无评测的自动改动不可审计 | 改进走 48 D2 实验 → 45 门禁 → 人工晋升 |
| 长 system prompt 塞入全部业务知识 | token 成本失控 + 与 L1 零 token 定位冲突（3+3 §二） | 宪法恒定段 + 按需注入，业务口径一律引用源文件而非复述 |
| 用 prompt 让模型自行判断该不该下单 | 违反 ADR-01/ADR-05 与 H1/H2 红线 | prompt 显式声明「无交易执行权」 |
| 版本号写死在 prompt 文本里 | 版本漂移不可查 | 版本由注册表运行时注入 |

**关键缺口（可机器验证）**：

1. **零版本可溯**：在 `56-`、`34-前端应用训练系统/core`、`47-MCP管理系统` 全量检索 `prompt_version` / `prompt_id` / `prompt_hash` → **0 命中**。而 56 §5 治理表已明文要求「记录 model + 参数摘要 + **prompt 版本**」——要求存在、承载为零。
2. **无评测门禁**：6 处 prompt 均无对应 golden set 或回归脚本；改动即上线。
3. **纪律只写在契约里，没写进 prompt**：56 IF-3 规定「文本结论不得出现『将会 / 预计 / 必然』」、G-L2-5 规定证据分级，但无任何一处 system prompt 承载该纪律，模型不可知。
4. **架构红线不在上下文里**：L2 对 L1 只读、实盘永不 MCP、热路径 in-process、写操作需 Mandate——这些只存在于 SPEC 与 registry，L2 的 prompt 上下文完全不含，模型无从遵守。
5. **人格分裂**：32 辩论（立场锁、JSON 强约束）、3.1 前端（Markdown 口语化）、1-ARCH 意图识别（Function Calling 风格）三套风格互不承认，同一用户在不同入口得到不同语气与不同免责口径。

## §9 结论

1. 我们的缺口不是「prompt 写得不好」，而是**没有承载层**：无注册、无版本、无门禁、无宪法。
2. 业界最值得学的不是技巧，而是**治理形态**：不可变注册表 + 评测晋升 + 优先级宪法。
3. 我们的特殊性在于**红线密度高**（只读、实盘、Mandate、证据分级、禁自证），因此宪法层必须比业界更厚，而任务层必须更薄以控 token。
4. 建议以「宪法 + 注册表 + 三道门禁」为 P0，**不改造任何现有 prompt 文本**，先建立可观测性。
