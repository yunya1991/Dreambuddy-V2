# ADR-001：脑暴编排器出关（shadow → 限量实盘）

- 状态：已采纳（灰度中）
- 日期：2026-11-11
- 决策人：用户（审核）+ 编排器维护方（提案）
- 关联：SPEC-33-G §2.11.6（自举问题）、§2.8（八门禁）；52 SPEC Phase 5 第 10 条

## 1. 背景与触发证据

脑暴编排器自 Phase 4 起为 shadow 模式：`executed` 恒为 `false`，只写 trace / outbox，不执行任何 DreamOS 执行链。这使得 SPEC-33-G 的 L2（功能级）自更新流水线一直没有执行端——「提案→门禁→合入」的最后一跳缺失。

触发证据：

- 52 SPEC Phase 4「已知差距」：`--no-shadow` 抛 `NotImplementedError`。
- SPEC-33-G §2.11.6 显式记录该自举问题，要求以 ADR 解锁而非直接改代码。
- shadow trace 已积累（`orchestrator/traces/brainstorm.jsonl`），双链提案、T1-T4 触发器、dispatch 决策链路均有实测数据。

这是一次 **L3（架构级）变更**：它改变了「系统可以自己执行什么」的边界，因此只出 ADR + 实现方案，不进入自动通道。

## 2. 候选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 保持 shadow | 继续只记录，不执行 | 零风险 | L2 流水线永远缺执行端，自进化闭环断在最后一跳 |
| B. 直接全量实盘 | 删除 shadow，任何角色/任意频次均可执行 | 实现最简单 | 无预算、无角色隔离、失败不可控，等于把编排器变成无闸门的执行器 |
| C. 门禁式限量实盘（采纳） | 策略文件 + 角色白名单 + 自然周预算 + 只执行 dispatch 胜方 + 失败也占预算 | 可执行、可回滚、可观测；灰度对象与额度都可审计 | 需要额外维护策略文件与账本 |

## 3. 取舍理由与 PoE 评分

采用 C。判据按 SPEC-33-G §2.8 的精神对齐：

| 判据 | C 的满足方式 |
|---|---|
| 证据充分 | shadow trace 已覆盖双链提案、触发器、dispatch 分支 |
| 变更幅度 | 新增 1 个策略模块（`live_policy.py`）+ 编排器局部分支，不改 DreamOS / 3.1 源码 |
| 可回滚 | 策略文件 `enabled=false` 即回到 shadow；账本 append-only 可审计 |
| 提案/评估分离 | 策略由 ADR 定义，执行器由调用方注入，二者不混在编排器内 |
| 预算与断路器 | 自然周额度 + 失败也占额，天然限流 |

PoE 自评：`evidence_chain=0.8`（trace + 单测 + CLI 双跑）、`coverage=0.7`（缺真实业务 outcome 回传）、`complexity_penalty=0.1` → `poe≈0.79`，接近门槛但不足以进入 S3 全自动，故**只批准灰度（auditor + 1 次/周）**。

## 5. 回滚与灰度

灰度阶梯：

1. **S1（当前）**：仅 `auditor` 角色，`allowed_routes=[workers,debate]`，`max_per_week=1`，只执行 `decision.kind=dispatch` 的胜方 PlanCard。
2. **S2**：观察 2 周，若执行成功率 100% 且无越权记录（账本 `role/route` 全在允许集内），扩到 3 次/周。
3. **S3**：仍不开放全自动；提额与开放新角色**必须新增 ADR**，不在本文件内自行修改。

回滚动作（任一触发即执行）：

- 策略文件改 `enabled=false` → 立即回到 shadow（无需重启，每次运行重读）。
- 若发生越权执行（账本出现非白名单 role/route）或执行器产生副作用：将对应 run 的 trace + 账本记录标 `tainted=true`，并按 SPEC-33-G §2.6 对污染 Case/Evidence 降权。
