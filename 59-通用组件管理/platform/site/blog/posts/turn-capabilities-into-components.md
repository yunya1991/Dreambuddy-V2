# 问题不是"代码重复"，是"没人敢改"

在一个持续演进的交易系统里，最先失控的往往不是策略，而是那些看起来最不起眼的基础能力：扫描目录、登记上下文、取行情、抓宏观数据。它们被复制进第二个模块时还算合理，到第三个模块时就开始分叉——同一个字段有三种叫法，同一份配置有三个默认值。

真正的痛点是：**没人知道改动会影响谁**。于是所有模块都倾向于再复制一份，而不是改公共那份。

我们把这类能力从业务模块里抽了出来，做成可登记、可版本化、可分发的组件。过程中踩过四个坑，最后收敛成四道门禁。

# 坑一：清单只在人脑里

第一版组件散落在各模块目录，靠口头约定维护。结果是构建脚本找不到入口、文档链接指向不存在的文件、版本号三处不一致。

**门禁一：统一清单，且由脚本生成。**

每个组件必须有一份 `component.yaml` 声明名称、版本、生命周期、入口、依赖与产出契约。模块索引表由脚本从这些文件生成，发版前跑校验，禁止手改生成块。

```bash
python3 tools/gen_index.py --check   # 生成块与 component.yaml 不一致就失败
```

清单不是文档，是构建输入。

# 坑二：版本靠"感觉"

组件被三个业务模块引用后，升级变成赌博：改一个默认参数，某个模块的产出口径就变了，但没人能说清是哪个版本引入的。

**门禁二：版本语义 + 生命周期状态。**

组件状态只有 `active / draft / deprecated` 三种，对外目录只允许出现 `active`。版本号在 `component.yaml` 与 `SKILL.md` 中必须一致，发版前校验；历史版本文档整体归档，主索引只指向当前版。

这条规则的价值不在"规范"，而在于它让"这个组件现在能不能用"变成一个可查询的事实，而不是一场讨论。

# 坑三：一份实现，四个分发形态

我们同时需要 CLI（本地运维调试）、Skill 包（对外分发）、MCP 工具（IDE 内调用）和在线形态（云端 Agent 调用）。第一反应是各写一套，很快出现四份版本、四种错误码。

**门禁三：一份源码，构建期生成多形态。**

同一份 `component.yaml` 驱动四种产物，不允许各自定义版本。组件的共享逻辑放进内核目录，构建时注入到各组件，源码树不直接引用。

一个副作用是：**契约比传输更重要**。我们最初的动作声明只有 `name / script / safety`，没有入参 schema，导致 MCP 工具无法生成稳定的参数表单，调用方只能"猜命令行"。补上参数声明后，同一份定义才能同时喂给 CLI、Skill 和 MCP。

# 坑四：边界是口头的

组件被抽出后，很快有人开始 import 交易域的私有 schema、引用本机绝对路径、读取内部数据文件。表面上组件化完成了，实际上只是把耦合换了个位置。

**门禁四：独立性闸门进构建流程。**

用脚本做机械检查：组件不得反向依赖交易域私有 schema、绝对路径与内部数据；越界即构建失败。

```bash
python3 tools/check_boundaries.py    # G1–G7 独立性检查
```

人工评审会漏，脚本不会。边界检查必须和编译一样，成为"改完就要跑"的动作。

# 可以直接抄走的检查清单

- 每个可复用能力都有唯一清单文件，索引由生成器产出
- 生命周期只有三种状态，对外只暴露 `active`
- 版本号单点声明，文档与清单不一致即失败
- 动作声明包含参数类型、必填与枚举，而不是只写脚本路径
- 独立性检查进 CI，越界即阻断
- 发版前一条命令跑完全部门禁

```bash
make check   # kernel 一致 + 独立性 + 索引 + 规则/站点一致
```

# 小结

组件化不是"把代码搬到另一个目录"，而是把**所有权、版本、边界**变成可执行的门禁。四道门禁里，没有一道是"写得更优雅"，全部是"让错误无法悄悄发生"。

下一篇我们会聊另一半问题：组件可以复用之后，**它给出的数据凭什么可信**——方法 ID、样本量、缺失标注与数据源许可，这些才是研究结论能不能被引用的前提。
