# SPEC：19-DAL 全量只读接入与镜像加固（v0.1）

- 日期：2026-11-22
- 组件：`components/dal-data`（内部）
- 关联：`31-分布式计算部署/phase7/08-local-mirror.sh`、`mcp_shells/l0_data/server.py`、`tools/cloud_sync.py`

## 1. 背景与实测事实

| 事实 | 证据 |
|---|---|
| 云端 19-DAL live 库共 **29 张表**，覆盖 6 域：`cv_*`（配置）、`tr_*`（交易）、`po_*`（持仓）、`rs_*`（风控）、`mm_*`（宏观，7 张）、`kg_*`（知识图谱） | 云端 `sqlite3 .../19-数据访问层/data/dreambuddy_core.db` 表清单 |
| 本地镜像库仅 **3 张表**（`mm_metrics`/`mm_metric_vintages`/`mm_events`），1.5G | 本地 `sqlite3 sqlite_master` |
| 云端快照 `dreambuddy_core.db` 为 5.4G（11-21 15:22），同时存在 8.1G 的 `.tmp` 正在 `PRAGMA integrity_check` | 云端 `ls -lh /home/luke/sync-snapshots/`、`ps -ef` |
| 本地镜像连续失败：`rsync: unexpected end of file` → `rc=255`，`local-mirror done FAILED=1` | `phase7/mirror.log` |
| 镜像脚本**直接覆盖**本地库，无完整性校验、无原子替换 | `08-local-mirror.sh:L99-L104` |
| `data_store_read` 只放行 `mm_metrics` 一张表，且经 `SqliteMarketMacroRepository`，禁裸 SQL | `mcp_shells/l0_data/server.py:L43,L160-L190` |
| 19-DAL 各域已有只读 Repository 方法（fear_greed/funding/oi/liquidation/long_short/taker/metric、query_trades、get_position、query_cases、get_active_version、query_subgraph_by_entity） | `dreambuddy_dal/protocols/*.py` |

**根因**：快照未就绪时，rsync 拉到残缺文件并直接覆盖本地库 → dal-data 只能看到 3 张表。不是"镜像清单漏库"，而是**镜像没有一致性保障**。

## 2. 目标与非目标

目标
- P1（数据面）：镜像链路具备"快照就绪检查 + 临时落盘 + 完整性校验 + 原子替换"，失败保留旧镜像并显式报错。
- P2（接口面）：把只读查询从 `mm_metrics` 扩展到可安全映射 Repository 方法的域/表，并提供 `tables` 能力清单。
- P3（规划）：给出实时通道方案，不改云端写入口、不新建私有通道。

非目标
- **当前阶段 dal-data 只读且仅本地**：不提供 sync/写动作、不联网、不触发镜像同步；镜像刷新由运维侧手动执行。
- 不开放 `data_store_write`；不直连云端生产库写；不做任意裸 SQL 查询。
- 不把 `ma_*`（迁移审计）、`sqlite_sequence`、`kg_terms_fts_*`（FTS 影子表）暴露为数据面。

## 3. P1 镜像加固（实施）

> 执行方为运维侧（LaunchAgent / 手动跑 `08-local-mirror.sh`）；dal-data 组件只读本地结果，不触发本脚本。

1. **快照就绪检查**：`sync-snapshots/dreambuddy_core.db.tmp` 存在或 snapshot 进程在跑 → 直接失败退出（`E_SNAPSHOT_BUSY`），不拉取。
2. **临时落盘 + 校验 + 原子替换**：
   - rsync 到 `dreambuddy_core.db.incoming`（同目录，保证同文件系统）；
   - 校验：`PRAGMA quick_check` = ok，且 `sqlite_master` 表数 ≥ 基线（当前 29，允许 ±0）；关键表存在：`cv_config_versions`、`tr_trades`、`po_positions`、`rs_state`、`mm_metrics`、`kg_triples`；
   - 校验通过才 `mv` 覆盖，失败删除 incoming 并返回非零，**旧镜像保留**。
3. **manifest 增强**：`tools/cloud_sync.py` 的 manifest 增加 `tables`（核心表是否齐全）与 `ok` 字段，`--check` 要求 `ok=true` 且 fresh。
4. **dal-data.status** 展示 `tables_ok`，便于一眼判断镜像是否可用。

验收：本地镜像表数从 3 → 29；`dal-data status` 显示 `fresh=true, tables_ok=true`；故意制造快照 busy 时 sync 失败且旧库不被破坏。

## 4. P2 只读接口扩展（实施分批）

表 → Repository 只读方法映射（白名单，禁裸 SQL）：

| 域 | 表 | 入口方法 | 批次 |
|---|---|---|---|
| 宏观 | `mm_metrics` | `query_metric_by_time` / `query_latest_metric` | P2-1（已支持） |
| 宏观 | `mm_fear_greed` / `mm_funding_rate` / `mm_open_interest` / `mm_liquidation` / `mm_long_short_ratio` / `mm_taker_volume` / `mm_events` / `mm_metric_vintages` | 对应 `query_*_by_time`（events/vintages 按时间窗） | P2-1 |
| 配置 | `cv_config_versions` | `get_active_version` / `get_specific_version` | P2-2 |
| 交易 | `tr_trades` / `tr_daily_stats` | `query_trades` / `get_daily_stats` | P2-2 |
| 持仓 | `po_positions` | `get_position` | P2-2 |
| 风控 | `rs_state` / `rs_cases` | `get_state` / `query_cases` | P2-3 |
| 知识图谱 | `kg_entities` / `kg_triples` | `query_subgraph_by_entity` | P2-3 |

接口形态：
- 新增 `data_tables`（read）：返回可读域/表/必填参数（供 LLM 与 CLI 发现能力）；
- 扩展 `data_store_read`：`table` 白名单化（按上表），每表校验必填过滤参数，缺参数拒绝（防全表扫描）；
- 未实现域返回 `unsupported_table` 并附 `tables` 提示，不静默降级。

本轮落地 P2-1（mm 域 8 张表 + `data_tables`），P2-2/P2-3 待镜像修复后按上表继续。

## 5. P3 实时通道规划（不改写入口、不新建私有通道）

优先顺序：
1. **复用既有站点只读 API**（推荐，零新建通道）：`https://www.neodrm.com/api/fundamental/news/snapshot`、`/api/data/query` 已在 news-monitor 组件验证可用，数据源即云端 19-DAL；后续为宏观/交易域补齐同类公开只读端点即可。
2. **云端 MCP 网关投影 `l0_data` 只读工具**（次选，需改云端 `mcp_shells/l0_components/http_server.py` 装载第二个 shell + 白名单）：适合结构化工具调用，但要新增部署面。
3. **禁止**：SSH 实时查库、客户端直连生产 SQLite、暴露写工具。

实时性目标：秒级（API）/ 分钟级（MCP）；快照链路保持 10 分钟兜底。

## 6. 风险与回滚

- 镜像校验新增失败路径：若关键表基线变化（schema 升级），需同步更新 `REQUIRED_TABLES`，否则 sync 会拒绝覆盖（安全侧失败）。
- 白名单扩展容易放大误用：所有新增查询必须带必填过滤参数，且默认 limit ≤ 500。
- 回滚：`08-local-mirror.sh` 与 `l0_data/server.py` 均保留旧逻辑分支，可用 git revert 单点回退；dal-data 组件不落数据。
