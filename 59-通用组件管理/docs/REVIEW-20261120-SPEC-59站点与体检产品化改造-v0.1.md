## 二、阻断项（必须修改后才能进入施工）

### M1 — 规则契约无法表达「frontmatter 缺失」这一类结构性判断

§5.1 只允许 6 种 `check.type`，但现有 `FM000` 的语义是「解析失败时只出一条 fail，而不是对 slug/version/displayName 各出一条 fail」。当前 YAML 无法表达这种「前置失败即短路」的关系。

**后果**：迁移后同一个坏包会从 1 条阻断变成 5 条阻断，`score` 被重复扣分，免费报告 6 条额度被同一根因占满。

**要求**：在契约中新增 `depends_on` 或 `group` 字段，并明确规则求值顺序：

```yaml
- id: FM000
  type: frontmatter_parse
  on_fail: skip_group
  group: frontmatter
```

同时写明「组内前置规则 fail 时，后续规则标记 `skipped` 而非 `fail`，且不参与计分」。`checks[].status` 需新增 `skipped` 枚举，前端需兼容。

### M2 — `index.html` 既是源文件又是生成产物，缺少保护

§5.3 让 `build_site.py` 直接改写 `index.html` 的 `<!-- GEN:COMPONENT-CARDS -->` 块。这会导致：

1. 开发者手工改首页后，跑一次 `--write` 就被覆盖；
2. 生成块与手工内容在同一个 diff 里，冲突无法自动解决；
3. `--check` 只能发现不一致，不能告诉人「哪部分是生成的」。

**要求**：二选一，写入 SPEC：

- (a) 模板分离：`platform/site/templates/index.html` 为源，`index.html` 为产物（头部加 `<!-- AUTO-GENERATED -->`），`templates/` 进 git，根 `index.html` 可进 git 但禁止手改；
- (b) 保留同体，但生成块必须带 `BEGIN/END` 标记 + 内容 hash，`--write` 前校验块外内容未被脚本修改。

推荐 (a)，与 `dist/` 的产物思路一致。

### M3 — 存量用户会遭遇「昨天通过、今天阻断」

§5.2 把 `score` 语义改为「结构合规分」，§5.1 新增 FM006/EX001 等 blocker/warn。§8 的基线保护只覆盖自家 8 个 SKU，**不覆盖外部用户**。外部用户重新体检时可能因为新增 blocker 从 `pass` 直接变 `fail`，而页面没有任何版本提示。

**要求**：

1. 报告必须携带 `rules_version` 与 `rules_changed` 摘要（新增/升级了哪些规则）；
2. 新增 blocker 规则先以 `warn` 发布一个版本（灰度），下一版再升 `blocker`；
3. `verdict` 变更时，报告顶部给出「本次评分口径已更新」的说明，而不是静默变红。

### M4 — 付费报告的增量价值不成立

§5.2 规定「所有 blocker 必出、warn 取前 6、pass 折叠」，§5.10 又不做服务端存储。结果是：**免费用户已经拿到全部阻断项，付费只多出若干 warn**。§1 的问题 P6/P7 说要提升转化，但付费动机被这版裁剪规则削平了。

**要求**：明确付费增量，至少包含两项可感知价值：

- 完整 `warn` 明细 + 每条规则的修复示例（不只是 `hint` 一句话）；
- 包级建议（文件结构、references 拆分方案、付费协议缺失项的具体补法）。

若不愿做这些，应把 `/api/audit` 的定位从「完整报告」改为「批量体检 / CI 接入」，并在 SPEC 与页面同步改口径。

## 八、评审决议

**修改后接受**。处理顺序：

1. **v0.2 必须关闭**：M1（规则短路）、M2（源产物隔离）、M3（存量评分迁移）、M4（付费增量）。
2. **v0.2 应关闭**：M5–M12 与 n1–n15。
3. 关闭后进入 S0；S0 的第一步是把本 SPEC 与 REVIEW 登记到 [INDEX.md](../INDEX.md) §2（n14）。

**评审人建议**：D1 选静态生成、D2 只报实测维度、D3 独立 8082、D4 本地导出、D5 仅声明式规则、D6 替换 `build_registry.py`——六项建议全部采纳，避免在 v0.2 反复讨论。
