## 三、阻断项（进入 S0 前必须修改）

### B1 — `FM006 name` 被设为 `stage: gray`，与「平台发布必填」直接冲突

§5.1 规则表把 `FM006`（name ≤64、kebab-case、无保留词）标为 `blocker + gray`，而同为平台必填的 FM001/FM002/FM003 是 `enforce`。按 §5.2 的灰度规则，`gray` 会按 `warn` 计分，`verdict` 最多是 `needs_work`——**缺少 name 的包会被判「建议修改」而不是「阻断」**，用户拿去上架照样被平台退回，这正是 P1 要消灭的场景。

**要求**：

1. `FM006` 改 `stage: enforce`；
2. 契约新增 `required_by_platform: true`，`FM001/FM002/FM003/FM006` 必须置真；
3. `sync_rules.py` 增加硬校验：`required_by_platform: true` 且 `stage: gray` → 构建失败；
4. 灰度只允许用于**启发式**规则：`FM007`（触发短语）、`DOC002`（结构）、`EX001`（示例）、`FAQ001`、`FM008`（目录名匹配）。

### B2 — 「承诺对齐」只覆盖 trial/guide 的生成块，首页 CTA 与 guide 表格仍是手写

§5.3 只声明 `trial.html` / `guide.html` 的 `GEN:RULES-SUMMARY` 块，但：

- `index.html` 的 CTA 文案「了解九项检查」仍是手写字符串，规则数变化后照样漂移；
- `guide.html` 的「上架体检：检查项说明」是 7 行手写表格，不是由规则渲染；
- `trial.html` 右侧「检查什么」卡片也是手写列表。

**要求**：把「所有对外检查项文案」列成生成清单，并加机器断言：

| 位置 | 生成方式 |
|---|---|
| index CTA | `了解 {{public_rule_count}} 项检查` 由模板变量渲染 |
| guide 表格 | 整表由规则渲染（列：类别 / 检查内容 / 不通过的后果） |
| trial 侧栏 | 由 `public: true` 规则渲染，最多 5 条 + 「共 N 项」 |
| 测试 | 页面中不得出现硬编码的「九项 / 9 项 / 七项」；命中即 V6 失败 |

### B3 — 付费增量仍是「更多文本」，缺少可验证的交付物

§5.2 的付费差异是：完整 warn、`messages.fix`、`remediation_plan`、包级建议。问题在于：

- 免费已给全部 blocker，用户最容易卡住的部分已经拿到；
- `fix` 与 `remediation_plan` 本质是同一批文字，付费买的是「字数更多」，不是「结果更好」；
- 没有可直接采用的东西，用户仍要自己改。

**要求**：付费报告新增 `patches[]`，至少覆盖三类高频修复：

1. **frontmatter 补全片段**：按缺失字段生成可直接粘贴的 `--- ... ---` 块；
2. **description 改写建议**：给定原文与建议版本（含触发短语）；
3. **目录结构建议**：当 PKG/结构规则失败时，输出目标 `tree` 与迁移命令。

每条 patch 结构固定：`{rule_id, target, before, after, apply_hint}`。若某规则无法生成 patch，必须在规则 YAML 标 `patchable: false` 并说明原因，不能静默缺失。

## 八、复审决议

**修改后接受**。处理顺序：

1. **v0.3 必须关闭**：B1（FM006 enforce + `required_by_platform` 校验）、B2（文案生成清单 + 硬编码断言）、B3（`patches[]` 交付物）。
2. **v0.3 应关闭**：M3–M7 与 n1–n15。
3. **范围冻结**：S3 移出本 SPEC；S0 拆为 S0a（纯模板化）/ S0b（规则与文案），S0a 产物 diff 仅允许生成头。
4. 关闭后进入 S0a；S0a 通过前不改任何规则与文案。

**评审人结论**：v0.2 已把「怎么做」写清楚，剩下的是「别把新机制用错地方」。三项阻断都是小改动，不需要重构方案。
