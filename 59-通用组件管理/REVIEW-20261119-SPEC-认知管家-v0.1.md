## 二、Journal-Fit Reviewer（产品与市场契合）

**结论：定位成立，但目标场景的证据不足。**

1. 市场空缺判断依据的是各产品的**定位描述**，不是功能级核对。Mem0/Zep/Letta 确实主打「记」，但它们的「冲突消解 / 事实更新」在功能上部分覆盖了本 SPEC 宣称的「该不该记」。**未做功能矩阵级对比就断言空缺，属于结论先行。**
2. 双版本策略正确，但 Office 版的核心假设未被验证：办公用户是否愿意接受「技能 / 文档 / 记忆 / 会话」这套分类？办公场景更常见的真实分类是「资料 / 模板 / 待办 / 闲聊」。**词表映射表只是改名，没有改变决策树本身的心智负担。**
3. 定价（Dev 129 / Office 79）缺乏依据。平台案例价集中在 19–79 元区间，129 元的买断需要明确的能力差支撑，SPEC 未给出。

## 三、方法评审（§5 四路分流）

**结论：决策树结构可用，但四项关键设计不可执行。**

### M1 — 四路互斥假设不成立，且未声明为简化

§5.1 假设任何内容只能落入一路。真实工作区中大量条目是多归属：

- 一份「发布检查清单」既是 DOC（稳定事实）又是 SKILL（可重复执行）；
- 一条「为什么选 SQLite」既是 MEMORY（设计取舍）又必须出现在 DOC（ADR）；
- 一个 SPEC 同时描述流程与事实。

当前设计下，用户或模型只能二选一，结果是**另一半信息丢失**，或者用户绕过系统手工维护——这正是本产品要解决的问题本身。

**要求**：引入「主载体唯一 + 从属引用」模型。`route` 返回 `primary` 与 `attachments[]`，用 `edges` 表记录 `references / implements / documented_by` 关系。并明确声明「互斥是主载体层面的简化，不是内容层面的排他」。

### M2 — Q1「重复执行 ≥2 次」不可观测

系统如何知道某流程已经执行过 2 次？§8 的 `runs` 表在 §5 中没有被引用，SPEC 也没说明 `cm route` 是否写入 run 记录。**这是一个无法验证的判据，属于伪精确。**

**要求**：二选一——
- (a) 由 `runs` 表提供计数，`route` 时查询同类意图的历史次数，并在 `reasons` 中给出实际计数；
- (b) 改为用户显式确认（「这个流程你会重复用吗？」），不假装系统能自动判断。

### M3 — A1「能否推导」无判定主体，且缺「不确定」分支

A1 由谁回答？如果是 LLM 自评，存在系统性乐观偏差（模型倾向于认为自己能推导）。SPEC 未定义判定证据，也未定义「拿不准」时的处理。

**要求**：
- A1 必须附证据：要么给出可检索到的文件路径，要么给出模型的实际推导结果；无证据不得判为「可推导」；
- 增加 `unknown` 分支：不确定时**不写入**，输出 `pending` 并在下次任务中复核，而不是默认归入 SESSION。

### M4 — 路由输出契约不完整

§5.3 的 JSON 缺少：`id`、`schema_version`、`primary/attachments`（见 M1）、`alternatives[]`（低置信时的次选）、`requires_user_confirm`、`idempotency_key`、`evidence[]`。同时 `confidence` 没有阈值定义，调用方无法判断何时该转人工。

**要求**：补齐字段并给出阈值表（如 `≥0.8` 直接执行、`0.5–0.8` 需确认、`<0.5` 只输出建议不写入）。

### M5（补充）— SESSION 是无治理黑洞

「其余 → SESSION（不落盘）」把所有无法分类的内容都吞掉，等同于没有治理。且 §9.2 未定义会话结束后的二次分拣。

**要求**：SESSION 增加 TTL 与到期提醒；`cm doctor` 输出「本次会话中未分类条目数」，并提供一次性批量分拣入口。

### m（方法层 Minor）

- 决策树顺序（Q1→Q2→Q3）未说明优先级理由，且缺少 tie-breaker 规则。
- 未定义「文档」边界：是否包含 PDF、图片、表格、二进制？扫描器遇到这些如何处理未说明。
- §5.4 的 2000 tokens 预算没有推导依据（入口索引实测多少？Top-K 取几？）。

## 四、统计评审（§12 验收标准）

**结论：8 条验收标准中，只有 V8 可当场复核，其余均不可复现。**

### M6 — V4「路由准确率 ≥ 90%」不可复核（最严重）

- 黄金集 30 条由作者自标注，属于**自证**；
- 30 条样本下 90% 的置信区间约为 [73%, 98%]，无法支撑任何决策；
- 只定义 accuracy，未区分 precision / recall，而「把文档误判成技能」与「漏判」代价完全不同；
- 未定义类别分布与争议裁定人。

**要求**：≥ 100 条、每类 ≥ 20 条、双人独立标注 + 分歧由第三人裁定；分别报告 primary 路由的 precision / recall / F1；阈值改为「precision ≥ 0.85 且 recall ≥ 0.80」（避免为刷 accuracy 而偏向多数类）。

### M7 — V2 / V3 / V5 / V6 判定口径缺失

| 项 | 问题 | 要求 |
|---|---|---|
| V2 | 未给机器基线、文件大小分布、冷/热缓存口径 | 固定机型 + 固定 fixture（1000 个 1–50KB 文件）+ 冷启动计时，取 3 次中位数 |
| V3 | fixture 未定义断链数量与正常条目数量 | 给定 30 条断链 + 200 条正常链接，召回与误报分别计数 |
| V5 | 未指定 tokenizer | 固定一种（如 cl100k_base），并注明与目标模型的偏差 |
| V6 | `pip list` 不能证明零依赖 | 在干净 venv 中运行全部命令 + AST 扫描 import 白名单 |

### M8 — 缺异常路径与边界验收

当前 8 条全部是正常路径。MVP 六命令在以下场景的行为未验收：空工作区、只读目录、超大文件（>10MB）、非 UTF-8 编码、符号链接环、文件名含空格/中文、路径大小写不敏感。

**要求**：增加 V9「异常路径用例集 12 条，全部返回明确错误码而非崩溃或静默跳过」。

### 其他 Minor

- V7 只说「不改内核代码」，没有要求两版各自跑通黄金集；应要求 Dev/Office 各有一份路由黄金集。
- V1「30 秒」未区分首次全量与增量。
- 缺用户价值验收：至少在 3 个真实工作区试用，记录「重复摸索次数」前后对比。

## 五、Devil's Advocate

| # | 反驳 | 评分 | 让步判定 |
|---|---|---|---|
| D1 | 四路分流把「分类不确定性」原样转嫁给用户和 LLM，系统本身没有降低不确定性；真实仓库 60%+ 内容是多归属，互斥模型会系统性丢信息 | **4** | **必须修改**（采纳 M1/M3） |
| D2 | 「90% 准确率」由作者自建 30 条样本自评，是典型的自证循环，无法证明产品有效 | **5** | **必须重新设计**（采纳 M6） |
| D3 | 这个产品可能只是把内部流程卖给不需要它的人：办公用户的心智是「资料/模板/待办」，不是「技能/记忆/索引」；没有真实用户试用就上架，风险是没人买 | **3** | 坚持原方案可以，但**必须补 3 个工作区前测**（见 Minor） |
| D4 | 「别人的记忆库越用越胖」是对手的产品缺陷，不等于用户痛点；用户可能根本不关心记忆库大小 | **3** | 需在文案与验收中补「可感知价值」（减少重复提问、减少文档断链） |
| D5 | 决定胜负的不是分流算法，而是首次 30 秒体验与 doctor 报告的可用性；当前 SPEC 把 80% 篇幅给了路由，MVP 体验设计不足 | **3** | 建议把 M1 的退出条件从「路由完成」改为「首次体验闭环」 |

**让步结论**：D1（4 分）、D2（5 分）必须让步并修改 SPEC；D3–D5 可保留方案，但需补证据与体验设计。

## 八、综合决议

**修改后接受。** M0 退出条件修订为：

1. M1–M8 全部关闭（逐条在 SPEC 中留下修改痕迹）；
2. 竞品功能级对比矩阵补齐（m4）；
3. 至少 3 个真实工作区完成前测并记录结论（D3）。

M1 阶段的退出条件同时调整：从「`cm init`/`cm doctor`/`cm scan` 跑通」改为「**首次 30 秒体验闭环 + doctor 报告可读**」，路由引擎后移到 M2。
