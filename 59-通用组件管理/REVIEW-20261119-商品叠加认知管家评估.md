## §0 结论（先说结论）

1. **方向对，但不能按字面"合并成一个包"来做。** 认知管家是「装配层 + 治理层」，不是「分析层」——它不读正文、不发网络请求、不算指标。把它说成"辅助分析"会同时误导买家和我们自己。
2. **对商品 B（事件）是真增强**：事件产物本来就是 `event_id + 来源 + 许可 + 时间` 的指针结构，与认知管家的 `pack / triage` 同构。
3. **对商品 A（数据）是弱增强**：A 的分析能力在 `context.py`（M14/M15/M16），认知管家替代不了；叠加只能做"用户本地数据资产的归属与体检"。
4. **推荐"包内轻量适配层"，不推荐把认知管家整包塞进商品。** 理由见 §3：SKILL.md 200 行装不下两套能力、权限面从 `Bash,Read` 扩到 `Read,Write,Glob,Grep,Bash`、且认知管家是内部核心资产，整包送出等于免费公开。

| 项 | 实测值 | 来源 |
|---|---|---|
| 包体 | 304KB / 34 个文件 | `du -sh` |

- 不做 RAG 托管、不做交易域、不做指标计算
- 路由默认 `plan` 不落盘，置信度 <0.8 时静默降级为 plan

## §2 把"辅助优化处理分析"拆成四件事

用户原话是"通过认知管家辅助优化处理分析"。这句话里其实有四种不同的事，必须拆开归属，否则方案一定会错位：

| # | 事情 | 谁来做 | 认知管家能做吗 |
|---|---|---|---|
| 1 | **取数**（拿到已发布的宏观/披露/链上/事件数据） | 商品包 `macro/filings/onchain/events.py` | ❌ 它 `network: none` |
| 2 | **口径上下文与统计**（这个数字怎么读、分位、相关、分组） | 商品 A `context.py`（M14/M15/M16） | ❌ 它不算指标 |
| 3 | **装配**（这次任务该带哪些文件/事件、预算多少 token） | 认知管家 `pack` | ✅ **这是它唯一真正能贡献的一层** |
| 4 | **治理**（这些资料放哪、哪些断链、哪些该清） | 认知管家 `doctor / route / triage` | ✅ 能做，但属用户本地资产管理 |

**关键判断**：叠加认知管家，实际买到的是第 3、4 层；第 1、2 层本来就是两个商品自己的。所以"叠加"的正确表述是「**数据/事件 + 可装配**」，不是「数据/事件 + AI 分析」。

误用风险：若商品页写"认知管家辅助分析行情"，等于对外承诺解读能力，会同时踩两条线——文案与实际不符（退款纠纷）、以及从数据服务滑向投资建议（R3 荐股软件认定）。

## §3 三个叠加方案

### 方案 1：整包合并（一个 zip 装两个技能）

```text
product.zip
├── SKILL.md              ← 两套能力要挤进 200 行
├── scripts/macro.py ...
└── cognition-manager/    ← 34 个文件
```

| 维度 | 评估 |
|---|---|
| 包体 | 304KB，远低于 3MB 上限 ✅ |
| SKILL.md | 认知管家自身 188 行 + 数据/事件说明，**必然超 200 行** ❌ |
| 权限面 | 从 `Bash,Read` 扩到 `Read,Write,Glob,Grep,Bash` + 写工作区，审核与用户信任成本上升 🟡 |
| 定位 | 一个 SKU 承载"数据服务 + 上下文治理"两种价值，商品页说不清 ❌ |
| 资产 | 认知管家 34 个文件可被买家单独复制分发，**发布即不可收回** 🔴 |
| 平台 | 单 zip 多技能结构**未验证**（此前只验证过单 SKILL.md）❓ |

**判定：不建议。** 除包体一项外全是负分。

### 方案 2：三商品拆分（认知管家独立上架）

| 商品 | 形态 | 价 | 卖点 |
|---|---|---|---|
| `market-data-hub` | 订阅 | ¥19.9/月 | 数据 + 口径 + 交叉统计 |
| `event-context` | 订阅 | ¥19.9/月 | 官方源事件五层装配 |
| `cognition-manager` | 买断或订阅 | 待定 | 工作区体检 / 归属路由 / 最小上下文包 |

| 维度 | 评估 |
|---|---|
| 定位 | 三者边界清晰，各自 SKILL.md 均达标 ✅ |
| 用户摩擦 | 三份购买；买数据的人未必需要治工作区 🟡 |
| 独立说服力 | 认知管家解决"工作区乱"，对只想要数据的人**没有直接吸引力**，需另做价值论证 🟡 |
| 资产 | 仍会公开认知管家全部能力 🔴 |
| 联动 | 商品与管家之间没有结构化对接点，只能靠用户自己拼 🟡 |

**判定：可选，但把它当"第三个商品"而不是"叠加"。**

### 方案 3：包内轻量适配层（推荐）

不搬认知管家的代码，只对齐它的**输入契约**：两个包各加一个约 80 行的 `handoff.py`。

```text
market-data-hub/
└── scripts/handoff.py     # 把 rows / describe / cross 结果转成"可装配指针清单"

event-context/
└── scripts/handoff.py     # 把五层结果转成"事件指针清单"
```

```bash
# 输出认知管家 pack 可直接消费的候选清单（纯 JSON，无副作用）
python3 scripts/handoff.py --series DGS10,CPIAUCSL --budget 2000
python3 scripts/handoff.py --subject AAPL --since 30 --emit cm-pack
```

输出契约（两个包一致）：

```json
{
  "handoff_version": "1.0",
  "target": "cogsteward/pack",
  "budget": 2000,
  "items": [
    {"id": "series:DGS10", "kind": "series", "title": "美国10年期国债收益率",
     "license": "Public Domain", "url": "https://fred.stlouisfed.org/series/DGS10",
     "estimated_tokens": 40, "method_ids": ["M02", "M12"]},
    {"id": "event:3f2a91c4b7de0051", "kind": "event", "title": "8-K - Apple Inc.",
     "license": "Public Domain", "url": "https://www.sec.gov/...",
     "estimated_tokens": 60, "event_time": "2026-11-18T16:30:00-05:00"}
  ],
  "total_tokens": 100,
  "read_only": true,
  "limits": "仅提供可装配指针，不含判断与建议。"
}
```

| 维度 | 评估 |
|---|---|
| 包体 | +1 个文件（约 4KB）✅ |
| SKILL.md | 只加一节「与认知管家配合」（约 25 行），总行数可控 ✅ |
| 权限 | 不扩权限，仍 `Bash, Read` ✅ |
| 资产 | 只公开**契约**，不公开认知管家的实现 🔴→🟢 |
| 兼容 | 用户装了认知管家 → 效果最佳；没装 → 退化为普通 JSON，功能不残缺 ✅ |
| 联动 | 两个商品共享同一 `handoff` 契约，相同 `id` 规则，**这是真正的组合卖点** ✅ |

**判定：推荐。** 它拿到"可装配"的全部好处，避开方案 1 的所有硬约束。
