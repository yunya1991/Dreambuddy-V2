# 数据冷热分层与归档 SPEC

- 版本：v1.0
- 日期：2026-10-17
- 状态：已调研，待实施
- 负责推进目录：38-数据库管理系统

## 1. 背景与目标

服务器（lhins-dy3kb79r，Ubuntu 24.04，4核/7.5G内存/118G磁盘）承载交易系统与数据采集中心，内存与 CPU 长期承压。调研发现存储大头并非数据库本身，而是冷数据混在热存储中，拖慢查询、污染页缓存。本 spec 定义数据冷热分层与归档方案，目标是：

1. 热数据（0-30 天）留在主库，支撑实时交易决策
2. 冷数据（30 天以上）压缩归档到本地磁盘，按需加载
3. 建立自动降层机制，避免人工干预
4. 降低主库体积，提升查询效率与页缓存命中率

## 2. 现状盘点（2026-10-16 实测）

| 存储 | 规模 | 内容 | 冷热特征 |
|---|---|---|---|
| SQLite 主库 18-数据获取中心/data_center.db | 507M | 32,076 条 records，时间跨度 2023-01 至今 | 78% 为 30 天前冷数据（24,938 条，timeseries/raw 字段约 446MB） |

| Redis（Docker dreambuddy-redis） | 小 | 缓存 | 无压力 |
| MinIO（Docker dreambuddy-minio） | 已就绪 | 对象存储 | 未承担归档角色 |

records 表结构：id, dedupe_key, source, category, sub_category, timestamp, metrics, events, timeseries, raw, schema_version。另有 metrics / quality_issues / alerts 表。

## 3. 参考的成熟方案（传统金融与工程实践）

1. 冷热分层（Hot/Warm/Cold Tiering）：热层 0-30 天（内存+SSD）；温层 30-90 天（本地磁盘）；冷层 90 天以上（压缩归档，按需加载）
2. 分区裁剪（Partition Pruning）：按时间分区，查询只扫相关分区（kdb+、TimescaleDB 核心机制）
3. 列式压缩归档：Parquet + ZSTD，JSON 文本可压缩 5-10 倍
4. 小文件合并（Compaction）：定期合并小文件为大文件，减轻文件系统负担
5. 数据生命周期管理（ILM）：自动降层、到期清理

## 4. 方案设计

### 方案 1：SQLite 冷数据归档（优先级最高）
- 将 30 天前的 records 导出为压缩归档（Parquet/ZSTD 或 JSONL+ZSTD），预计 446MB → 约 50-90MB
- 主库从 507M 缩到约 60M；归档文件存放于 38-数据库管理系统/archive/
- 执行步骤：备份主库 → 导出冷数据 → 验证采集与查询正常 → 删除主库冷数据 → VACUUM 回收空间
- 回滚方式：从备份库恢复

### 方案 2：L4 案例库小文件治理
- 将 90 天前旧案例按月合并打包（tar.zst 或 Parquet），保留索引用于按需检索
- 交易决策依赖近期案例，旧案例仅回测时按需加载

### 方案 3：自动降层机制
- 复用每日凌晨 4 点低峰窗口，增加归档定时任务：自动将超过 30 天的数据从热库移到归档区
- MinIO 可作为归档区，形成『热库 SQLite + 冷库对象存储』两层架构

### 方案 4：长期演进
- 数据量持续增长时，SQLite 迁移到 PostgreSQL 分区表或 TimescaleDB（按月分区 + 自动归档），与现有 Docker 架构兼容

## 5. 执行顺序

1. 方案 1（SQLite 冷数据归档）——收益最直接、可回滚
2. 方案 3（自动降层）——一劳永逸
3. 方案 2（案例库治理）——视增长速度择机执行
4. 方案 4（数据库迁移）——长期规划

## 6. 风险与约束

- 归档操作前必须完整备份主库
- 删除冷数据前必须验证导出文件完整性（行数、校验和）
- 归档任务避开交易时段，安排在凌晨低峰
- 采集与消费代码的查询逻辑不受影响（只动数据，不改代码）
