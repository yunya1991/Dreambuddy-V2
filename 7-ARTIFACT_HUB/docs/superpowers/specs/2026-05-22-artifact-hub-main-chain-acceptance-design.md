# Artifact Hub Main Chain Acceptance Design

> Date: 2026-05-22
> Scope: `7-ARTIFACT_HUB`
> Status: Ready for review

## 1. Goal

本设计用于正式定义 `7-ARTIFACT_HUB` 下一阶段的中台承接方案。

这一轮的目标不是继续讨论某个页面怎么画，也不是直接进入实现，而是先把一个核心问题定清楚：

- 中台到底从哪里开始承接这条已经成立的新主链
- 中台承接之后，`ui-map`、`feed`、`chain` 分别承担什么职责
- 中台内部依赖哪一套统一对象模型与索引骨架
- 后续演进时，应该先统一什么，再建设什么页面

本轮已经确认的统一主链为：

- `策略设置成功 -> 策略任务单 -> 交易链条 -> 交易执行 -> 结果产物 -> 索引`

因此，这份设计的重点不是重新定义上游策略设置，而是明确中台如何从“设置成功之后”开始承接这条主链，并保持横向统一性。

## 2. Problem Statement

前一轮已经完成了业务主链的统一收口：

- 不管是 `系统策略` 还是 `自定义策略`
- 只要策略设置成功
- 后续都进入同一套系统
- 统一走 `策略任务单 -> 交易链条 -> 交易执行 -> 结果产物 -> 索引`

但当前中台仍然缺少一份正式承接设计，因此还存在三个风险：

- 容易把 `feed` 继续做大，最终既想做产物入口，又想做总入口，还想做关系中心
- 容易把 `ui-map` 误解成普通关系图页，而不是中台总入口和编排层
- 容易让 `feed`、`chain`、未来 `ui-map` 各自发展自己的对象体系，最后破坏横向统一

当前真正要回答的不是“中台再加一个入口”这么简单，而是：

- 中台承接的起点是什么
- 中台承接的主对象是什么
- 三个页面各自先承接什么，不重复承接什么
- 中台应该先统一骨架，还是先堆页面

如果这些边界不先定清楚，后续无论页面怎么扩展，都会再次回到“页面很多，但对象不统一”的状态。

## 3. Architecture Decision

本设计选择：

- `feed` 继续承担统一产物入口
- 新增 `ui-map` 作为中台总入口
- `chain` 继续承担链路透视入口
- 三者共享同一套对象模型与索引骨架

这意味着中台不是一个页面，也不是把现有 `feed` 做成大而全首页，而是一套统一对象模型在三个页面上的不同投影。

### 3.1 Why Not Make Feed The Only Entry

本轮不选择“直接把 `feed` 升级成总入口”的原因是：

- `feed` 的核心职责是承接结果产物
- 如果继续把总览、编排、关系导航全部压到 `feed`
- 它很快就会失去“统一产物入口”的清晰定位
- 后续扩展会变成页面叠功能，而不是中台承接

因此，`feed` 必须守住自己的职责边界，而不是无限膨胀。

### 3.2 Why UI-Map Must Exist

`ui-map` 不是结果页，也不是普通关系图页。

它存在的原因是：

- 中台需要一个真正的总入口
- 用户进入中台后，需要先判断自己当前要看的是哪类对象、哪个阶段、哪条链路
- 这个动作不应该在 `feed` 中完成，也不应该在 `chain` 中完成

因此，`ui-map` 的定位明确为：

- 统一导航入口
- 统一编排入口
- 统一状态总览入口
- 跨对象跳转入口

### 3.3 Three Views, One Backbone

中台内部不能存在三套页面、三套对象、三套语义。

本轮主约束明确为：

- `ui-map`、`feed`、`chain` 看到的是同一套对象
- 它们的差异只在于“先承接什么、重点展示什么、引导用户做什么动作”
- 它们不允许各自维护一套彼此割裂的主对象语义

换句话说：

- 中台不是三个页面拼起来
- 中台是一套统一骨架，被投影成三种视角

## 4. Acceptance Start Point

中台不是从“策略对象产生时”开始承接，也不是从“用户打开页面时”开始承接。

中台承接的正式起点明确为：

- `策略设置成功`

原因是：

- 上游 `Strategy` 仍然表示来源对象
- 上游设置流程仍由前端策略面板或系统策略来源负责
- 中台不替代这些上游发起动作
- 中台只在“已经形成可执行主链”之后开始接手

因此，中台的职责是：

- 承接
- 组织
- 分发
- 回查

而不是重新发起策略设置本身。

## 5. Primary Object Order

中台承接顺序必须和统一主链保持一致，不能因为页面差异而改变。

### 5.1 Strategy Is Source, Not Hub Primary Object

`Strategy` 仍然表示来源对象。

它用于说明：

- 这是系统策略还是自定义策略
- 原始配置是什么
- 来源侧是谁发起的

但它不是中台内部的统一主对象。

### 5.2 StrategyTaskOrder Is The First Hub Object

中台承接的第一个核心对象明确为：

- `StrategyTaskOrder`

原因是：

- 一旦策略设置成功，不管来源是什么，后续都先进入 `策略任务单`
- 它是统一主链进入中台后的第一个稳定锚点
- 后续执行、结果、索引、关系都应该围绕它逐步展开

因此，本轮明确把 `StrategyTaskOrder` 定义为中台中的统一主对象。

### 5.3 ExecutionRun Is The Second Hub Object

中台承接的第二层核心对象为：

- `ExecutionRun`

它解决的问题不是“做什么”，而是：

- 这张任务单实际触发了哪一次执行
- 哪一次执行正在运行
- 哪一次执行产出了对应结果

因此：

- `StrategyTaskOrder` 负责承接“要做什么”
- `ExecutionRun` 负责承接“哪一次真的做了”

### 5.4 Artifact Is The Result Object

中台承接的第三层核心对象为：

- `Artifact`

它表示执行之后真正沉淀下来的结果对象，包括：

- 中间桥接产物
- 阶段结果
- 最终结果

这些结果不允许散落在各个页面自己的临时状态中，而应统一进入产物体系。

### 5.5 Index And Relation Map Complete The Backbone

`Index` 与 `Relation Map` 不是单独业务页面，但它们是中台成立的必要条件。

因为只有建立统一索引和关系骨架，中台才能做到：

- 从任务单定位执行
- 从执行定位结果
- 从结果反查来源
- 从任一页面跳回其他页面

因此，中台承接顺序正式定义为：

1. 先承接 `StrategyTaskOrder`
2. 再承接 `ExecutionRun`
3. 再承接 `Artifact`
4. 最后通过 `Index` 和 `Relation Map` 串成统一骨架

## 6. Page Responsibility Contract

三个页面不重复承接同一动作，而是围绕同一套对象承担不同职责。

### 6.1 UI-Map

`ui-map` 是中台总入口。

它先承接的是：

- 对象关系
- 当前状态
- 下一步进入路径

它最先回答的问题是：

- 现在有哪些任务单
- 这些任务单分别走到哪一步
- 哪些执行正在发生
- 哪些结果已经产出
- 接下来应该进入哪个页面继续看

因此，`ui-map` 的职责定义为：

- 统一导航
- 统一编排
- 总览判断
- 跨对象跳转

它不是结果明细页，也不是链路明细页。

### 6.2 Feed

`feed` 是统一产物入口。

它先承接的是：

- 结果产物
- 产物检索
- 产物详情
- 从产物回跳其他对象

因此，用户进入 `feed` 之后，优先完成的是：

- 找到结果
- 查看结果
- 进入结果详情
- 从结果反查任务单或链路

`feed` 可以显示来源关系，但不能承担总入口和关系中心两种职责。

### 6.3 Chain

`chain` 是链路透视入口。

它先承接的是：

- 过程关系
- 阶段流转
- 前后追踪
- 异常定位

因此，用户进入 `chain` 之后，优先回答的是：

- 这条任务单之后发生了什么
- 中间经过了哪些阶段
- 哪一次执行产出了哪个结果
- 哪个阶段中断了

`chain` 看重的是过程透视，而不是承担总入口或产物入口。

### 6.4 Closed Navigation Loop

三个页面的承接关系应明确为：

- `ui-map` 负责先分流
- `feed` 负责先看结果
- `chain` 负责先看过程

典型跳转关系应为：

- 从 `ui-map` 进入 `feed`，表示用户要看结果
- 从 `ui-map` 进入 `chain`，表示用户要看过程
- 从 `feed` 回跳 `chain`，表示用户要追这个结果怎么来的
- 从 `chain` 回跳 `feed`，表示用户要看这一步最终产出了什么

## 7. Scope Boundary

本轮设计必须先把边界卡住。

### 7.1 In Scope

这一轮中台承接的范围明确包括：

- 承接统一主链
- 承接统一对象模型
- 承接统一索引
- 承接统一跳转关系

### 7.2 Out Of Scope

这一轮明确不追求：

- 把中台一次做成全功能工作台
- 重做所有历史页面
- 把所有历史对象一次并进来
- 让中台替代上游业务前台

### 7.3 Upstream And Downstream Boundary

职责边界明确为：

- 上游负责发起策略设置
- 中台从设置成功之后开始接手
- 下游负责执行、产出、沉淀

因此：

- `ui-map` 不负责发起策略设置
- `feed` 不负责编辑策略
- `chain` 不负责替代产物详情

三层都只处理“设置成功之后”的统一主链对象。

## 8. Evolution Order

这套方案的演进顺序不能从页面开始，而要从骨架开始。

### 8.1 Phase 1: Define Acceptance Contract

第一阶段先把中台承接语义定清楚。

至少要明确：

- 中台承接什么
- 中台不承接什么
- `ui-map` / `feed` / `chain` 分别承接什么
- 共享对象模型是什么

### 8.2 Phase 2: Align Shared Backbone

第二阶段先对齐共享对象模型与索引层。

这一阶段至少需要稳定表达：

- `StrategyTaskOrder`
- `ExecutionRun`
- `Artifact`
- `Index`
- `Relation Map`

没有这层，对后续页面来说就没有统一语言。

### 8.3 Phase 3: Stabilize Feed As Artifact Entry

第三阶段先让 `feed` 稳定承担统一产物入口。

原因是：

- 结果产物是中台最容易首先稳定承接的部分
- 只要产物已经能稳定汇入、检索、回跳，中台就先站住了一个明确入口

### 8.4 Phase 4: Build UI-Map As Hub Entry

第四阶段补 `ui-map`。

此阶段重点不是先做复杂视觉，而是先让它能回答：

- 现在有哪些任务单
- 哪些执行正在发生
- 哪些结果已经产出
- 下一步从哪里进入最合适

### 8.5 Phase 5: Strengthen Chain As Process View

第五阶段补强 `chain`。

目标是让它真正围绕：

- 任务单
- 执行
- 结果

来回答“这条主链怎么流转、在哪里中断、最后落了什么”。

## 9. Success Criteria

这份设计成立后，中台方案应满足以下判断标准：

- 不再把 `feed` 误做成大而全首页
- 不再把 `ui-map` 误做成普通关系图页
- `ui-map`、`feed`、`chain` 三者共享同一套主对象语义
- 中台承接从 `策略设置成功` 开始，而不是提前侵入上游设置流程
- 中台演进顺序以“统一主链、统一对象模型、统一索引”为先，而不是先堆页面

## 10. Final Statement

本轮最终结论明确为：

- 中台不是从页面开始建设
- 中台是从统一主链、统一对象模型、统一索引开始建设
- 页面只是这套承接体系的可视化投影

因此，`7-ARTIFACT_HUB` 的下一阶段推荐方向正式收口为：

- `feed` 继续做统一产物入口
- `ui-map` 作为中台总入口
- `chain` 继续做链路透视入口
- 三者共享同一套对象模型与索引骨架
