## 0. 文档说明

### 0.1 文档范围

本文档规划 Dream OS 在多交易子系统并存环境下的双重角色定位、落地路径与约束条件。

### 0.2 核心约束

- 各子交易系统处于研发阶段，**暂不引入外部干预**
- Dream OS 优先服务于**自身交易系统**的完善
- 总调度层以**观察+评估**为主，不介入子系统实盘执行

## 1. 背景与修正

### 1.1 早期调研修正

初始调研误判 V15 经典马丁与易经推理系统使用同一 OKX 账户，经核实两者为**独立账户**：

| 子系统 | API Key | Secret Key | Passphrase |
|--------|---------|-----------|------------|
| V15 经典马丁 | `5af4066c-...` | `0B3334CB...` | `Zjt@199107293419` |
| 易经推理 | `d988a164-...` | `1403C63E...` | `Zjt@199107293419` |

**关键结论**：API Key 和 Secret Key 完全不同，属于**独立 OKX 账户**，不存在同账户反向持仓冲突。Passphrase 相同仅为密码管理习惯，不影响账户隔离性。

### 1.2 各子系统实盘状态

| 子系统 | 交易所 | 账户类型 | 周期 | 标的数 | 实盘状态 |
|--------|--------|---------|------|--------|---------|
| V15 经典马丁 | OKX | 独立账户 | 1H | 31 | 实盘运行（35笔+） |
| 易经推理系统 | OKX | 独立账户 | 1H | 6 | 实盘运行 |
| 三屏趋势系统 | Aster | EVM签名账户 | 60s | 9 | 实盘运行 |
| AB-Trading | Hyperliquid | 独立账户 | 4H | - | 实盘运行 |
| Dream OS 交易系统 | - | - | 1H | 3 | 仅回测 |

**风险等级**：各账户物理隔离，**无同账户冲突**。剩余风险仅为跨账户总暴露叠加（可控）。

## 2. Dream OS 双重角色定位

### 2.1 角色1：总调度协调层（观察+评估）

**职责边界**：
- 观察各子系统持仓和信号（只读，不干预）
- 按场景评估各子系统表现
- 输出评估报告和冲突告警（建议制，不强制执行）
- **不直接指导子系统交易决策**

**设计原则**：
- 复用 `16-调控系统` 的 `unified_position_query.py` 进行持仓聚合
- 复用 Dream OS 内核的 `ScenarioClassifier` 进行 36 场景分类
- 各子系统保持完全独立运行

### 2.2 角色2：旗舰交易系统（自身完善）

**职责边界**：
- 持续完善内置 22 个交易节点（A/C/F/G 系列）
- 通过适配器框架封装子系统能力为扩展节点
- A 层动态编排根据场景选择最优节点组合
- 回测评估驱动节点能力评分

**关键设计**：子系统封装节点是**旗舰交易系统的内部扩展**，不是对子系统的接管。子系统本身仍在自己账户独立运行，封装节点仅用于：
- Dream OS 自身交易系统的回测验证
- 场景适配度评估
- 节点能力对比基线

### 2.3 两个角色的关系

```
┌──────────────────────────────────────────────────────────────┐
│              Dream OS 双重角色                                │
│                                                              │
│  角色1: 总调度协调层                角色2: 旗舰交易系统       │
│  ─────────────────────              ─────────────────────     │
│  • 观察子系统持仓                   • 22内置节点持续完善       │
│  • 场景-系统能力评估                • 子系统封装为扩展节点     │
│  • 冲突告警（建议制）               • A层动态编排最优组合      │
│  • 不干预子系统实盘                 • 回测验证驱动优化         │
│                                                              │
│              ↓ 评估数据参考 ↓                                │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  各子交易系统（独立实盘，不受干预）                     │   │
│  │  V15 马丁 | 易经推理 | 三屏趋势 | AB-Trading           │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

## 3. 落地路径

### 3.1 阶段1：总调度观察层（立即启动，零风险）

**目标**：建立跨账户持仓聚合与冲突检测能力

**任务清单**：
1. 复用 `16-调控系统/core/unified_position_query.py` 建立持仓查询
2. 实现跨账户总暴露计算（按币种聚合4个系统的净敞口）
3. 接入 `core/sense/scenario_classifier.py` 36场景分类
4. 实现冲突检测规则：
   - 同币种跨账户净敞口超过阈值（如40%）
   - 跨账户方向极度不一致（如2个做多+2个做空）
5. 输出观察看板（日志/文件形式）

**约束条件**：
- 完全只读，不调用任何下单接口
- 不修改任何子系统的配置或状态
- 观察周期建议与 master_daemon 同步（1H）

**验收标准**：
- [ ] 能正确聚合4个子系统的持仓数据
- [ ] 能计算每个币种的跨账户净敞口
- [ ] 能识别并记录冲突事件
- [ ] 输出格式统一的观察报告

### 3.2 阶段2：能力评估层（1-2周）

**目标**：建立场景-系统二维能力评估体系

**任务清单**：
1. 扩展 `capabilities/trading/evaluator.py`：
   - 评估对象从"自身节点"扩展到"各子系统"
   - 按场景-系统二维记录实盘表现
   - 5维评分：准确率/胜率/盈亏比/稳定性/时效性
2. 建立数据采集管道：
   - 从各子系统的 state/memory 文件中提取交易记录
   - 按场景 ID 分类归档
3. 输出"场景→最优子系统"映射表
4. Dream OS 自身回测作为基线对比

**约束条件**：
- 仅基于历史数据进行离线评估
- 不实时干预任何子系统
- 评估结果仅用于 Dream OS 自身交易系统的节点优化参考

**验收标准**：
- [ ] 能按36场景分类各子系统的交易记录
- [ ] 能输出每个场景下的子系统能力评分
- [ ] 能生成"场景→最优子系统"推荐映射
- [ ] 评估报告可持久化存储

### 3.3 阶段3：旗舰交易系统节点扩展（2-4周）

**目标**：丰富 Dream OS 自身节点生态

**任务清单**：
1. 封装三屏趋势信号为 `C_S3_TREND` 节点（FunctionAdapter）
2. 封装易经推理为 `A_YJ_INFER` 节点（SkillAdapter）
3. 封装 V15 马丁信号为 `C_MARTIN_V15` 节点（FunctionAdapter）
4. 注册扩展节点到 `registry/node_registry.py`
5. 扩展 `OrchestrationMemory` 支持场景→最优节点选择
6. 回测验证：
   - 22内置节点基线
   - 单扩展节点表现
   - 组合节点表现

**关键约束**：
- 封装节点为**只读调用**子系统信号接口
- 不允许封装节点触发子系统下单
- 子系统实盘账户完全独立，不受影响
- 所有新节点必须先通过回测验证才能纳入编排

**验收标准**：
- [ ] 至少封装2个子系统为扩展节点
- [ ] 扩展节点能通过回测验证
- [ ] 场景-节点评分矩阵可更新
- [ ] 组合策略回测胜率 > 基线

### 3.4 阶段4：建议制协调上线（暂缓）

**暂缓原因**：
- 各子系统处于研发阶段，策略逻辑和参数仍在频繁调整
- 过早介入可能干扰子系统的独立进化
- Dream OS 自身交易系统和评估体系尚需完善

**上线条件（需同时满足）**：
1. 各子系统策略逻辑稳定（至少连续2周无重大调整）
2. Dream OS 自身交易系统回测胜率稳定在50%以上
3. 阶段2的评估数据样本量充足（每个场景至少20笔交易）
4. 有明确的冲突处理预案

## 4. 子系统封装节点设计草案

### 4.1 C_S3_TREND（三屏趋势信号节点）

```python
node_id = "C_S3_TREND"
name = "三屏趋势信号"
chain = "C"
tags = ["trend", "multi-timeframe", "screen3"]
priority = 70

# 调用点: 12-三屏趋势系统/core/indicators.py
# 输入: symbol, market_data
# 输出: direction(LONG/SHORT/HOLD), confidence, rationale
```

### 4.2 A_YJ_INFER（易经推理节点）

```python
node_id = "A_YJ_INFER"
name = "易经卦象推理"
chain = "A"
tags = ["divination", "yi-jing", "inference"]
priority = 65

# 调用点: 11-易经推理系统的卦象推理 SKILL
# 输入: symbol, market_data
# 输出: direction, confidence, hexagram_info, rationale
```

### 4.3 C_MARTIN_V15（马丁策略信号节点）

```python
node_id = "C_MARTIN_V15"
name = "V15马丁策略信号"
chain = "C"
tags = ["martin", "grid", "v15"]
priority = 60

# 调用点: 14-V15经典马丁策略/core/v15_signal.py
# 输入: symbol, market_data
# 输出: direction, confidence, grid_levels, rationale
```

### 4.4 节点调用约定

所有封装节点必须遵守：
1. **只读原则**：仅读取子系统的信号输出，不修改子系统状态
2. **超时保护**：调用子系统接口设置超时（默认5秒）
3. **降级处理**：子系统不可用时返回 HOLD + 低置信度
4. **结果标准化**：统一返回 `NodeResult` 格式

## 5. 风险声明

### 5.1 已知风险

| 风险 | 等级 | 描述 | 缓解措施 |
|------|------|------|----------|
| 子系统接口变动 | 中 | 子系统研发阶段接口可能频繁变化 | 封装层增加版本兼容处理 |
| 评估数据不足 | 中 | 新场景样本量不足时评分不可靠 | 设置最小样本阈值（20笔） |
| 过度拟合 | 低 | 按场景细分可能导致过拟合 | 交叉验证 + 滚动窗口评估 |
| 子系统信号延迟 | 低 | 实时调用子系统接口可能有延迟 | 异步采集 + 缓存机制 |

### 5.2 禁止事项

- ❌ 任何封装节点不得触发子系统下单
- ❌ 总调度层不得修改子系统的配置或状态文件
- ❌ 不得在子系统实盘运行时进行干预性操作
- ❌ 阶段4上线前，不得向子系统输出强制指令
