## 0. 核心目标与最高原则

**本工作区的核心任务是持续推进 `3.1-FRONTEND` 的工业级可用性，并使其与现有后端真实、稳定、可观测地联通。云端部署、问题修复、LobeHub 及其他同类方案的评估都是实现这一目标的手段，而不是目标本身。**

### 0.1 三项最高原则

1. **以前端工业级可用为主**：围绕真实用户工作流，不断提升可用性、稳定性、性能、异常恢复、可观测性、安全性和运维能力，并打通 `前端 → DreamOS（SACG）→ DSH → L0/L1` 的真实后端链路。
2. **不改变核心架构**：严格遵守 `1-ARCHITECTURE/3+3架构模块映射.md` 及其上游 SSoT，不新增架构层、不替换 DreamOS/DSH 主骨架、不建立旁路。
3. **不改变既有功能**：保留现有页面、业务入口、交互流程、数据语义和后端能力，不擅自删除、替换、降级或以新方案重做既有功能。

**功能不变不等于缺陷保留。** 可以修复 bug、改善易用性、性能、稳定性、错误提示和恢复能力；但不得借“工业级改造”改变既有业务语义或让原有能力回退。

### 0.2 工业级可用的判定口径

工业级可用不等于页面返回 HTTP 200，而是同时满足：

- 核心用户工作流真实可用，操作状态与错误反馈明确；
- 前端到后端的真实业务链路联通，不以 mock 代替活体证据；
- 现有功能无回归，异常可恢复、请求可取消、超时可控制；
- 加载、流式响应和长时间运行无未经登记的明显退化或资源泄漏；
- `trace_id` 可贯穿请求、执行、响应与日志，问题可定位；
- 鉴权与数据边界有效，密钥不泄露；
- 部署版本明确、过程可复现、结果可验证、故障可回滚。

## 2. 当前基线

以下能力已经完成代码落地和本地验证，后续首先部署与复验，不默认重做：

1. **链路 A：Agent 聊天断网恢复**
   - 断网状态提示；
   - 恢复联网后最多自动重试一次；
   - 消息为空时不得调用 `regenerate()`；
   - 自动重试异常必须被捕获，避免未处理 Promise rejection。

2. **链路 B：BAC Timeline 生命周期治理**
   - 组件卸载时通过 `AbortController` 中断请求；
   - 卸载后不得继续写入组件状态。

3. **链路 C：DSH 调用与全链追踪**
   - 浏览器代理、DSH HTTP、DSH IPC 透传 `trace_id`；
   - 请求头、请求体和响应回显使用同一追踪语义；
   - `DSH_API_TOKEN` 转为 `Authorization: Bearer ...`；
   - 异步轮询使用后端真实能力名 `orchestrator_status`；
   - 按真实返回信封判断终态，不死等不存在的 `status === 'done'`。

4. **本地活体验证基线**
   - 已验证真实 Python `/execute` 服务、Bearer、trace 回显、HTTP/IPC 和异步终态；
   - 本地验证通过不代表云端通过，云端仍须逐项复核。

当前第一阶段任务是：**以最新 GitHub 主干为候选版本，在真实云端完成部署和验收。** 部署只是工业级可用性的起点；验收后仍须针对发现的问题持续修复或评估合适方案，直至核心用户工作流与后端联通达到本 SPEC 的完成定义。

## 4. 架构与数据边界

### 4.1 主链路

```text
用户
  ↓
3.1-FRONTEND（唯一 UI、交互、可视化、API 适配）
  ↓
DreamOS / SACG（认知规划、OKR 验收、执行驱动、压缩沉淀）
  ↓
DSH（能力执行与子 Agent 隔离执行）
  ↓
L0/L1（数据、认知、工程事实、零 token 确定性能力）
  ↓
交易链与训练链（只读观察，不越权执行）
```

职责约束：

- 前端负责交互、展示、协议适配和基础设施治理，不做交易业务决策；
- DreamOS 保留编排主权；
- DSH 负责能力执行，不在前端复制一套执行编排；
- L0 是数据与认知事实边界，前端不得直连认知数据库；
- L2 对交易和训练链只读，实盘执行永不暴露 MCP。

### 4.2 LobeHub / 52 专项约束

以 `52-lobehub协议集成/SPEC.md` 现行版本为准，至少遵守：

1. `3.1-FRONTEND` 是唯一前端，不部署独立 LobeHub 应用，不新建第二聊天页面；
2. LobeHub 作为协议与设计参考，52 的落点是 3.1 内置 LLM 协议层；
3. 禁止 fork 或 vendor LobeHub 源码进行二次开发；
4. 通过 Vercel AI SDK、配置、插件和 MCP client 复用同构能力；
5. L0 能力消费以 MCP 为唯一接口，挂载壳必须登记在 47 registry 并通过 drift 检查；
6. 协议层 agent loop 只能作为执行器，不能替代 DreamOS NodeRegistry 或 SACG 编排；
7. 认知记忆只能经 L0 cognition 壳访问，禁止直连 `4-MEMORY`；
8. 首期只挂只读能力，交易写能力需独立评审，live 交易不在本 SPEC 范围内。

## 6. 分阶段执行契约

### Phase 0 — 目标冻结与部署准备

1. 获取并记录 `origin/main` 的完整 SHA，确认包含本工作区和其他工作区已完成的相关改动；
2. 记录云端当前服务、部署目录、运行 PID、当前版本、Node/pnpm 版本与健康状态；
3. 检查云端原工作区状态，仅用于识别冲突，不处理其他工作区文件；
4. 在独立干净工作树检出目标 SHA，安装依赖并执行生产构建；
5. 构建失败则不切换线上服务，先按 §8 分类处理。

**出口门禁**：目标 SHA 唯一、构建来源干净、依赖安装与生产构建成功、回滚版本可用。

### Phase 1 — 云端部署与基础健康验证

1. 保持原工作区改动不变，使用已验证的干净构建切换服务；
2. 重启前后记录代码版本和工作区状态；
3. 验证 systemd 状态、端口、HTTP、页面资源和运行日志；
4. 若出现致命异常，停止验收并回滚到部署前版本。

**出口门禁**：服务稳定运行，运行版本等于目标 SHA，核心页面可访问，无新增致命日志。

### Phase 2 — 核心链路与回归验收

按 §7 的验收矩阵逐项收集证据。任一 P0 项失败，不得宣告整体完成。

### Phase 3 — 工业级可用性修复与方案评估

1. 前端实现缺陷：优先最小修复 + 回归测试 + 云端复测；
2. Next.js / AI SDK 基础框架缺口：先核对官方契约和现有实现，再决定最小改造；
3. LobeHub 或其他同类方案：针对真实可用性问题或明确改进需求开展评估，形成复用矩阵；能提升工业级可用性且不改变核心架构、既有功能和后端契约时，按门禁实施；
4. 其他工作区缺陷：提交证据和契约，不越界修复。

每轮以已复现的问题或有证据的改进需求为输入，完成后回到 Phase 0/1 重新部署并执行受影响项及回归项。方案选择以实际效果为准，不预设必须自研，也不预设必须采用 LobeHub。

## 8. 失败分类与处置路由

| 分类 | 判定依据 | 本工作区动作 |
|---|---|---|
| F1 前端实现 | 组件、route、状态、请求生命周期或 trace 适配错误 | 最小修复、补测试、重新部署复验 |
| F2 基础框架契约 | Next.js / React / AI SDK 的真实行为与原假设不符 | 查官方文档和源码契约，形成最小适配方案 |
| F3 外部方案可复用缺口 | 现有方案缺口明确，LobeHub 或其他同类方案已有可复用能力、协议或设计 | 评估并更新复用矩阵，按现有架构与 52 SPEC 门禁评审后集成 |
| F4 跨工作区契约 | DSH/L0/数据等返回不符合已公布契约 | 固定 trace 与复现证据，交对应工作区 |
| F5 云端运维 | 权限、环境、依赖、systemd、端口或历史构建污染 | 隔离运行态问题，不改业务代码顶替运维修复 |
| F6 需求或架构冲突 | 实现目标与 SSoT、52 SPEC 或唯一前端原则冲突 | 停止实施，先修订目标并获得用户确认 |

禁止把 F4/F5 误当 F1 在前端堆兜底，也禁止把 F1 掩盖为第三方框架缺陷。

## 9. LobeHub 及同类方案评估门禁

出现以下任一情况时，应评估“修复现有实现”与“借鉴外部成熟方案”两条路径，不局限于 LobeHub：

- 云端验收或真实使用暴露可用性、稳定性、性能、异常恢复、可维护性或后端联通问题；
- 现有 Next.js / AI SDK 方案无法合理满足已确认的能力需求；
- 需要模型路由、MCP 消费、PlanCard、流式恢复或 Agent 执行语义等已知协议能力；
- 自行修复将造成重复建设，而 LobeHub、52 专项 SPEC 或其他同类方案已有成熟能力可复用。

**处置原则**：能以小成本可靠修复现有实现时优先最小修复；现有方案不适合时，可以借鉴、评估并复用 LobeHub 或其他同类解决方案。选择标准是实际解决问题的效果、既有功能保持、核心架构不变、后端契约兼容、最小侵入、可测试和可回滚，而不是技术偏好。

评估产出必须包含：

1. 问题证据与最小需求；
2. 现有前端、Next.js、AI SDK、LobeHub 及其他候选方案的能力对照；

## 10. 后续开工流程

每个后续任务按以下顺序执行：

1. **召回与定位**：调用 `recall`，阅读本 SPEC 及相关专项文档，标注对应验收 ID；
2. **任务绑定**：记录目标、范围、目标 commit、run_id 和明确不处理的文件；
3. **证据复现**：先获取症状、日志、网络或测试证据，禁止凭感觉改代码；
4. **最小计划**：列出要修改的文件、契约影响、测试和回滚方式；
5. **实施验证**：优先 TDD；代码、测试和文档保持同一语义；
6. **安全交付**：只暂存本任务文件，提交或推送须有用户明确要求；
7. **云端验收**：按 §7 执行受影响项和必要回归项；
8. **收尾闭环**：更新证据、已知限制和认知记录；未验证项保持 `PENDING/BLOCKED`。

本轮仅创建目标 SPEC，不执行第 4 步之后的代码实施或线上变更。

## 11. 完成定义（Definition of Done）

本目标只有同时满足以下条件才可宣告完成：

- 所有 P0 验收项为 `PASS`，或经用户明确接受的有证据 `DEGRADED_PASS`；
- P1 项无未登记的失败，未执行项有明确原因和后续归属；
- 现有功能无回归，三条核心链路均有云端真实证据；
- 至少一条现有核心用户工作流完成前端到后端再到界面展示的端到端活体验收；
- 本轮发现的工业级可用性问题均已修复，或已完成方案评估并有明确的阻塞归属与后续门禁；
- 部署版本、配置形态、日志位置和回滚路径明确；
- 未把其他工作区改动混入本次提交或部署；
- 未引入第二套 UI、LobeHub fork、DreamOS 旁路、认知库直连或交易执行旁路；
- 所有失败与降级均如实记录，没有用 mock、缓存旧结果或单次 HTTP 200 替代活体结论。
