## §0 Executive Summary

两个想法拆成两层交付，**共用一个事实源**：

| 想法 | 交付层 | 一句话 |
|---|---|---|
| ① 统计能力封装为 DSH 插件，L2 调 L1，算法组件可自主更新，前端「+」选能力 | **A 插件层（出口）** | 新增 `dreambuddy-stats` 插件 + `l1.stats.mcp` 壳，4 个工具（list/run/validate/explain），只透传不决策 |
| ② 建「数据-价格关系」统计算法系统（目标→分类→归纳→验证→推荐→实践→反思） | **B 算法层（闭环）** | 复用已有 Discovery/MERS 骨架，补「分类法 / 归纳层 / 推荐卡片 / 信号层 / 反思消费」五段 |

**最关键的一条现状判断（决定工作量）**：想法 ② 的**第 4 步（假设与验证）在仓库里已经实现了 60%~70%**，不是从零开始 —— 已有预注册搜索空间、RankIC 检验、BH-FDR 校正、70/30 holdout、`relationship_registry.db` 状态机、两个只读出口能力。缺口在于**分类法（S2）、归纳（S3）、推荐卡片（S5 的可视化侧）、信号与下单（S6）、反思回写（S7）**，以及想法 ① 的**插件出口完全为零**（14 个插件包里没有 stats 包，python-server 13 个 method 里没有统计方法）。

**架构结论**：L1 算、L1 只读出口、插件只透传、L2 只编排；全链路零 LLM；插件不是新计算层，只是「L1 能力 → DSH Worker」的低延迟工具面。

## §2 目标与非目标

### 2.1 目标

1. **出口层**：L1 全部统计能力以 **1 个 DSH 插件 + 4 个工具** 暴露给 L2，L2 无需知道 93 个能力 ID 的内部细节也能发现、调用、预检、自述。
2. **可更新性**：统计算法组件（manifests / executor 版本）升级后，插件工具面自动跟随，不需要改插件代码、不需要重启 L2。
3. **供给层**：前端「+」可从统计能力库挑选能力挂到看板，能力库与后端 manifest 同源，禁止前端硬编码能力清单。
4. **算法闭环**：把「目标→分类→归纳→验证→推荐→实践→反思」七步全部落成**可机器判定**的工程对象，每步有输入/输出/门禁。
5. **零 LLM**：全程规则 + 统计量 + 回测，任何一步不得调用生成式模型。

### 2.2 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 不为 93 个能力各建一个插件包 | 工具面爆炸 + 白名单 93 条维护成本不可接受（见 ADR-A1） |
| 插件内做统计计算 / 缓存计算结果 | 违反 HC-9「插件只透传不决策」；会与 L1 产出漂移 |
| 新增第二套图表契约 / 新 `kind` | 硬约束：`visual` 只允许 5 种 kind（§1 事实 11） |
| 让 Discovery 运行期写注册表 | 已有硬规则：运行期只出 `candidate`，落库只能由 MERS 写（§1 事实 4/6） |
| 让 L1 或插件直接下单 | 执行层唯一入口是 22-执行引擎中心（SPEC-54-L1交易层已定边界） |
| 在前端展示算法流水线内部 | 候选枚举 / RankIC 分布 / 门禁漏斗 / patterns 中间产物属后端研发可见；前端只输出能力与结论（§11） |
| 前端全量铺开 93 个能力 | 默认 13 卡，其余按需「＋」挂载，有 tab/卡上限（§11） |
| 引入 LLM 做「关系解释」 | 本 SPEC 的归纳输出是结构化 table，文案走模板渲染 |

## §3 设计原则（硬约束，评审时逐条对照）

| # | 原则 | 落地方式 |
|---|---|---|
| P1 | **插件只透传** | 插件内不出现任何统计公式；只做参数校验 → IPC → 信封原样返回 |
| P2 | **单一事实源** | 能力清单 = `capability_manifest.yaml`；算法包 = 新增 `algorithm_registry.yaml`；搜索空间 = `discovery_space.yaml`（引用算法包，不自带方法清单） |
| P3 | **只读治理** | 发现器只产出 `candidate` 报告；注册表写入只走 MERS；反思只产出**建议**不写库 |
| P4 | **FAIL-OPEN** | 插件/能力/服务任一异常 → `degraded` 信封，L2 拿到降级结果而非异常 |
| P5 | **契约不扩** | 新字段一律进 `dataset`/`meta`，`spec_version` 保持 `"1.0"` |
| P6 | **无 LLM** | 分类、归纳、文案全是规则/模板/统计量 |

## §4 A 层：统计能力 DSH 插件化

### 4.1 ADR-A1 插件粒度：**单插件聚合**（不是 per-capability）

**决策**：新增 1 个包 `cordis-plugin-stats`（插件 id `dreambuddy-stats`），内部注册 4 个工具；**不为 93 个能力建 93 个包**。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 93 个包 | 语义最清晰 | 白名单 93 条、工具体积、版本漂移、启动开销 | ❌ |
| B. 按域 8~10 个包（A/E/G/J/K） | 折中 | 域边界会随能力增长漂移；仍要维护 10 份白名单 | 🟡 备选 |
| **C. 单包 + 4 工具（本方案）** | 白名单 1 条；工具面稳定；能力扩张只改 manifest | 单个 tool 的参数是「能力 ID + 载荷」，语义靠 `explain` 补 | ✅ |

**代价与缓解**：L2 看不到「93 个独立工具」，靠 `stats.list` 拿到目录 + `stats.explain` 拿到契约自述来补偿。这与 MCP 的「资源发现」思路一致。

### 4.2 工具面（4 个工具，全部只透传）

| 工具 | 入参 | 出参 | 是否触碰计算 |
|---|---|---|---|
| `stats_list` | `{domain?, min_n_max?, viz_kind?, q?}` | `{items:[{capability_id, intent, domain, min_n, methods, viz_kinds, status}], total, manifest_version}` | ❌ 只读 manifest |
| `stats_run` | `{capability_id, payload}` | 标准 `capability_result` 信封（含 `status/data/visual/meta`） | ❌ 转发 `run_capability` |
| `stats_validate` | `{capability_id, payload}` | `{ok, errors[], warnings[], required_fields[], min_n, sample_n}` | ❌ 只做形状/日期/缺失率预检 |
| `stats_explain` | `{capability_id}` | `{notes, methods, degradation_policy, contract, examples[]}` | ❌ 只读 manifest + 契约 |

**为什么需要 `stats_validate`**：能力层是 FAIL-OPEN 的，非法输入会静默降级成 `empty`。L2 在编排时最需要的是「我先问一句能不能跑」，而不是「跑完发现是空的」。这个工具零计算量，但能显著降低 L2 的无效 token 消耗。

### 4.3 通道：新增唯一 IPC method

```
cordis-plugin-stats (lib/index.js)
  └─ shared IPC ──► python-server/server.py  method="stats_capability"
                     ├─ op=list     → capability_manifest 读取（只读）
                     ├─ op=run      → l1agg.capabilities.stats.run_capability
                     ├─ op=validate → 契约预检（不调用 executor）
                     └─ op=explain  → manifest.notes + contracts
```

- `server.py` 需在 method 分发链（现状 [L1769-L1793](../../1-ARCHITECTURE/dream-harness-bridge/packages/python-server/server.py#L1769-L1793)）增加**一个** `elif method == "stats_capability"`。
- 4 个 op 走同一 method，避免 4 条分发分支；op 非法 → `degraded`。

### 4.4 MCP 壳 `l1.stats.mcp`

- 白名单要求自有 approved 插件 `mcp_shell_required: true`（§1 事实 10），因此**必须有壳**：`plugin_shell: "l1.stats.mcp"`。
- 壳与插件**共用同一 dispatch 函数**（4 个 op），禁止两份实现。
- 分工：
  - DSH Worker → 插件 → IPC（低延迟，进程内）；
  - 非 DSH 消费方（前端 BFF / 其他 agent / 外部）→ `l1.stats.mcp` HTTP。
- 两者返回**同一个信封**，区别只是传输层。

### 4.5 算法组件「自主更新」（想法①的第二诉求）

设计为**版本协商**，而不是热替换代码：

| 机制 | 做法 |
|---|---|
| 组件版本 | `capability_manifest.yaml` 每条能力新增 `component_version`（如 `stats-2026.11.1`），manifest 顶层加 `manifest_version` |
| 启动协商 | 插件启动时读 manifest，生成工具描述（可用能力数、域分布、manifest_version）；不缓存结果 |
| 运行期漂移 | 每次 `stats_run` 回读 `capability_id` 是否仍注册；不存在 → `degraded(reason=capability_retired)`，不 crash |
| 升级方式 | 新增/替换 executor + 改 manifest 条目（版本号递增）→ 插件侧零改动；L2 通过 `stats_list` 感知新能力 |
| 回滚 | manifest 回退 + `component_version` 回退；注册表保留 `data_version`，可判定「关系是否因数据版本变化失效」 |

> 说明：**不实现**「运行中动态加载 Python 模块」。那会让 L1 变成可变执行环境，违反 P2/P3。所谓「自主更新」= 新算法作为**新能力 ID** 注册进 manifest，旧 ID 保持不变或标记 `retired`。

### 4.6 前端「+」能力库

| 项 | 设计 |
|---|---|
| 数据源 | `GET /api/visual/capabilities`（BFF 聚合 `stats_list`），与 L1 manifest 同源 |
| 交互 | 「+」→ 抽屉：域分组（A 指标/E 关系/G 横截面/J 方法/K 出口）、搜索、`min_n` 徽标、所需数据域徽标、预览按钮 |
| 预览 | 调 `stats_validate`；`ok=false` 直接灰掉不可选，显示缺失字段，**不发执行请求** |
| 添加 | 生成 `panel_spec = {capability_id, args, viz:{kind, title}, collapsed}`，写入看板配置 |
| 两级入口 | tab 级「＋」新建 tab（≤8）并选首卡；卡片级「＋」追加能力卡（≤12/tab）；超限置灰 |
| 折叠 | 卡片折叠只留标题行；折叠态不渲染不请求（懒加载），展开才调 `stats_run` |
| 去重 | `panel_key = capability_id + hash(args)`；重复添加定位已有卡而非新建 |
| 配置落点 | 前端本地配置（localStorage）优先；跨端一致需求出现后再上后端（见 §10 开放问题 Q3） |
| 与默认配置关系 | 首次进入给 3 tab / 13 卡作为默认配置，其余能力按需挂载；默认配置也可被用户改写 |

### 5.2 S2 关系类型分类法（用户说的「归类」）

把「价格-数据关系」拆成 6 类，每类绑定**判据统计量 + 现有能力 ID**。这是整个算法系统的骨架：

| 类型 | 定义 | 判据 | 现有能力 |
|---|---|---|---|
| **R1 趋势延续** | 状态有粘性，趋势不变 | 状态转移对角概率 > 0.5；Hurst > 0.5；trend_test 拒绝随机游走 | D-E07、D-J01、D-J13 |
| **R2 趋势变化（形态切换）** | 结构发生切换，方向改变 | change_point 显著；转移矩阵非对角跃升；谱包络拐点 | D-J04、D-E07、D-J07 |
| **R3 周期规律与方向** | 存在季节/周期相位 | 谱峰显著（cycle_spectrum）；月度效应 p_adj<0.05；季节调整后残差可预测 | D-J05、D-E03、D-J02 |
| **R4 惯性（动量/反转）** | 自身历史预测未来 | lead-lag 自相关；12-1 动量 IC；条件收益单调 | D-A12、D-G08、D-E01、D-G20 |
| **R5 前瞻指标** | 外部序列领先价格 | lead_lag 互相关显著；transfer entropy 方向性；conditional_ic 稳定 | D-A12、D-J11、D-E08 |
| **R6 阻力最小方向** | 条件收益非对称 | 上/下分位条件收益差显著；quantile_monotonic 单调；FNS 价尺 | D-E01、D-G20、[SPEC-54-金融价尺系统](../../54-L1架构能力聚合层/SPEC-54-金融价尺系统.md) |

> 关键约束：**类型不是人工贴标签**，由 `algorithm_id` 的 `relation_type` 字段声明 + 判据能力在验证阶段复核。R6 复用未落地的金融价尺（FNS）作为 North Star，落地前 R6 只做统计描述、不出信号。

### 5.4 S3 归纳层（无 LLM）

**输入**：`reports/discovery/<YYYYMMDD-HHMM>/findings.jsonl`
**输出**：同目录 `patterns.json`（新增）

规则（确定性）：

1. 按 `(relation_type, transform_family, horizon)` 分组（变换族见 `patterns.py::TRANSFORM_FAMILY`）；
2. **一条 finding 只归主类**（CR-7）：`primary_only=True`，按 `algorithm_registry.method_roles` 的**首个** relation 归类（B14 → R1，R4 不再重复消费同一证据）；
3. 每组统计：`support`（`p_adj < alpha` 且 `rank_ic > 0`）、`oppose`（`p_adj < alpha` 且 `rank_ic < 0`）、`sign_agreement = max(support, oppose) / significant_n`；
4. 组内二项检验（H0: p=0.5）→ 全组 BH（**秩次缩放**，不是 `p × 检验次数`）→ `p_adj`（CR-12）；
5. `stable` 需同时满足：`sign_agreement ≥ 0.8`、`p_adj < 0.05`、`significant_n ≥ 10`（`MIN_MEMBERS`，二项功效下限：n=9 全同向 p≈0.0039 仍只判 candidate）；否则 `candidate`；
6. 少数派占比 `1 − sign_agreement ≥ 0.3` 时打 `bimodal=true`，提示按 regime 拆分，不因此直接降级（CR-13）；
7. `members` 只允许 `eval_id`（去重排序）；findings 缺 `eval_id` 视为非法输入计入 `skipped`（CR-11）；
8. 输出结构（示意，不是自然语言）：

```json
{
  "pattern_id": "PAT-R4-mom-h5",
  "relation_type": "R4",
  "family": "mom",
  "horizon": 5,
  "direction": 1,
  "support": 7,
  "oppose": 1,
  "significant_n": 8,
  "sign_agreement": 0.875,
  "bimodal": false,
  "p_value": 0.070312,
  "p_adj": 0.070312,
  "members": ["EV-0001", "EV-0002"],
  "status": "candidate"
}
```

9. **硬规则**：`patterns.json` 的文案由前端模板渲染（「8 条同类关系里 7 条同向」），禁止生成因果/预测措辞（对齐 D-K02 的「禁止因果与预测措辞」）。

### 5.5 S4 有效性门禁（「准确率 ≥60%」的可执行口径，CR-1~CR-9 关闭后冻结）

**裁定**：`hit_rate ≥ 0.60` **不能单独作为关系成立条件**。命中率必须相对基线、按有效样本量、通过样本外与跨期复现、且覆盖交易成本。定义为 **G0 前置 + G1–G6 六门**：

`gate_pass = G0 ∧ G1 ∧ G2 ∧ G3 ∧ G5 ∧ G6`；**G4 是晋升门**（`status` 升 `stable` 的必要条件），不进门禁布尔值——否则 `pass_streak` 与 `gate_pass` 互为前置，状态机无法启动。

#### 5.5.1 冻结常量（运行期不可调，写入 `params_hash` / `replay_key`）

| 常量 | 值 | 说明 |
|---|---|---|
| `HIT_RATE_MIN` | 0.60 | 用户原始要求，保留为**必要不充分**条件 |
| `EXCESS_HIT_MIN` | 0.03 | 超额命中率下限（3pp），低于此视为信息量不足 |
| `HIT_EXTREME_Z` | 1.0 | 方向命中的极值定义：`|z| ≥ 1.0`（raw / diff / pct / zscore60 走此口径） |
| `HIT_EXTREME_QUANTILE` | `{1, 5}` | `quintile5` 只取两端桶；`ts_rank60` 取 `≤0.2 / ≥0.8` |
| `HOLDOUT_FRACTION` | 0.30 | 按时间顺序 70/30 切分，禁止随机打乱 |
| `HOLDOUT_HIT_MIN` | 0.55 | 样本外命中率下限 |
| `HOLDOUT_EXCESS_MIN` | 0.0 | 样本外超额命中必须 `> 0` 且与 screen 同号 |
| `FDR_ALPHA` | 0.05 | 单期 BH，**秩次缩放** |
| `MIN_N` | 250 | 原始样本量门槛 |
| `MIN_N_EFF` | 30 | 有效样本量门槛：`n_eff = floor(n / h)` |
| `COST_BPS_DEFAULT` | 10.0 | 单边 5bps + 双边滑点；可被能力参数覆盖，须记录来源 |
| `REPLICATION_PERIODS` | 3 | 跨期复现所需连续期数 |
| `MIN_MEMBERS` | 10 | 归纳层 stable 的最少显著成员数（二项功效下限） |

#### 5.5.2 六门（全部机器可判定）

| 门禁 | 判据 | 数据落点 |
|---|---|---|
| **G0 可计算性** | `n ≥ 250` ∧ `coverage ≥ 0.8` ∧ `n_eff = floor(n/h) ≥ 30` | `n / coverage / n_eff`（CR-3） |
| **G1 超额命中** | `hit_rate ≥ 0.60` ∧ `excess_hit = hit_rate − base_rate ≥ 0.03` ∧ `wilson_lb(hits, n_eff) > base_rate` | `hit_rate / base_rate / excess_hit / hit_rate_lb`（CR-1） |
| **G2 样本外** | `holdout_hit_rate ≥ 0.55` ∧ `holdout_excess = holdout_hit_rate − holdout_base_rate > 0` ∧ 与 screen 同号 ∧ **该评估为首次**（首次评估事务内写 `holdout_used_at`；同 `eval_id` 重跑走幂等分支，不重算、不覆盖） | `holdout_hit_rate / holdout_base_rate / holdout_agree / holdout_used_at`（CR-8） |
| **G3 多重检验** | 整期 findings 全量 BH（秩次缩放）→ `p_adj < 0.05` | `p_adj`（CR-12） |
| **G4 跨期复现（晋升门）** | `pass_streak ≥ 3`：连续 3 个报告期同 `(method, transform, target, horizon)`、`sign(rank_ic)` 同号、同 relation 族；任一期不满足即归零 | `pass_streak`（CR-4） |
| **G5 效应量 > 成本** | `effect_bps > cost_bps`（`effect_bps` = 命中组条件收益中位数，bps） | `effect_bps / cost_bps`（CR-5） |
| **G6 结论边界** | `scope` 四元组齐备：`time_range / markets / params / sample`；缺任一 → `gate_pass=0` | `scope_json` / 卡片 `scope`（CR-9） |

> 旧四门（hit + Wilson + holdout + p_adj + streak）是 G1–G4 的子集；新增 G0 / G5 / G6 与基线口径。**`hit_rate` 只作必要条件，不再单独触发推荐。**

**命中样本口径（CR-2 落地约束）**：`hit_rate` 必须在该单元的**冻结极值子样本**上计算（`|z|≥1.0` / `quintile∈{1,5}` / `ts_rank60≤0.2 或 ≥0.8`），并按关系方向定义「命中」：`direction=+1` 时极值侧前瞻收益同号算命中，`direction=-1` 时反向算命中。**全样本同向率（M23 `ratio`）不得作为 G1 输入**；极值子样本的 `n_eff < 30` → G0 不过。冻结极值定义进 `params_hash`，发现器不得按事后阈值重算。

**Wilson 下界必须用 `n_eff`（CR-3）**：
- `n=250, h=20` → `n_eff=12`，即使 `hit=0.75`，Wilson 95% 下界 ≈ 0.47 → 不过 G1；
- `n=250, h=1` → `n_eff=250`，`hit=0.60` 下界 ≈ 0.537 > `base_rate=0.50` → 可过。

> 命中率是**极值子样本**上的比例，因此 G1 的区间用该子样本的有效量 `n_eff_hit = floor(n_hit / h)`；`n_eff` 列（全样本 `floor(n/h)`）只服务 G0。二者不可混用，否则会用大样本精度包装小样本结论。

这条修正替代 v0.6 的示例，避免「高命中率蒙对小样本」进 `D-K01` Top3。

**`base_rate` 定义（CR-1）**：同一 `(target, horizon, 样本区间)` 上**无条件**方向基准命中率，即该窗口前瞻收益为正（`direction=+1`）或为负（`direction=-1`）的样本占比。必须与 `hit_rate` 用同一批对齐样本计算，禁止用全市场均值代替。

> `base_rate` 就是「同区间 buy-and-hold 方向基准」的等价对照——它回答「不做任何条件筛选时本来能中多少」。G1 要求条件命中率**超出**该基准，§5.5.6 的置换检验是第二对照（打破单一框架）。

**holdout 一次性（CR-8 执行语义）**：`holdout_used_at` 必须在**首次评估的同一事务内**写入；该字段非空时再次评估 → 直接返回 `degraded(holdout_reused)`，**不得重算、不得覆盖、不得续用同一段 holdout**。重新切分 holdout 需要新 `data_version` 且旧版本关系标记失效。

**stable 的唯一路径（CR-4 执行语义）**：单期通过 G0–G3、G5、G6 只记 `candidate`；只有 G4 `pass_streak ≥ 3` 才允许升 `stable`。**单期 `p_adj < 0.05` 永远不能直接升 `stable`**，避免跨期重跑线性累积假阳性。

**跨期 α 预算（CR-4）**：单期 BH 只控制期内 FDR；跨期以「连续 3 期同号同族复现」作为第二道控制，不再按天数重复累加 α。每期重跑都写独立报告目录，`pass_streak` 由 MERS 依据历史报告推进，不手工改写。

### 5.8 S7 反思进化（v0.12：接入 48 涌现架构，已裁定）

> 54 侧接口事实表（48 的 walk-forward / 做梦器 / 思维树 / gap registry / 40·50 消费门槛）已同步到 [`54-L1架构能力聚合层/docs/TECHNICAL_DESIGN.md` §8](../../54-L1架构能力聚合层/docs/TECHNICAL_DESIGN.md)（v2.67）；48 侧字段变更须先更新该节再改代码。

**职责边界**：**54 拥有预注册，48 拥有 verdict**。54 产出证据包与实验预注册；48 负责实验编排、在线分流与裁决。54 只读回填 `OutcomeRecord`，**不得改写 verdict**。

#### 5.8.1 三个契约对象

| 对象 | 生产 → 消费 | 必填字段 | 纪律 |
|---|---|---|---|
| `EvidencePacket` | 54 → 48（D3 证据池） | `evidence_group_id / n_tests / eval_id / relation_type / target / horizon / hit_rate / base_rate / excess_hit / n_eff / effect_bps / cost_bps / perm_p / scope / data_version / space_version` | 只读、含 provenance，**不含方向措辞**；同族证据按 `evidence_group_id` 去重，严禁多 horizon 重复计分 |
| `ExperimentPrereg` | 54 → 48 | `experiment_id / hypothesis_key / hypothesis / evidence_ids[] / arm_scheme / unit / endpoint / guardrail{min_periods, effect_bps>cost_bps, max_drawdown} / cooldown_days=7 / frozen_params_hash / status` | 预注册后参数冻结；改参数 = 新 `experiment_id` |
| `OutcomeRecord` | 48 → 54 | `experiment_id / suggestion_id / verdict / verdict_scheme / effect / evaluated_at / reason_code` | 54 只读回填，不改 verdict |

`verdict` 沿用 48 四态：`candidate / verified / rejected / falsified`（样本不足记 `insufficient_data`，方向相反显著记 `falsified`）。**`verdict_scheme="stat_relation_v1"`** 必须随记录落盘：48 的 D3 实验使用「CI_low>0 且盲评 ≥4/5」，与本实验判定不同，共用 `verified` 一词但不得共用判定器。

**晋级门槛（按评审 M1 修订）**：

| 阶段 | 条件 | 判定 |
|---|---|---|
| `candidate` | 每期独立过 G0–G3，且同号期数 ≥3 | 只进观察，不改参数 |
| `verified` | 同号期数 **≥8**（单侧二项 p<0.01）且合并样本 Wilson 下界 > 合并 `base_rate` 且 `effect_bps>cost_bps` | 才允许改参数版本 |
| `falsified` | 同号期数 ≥3 且方向相反显著 | 关闭该 hypothesis |

> 3 期同号单侧 p≈0.125，不足以支撑「已验证」；因此 3 期只到 `candidate`，`verified` 需 ≥8 期。

#### 5.8.2 信号契约：复用 49，不新增 schema

`D-K03` 对外包装成 **`SignalSchema v1`**（49 冻结）：`signal_id / source="l1.stat_relation" / ts / symbol / direction / confidence / horizon / risk_exposure_hint / expires_at / payload`，其中 `payload` 携带 `excess_hit / base_rate / n_eff / effect_bps / cost_bps / scope / data_version`。

48 内部以 **`evidence_type="stat_relation"`** 分类消费（已裁定独立消费），**不映射进 `factor_contradiction_priors`**，不写 40→50 的因子先验 overlay。这样既不扩契约（P5），也不与 48 的因子先验混口径。

#### 5.8.3 分表 + 只读统一视图（已裁定）

| 层 | 表 | 单元 | 臂 | 终点 |
|---|---|---|---|---|
| 54 | `experiment_prereg` | `as_of`（统计期） | `aba`（A 现状 / B 提案） | `excess_hit` / `effect_bps` |
| 48 | `experiments/*/results/*.json` + `metrics/verdict_dashboard.json`（**文件态，无 SQLite 表**） | `run_id`（会话级） | `abcd_2x2_v1` | `time-to-correct-action` |

- **物理分表**，不建单表 `unit` 列：两套 `n`、`endpoint`、检验方法不同，混表会让统计分母漂移。
- **派生只读视图**（T7-2b 核对后修订）：48 **没有** SQLite 实验表，实验结果是 `experiments/*/results/*.json`，裁决汇总在 `metrics/verdict_dashboard.json::entries[]`。因此不做 UNION、不建跨库视图，改为 54 侧派生 `reports/registry/experiment_registry.jsonl`：`build_registry(experiment_prereg 行, verdict_dashboard 条目)`，只读、可重生成，**不写 48 存储**。
- 视图统一输出 `experiment_id / unit / arm_scheme / endpoint / n / status / verdict / verdict_scheme / reason / generated_at / provenance`，**无写权限**。
- `arm_scheme` 必填且带版本（`aba_v1` / `abcd_2x2_v1`），`verdict_scheme` 对应 `stat_relation_v1` / `d3_online_ab_v1`；错配记录进 `skipped`，不静默丢弃。
- 跨表查询必须显式带 `unit`；`summarize()` 只按 unit 分组，`cross_unit_total` 恒为 `None`。

#### 5.8.4 受控参数变更通道（已裁定：允许，但必须回测验证）

```
suggestion(pending)
  → ExperimentPrereg（冻结 frozen_params_hash）
  → walk-forward 回测（复用 48 nested_walk_forward：报告 mean_outer_score / selection_gap / leakage_free）
  → 期级 A/B：≥3 期同号 → candidate；累积 ≥8 期同号 → 可申请 verified
  → 48 verdict=verified（verdict_scheme=stat_relation_v1）
  → 才允许提升 manifest 参数版本（component_version+1，带回滚快照）
```

硬约束：

1. `selection_gap / mean_inner_score > 0.2`（相对值，评审 M3）视为选择过拟合 → `rejected`；`mean_inner_score≤0` 时直接 `rejected`；
2. `leakage_free=false` 或 `degraded=true` → `insufficient_data`，不晋级；
3. 参数变更**禁止在线热改**，必须新版本 + 回滚位；
4. 未拿到 48 `verified` 的建议只停留在 `pending`，不进入反思消费。

#### 5.8.5 硬门禁

- 同一 `hypothesis_key` 30 天内只允许一个 open experiment（否则 `rejected: duplicate_hypothesis`）。`hypothesis_key` 必须是**结构化键**：`sha1(relation_type|target|horizon|param_name|delta_sign)`，自然语言 `hypothesis` 仅作展示，不得参与去重（评审 M4）。
- `cooldown_days=7`：同一 `suggestion_id` 回填后 7 天内不得再提案同一参数。
- 反思建议**不进** `capability_gaps.jsonl`：该池是工程缺口，不是市场假设。
- 54 侧状态机仍为 `pending → evaluated / rejected`，`evaluated` ≠ 48 的 `verified`，禁止直接映射。

#### 5.8.6 与做梦器 / 思维树的协同

- 建议作为做梦器**新增候选算子** `stat_gate_params`（只变异门控参数：`min_members / hit_extreme_z / vol_pct_max / crowd_pct_max`），不改原有序列重排/预算/并行度算子。
- 思维树沿用 `beam_search_dream`：输出 `best_strategy / best_v / path[{depth, transform, v, strategy}]`。
- **V 函数必须含效应项**（评审 M5）：原生 `replay_objective` 只衡量成本/延迟，直接用于门控参数会奖励「调严门控 → 成本降 → V 升」。因此 `stat_gate_params` 分支改用 `V_stat = z(effect_bps − cost_bps) − λ·complexity − μ·(1 − coverage)`；`coverage` 为信号覆盖标的比例，防止把门控调到只放行 1 个标的。
- 做梦结果**不得**直接进 `experiment_prereg`；必须先形成可证伪 hypothesis 并通过上面的回测通道。

**硬边界（保留）**：反思只能产出 `suggestion`，写入 `reports/reflection/` 与 `reflection_suggestion` 表；**不得直接改 `relationship_registry.db` 或 manifest**。状态迁移仍只由 MERS 的 G0–G6 驱动（P3）。

## §11 前端信息架构：数据研究 / 技术图表双顶栏（v0.2 增补）

**导航层级（v0.3 修订）**：`基本面` / `数据研究` / `技术图表` 是**同级主导航**，不再把两者塞进同一页做二级 tab。理由：数据研究是「能力库」，技术图表是「读图工作台」，方向轴不同；同级各自展开才不拥挤。

| 步骤 | 归属 | 是否对外展示 |
|---|---|---|
| S1 目标 / S2 分类 / S3 归纳 / S4 验证 | 后端流水线（Discovery / MERS / patterns） | ❌ 不展示（研发/运维页可见） |
| S5 推荐 | 前端能力卡片（`D-K01` 等） | ✅ 以「能力」形态展示 |
| S6 实践 | 技术图表 | ✅ |
| S7 反思 | 技术图表「信号反馈」+ 报告 | ✅（只读） |

**数据研究 = 算法推荐 → 能力出口**（v0.4 核心修订）

- 组织轴是**推荐项**，不是能力域：左栏是推荐列表（关系类型 + 标的 + 期限 + RankIC + hit），右栏是该推荐的出口卡；
- 一张出口卡 = 一个能力（方法口径 / 证据序列 / 同类归纳），可折叠、可继续「＋」；
- **不展示**：候选枚举、淘汰漏斗、`patterns.json` 全量 —— 推荐列表本身就是筛选后的结果；
- 用户仍可从能力库「＋」自建 tab / 加卡，默认给 2 tab（推荐总览 / 全部出口）13 卡。


**动态 tab 与卡片**

| 层级 | 交互 | 上限 | 数据来源 |
|---|---|---|---|
| tab 级「＋」 | 新建 tab（或复用空 tab），从能力库选首卡 | ≤ 8 tab | `stats_list` |
| 卡片级「＋」 | 当前 tab 内追加能力卡 | ≤ 12 卡/tab | `stats_list` + `stats_explain` |
| 卡片折叠 | 只留标题行；折叠后**不渲染不请求**（懒加载） | per-card | 前端 UI state |
| 卡片「－」/ tab「×」 | 移除卡片 / 删除自建 tab，二次确认 + 撤销；**只删配置，不删能力**；默认 tab 不可删 | — | 配置 store |
| 预览 | `stats_validate` + 一次小样本取数；不满足前置 → 灰掉并显示缺失字段 | — | 后端 |

- **去重**：`panel_key = capability_id + hash(args)`；同 key 重复添加直接定位到已有卡。
- **超限**：「＋」置灰并提示清理，不静默截断。
- **持久化**：`localStorage` 起步（见 Q3）；跨端一致需求出现后再上后端。
- **默认配置**：首次进入给 3 个 tab（跨资产 / 趋势 / 波动）共 13 卡，其余按需添加 —— 上百个能力不全量铺开。

**可行性结论**：可实现，且不需要新增计算能力。后端已有 `capability_manifest.yaml`（93 条，含 `min_n/intent/methods/executor`）+ 统一信封 + 5 种 `kind` 渲染器；前端动态挂载只是「按 manifest 生成卡片 → 按信封渲染」，属纯展示层组合。唯一前置是 §4 的 `stats_list / stats_run / stats_validate / stats_explain` 四个出口。

**技术图表（= v3 独立页）**：8 子页（加权信号点阵 / 点亮图影 / 技术分析叠加 / 信号反馈 + 跨资产 / 波动与回撤 / 周期与资金 / 数据口径）。其中「目标与覆盖 / 算法分类 / 现象归纳 / 假设验证 / 数据卡片」5 个子页作为**完整链路**保留，便于端到端识别；对外开关默认关闭（对内可见），后期可一键隐藏。与数据研究通过「推荐卡片 → 叠加锚点」单向承接，不反向耦合。

**设计稿**：`数据研究` 用 [visual-page-v5-data-research.html](../../3.1-FRONTEND/docs/design/visual-page-v5-data-research.html)（推荐列表 × 出口卡 master-detail + 两级「＋」）；`技术图表` 用 [visual-page-v3.html](../../3.1-FRONTEND/docs/design/visual-page-v3.html)（8 子页完整交互，含 5 个链路子页）。v4 为 v5 的前一版（域地图组织方式，已否定）；v2 保留原始 8 子页。
