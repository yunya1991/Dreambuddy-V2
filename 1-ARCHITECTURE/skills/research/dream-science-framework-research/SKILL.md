# dream-science-framework-research — 整体框架研究

> dreambuddy-v2 科研 SKILL 支柱核心能力之一。借鉴 TrustResearcher/EvoSci 的多 Agent 辩论模式，研究交易系统顶层架构。

## 一、何时调用

满足以下任一条件：
1. 需要研究交易系统的整体架构
2. 需要对比不同框架的设计权衡
3. 需要规划系统演进路径
4. A4 `dream-strategy-designer` 调用本 SKILL 做框架设计

## 二、多 Agent 辩论流程

### Agent 角色设定
1. **极简主义者**：主张最简单的方案，奥卡姆剃刀
2. **复杂系统专家**：主张考虑涌现和非线性
3. **风控优先者**：主张稳健性和安全性
4. **性能追求者**：主张最大化收益和效率
5. **维护工程师**：主张可维护性和可扩展性
6. **跨学科视角者**：引入其他学科的框架（调用 `dream-science-cross-disciplinary`）

### 辩论流程
1. **问题陈述**：明确框架研究的问题
2. **立场陈述**：每个 Agent 提出自己的框架建议
3. **交叉质询**：Agent 之间互相质疑
4. **妥协协商**：寻找共识和折中方案
5. **综合决策**：human-in-the-loop 最终决策

### 让步阈值协议（借鉴 Devil's Advocate）
- 每个反驳评分 1-5
- 评分 ≥ 4 才让步修改立场
- 评分 < 4 坚持原立场，需提供更强论据

## 三、框架对比模板

### 对比维度
1. **复杂度**：组件数量、依赖关系、理解难度
2. **性能**：收益、风险、效率
3. **稳健性**：抗噪声、抗攻击、容错
4. **可扩展性**：添加新组件的难度
5. **可维护性**：调试、更新、重构成本
6. **理论基础**：是否有扎实的理论支撑

### 对比表模板
```
| 维度 | 框架A | 框架B | 框架C | 权重 |
|------|-------|-------|-------|------|
| 复杂度 | 低(2) | 中(5) | 高(8) | 0.2 |
| 性能 | 中(6) | 高(9) | 高(8) | 0.3 |
| 稳健性 | 高(8) | 中(5) | 低(3) | 0.2 |
| 可扩展性 | 高(8) | 中(5) | 低(3) | 0.1 |
| 可维护性 | 高(9) | 中(6) | 低(3) | 0.1 |
| 理论基础 | 中(5) | 高(8) | 高(9) | 0.1 |
| 加权总分 | 6.7 | 6.9 | 5.9 | 1.0 |
```

## 四、设计权衡分析

### 常见权衡
- **复杂度 vs 性能**：更复杂的框架可能性能更好，但更难维护
- **灵活性 vs 稳定性**：更灵活的框架更易适应变化，但稳定性更差
- **集中式 vs 分布式**：集中式更易控制，分布式更具韧性
- **通用 vs 专用**：通用框架适用面广，专用框架性能更优

### 权衡分析方法
1. 列出每个权衡的两面
2. 评估在当前场景下的重要性
3. 给出推荐方向和理由
4. 标注可能的后悔点

## 五、演进路径规划

### 路径规划要素
1. **起点**：当前架构状态
2. **终点**：目标架构状态
3. **阶段**：中间步骤（每步可独立交付）
4. **依赖**：阶段间的依赖关系
5. **回滚**：每步的回滚方案

### 演进路径模板
```
阶段1: <当前> → <目标1>
  - 变更: <具体变更>
  - 风险: <风险点>
  - 验证: <验证方法>
  - 回滚: <回滚方案>

阶段2: <目标1> → <目标2>
  ...
```

## 九、金融交易适配

### 适用场景
- 交易系统架构设计（如多因子 vs 时序策略）
- 策略框架选型（如趋势跟踪 vs 均值回归）
- 技术栈选型（如 Python vs C++ 回测引擎）

### 局限性
- 金融系统的"最优"框架依赖市场状态，无绝对最优
- 框架对比的加权评分具有主观性
- 新框架的成熟度和生态支持可能不足

### 适配建议
- 框架对比必须包含实盘可行性维度
- 优先选择有成熟开源生态的框架
- 新框架先在模拟盘验证再考虑实盘

## 十、约束

- 框架对比必须客观，不得预设结论
- 设计权衡必须明确，不得掩盖取舍
- 演进路径必须可执行，每步可验证
- 坚持 human-in-the-loop：AI 做对比和分析，人类做最终决策
