# 前端搜索优化方案

> 版本：v1.0（草案）
> 日期：2026-10-21
> 依据：33-REA逆向解析工程 Evidence-First 原则 + 市场主流搜索类项目调研

---

## 一、现状分析（基于工程实际代码）

### 1.1 技术栈现状

- 框架：Next.js 15（App Router）+ React 19 + TypeScript 5.7
- 状态管理：Zustand 5
- 数据层：Prisma 6 + NextAuth
- UI：Tailwind CSS 4 + 自研 V3 组件库（V3Card / V3Badge / V3Tooltip 等）

### 1.2 搜索能力现状

| 位置 | 现状 | 问题 |
|---|---|---|
| ReportsScreen（报告页） | taskId 精确匹配输入框，回车触发 | 仅支持精确 ID 匹配，无模糊搜索、无联想、无防抖 |
| case-retriever（案例检索） | Soft Q-Learning 检索，面向后端训练链路 | 未暴露为用户可用的前端搜索能力 |
| 全局导航 | 无全局搜索入口 | 用户无法跨模块（策略/报告/记忆/文档）统一检索 |

### 1.3 核心痛点

1. **无全局搜索**：功能分散在各面板，查找历史报告/策略/记忆只能逐页翻找。
2. **搜索体验原始**：无 search-as-you-type（即时搜索）、无高亮、无键盘导航、无空态引导。
3. **检索能力割裂**：后端已有案例检索能力，但前端没有统一检索入口承接。

## 二、市场调研结论

### 2.1 主流开源搜索项目对比

| 维度 | Meilisearch | Typesense | Elasticsearch |
|---|---|---|---|
| 定位 | 面向用户搜索的轻量引擎 | 内存优先的即时搜索引擎 | 全文检索 heavyweight |
| 响应速度 | search-as-you-type < 50ms | 内存索引，毫秒级 | 较快但资源占用高 |
| 开箱即用 | 零配置智能预设 | 零配置，号称『无需博士学位』 | 需较多调优 |
| 容错能力 | 内置 typo tolerance | 内置模糊搜索 | 需配置 fuzziness |
| 分面/过滤 | 支持 | 内置 Faceted Navigation | 支持 |
| 语义/向量 | 支持（AI 检索方向） | 内置向量搜索 + 语义搜索 + RAG | 需插件（kNN） |
| 运维成本 | 单二进制部署，极低 | 单二进制/Docker，低 | JVM，较高 |

### 2.2 可借鉴的交互设计模式

- **即时搜索（Search-as-you-type）**：输入即出结果，延迟控制在 50ms 量级（Meilisearch 官方基准）。
- **自动补全（Autocomplete）**：Typesense/Algolia InstantSearch 模式，输入过程中给出建议词。
- **分面导航（Faceted Navigation）**：结果按类型（报告/策略/记忆/文档）分桶过滤。
- **高亮命中片段**：结果中高亮匹配词，降低用户确认成本。
- **键盘导航**：↑↓ 选择、Enter 跳转、Esc 关闭，符合 Power User 习惯。

### 2.3 选型结论

- **数据规模较小（当前单机、模块内检索为主）**：优先不引入外部搜索引擎，基于现有 Prisma + 前端内存索引（如 minisearch/FlexSearch 类轻量库）实现，零运维成本。
- **数据规模增长后**：引入 Meilisearch（部署最简、中文分词与容错好）作为统一检索后端，前端通过 API Route 代理访问。

## 三、优化方案

### 3.1 目标

1. 提供全局统一搜索入口（Cmd/Ctrl+K 唤起），覆盖报告、策略、记忆、文档四大模块。
2. 搜索响应 < 100ms（本地索引阶段），支持模糊匹配与大小写容错。
3. 搜索体验对齐市场主流水准：即时联想、高亮、分面过滤、键盘导航、最近搜索。

### 3.2 分阶段实施

#### 阶段一：全局搜索组件（P0，1~2 周）

- 新建 GlobalSearchDialog 组件（复用 V3 组件库风格），挂载到全局布局。
- 快捷键 Cmd/Ctrl+K 唤起；顶部导航增加搜索框入口。
- 前端轻量索引：对报告 taskId/标题、策略名、记忆条目、文档标题建立内存倒排索引（FlexSearch 或 minisearch，均 < 10KB）。
- 交互：防抖 150ms 即时搜索、结果高亮、↑↓/Enter/Esc 键盘导航、最近搜索记录（localStorage）。

#### 阶段二：检索能力统一（P1，1~2 周）

- 新增 /api/search 统一检索 API Route，聚合各模块数据源。
- 将 ReportsScreen 的 taskId 精确匹配升级为模糊搜索，并复用全局搜索结果跳转。
- 将 case-retriever 的检索能力包装为『相似案例』搜索结果分区，打通后端已有能力。

#### 阶段三：搜索引擎升级（P2，按需）

- 数据量超过内存索引舒适区（约 5 万条以上）或需要语义检索时，引入 Meilisearch：
  - 单二进制部署，Next.js API Route 代理，前端接口不变。
  - 启用 typo tolerance 与分面过滤。
- 预留向量检索接口，与工程的语义蒸馏系统（39-金融语义蒸馏系统）对接。

### 3.3 技术要点

- **索引更新策略**：列表数据在请求返回时增量更新索引，避免全量重建。
- **权限**：搜索 API 复用 NextAuth 会话，结果按用户可见范围过滤。
- **性能**：索引构建放 Web Worker，避免阻塞主线程；搜索框组件懒加载（dynamic import）。
- **可测试性**：沿用工程 Jest 体系，为搜索核心逻辑（索引、排序、高亮）编写单测。

### 3.4 验收标准

1. Cmd/Ctrl+K 可唤起全局搜索，覆盖 4 大模块数据。
2. 输入到出结果延迟 < 100ms（本地索引阶段）。
3. 模糊输入（部分 ID、错别字）可命中目标。
4. 键盘可完成完整搜索-跳转流程。
5. Jest 单测覆盖搜索核心逻辑，通过率 100%。

## 四、风险与对策

| 风险 | 对策 |
|---|---|
| 内存索引随数据增长膨胀 | 阶段三切换 Meilisearch，接口已预留 |
| 搜索结果越权 | API 层统一走会话过滤，前端不做权限判断 |
| 交互复杂度上升 | 遵循 V3 组件库既有设计语言，渐进增强 |
