## 0. 背景与问题证据

### 0.1 现状（实然）

| 环节 | 当前实现 | 问题 |
|---|---|---|
| 拆解 | `spec-builder.ts` 关键词打分出 `quick/standard/deep`，`stepsFor()` 套固定步骤文案 | 只是给人看的文字，不驱动执行 |
| 派发 | `streamText` 单模型工具循环，`stopWhen: steps>=5` | 没有按任务结构派给子 Agent |
| 评估 | `onStepFinish` 的 `reviewStepReport`（LLM 裁判，FAIL-OPEN） | 无确定性评估器，无 KR 级验收 |
| planner | `lib/planner/orchestrate()`、`chain-planner`、`dynamic-node-planner`、`methodology-executor` | **全仓库零调用**，属孤岛 |
| PlanCard | `/api/agent/plan` 可产出 `plan_steps[].tool` 并校验 47 registry | **无调用方**（除单测） |

### 0.2 后果

- 长任务没有显式步骤边界，trace/step 事件全部堆在同一条流里 → 前端更新风暴（React #185）与「越跑越乱」同源；
- 任务看板的 `dispatch / acceptance` 阶段只是 UI 投影，没有真实编排语义；
- 子 Agent（DSH / MCP shell / capability worker）无法按任务被精确调度。

## 1. 目标与非目标

### 1.1 目标

1. **链路固定为 S→A**：S 层拆解并指派到 A 层能力；A 层把任务落成 OKR；OKR 明确（owner / criteria / 验收级别）后**才允许派发**。
2. **三角色隔离**：拆解模型 ≠ 执行模型 ≠ 验收模型，三者独立调用、上下文隔离、模型实例不得复用。
3. **KR 即能力域**：每个 KR 归属一个可注册的能力域（superpowers skill / capability registry），后续按域优化与调度。
4. 子 Agent 只按分配给自己的 KR 执行，不获得全局上下文与全局工具清单。
5. 每个 KR 有独立验收记录；未通过不进入下一 KR。
6. 全链路事件可回放，`trace_id` 串起 S、Debate、A、子 Agent、验收。
7. planner 不可用时 FAIL-OPEN 降级为现有单模型循环并标注 `degraded`，绝不白屏。

### 1.2 非目标

- 不改 46-DSH Router/Worker 契约、不重写 52 lobehub 协议；
- 不改造交易域 `/api/task/stream` 链路；
- 不在本 SPEC 内升级 45 评测 registry 的算法（只做接入）。

## 2. 总体链路

```
用户输入
  │
  ▼
[S1] 意图识别 + SPEC 生成（已有）────────────► 409 SPEC_CONFIRM_REQUIRED
  │  用户确认 SPEC
  ▼
[S2] 拆解（独立拆解模型）：SPEC → TaskObjective + OkrNode[]
  │       每个 KR 必须带：criteria / verify / owner_domain / 能力匹配
  ▼
[D1] Debate（deep/显式择优时启用）：KR 草案 → 多方方案 → 评估器裁决
  │       裁决 WIN/LOSE → 修订 KR；INCONCLUSIVE → 转人工，禁止派发
  ▼
[A1] 能力域匹配与校验：KR → 能力域（可注册）+ 具体 AgentRun
  │       匹配不到 → gap 事件，阻断派发
  ▼
[G1] dispatch 门：standard 自动通过；高不确定性 → 人工确认
  │       未通过前 agent 不得 running
  ▼
[A2] 派发：1 KR = 1 AgentRun（并发≤3，只给本 KR 上下文与能力白名单）
  ▼
[子 Agent] 执行 → step.reported
  ▼
[A3] 独立验收模型 + 确定性证据 → acceptance.recorded(pass|fail|pending)
  │       fail → 停止后续 KR；pending → 标注放行
  ▼
[G2] 全部 KR pass ──► summary.ready
```

一句话：**S 先拆、Debate 裁决、A 再立 OKR、OKR 不清不派发、子 Agent 只做自己的 KR、执行与验收分离。**

## 3. 数据结构（复用现有契约，向后兼容演进）

复用 [task-board.ts](../../3.1-FRONTEND/src/types/task-board.ts) 已有类型：

| 概念 | 类型 | 关键字段 |
|---|---|---|
| SPEC | `TaskSpec` | `spec_id / version / status(draft|confirmed) / fields[]` |
| OKR 目标 | `TaskObjective` | `title / owner / mode / confidence_threshold / claims[] / required_verdict_level(U0-U3) / waiting_verdict` |
| 关键结果 | `OkrNode` | `node_id / objective / criteria / verify / owner / evidence_id / evidence_count / verdict` |
| 子 Agent | `AgentRun` | `role / label / state / capability_ids[] / evidence_count / duration_ms` |
| 步骤汇报 | `TaskStep` | `step_id / index / title / summary / verdict / reviewer / comment` |
| 验收 | `AcceptanceRecord` | `role / node_id / verdict / evidence_refs[]` |

### 3.1 新增可选字段（不破坏现有消费者）

| 字段 | 位置 | 含义 |
|---|---|---|
| `owner_domain` | `OkrNode?` | 能力域 ID（如 `domain:analysis`），可注册到 superpowers skill registry |
| `owner_agent` | `OkrNode?` | 本次执行绑定的 AgentRun.role；与 `owner_domain` 为「域 + 实例」双层 |
| `decompose_model` / `verify_model` | `TaskStep?` / `AcceptanceRecord?` | 记录拆解/验收模型标识，用于角色隔离审计 |
| `debate_ref` | `TaskObjective?` | Debate 裁决引用（trace / evidence_ref） |

> 契约原则：只加可选字段，不改既有字段语义；`verdict` 仍为 `pass|pending|fail` 三态。

### 3.2 拆解产物约束

- `deep`：2–5 个 KR；`standard`：2–3 个；`quick`：1 个且跳过 A 派发（直接回答）。
- 每个 KR 必须满足：`criteria` 非空、`verify` 已定、`owner_domain` 已填、至少 1 个 `capability_ids`；否则视为「OKR 不明确」，禁止派发。
- 涉及策略/回测的 KR 必须 `required_verdict_level` ≥ `U2`（沙箱或回测证据）。

### 3.3 事件流（append-only）

```
spec.updated(confirmed)
  → okr.updated(draft, debate_ref?)
  → debate 产物（复用 trace / 52 协议 outbox，不新增 task-board 事件类型）
  → okr.updated(reconciled)                    # Debate 裁决后修订
  → gate.updated(dispatch, auto|required)
  → (必要时人工确认)
  → agent.updated(pending→running→done|failed) # 每个 KR 一条
  → step.reported
  → acceptance.recorded
  → summary.ready
```

**事件节流硬约束**（承接 b7378ebe80 的 #185 修复）：同一 `(type, entity)` 内容未变不得重发；`agent.updated` 每 KR 每状态最多 1 次；前端按签名去重，禁止无差别 setState。

## 4. S 层：拆解（独立拆解模型）

### 4.1 角色与隔离

- **拆解模型**：独立调用（`/api/agent/plan` 或 `planner-service`），输出结构化 PlanCard / KR 草案；
- 拆解模型**不同**于执行模型，也**不同**于验收模型；三者 model id 不得相同（审计字段写入 trace）；
- 拆解模型无工具执行权，只输出结构。

### 4.2 流程

1. 输入：`confirmedSpec + userText + intent + complexity + skills[]`；
2. 生成 PlanCard 草稿（复用 47 registry 工具白名单校验）；
3. 将 `plan_steps[]` 归并为 2–5 个可验收 KR（同一能力域强制合并）；
4. 为每个 KR 写入：`criteria / verify / owner_domain / capability_ids`；
5. 产出 `okr.updated(draft)`，同时写入 `objective`。

### 4.3 拆解策略：A/B 对比决策（问题 1 结论）

不拍脑袋选「LLM 拆解」或「确定性 planner」，用同一批样本做对比：

| 策略 | 实现 | 现状 |
|---|---|---|
| P1 确定性 planner | `chain-planner` / `dynamic-node-planner`（已实现） | 可控、零 token，但语义理解弱 |
| P2 LLM 拆解模型 | `/api/agent/plan` + PlanCard（已实现，未接线） | 语义强，但有漂移与成本 |

- 样本：**构造任务集**（deep/standard 各半，≥30 条，覆盖数据查询/分析/策略/工程四类，固定随机种子，保证可复现）；
- 指标（按优先级）：KR 验收一次通过率 → 能力匹配率 → KR 数量偏差 → 端到端耗时 → token 成本；
- 判定：胜者设为默认策略，另一条保留开关 `DECOMPOSE_STRATEGY=deterministic|llm`；
- 结论与数据回写 SPEC v0.3，不在本版内定死。

### 4.4 失败处理

- 拆解失败 → 降级：按 `stepsFor(level)` 生成等量 KR，`verify=evidence_backed`，标注 `degraded`；
- `quick` 复杂度 → 不进入 A 派发，保持现有 L1/单模型直答。

## 5. Debate 串链（问题 4 结论）

### 5.1 位置

`S2 拆解 → D1 Debate → 裁决 → A1 能力匹配 → dispatch`。

### 5.2 触发条件

- `deep` 且（`BRAINSTORM_INTENTS` 命中 或 文本含「方案/择优/对比/选哪个」）；
- `standard` 默认不触发；用户显式要求或 SPEC 中 `brainstorm=启用` 时触发。

### 5.3 输入输出

- 输入：SPEC + KR 草案（不是原始用户文本）；
- 输出：`WIN | LOSE | INCONCLUSIVE` + 证据引用；
- 裁决必须走**评估器**（52 D5 铁律①：45 评测 / acceptance 证据 / 回测），LLM 只能在评估器无法判定时有限仲裁；
- `WIN/LOSE` → 按胜者方案修订 KR 并写 `okr.updated(reconciled)`；
- `INCONCLUSIVE` → 视为高不确定性，dispatch 门转人工，禁止自动派发。

### 5.4 成本与时延

- 沿用现有 170s 超时；超时或失败 → FAIL-OPEN：保留拆解草案，标注 `debate_degraded`，按高不确定性处理（转人工）；
- Debate 结果不计入执行模型上下文，只以证据引用进入验收。

## 6. A 层：OKR 明确性与派发门禁

### 6.1 A 层职责

1. 校验 OKR 完整性：`objective.owner/title`、每个 KR 的 `criteria / verify / owner_domain / capability_ids`；
2. **能力域匹配**：KR → 能力域（superpowers skill / capability registry 可注册、可版本化），再从域内选具体 `AgentRun`；
3. 生成 `gate.updated(dispatch)`：`required` 由不确定性判定（见 6.3）。

### 6.2 KR 双层归属（问题 2 结论）

- `owner_domain`：能力域 ID，**长期优化对象**；能力域通过 superpowers skill 注册，含能力清单、验收口径、证据类型；
- `owner_agent`：本次执行的 Agent 实例（`AgentRun.role`），由 A 层从域内选出；
- 能力域字段集**直接对齐 superpowers skill manifest**（name / description / capabilities / acceptance / evidence_types / version），不另造一套元数据；
- 域注册缺失 → gap 事件，禁止派发（fail-closed），提示注册能力而非临时猜。

### 6.3 不确定性判定（问题 3 结论）

`standard` 的 dispatch 门**默认自动通过**；命中以下任一条件转人工：

| 条件 | 判定 |
|---|---|
| 复杂度评分处于边界（deep 阈值 4，score=3） | 高不确定 |
| 能力匹配缺口 > 0 | 高不确定 |
| KR `verify=evidence_backed` 但无 `evidence_id` | 高不确定 |
| 验收模型对 KR criteria 预检返回 `pending` / 自评置信度低于 `confidence_threshold` | 高不确定 |
| Debate 裁决 `INCONCLUSIVE` 或超时降级 | 高不确定 |

- 未命中 → 自动确认，`gate.updated(status=approved, by=system:auto)`，留审计痕迹；
- 命中 → `gate.updated(required, evidence_refs=触发条件)`，人工确认后才派发。

### 6.4 硬门禁（不可绕过）

| 条件 | 结果 |
|---|---|
| 无 `objective` 或 KR < 1 | 禁止 dispatch，返回 `OKR_INCOMPLETE` |
| 任一 KR 缺 `owner_domain / criteria` | 禁止 dispatch，列出缺失项 |
| 任一 KR 无能力匹配 | 写 gap 事件，禁止 dispatch |
| dispatch 门未通过 | 任何 `agent.updated` 不得写 `running` |
| `required_verdict_level` 未满足 | 该 KR `waiting_verdict`，不得出 `summary.ready` |

> 原则：**OKR 不清 = 不开工**。宁可停在 dispatch 门，也不放子 Agent 自由发挥。

## 7. 子 Agent 派发与执行

### 7.1 派发规则

- 每个 KR 生成 1 个 `AgentRun`，`role` 从 `owner_domain` 域内选出；
- 子 Agent 上下文只包含：本 KR 的 `objective + criteria + verify`、能力白名单、必要上游产物引用；
- 无依赖 KR 可并行，**并发上限 3**；有依赖按 `node_id` 顺序串行。

### 7.2 执行约束

- 工具调用必须落在 `capability_ids` 白名单内，越界即 `failed`；
- 每步写 `step.reported`；`verdict=fail` 立即停止本 KR 及下游；
- 单 KR 超时/预算沿用 `TOOL_BUDGET`，超限转 `degraded` 并落验收 `pending`。

### 7.3 与 DSH 的关系

A 层只负责「选谁、给什么、验收什么」；进程/Worker 拉起与租约仍由 46-DSH 负责，本 SPEC 不侵入其契约。

## 8. 评估（执行与验收分离）

### 8.1 角色隔离（问题 2 结论）

- **执行模型**：主工具循环 / 子 Agent，产出结果与证据；
- **验收模型**：独立模型实例，输入只含 `KR criteria + 执行证据`（不含执行对话全文），无工具执行权；
- 硬约束：验收模型 ≠ 执行模型 ≠ 拆解模型（model id 三元互异，写入审计字段）；
- 验收置信度阈值：**全局配置** `AGENT_VERIFY_CONFIDENCE_THRESHOLD`，默认 `0.7`；低于阈值判 `pending` 并计入不确定性（触发人工门）。

### 8.2 评估优先级（与 52 D5 铁律①一致）

1. 确定性证据：registry 调用结果、回测统计、文件/验收用例 → 直接 `pass/fail`；
2. 证据齐备但存在解释歧义 → 验收模型裁决，仍需引用证据；
3. 无确定性证据 → 只能 `pending`（放行但显式标注），**不得单独判 pass**；
4. 策略/交易 KR 必须 `U2` 及以上证据，否则 `waiting_verdict`。

### 8.3 产出

- 每 KR 一条 `acceptance.recorded`（含 `evidence_refs / reviewer / verify_model`）；
- 全部 KR `pass` → `summary.ready`；
- 任一 KR `fail` → 停止推进并生成返工建议（不自动递归重试，避免死循环）。

## 10. 验收标准

| 编号 | 标准 | 验证方式 |

## 14. 已决策事项（v0.2.0）

1. **拆解策略**：先按现有实现能力做 P1/P2 对比，用效果数据决策，保留开关（§4.3）。
2. **拆解与验收**：由独立大模型拆解并验收；执行与验收不同模型；KR 升级为能力域，通过 superpowers skill 注册（§4.1、§6.2、§8.1）。
3. **dispatch 门**：`standard` 默认自动通过；命中高不确定性条件转人工（§6.3）。
4. **Debate**：串入链路，顺序为「拆解 → 辩论 → 裁决 → 派发」（§5）。

## 15. 补充决策（v0.2.1）

1. **能力域字段集**：直接对齐 superpowers skill manifest，不另造元数据（§6.2）。

3. **A/B 样本**：使用构造任务集，固定种子、可复现（§4.3）。
