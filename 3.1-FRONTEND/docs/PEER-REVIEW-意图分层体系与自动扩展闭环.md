## 2. Major 问题

### M1：P1.5 采集点的跨进程写入路径未定义
SACG 编排/DSH 调度/子 agent 执行均在前端 Node 进程内（next-server），而案例库 l1_case_store.jsonl 与 34 训练机制在 Python 侧。settle_case_cli 的 spawn 桥接模式仅验证于 /api/task 单点，SACG/DSH/子 agent 环节的案例写入需明确桥接方式（spawn CLI vs HTTP vs 共享文件追加），且 next start 生产模式下高频 spawn 的稳定性与延迟未评估。
**要求**：P1.5 实施前补充桥接设计（建议复用 settle_case_cli 模式并做异步批量写入），并给出写入失败时的 FAIL-OPEN 策略。

### M2：intent_registry 与 intent-descriptions.ts 双事实源漂移风险
38 PG 表与 TS 描述库各自可写时必然漂移。spec §5⑤ 仅定义了『扩展合入时 UPSERT』的单向同步，未定义权威源与一致性校验。
**要求**：P1 实施前明确——intent-descriptions.ts 为唯一权威源，intent_registry 为只读投影；P1 的同步通道附带一致性校验（registry 与 TS 导出的 diff 为空才通过验收）。

### M3：R-3 reasoning_trace 采集点的调用方与成本未确认
39 mcp 的消费方（前端 or 34 训练）在 spec 中未确认；推理过程记录若涉及 LLM 调用，token 成本无预算（对比：33 SpecEnhancer 有 8K 预算约束）。
**要求**：P5 实施前确认 39 mcp 实际调用链路，reasoning_trace 定义为规则可记录的链路数据（查询输入→各层命中→综合结论），LLM 参与时给出 token 预算。

### M4：回归测试集负例的维护成本随意图增长线性上升
§5② 负例（≥2/意图）依赖人工构造，15 种意图即 30+ 负例，扩展后维护成本持续上升。
**要求**：P2 实施时将 ③ 逆向验证的误识别归因产出自动转化为回归负例（误识别案例→期望意图标注→入集），形成负例自动生长，人工仅审核。

## 3. Minor 问题

- m1：§6『案例覆盖率（按域）』的分母（环节总量）未定义，建议改为『已定义采集点中实际有案例流入的比例』；
- m2：P3（R-1）仅依赖 P1，但 R-1 解析子模块代码不依赖 P1.5 案例采集，依赖关系正确；建议 spec 中说明 R-1 与 P1.5 并行可行，缩短关键路径；
- m3：L1 组合意图拆分失败的降级路径未定义（建议：拆分置信度不足→降级 L3 澄清，对齐 FAIL-OPEN 原则）；
- m4：41 同步的意图元数据文档路径未定，建议固定于 2-KNOWLEDGE 下（如 2-KNOWLEDGE/6-PRODUCT-BUSINESS/INTENT-REGISTRY.md），确保落入 41 索引范围。

## 4. Devil's Advocate

### DA1：闭环自增强偏差
逆向训练案例回流训练模型，模型又参与案例标注与候选意图聚类，存在自我确认循环风险。现有 EWMA 衰减 + 质量门控 + 人工合入批准可缓解，但建议增加独立 holdout 验证集（不参与任何训练，仅用于回归测试），作为闭环自增强的独立校验。**让步**：holdout 集规模可小（每意图 1-2 例），维护成本低。
