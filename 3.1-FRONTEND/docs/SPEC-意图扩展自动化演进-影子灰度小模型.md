# SPEC：意图扩展自动化演进——影子模式 + 灰度测试 + 小模型评测

> 版本：v0.2（评审通过，5 项决策点已裁决）
> 日期：2026-10-25（裁决时间 10:22）
> 关联：SPEC-意图分层体系与自动扩展闭环.md（v0.5 最终版，§14）
> 关联系统：3.1-FRONTEND（意图引擎）、34-前端应用训练系统（闭环/案例库）、39-金融语义蒸馏系统（蒸馏范式参考）、41-文件索引系统（向量桥接常驻进程先例）

---

## 1. 背景与动机

### 1.1 现状

spec v0.5 已实现意图扩展闭环：新案例 → 提案（jieba 分词）→ 自动评审 → 回归门禁 → 合入暂存 → **人工批准** → ADR 决策记录。

### 1.2 问题（用户裁决）

人工审批存在缺陷：人力有限，提案量随案例增长必然积压；意图扩展本就是正向训练与逆向解析训练的成果，人工参与是瓶颈。

### 1.3 演进方向（用户裁决）

通过 **影子模式（Shadow）+ 灰度测试（Canary）+ Transformer 小模型** 替代人工审批，实现合入决策自动化。

核心思路转变：从『批准前用人的判断力兜底』转为『合入后用真实流量与模型验证』——把验证成本从人力转移到算力与流量。

---

## 2. 总体架构：四阶段演进

| 阶段 | 合入决策机制 | 人工角色 | 进入条件 | 退出条件 |
|---|---|---|---|---|
| S0（现状） | 人工批准 | 逐条复审 | — | — |
| S1 影子期 | 自动评审 + 影子验证通过即合入 | 抽检分歧样本（初期 1%） | 本 spec 评审通过 | 连续 N 轮（建议 10 轮）影子结论与人工抽检一致率 ≥ 95% |
| S2 灰度期 | 影子通过 + 灰度指标达标即全量 | 仅处理回滚告警 | S1 退出条件达成 | 灰度自动回滚率 < 5%（滑动窗口 30 天） |
| S3 模型期 | 小模型评测器替代自动评审 | 仅审计（月度） | 评测器训练数据 ≥ 500 样本 | 评测器与灰度结论一致率 ≥ 90% |

规则生命周期状态机：`pending → shadow → canary(5%→25%→100%) → active → (degraded → 摘除)`。

## 3. S1 影子模式设计

### 3.1 机制

新规则合入后**不参与线上路由**，在识别链路旁路并行执行：每条用户消息同时跑『线上规则集』与『线上+影子规则集』，记录两者分歧。

### 3.2 衔接点（现有架构）

- 意图识别在 createTask（task-manager.ts）内完成；影子评估在 recognizeIntent 返回后追加，读影子规则表，**只记录不干预**，FAIL-OPEN 不影响主链路
- 影子规则表：fallback-engine.ts 规则条目增加 `status` 字段（active/shadow/canary/degraded），识别引擎主匹配仅认 active；影子评估单独读 shadow/canary
- 分歧数据落 `34-前端应用训练系统/shadow_divergence.jsonl`（复用域案例沉淀桥接模式，spawn 调用 FAIL-OPEN）

### 3.3 影子验证指标

| 指标 | 定义 | 合入阈值 |
|---|---|---|
| 抢占率 | 影子规则命中且与线上结论冲突的比例 | = 0 |
| 有效命中率 | 影子规则命中且线上结论为兜底（simple_qa 默认）的比例 | > 0（观察窗口内） |
| 观察窗口 | 影子运行时长/消息量 | ≥ 500 条真实消息或 ≥ 72 小时 |

### 3.4 影子通过 → 灰度

三项指标达标 → 规则状态 shadow → canary，ADR 记录 `shadow_passed`。

---

## 4. S2 灰度测试设计

### 4.1 机制

灰度规则按流量比例参与线上路由：按 session_id 哈希分桶（5% → 25% → 100%），每级观察窗口 ≥ 24 小时。

### 4.2 自动回滚触发条件（任一触发即 degraded 摘除）

- 误归因率上升（复用逆向验证管线 misidentify-attribution 指标）
- 澄清率（need_clarification 占比）环比上升 > 2 个百分点
- 用户重试率（同 session 10 秒内重发相似消息）上升 > 2 个百分点

### 4.3 回滚

规则状态置 degraded，ADR 记录 `canary_rolled_back`（含触发指标与样本），可追溯可回滚（摘除即回滚，规则保留在提案库不删除）。

## 5. S3 小模型设计

### 5.1 硬件预算（实测 2026-10-25）

| 资源 | 实测值 |
|---|---|
| 内存 | 15GB 总量 / 10GB 可用 |
| CPU | 4 核 AMD EPYC 7K62（无 GPU） |
| 磁盘 | 136GB 空闲 |

### 5.2 模型选型

| 用途 | 模型 | 部署 | 内存 | 推理延迟 |
|---|---|---|---|---|
| 提案评测器（优先） | **RBT3 微调**（裁决 4：准确优先） | 离线批处理（闭环 run 调用） | ~400MB | 毫秒级 |
| 意图分类器（接管长尾） | **RBT3 微调**（裁决 4：准确优先） | 常驻进程（复用向量桥接守护进程模式：Unix socket + 行分隔 JSON + 空闲退出） | ~400MB | 毫秒级 |
| 提案描述生成（可选） | Qwen2.5-0.5B Q4 | 离线批处理 | ~1GB | 5-15 token/s（仅离线） |

约束：本地推理，零外部 token（零 LLM 依赖原则保持）；7B 级以上模型明确排除（内存挤占 + CPU 推理过慢）。

### 5.3 训练数据

- 冷启动：126 份提案评审结论（22 初版 + 104 jieba 版，含人工复审 3 份）+ 106 回归案例 + 111 案例库
- 持续回流：影子分歧样本 + 灰度回滚样本（S1/S2 产出的正是评测器训练燃料）
- 门槛：≥ 500 样本启动评测器训练（CPU 微调 albert_tiny 分钟级，本机可完成）

### 5.4 分类器与关键词规则的关系

关键词规则保留为快速路径（毫秒级、零依赖）；分类器处理关键词未覆盖的长尾（如『BTC现在什么价』类碎片表达）。路由顺序：关键词 active 规则 → 分类器 → 兜底。

## 6. 分期实施计划

| 期 | 内容 | 前置 | 验收标准 |
|---|---|---|---|
| E1 | 影子模式落地：规则 status 字段 + 影子评估旁路 + 分歧落盘 + 影子验证命令（**与 CPI 提案规则写入合并实施**，裁决 5：CPI 规则以 shadow 状态写入作为首个验证规则） | 本 spec 评审通过（v0.2） | 影子规则在真实流量下产生分歧数据；影子验证命令输出三指标 |
| E2 | 灰度机制：分桶路由 + 自动回滚触发器 + degraded 状态 | E1 | 灰度规则按比例生效；模拟劣化指标触发自动摘除 |
| E3 | 评测器训练：样本积累 ≥ 500 → albert_tiny 微调 → 与自动评审并行输出对比 | E1/E2 数据回流 | 评测器与灰度最终结论一致率 ≥ 90%（连续 3 轮） |
| E4 | 分类器常驻：意图分类器守护进程 + 路由接入（关键词 → 分类器 → 兜底） | E3 | 长尾案例（关键词未命中）分类准确率 ≥ 85%；/api/task 响应增量 < 100ms |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 影子期流量不足（消息量少） | 观察窗口按『消息量或时长』双阈值，先到为准；可用回放池 106 案例预跑 |
| 灰度误伤真实用户 | 分桶哈希保证同 session 一致体验；回滚触发条件保守设置；摘除即时生效 |
| 评测器冷启动样本偏差 | S1 抽检 1% 人工校准持续到 S3 达标；分歧样本全量回流训练 |
| 分类器内存挤占向量检索 | 常驻进程内存上限 500MB；空闲自动退出复用既有模式 |
| 模型误判合入坏规则 | 灰度自动回滚兜底（模型只决定『进入灰度』，不跳过灰度） |

---

## 8. 已裁决决策点

1. 人工审批确认为瓶颈，演进方向为影子 + 灰度 + 小模型（用户裁决 2026-10-25）
2. 模型仅本地小模型（分类/评测），零外部 token；7B+ 排除（硬件实测裁决）
3. 模型不跳过灰度：S3 评测器输出仍需经 S2 灰度验证，模型只替代『评审』不替代『验证』
4. 关键词规则不废弃，保留快速路径；分类器接管长尾

## 9. 决策点裁决记录（2026-10-25 10:22，用户裁决）

1. 影子观察窗口阈值（500 条消息 / 72 小时）：**合理，维持**
2. 灰度分桶比例（5%→25%→100%）与每级观察时长（24 小时）：**合理，维持**
3. S1 退出条件（10 轮一致率 ≥ 95%）：**合理，维持**
4. 评测器选型：**RBT3（准确优先，内存约 400MB，替代原 al_tiny_tiny 首选方案）**
5. E1 与 CPI 提案规则写入：**合并实施**（CPI 规则以 shadow 状态写入，作为 E1 影子模式的首个验证规则）
