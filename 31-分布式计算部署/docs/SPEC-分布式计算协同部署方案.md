## 0. 文档边界

本文档定义 DreamOS 交易系统**线上（云端）与线下（本地）协同部署**的完整架构方案。目标是在控制云成本（¥300-500/月）的前提下，实现 7×24 高可用运行 + 线下算力分担 + 故障自动降级接管。

**本 SPEC 覆盖**：

## 1. 背景与核心矛盾

### 1.1 现状

- 所有交易服务（V15、BCRM2、BDSM、自进化、事件驱动、战略层）当前全部在**本地 Mac** 上运行
- 依赖本地网络，断网即停摆
- 自进化系统（torch）、BCRM2（LightGBM/HMM）等重计算模块挤占本地资源

### 1.2 需求

| 需求 | 描述 |
|------|------|
| 高可用 | 云端部署核心交易模块，避免本地断网影响 |
| 成本可控 | 云服务器月费 ¥300-500，不能无限加内存 |
| 算力分担 | 线下 M3 Mac 承担训练/优化等重计算 |
| 故障降级 | 线下断网/宕机时，云端用简化模型继续交易 |
| 可扩展 | 未来支持多台线下机器分布式计算 |

### 1.3 核心矛盾

| 维度 | 纯云端方案 | 纯本地方案 | 本方案（云+端协同） |
|------|----------|----------|------------------|
| 可用性 | 高（7×24） | 低（依赖本地网络） | 高（云端常驻） |
| 成本 | 高（需 GPU 大内存） | 低（用现有机器） | 中（轻量云端+重计算线下） |
| 算力 | 受限于云规格 | M3 GPU 可用 | 结合两者优势 |
| 容错 | 单点（云端挂=全挂） | 单点（本地挂=全挂） | 主备降级（线下挂云端接管） |

### 1.4 设计哲学

**云端做"实时交易大脑+前端入口"，线下做"训练/优化肌肉"，中间用任务队列+心跳实现协同与降级。**

借鉴区块链的**去中心化容错**思想，但不照搬区块链共识（太重，不适合交易实时性），采用更轻量的**主备+心跳检测**机制。


### 3.2 核心原则

1. **推理/训练分离**：同一子系统，推理在云端（轻量，必须在线），训练在线下（重计算，可延迟）
2. **云端是主，线下是从**：交易决策的最终执行权在云端，线下只提供计算结果
3. **降级而非停摆**：线下故障时云端用简化模型继续运行，只是质量下降
4. **数据云端统一**：交易数据、配置、状态以云端 PostgreSQL 为准，线下只读

### 4.3 推理/训练分离机制

```
线下训练完成 → 模型权重 → 上传云端 MinIO (s3://models/{module}/{version}.pkl)
云端推理模块监听 MinIO 变更 → 下载新模型 → 热加载（不中断交易）
线下挂了 → 云端继续用旧模型推理，只是模型不再更新
```

**热加载安全措施**：
- 保留上一版本模型作为回滚
- 新模型加载失败 → 自动回滚到上一版本
- 飞书告警通知

### 4.4 模型热加载灰度策略（D-7）

**两阶段策略**：

| 阶段 | 模式 | 行为 | 适用期 |
|------|------|------|--------|
| 初期 | 直接切换（默认） | 新模型上传后立即替换旧模型，保留回滚能力 | 高频迭代期，模型迭代快 |
| 成熟期 | 灰度比例模式（手动开启） | 新模型先处理 X% 信号，逐步提升到 100% | 模型稳定后，谨慎切换 |

**灰度比例模式实现**：
```
config: grayscale_enabled = false  # 默认关闭
config: grayscale_ratio = 0.3       # 初始灰度比例

灰度开启时：
  推理请求 → 随机分配到 {new_model: 30%, old_model: 70%}
  → 对比两者输出差异 → 差异过大则暂停灰度 + 告警
  → 灰度运行 N 小时无异常 → ratio 提升到 60% → 100% → 切换完成
```

**灰度启用条件**（手动触发）：
1. 模型迭代频率降低（周更以下）
2. 当前模型已运行 >7 天且表现稳定
3. 用户手动开启 `grayscale_enabled = true`

## 5. 通信与协同机制

### 5.1 混合通信架构（D-8：API中转 + MinIO直传）

**设计原则**：控制面走 API（安全、可观测），数据面走 MinIO 直传（避免大文件过 API）。

```
┌─ 云端 ────────────────────────────────────────────────────┐
│                                                           │
│  ┌─────────────┐    ┌──────────────┐   ┌───────────────┐  │
│  │ FastAPI      │    │ Redis        │   │ MinIO         │  │
│  │ Scheduler    │───→│ (内部队列)   │   │ (模型/结果)   │  │
│  │ API :443     │←───│              │   │               │  │
│  └──────┬───────┘    └──────────────┘   └──────┬───────┘  │
│         │                                       │          │
│  控制面 │ HTTPS (任务拉取/结果上报/心跳)          │ presigned│
│         │                                       │ URL     │
└─────────┼───────────────────────────────────────┼──────────┘
          │                                       │
          │          数据面（大文件直传）           │
┌─────────▼───────────────────────────────────────▼──────────┐
│  线下 Worker                                                 │
│                                                             │
│  ① POST /api/worker/poll_task → 获取任务（含 presigned URL） │
│  ② GET MinIO presigned URL → 下载训练数据                    │
│  ③ 执行训练（torch/LGBM/Bayesian）                           │
│  ④ PUT MinIO presigned URL → 上传模型权重/回测结果           │
│  ⑤ POST /api/worker/report_result → 上报完成 + 心跳          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**API 中转评估（针对分布式架构适用性）**：

| 评估维度 | 结论 | 分析 |
|---------|------|------|
| **延迟** | ✅ 可接受 | 训练任务耗时小时级，API 额外 10-50ms 延迟可忽略 |
| **安全** | ✅ 最优 | Redis 不暴露公网，所有访问经 API 鉴权 |
| **多 Worker 扩展** | ✅ 天然支持 | 每个 Worker 只需 API 地址+密钥，无需 Redis 凭据 |
| **单点风险** | ⚠️ 低风险 | API 与交易同服务器，API 挂=交易也挂，不存在额外单点 |
| **大文件传输** | ✅ 已解决 | 模型/数据走 MinIO presigned URL，不过 API |
| **可观测性** | ✅ 最优 | 所有任务流转经 API，易于日志和监控 |
| **实现复杂度** | 中等 | 需实现 5 个 API 端点（见 §5.3），但逻辑清晰 |

**结论**：API 中转模式**适合**本分布式架构。核心原因是交易系统的计算任务都是**长耗时批处理**（小时级），通信延迟不是瓶颈，安全性和可观测性更重要。大文件通过 MinIO presigned URL 绕过 API，避免瓶颈。

### 5.2 API 端点设计

| 端点 | 方法 | 用途 | 调用方 |
|------|------|------|--------|
| `/api/worker/register` | POST | Worker 注册（能力标签+密钥） | 线下 |
| `/api/worker/poll_task` | POST | 拉取任务（含数据 presigned URL） | 线下 |
| `/api/worker/report_result` | POST | 上报结果 + 模型 presigned URL | 线下 |
| `/api/worker/heartbeat` | POST | 心跳（30s 一次） | 线下 |
| `/api/worker/status` | GET | 查询 Worker 状态 | 云端/前端 |

**任务类型定义**：

```
┌──────────────────┬──────────────┬──────────┬──────────┐
│ task_type        │ module       │ priority │ timeout  │
├──────────────────┼──────────────┼──────────┼──────────┤
│ evolution_train  │ 23-自进化    │ high     │ 4h       │
│ bcrm2_optimize   │ 11-BCRM2     │ high     │ 2h       │
│ param_sweep      │ 16-战略层    │ medium   │ 6h       │
│ bdsm_scan        │ BDSM         │ medium   │ 1h       │
│ backtest         │ 通用         │ low      │ 8h       │
│ feature_eng      │ 21-特征      │ low      │ 2h       │
└──────────────────┴──────────────┴──────────┴──────────┘
```

**任务生命周期**：
```
PENDING → ASSIGNED → RUNNING → COMPLETED
                      ↓
                   FAILED/Timeout → REQUEUE（重试3次）→ DEAD_LETTER
```

### 5.3 心跳机制

```
线下 Worker 每 30s → POST /api/worker/heartbeat
  body: {worker_id, load, mem_usage, gpu_usage, active_tasks}

云端记录到 Redis: worker:{id}:last_heartbeat = timestamp

故障检测（云端定时任务，每 60s 扫描）：
  if now - last_heartbeat > 120s:
    mark worker OFFLINE
    requeue 该 worker 未完成的任务
    trigger DEGRADED mode for affected modules
```

### 5.4 多线下机器扩展

- 每个 Worker 启动时通过 `/api/worker/register` 注册能力标签：`{"gpu": "m3_mps", "mem_gb": 16, "cpu_cores": 8}`
- Scheduler 按能力标签路由任务（GPU任务→有GPU的机器，大内存任务→大内存机器）
- 同类型任务可并行分发到多台机器（分布式回测/参数搜索）
- 新增 Worker 只需配置 API 地址 + 密钥，自动加入调度池

## 6. 降级接管策略

### 6.1 线下ML故障 → 云端简化模型继续交易

| 子系统 | 线下完整版 | 云端降级版 | 降级影响 |
|--------|----------|----------|---------|
| **自进化推理** | Neural SDE + Cross-Attention | 逻辑回归 / XGBoost（预训练轻量模型） | 置信度下降，提高入场阈值 |
| **BCRM2推理** | HMM + LightGBM 集成 | 单模型 LightGBM（砍掉集成） | 信号数量减少 ~30% |
| **战略层优化** | Ray Bayesian 优化 | 固定参数（上次最优值） | 参数不再自适应 |
| **BDSM** | 全板块估值扫描 | 只看 BTC/ETH/SOL 三大标的 | 小币种信号缺失 |
| **事件驱动** | 多因子事件评分 | 只看新闻情绪分 | 事件覆盖度降低 |

### 6.2 降级时的安全措施

1. **仓位减半**：所有策略 base_position × 0.5
2. **阈值提高**：入场置信度阈值 0.65 → 0.80
3. **频率降低**：轮询间隔 5min → 15min
4. **告警通知**：飞书推送"⚠️ 系统降级运行中"

### 6.3 恢复流程

```
线下 Worker 心跳恢复（ONLINE）
  ↓
云端等待线下完成一次"模型健康检查"（跑验证集）
  ↓
验证通过 → 云端切回线下最新模型
验证失败 → 继续降级 + 飞书告警
```

### 6.4 云端宕机处理

- 线下 Worker 连续 3 次心跳失败 → 进入**自治模式**
- 继续消费本地已缓存任务队列
- 实时交易**暂停**（不盲目下单），写本地日志
- 云端恢复后，数据自动同步

## 7. 数据同步策略

### 7.1 模型权重同步

```
线下训练完成 → 模型文件 → 上传云端 MinIO
云端推理模块监听 MinIO 变更 → 下载 → 热加载
```

### 7.2 交易数据同步

- 交易记录、仓位、订单 → **实时写入云端 PostgreSQL**
- 线下只读不写（通过 API 查询），避免数据冲突

### 7.3 回测结果同步

## 9. 实施路线

### Phase 1：云端核心上线（3-4天）

### Phase 2：任务队列 + 线下Worker（3-4天）

1. 云端实现 Scheduler（FastAPI + Redis Streams）
2. 线下实现 Worker-Agent（消费任务 + 心跳上报）
3. 先跑非关键任务（回测）验证全链路
4. 实现模型权重上传/热加载
5. **验收**：云端下发回测任务 → 线下执行 → 结果回传 → 前端展示

### Phase 3：降级接管（4-5天）

1. 实现心跳监控 + 故障检测

5. **验收**：降级期间交易正常，飞书收到告警

### Phase 4：多线下机器支持（2-3天）

1. Worker 注册能力标签
2. Scheduler 按能力路由

4. **验收**：两台线下机器同时跑不同任务，互不干扰

### 12.4 Conda 环境策略详解（D-13）

| 环境 | 用途 | 核心包 | 覆盖模块 |
|------|------|--------|---------|
| `base`（现有 anaconda） | 日常+推理+轻计算 | pandas/numpy/scipy/lightgbm/ccxt/requests/flask | BCRM2推理、BDSM、事件驱动、V15、战略层、数据获取、特征工程 |
| `dreambuddy-torch`（新建） | torch 训练专用 | torch(MPS build) + 自进化专属依赖 | 23-自进化训练（shadow_rl_trainer/neural_sde/cross_attention） |

**Worker 环境路由**：
- 任务到达 Worker 时，根据 `task_type` 选择对应 Conda 环境
- `evolution_train` → `conda run -n dreambuddy-torch python ...`
- 其他任务 → `conda run -n base python ...`（或直接 `/opt/anaconda3/bin/python3`）

**为什么 2 个而非 1 个**：torch 占 2GB+，M3 MPS 构建偶尔有版本兼容问题，且 80% 的模块不需要 torch
**为什么 2 个而非 3+ 个**：M3 16GB 统一内存，多环境浪费空间；大部分模块依赖高度重叠
