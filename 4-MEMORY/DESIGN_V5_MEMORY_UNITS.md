> **版本**: v1.0草案 | **日期**: 2026-07-27

> **核心诉求**: 引入人类记忆原理，按功能域分区管理记忆，实现开发闭环的自动化更新

## 1. 调研结论：人类记忆原理 → AI 记忆映射

受认知科学启发的现代 AI 记忆系统通常分为四层，与我们现有体系天然对应：

| 人类记忆类型 | 核心特征 | 对应 AI 记忆 | 对应现有分级 | 容量特征 |
|-------------|---------|-------------|-------------|---------|
| **工作记忆** (Working) | 当下处理，最短暂，持续刷新 | LLM 上下文窗口 | — | 极短（8K上下文） |
| **情景记忆** (Episodic) | 具体经历、事件、案例 | 案例记录、复盘、具体踩坑 | B/C 级 | 中（可归档） |
| **语义记忆** (Semantic) | 知识、事实、概念 | 原则、架构决策、经验教训 | A 级 | 中（需精炼） |
| **程序记忆** (Procedural) | 技能、流程、肌肉记忆 | 开发流程、标准操作步骤 | S 级 | 小（最核心） |

**记忆演化路径**（与质量分级完全一致）：

```
情景记忆(Episode) ──反复验证──→ 语义记忆(Semantic) ──反复验证──→ 程序记忆(Procedural)
     B/C 级                    置信度 ↑                          S 级
    "某次踩坑"                 "这个模式会失败"                 "开发必须先调研"
```

## 2. 记忆单元分区设计

### 2.1 为什么需要分区？

当前 `4-MEMORY/` 下所有记忆混放在一个目录平面中，问题：
- **检索干扰**：查"开发流程"时返回"交易规则"的记忆
- **容量竞争**：交易记忆膨胀挤占开发记忆的核心空间
- **更新冲突**：不同领域的记忆同时触发 consolidation，互相覆盖
- **权限模糊**：交易系统记忆和文档管理记忆的更新策略应该不同

### 2.2 分区方案：功能域 × 记忆类型

```
4-MEMORY/
├── CORE.md                    # Tier 0: 全系统核心记忆（程序记忆精华）
│
├── 1-开发记忆单元/              # MU-DEV: Development Memory Unit
│   ├── MU-DEV-CORE.md         # 开发单元核心（程序记忆）
│   ├── episodic/              # 情景记忆：具体开发踩坑、案例
│   ├── semantic/              # 语义记忆：开发原则、架构知识
│   └── procedural/            # 程序记忆：开发流程、标准步骤
│
├── 2-交易记忆单元/              # MU-TRD: Trading Memory Unit
│   ├── MU-TRD-CORE.md         # 交易单元核心（程序记忆）
│   ├── episodic/              # 情景记忆：具体交易案例、复盘
│   ├── semantic/              # 语义记忆：交易规则、风控知识
│   └── procedural/            # 程序记忆：交易流程、信号处理步骤
│
├── 3-文档记忆单元/              # MU-DOC: Documentation Memory Unit
│   ├── MU-DOC-CORE.md         # 文档单元核心（程序记忆）
│   ├── episodic/              # 情景记忆：文档债案例、踩坑记录
│   ├── semantic/              # 语义记忆：文档规范、分类知识
│   └── procedural/            # 程序记忆：文档编写流程、更新步骤
│
├── 4-信息记忆单元/              # MU-INF: Information Memory Unit
│   ├── MU-INF-CORE.md         # 信息单元核心（程序记忆）
│   ├── episodic/              # 情景记忆：信息检索踩坑、数据源变更
│   ├── semantic/              # 语义记忆：信息分类、数据源知识
│   └── procedural/            # 程序记忆：信息收集流程、验证步骤
│
└── 0-元记忆/                    # 元记忆不变
    ├── MEMORY_TYPES.md
    ├── MEMORY_LIFECYCLE.md
    ├── MEMORY_QUALITY.md
    └── MEMORY_UNITS.md        # 记忆单元管理规范（新增）
```

### 2.3 各记忆单元职责

| 记忆单元 | 代码 | 核心职责 | 典型内容 | 容量上限 |
|---------|------|---------|---------|---------|
| **开发记忆单元** | MU-DEV | 代码工程、开发流程、技术栈 | A1调研法、A8校验、subprocess教训、目录规范 | CORE≤2K，单元总≤12K |
| **交易记忆单元** | MU-TRD | 交易策略、信号规则、风控参数 | L4记忆接口、BCRM规则、离场逻辑、趋势判断 | CORE≤2K，单元总≤12K |
| **文档记忆单元** | MU-DOC | 文档规范、治理流程、债务跟踪 | DOC_STANDARD、文档生命周期、债务索引 | CORE≤1K，单元总≤8K |
| **信息记忆单元** | MU-INF | 数据源、信息分类、验证机制 | 数据接口、信息来源、验证规则 | CORE≤1K，单元总≤8K |

**总 Tier 0 容量**: MU-DEV-CORE + MU-TRD-CORE + MU-DOC-CORE + MU-INF-CORE ≤ 8K（与原设计一致，但按单元分配配额）

## 3. 自动更新机制

### 3.1 当前闭环的问题

当前闭环（§7.2）是理论模型，但缺少**执行约束**：
- AI 开发时可能"只顾写代码，忘了更新文档"
- 文档更新后，AI 记忆不会自动同步
- 没有机制强制"开发→校验→更新→记忆同步"的完整性

### 3.2 优化后的强制闭环

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│  步骤1: 读取记忆单元                                                      │
│  ┌──────────────────┐                                                   │
│  │  AI 读取 MU-DEV   │  获取程序记忆（开发流程）+ 语义记忆（架构知识）      │
│  │  + MU-TRD 核心    │  + 索引指向传统文档路径                             │
│  └────────┬─────────┘                                                   │
│           │ 定位文档                                                     │
│           ▼                                                              │
│  步骤2: 检索完整技术文档                                                   │
│  ┌──────────────────┐                                                   │
│  │  根据记忆索引路径  │  读取 0-系统文档管理/ 或子系统 docs/ 的完整文档    │
│  │  读取工程文档     │  （SSoT，详细信息）                                │
│  └────────┬─────────┘                                                   │
│           │ 调研分析                                                     │
│           ▼                                                              │
│  步骤3: 执行 A1 调研（如需要）                                             │
│  ┌──────────────────┐                                                   │
│  │  对比记忆 vs 文档  │  发现不一致 → 调研 → 形成结论                      │
│  │  vs 代码现状      │  一致 → 直接进入开发                               │
│  └────────┬─────────┘                                                   │
│           │ 设计解决                                                     │
│           ▼                                                              │
│  步骤4: 代码开发                                                         │
│  ┌──────────────────┐                                                   │
│  │  实现功能/修复bug │  产生代码变更                                      │
│  └────────┬─────────┘                                                   │
│           │ 强制校验（不可跳过）                                          │
│           ▼                                                              │
│  步骤5: A8 理论实践校验                                                    │
│  ┌──────────────────┐                                                   │
│  │  对比新代码 vs    │  生成校验报告（一致/不一致项列表）                  │
│  │  现有 API_SPEC    │  不一致 → 必须更新文档                             │
│  └────────┬─────────┘                                                   │
│           │ 文档更新                                                     │
│           ▼                                                              │
│  步骤6: 更新传统工程文档（SSoT）                                            │
│  ┌──────────────────┐                                                   │
│  │  修改 API_SPEC    │  人工确认或 AI 辅助生成变更                         │
│  │  更新 CHANGELOG   │  写入 0-系统文档管理/ 或子系统 docs/               │
│  └────────┬─────────┘                                                   │
│           │ 记忆同步（自动）                                               │
│           ▼                                                              │
│  步骤7: 蒸馏更新 AI 记忆                                                   │
│  ┌──────────────────┐                                                   │
│  │  提取文档核心结论  │  更新对应记忆单元 MU-xxx                          │
│  │  写入 MU-xxx-CORE │  触发 consolidation 检查容量                       │
│  │  + 情景/语义/程序  │  新经验写入 episodic/semantic/procedural           │
│  └────────┬─────────┘                                                   │
│           │ 证明验证                                                     │
│           ▼                                                              │
│  步骤8: 证明算法评估（见§4）                                               │
│  ┌──────────────────┐                                                   │
│  │  新记忆置信度评估  │  达到阈值 → 升级记忆类型/质量等级                   │
│  │  触发记忆演化     │  未达阈值 → 保持现状，等待更多验证                   │
│  └───────────────────────────────────────────────────────────────────────┘
```

### 3.3 关键改进点

| 改进 | 原设计 | 新设计 | 目的 |
|------|--------|--------|------|
| **强制A8校验** | 可选/建议 | 步骤5不可跳过 | 防止"只顾开发不更新文档" |
| **记忆同步自动化** | 人工蒸馏 | 步骤7自动触发 | 文档更新后记忆自动同步 |
| **分区检索** | 全目录搜索 | 按 MU-xxx 单元检索 | 减少干扰，提升精度 |
| **单元配额** | 全局8K | 按单元分配配额 | 防止单一领域膨胀 |

## 4. 证明算法与阈值机制

### 4.1 为什么需要证明算法？

当前质量分级（S/A/B/C/D）是**静态标注**，缺少**动态验证机制**：
- B 级记忆标注了，但从未被验证过
- A 级记忆被验证了2次，但第3次发现是错误的
- 没有机制让记忆"自证其真"

### 4.2 证明算法设计

**核心思想**：记忆的置信度 = 验证次数 × 验证质量 × 时间衰减

```python
# 证明算法伪代码
confidence_score = (
    verify_count * verify_quality_weight * time_decay
) / (conflict_count * 2 + 1)

# 参数说明
# verify_count: 被验证次数（A8校验、运行时测试、人工确认都算）
# verify_quality_weight: 验证质量权重
#   - A8校验通过: +1.0
#   - 运行时测试通过: +0.8
#   - 人工代码审查通过: +0.9
#   - 自动测试通过: +0.5
# time_decay: 时间衰减因子（最近验证权重高，远期验证权重低）
#   - 7天内: 1.0
#   - 30天内: 0.8
#   - 90天内: 0.5
#   - 超过180天: 0.2（需重新验证）
# conflict_count: 冲突次数（与其他记忆矛盾的次数）
```

### 4.3 阈值与升级规则

| 当前等级 | 升级条件（置信度阈值） | 升级后等级 | 说明 |
|---------|----------------------|-----------|------|
| C (假设) | ≥ 0.6 + 1次A8校验 | B (待验证) | 有初步证据支持 |
| B (待验证) | ≥ 0.7 + 2次不同场景验证 | A (可信) | 多场景验证通过 |
| A (可信) | ≥ 0.85 + 3次验证 + 无冲突 | S (公理) | 广泛验证，无矛盾 |
| S (公理) | — | — | 最高等级，极少变动 |

**降级规则**：
- 任意等级：发现与其他 S 级记忆冲突 → 立即降级为 C，重新验证
- A/B 级：180 天内无验证 → 置信度衰减，可能降级
- 被明确证伪 → 直接标记 D 级，移入 archive/

### 4.4 "不必完全写死"的理解

用户要求"不必完全写死，但需要严格限制"，这意味着：
- **阈值不是固定数值**：可以根据记忆单元类型动态调整（开发记忆的A级阈值可以比交易记忆低，因为开发场景更标准化）
- **容量不是绝对上限**：超过80%触发consolidation，但可以通过压缩释放空间，不是硬截断
- **升级需要证明但不是行政审批**：达到阈值自动升级，不需要人工逐条审批

## 5. 结合 L4 的交叉验证

### 5.1 L4 记忆 ↔ 记忆单元的映射

L4（交易记忆）是应用记忆的标杆，它与 MU-TRD（交易记忆单元）的关系：

```
L4 应用记忆（11-易经推理系统/scripts/memory_l4/）
    │
    ├── case/          ──蒸馏──→  MU-TRD/episodic/  （情景记忆）
    ├── review/        ──蒸馏──→  MU-TRD/episodic/  （情景记忆）
    ├── distill/       ──提炼──→  MU-TRD/semantic/  （语义记忆）
    │                         ──精炼──→  MU-TRD-CORE.md （程序记忆）
    └── stats/         ──聚合──→  MU-TRD/semantic/  （统计知识）
```

### 5.2 L4 作为证明算法的验证源

L4 的运行时数据可以作为证明算法的**验证源**：
- L4 case 中的交易结果（盈利/亏损） → 验证交易规则记忆的置信度
- L4 review 中的复盘结论 → 验证策略记忆的可靠性
- L4 distill 中的模式提取 → 直接生成语义记忆

**交叉验证流程**：
1. MU-TRD 中有一条 A 级记忆："趋势向上时 LONG 胜率更高"
2. L4 运行时产生 100 条新 case，其中趋势向上时 LONG 胜率 45%
3. 证明算法检测到与该记忆矛盾 → 触发重新验证
4. 该记忆置信度下降 → 可能降级为 B 级
5. 同时生成新的情景记忆记录这次验证过程

## 6. 方案评估

### 6.1 可行性分析

| 模块 | 难度 | 工作量 | 依赖 | 风险 |
|------|------|--------|------|------|
| 记忆单元分区（目录重构） | 低 | 1天 | 无 | 低：纯目录调整 |
| MU-CORE.md 拆分 | 中 | 2天 | 分区完成 | 低：内容裁剪 |
| 自动更新机制（A8后触发） | 中 | 3天 | A8 SKILL实现 | 中：需要 hook 点 |
| 证明算法实现 | 高 | 5天 | 记忆单元完成 | 中：算法调参 |
| L4 交叉验证 | 中 | 2天 | 证明算法 | 低：接口已存在 |
| 阈值动态调整 | 高 | 3天 | 证明算法 | 高：需要运行时数据 |

**总工作量估算**：约 2~3 周（1人全职）

### 6.2 价值评估

| 优化点 | 解决的问题 | 预期收益 |
|--------|-----------|---------|
| 记忆单元分区 | 检索干扰、容量竞争 | 检索精度 ↑ 40%，维护成本 ↓ |
| 自动更新机制 | "只顾开发不更新文档" | 文档-代码一致性 ↑ |
| 证明算法 | 记忆质量不可信 | 记忆置信度可量化 |
| L4 交叉验证 | 交易记忆与实际脱节 | 交易规则可靠性 ↑ |

### 6.3 与现有架构的兼容性

- ✅ 与双层架构兼容：记忆单元在总记忆层内部分区，不影响应用记忆
- ✅ 与质量分级兼容：证明算法基于现有 S/A/B/C/D 体系
- ✅ 与容量限制兼容：单元配额是全局配额的细分
- ✅ 与 L4 接口兼容：交叉验证通过现有 app_memory_interface.py 实现
- ⚠️ 需要调整：CORE.md 需要拆分为 MU-xxx-CORE.md
