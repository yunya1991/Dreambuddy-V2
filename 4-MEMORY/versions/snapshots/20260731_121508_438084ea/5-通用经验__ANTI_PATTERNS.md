# 反模式 — ANTI PATTERNS

> **版本**: v1.0
> **更新日期**: 2026-07-26
> **定位**: 经过验证的错误做法，要警惕和避免
> **来源**: 项目踩坑经验 + 观察总结
> **说明**: 这些做法看起来快、省事，但长期来看是有害的

## AP-001：上来就改，从不调研

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-001 |
| **等级** | A（已验证的反模式） |
| **危害程度** | 高 |
| **常见程度** | 高 |
| **来源** | 多次踩坑总结 |
| **对应最佳实践** | BP-001：A1调研法 |
| **标签** | 反模式, 调研, 流程 |

### 表现

- "这么简单，不用调研，直接改就行"
- 上来就动手改代码
- 改之前不读文档，也不读相关代码
- 完全靠记忆和猜测

### 为什么有人这么做

- 觉得自己懂了，不用再看
- 觉得调研浪费时间
- 任务紧，没时间调研
- 习惯了拿到就做

### 后果

1. **改了 A 影响了 B**：不知道有依赖，改完发现别的地方坏了
2. **找错根因**：以为是这个问题，其实是另一个，白忙活
3. **重新发明轮子**：做了已有的功能，浪费时间
4. **踩文档的坑**：文档和代码不一致，按记忆做结果错了
5. **越改越乱**：改到一半发现方向错了，回退也不是，继续也不是

### 反例（正确做法）

参考 A1 调研方法论：
- 先明确调研目标和范围
- 先读文档，再读代码
- 搞清楚现状再动手
- 哪怕只花 15 分钟调研，也比完全不调研强

## AP-002：只看文档，不看代码

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-002 |
| **等级** | A（已验证的反模式） |
| **危害程度** | 高 |
| **常见程度** | 中 |
| **来源** | 文档债治理实践 |
| **对应最佳实践** | BP-003：A8理论实践校验法 |
| **标签** | 反模式, 文档, 调研 |

### 表现

- "文档是权威，按文档来就行"
- 只看文档，不验证代码实际是不是这样
- 文档说什么就信什么
- 发现不对也不怀疑文档，怀疑自己

### 为什么有人这么做

- 文档看起来很专业，应该没错
- 读代码比读文档累
- 信任前人写的文档
- 不知道文档可能过时

### 后果

1. **按文档做，结果全错**：文档早就过时了
2. **发现不了问题**：文档和代码不一致的地方完全看不到
3. **踩坑才发现**：做完了运行才发现不对
4. **浪费时间**：按文档做的东西全部要返工

### 典型案例

- 16-调控系统 ENGINEERING_INDEX 说 core/ 只有 `__init__.py`，实际有 19 个文件
- 10-经典指标系统文档说有 `docs/TECHNICAL_DESIGN.md`，实际在根目录叫 `技术文档2.0.md`

### 反例（正确做法）

- 文档是参考，代码才是事实
- 文档和代码两边都看，对比校验
- 发现不一致，以代码为准（但要理解设计意图）
- 把不一致记录为技术债，后续修复

## AP-003：只看代码，不看文档

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-003 |
| **等级** | B（待验证） |
| **危害程度** | 中 |
| **常见程度** | 高 |
| **来源** | 观察总结 |
| **对应最佳实践** | BP-003：A8理论实践校验法 |
| **标签** | 反模式, 代码, 调研 |

### 表现

- "文档都是扯淡，直接读代码才是真的"
- 上来就扎进代码细节里
- 不看设计文档，不看架构图
- 不知道整体设计，只看到局部

### 为什么有人这么做

- 被过时的文档坑过，不信文档了
- 觉得代码才是真相
- 觉得读文档浪费时间
- 习惯了读代码

### 后果

1. **只见树木不见森林**：读了半天代码，还是不知道整体架构
2. **不理解设计意图**：不知道为什么这么设计，改的时候容易破坏设计
3. **效率低**：从零开始读代码，比先看文档再读代码慢
4. **容易误判**：把设计决策当成 bug，把 bug 当成设计

### 反例（正确做法）

- 先读文档，建立整体认知
- 再读代码，验证文档说法
- 文档帮你快速建立框架，代码帮你了解细节
- 两者结合，效率最高

## AP-004：眉毛胡子一把抓，不分主次

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-004 |
| **等级** | A（已验证的反模式） |
| **危害程度** | 高 |
| **常见程度** | 高 |
| **来源** | 技术债治理实践 + 项目管理经验 |
| **对应最佳实践** | BP-002：矛盾论找主要矛盾 |
| **标签** | 反模式, 优先级, 效率 |

### 表现

- 问题一大堆，哪个都想解决
- 今天做这个，明天做那个
- 什么重要什么不重要，全凭感觉
- 忙忙碌碌，但进展不明显

### 为什么有人这么做

- 觉得每个问题都重要
- 不忍心放下任何一个问题
- 不知道怎么判断优先级
- 喜欢做简单的，不管重不重要

### 后果

1. **效率低下**：精力分散，哪个都没做好
2. **进展缓慢**：忙了半天，核心问题还是没解决
3. **容易放弃**：看不到进展，失去动力
4. **质量下降**：每个问题都只是表面解决，不彻底

### 反例（正确做法）

用矛盾论分析：
1. 把所有问题列出来
2. 分类归组
3. 找到主要矛盾
4. 集中力量解决主要矛盾
5. 主要矛盾解决了，次要矛盾可能跟着就解决了

## AP-005：发现问题不改，只记录不行动

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-005 |
| **等级** | B（待验证） |
| **危害程度** | 中 |
| **常见程度** | 中 |
| **来源** | 观察总结 |
| **对应最佳实践** | BP-004：技术债先记录再偿还 |
| **标签** | 反模式, 技术债, 执行 |

### 表现

- 发现了问题，记下来了，然后就没有然后了
- 债务清单越来越长，但是一个都没修
- 每次回顾都是"下次再说"
- 报告写了一堆，问题还是那些问题

### 为什么有人这么做

- 太忙了，没时间修
- 觉得不是紧急的，先放放
- 不知道从哪个开始
- 记录了就好像完成了

### 后果

1. **债务越积越多**：今天不还，明天更多
2. **利息越来越高**：越晚还，成本越高
3. **记录失去意义**：反正也不做，记了白记
4. **最后爆发**：小问题攒成大问题，不得不花更大代价解决

### 反例（正确做法）

- 记录只是第一步，不是终点
- 排优先级，从最严重的开始
- 每次开发顺手还一点债
- 定期回顾，确保有进展
- 设定还债目标，比如每月还 2-3 个

## AP-006：大干快上，一步到位

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-006 |
| **等级** | A（已验证的反模式） |
| **危害程度** | 高 |
| **常见程度** | 中 |
| **来源** | 软件工程通用反模式 + 项目经验 |
| **对应最佳实践** | BP-006：小步快跑，每步验证 |
| **标签** | 反模式, 开发流程, 风险 |

### 表现

- "要改就一次性改完"
- 一口气改一大堆文件
- 改完才测试，才发现问题
- 出了问题不知道是哪一步引起的

### 为什么有人这么做

- 觉得分步做太慢
- 觉得一次性改完更高效
- 对自己的代码有信心
- 觉得小步太麻烦

### 后果

1. **风险大**：万一出错，影响范围大
2. **难定位**：出了问题不知道是哪改坏的
3. **难回滚**：改的太多，回退也麻烦
4. **质量差**：好多地方没验证，隐藏bug多
5. **容易烂尾**：改到一半发现太复杂，进退两难

### 反例（正确做法）

小步快跑：
- 大任务拆成小任务
- 每步做完都验证
- 错了及时回退，损失小
- 稳步推进，质量有保障

## AP-007：完美主义，无限调研/设计，总不行动

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-AP-007 |
| **等级** | B（待验证） |
| **危害程度** | 中 |
| **常见程度** | 低 |
| **来源** | 观察总结 |
| **对应最佳实践** | BP-001：A1调研法（适度调研） |
| **标签** | 反模式, 效率, 执行 |

### 表现

- "还没完全搞懂，再调研调研"
- 方案改了一遍又一遍，总觉得不够完美
- 永远在准备，永远不开始
- 想的很多，做的很少

### 为什么有人这么做

- 追求完美，不想有瑕疵
- 怕做错，想一次做对
- 觉得准备充分了风险小
- 喜欢思考，不喜欢执行

### 后果

1. **效率极低**：花了很多时间，什么都没做出来
2. **错失时机**：等你准备好了，机会已经没了
3. **脱离实际**：想的都是理想情况，实际一做发现不是那么回事
4. **失去信任**：总是说要做但没进展，别人不信了

### 反例（正确做法）

- 调研到够用就行，不要追求完美
- 方案到能指导行动就行，细节可以边做边调
- 先做最小可行版本，再迭代优化
- 在行动中完善，而不是想好了再行动
- 判断标准：能不能回答"这个改动影响范围有多大？风险在哪里？"，能回答就够了
