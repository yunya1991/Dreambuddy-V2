# 工程原则 — ENGINEERING PRINCIPLES

> **版本**: v1.0
> **更新日期**: 2026-07-26
> **定位**: 项目级工程原则，所有开发和维护工作必须遵循
> **等级**: S（公理级）— 经过大量实践验证的基本原则

---

## 0. 三原则（项目最高指导）

### 原则一：工业级标准

**核心理念**：按照代码工程工业级标准流程、规范以及严谨度来实现。

**具体要求**：
- 代码有规范，文档有模板，流程有标准
- 命名一致，结构清晰，职责明确
- 测试有覆盖，发布有校验，回滚有预案
- 不接受"能用就行"，追求"专业可靠"

**检查清单**：
- [ ] 代码是否通过 lint/type check？
- [ ] 是否有对应的测试用例？
- [ ] 文档是否同步更新？
- [ ] 变更是否有记录（CHANGELOG）？
- [ ] 出问题是否有回滚方案？

---

### 原则二：彻底解决 + 充分调研

**核心理念**：由于系统比较庞大，不要求一次解决所有问题，但要求解决彻底。所以充分调研非常有必要。

**具体要求**：
- 动手之前先调研，搞清楚现状再动手
- 用 A1 SKILL + 矛盾论指导调研过程
- 找到根因再修复，不满足于表面现象
- 解决一个问题就彻底解决，不留尾巴
- 宁可慢一点，也要稳一点

**检查清单**：
- [ ] 是否充分调研了相关代码和文档？
- [ ] 是否找到了根因而不是表面现象？
- [ ] 是否考虑了所有相关的边缘情况？
- [ ] 修复后是否有验证手段？
- [ ] 是否更新了相关文档和记忆？

---

### 原则三：理论与实践一致性

**核心理念**：我们核心是解决代码和文档规划不一致问题，A8 SKILL 理论与实践可以充分应用。

**具体要求**：
- 文档写的和代码做的必须一致
- 不一致的地方就是技术债，必须记录并偿还
- 代码变更必须同步更新文档
- 文档变更必须落实到代码实现
- 用 A8 方法论定期校验理论实践对齐状态

**检查清单**：
- [ ] 代码实现是否与技术设计文档一致？
- [ ] API 接口是否与 API_SPEC 一致？
- [ ] 配置参数是否与文档说明一致？
- [ ] 变更是否同时更新了代码和文档？
- [ ] 是否存在"文档说有，代码没有"或"代码有，文档没说"的情况？

## 1. 开发工作流原则

### 1.1 七步工作流

```
需求 → 调研 → 设计 → 实现 → 验证 → 发布 → 复盘
```

**每一步的产出**：

| 步骤 | 产出 | 验证标准 |
|------|------|---------|
| 需求 | 需求说明 + 优先级 | 明确"做什么"和"为什么做" |
| 调研 | 调研报告 + 现状分析 | 搞清楚"现在是什么样" |
| 设计 | 技术方案 + 影响评估 | 明确"怎么做"和"影响什么" |
| 实现 | 代码 + 单元测试 | 功能正确 + 代码规范 |
| 验证 | 测试报告 + 验证结果 | 功能正确 + 无回归 |
| 发布 | 发布说明 + 变更记录 | 用户可用 + 可回滚 |
| 复盘 | 经验教训 + 过程改进 | 沉淀到记忆系统 |

### 1.2 调研优先原则

> **没有调研就没有发言权**

- 任何改动之前，先充分调研现状
- 调研要覆盖：相关代码、相关文档、相关配置、相关测试
- 调研要回答：现状是什么？问题在哪里？影响有多大？
- 调研工具：A1 SKILL + 矛盾论 + 代码搜索 + 文档阅读

### 1.3 小步快跑原则

- 大任务拆成小任务，每个小任务可独立验证
- 每次变更的影响范围可控
- 出错能快速回滚
- 进度可追踪可衡量

## 2. 代码质量原则

### 2.1 可读性优先

> 代码是写给人看的，顺便能在机器上运行。

- 命名清晰：变量名、函数名、类名要见名知意
- 结构清晰：函数不要太长，文件不要太大
- 注释必要："为什么这样做"比"做了什么"更重要
- 一致风格：遵循项目的代码规范，不要特立独行

### 2.2 防御式编程

- 对输入做校验，不假设外部传进来的都是对的
- 对错误有处理，不假设一切都会顺利
- 边界条件要考虑，正常路径和异常路径都要测试
- 失败要可诊断：错误信息要足够定位问题

### 2.3 单一职责

- 一个函数只做一件事
- 一个模块只负责一个领域
- 职责边界清晰，依赖关系明确
- 修改一个地方不应该牵动全身

## 3. 文档原则

### 3.1 文档与代码同步

- 代码变了，文档必须跟着变
- 文档变了，代码必须落实
- 文档和代码不一致就是技术债
- 用 A8 方法论定期校验

### 3.2 文档要有结构

- 遵循文档规范（见 0-系统文档管理/1-规范体系/DOC_STANDARD.md）
- 使用标准模板，保持风格一致
- 有版本号，有更新日期
- 有清晰的目录和导航

### 3.3 文档要有用

- 不写没人看的文档
- 文档是给未来的自己和同事看的
- 假设读者不了解上下文
- 关键决策要有理由说明

---

## 4. 测试原则

### 4.1 测试是投资，不是负担

- 测试能让你放心重构
- 测试能快速发现回归问题
- 测试本身就是最好的文档
- 没有测试的代码是不可靠的

### 4.2 测试金字塔

```
        /\
       /  \      E2E 测试（少量）
      /----\
     /      \    集成测试（适量）
    /--------\
   /          \   单元测试（大量）
  /------------\
```

- 单元测试：覆盖核心逻辑，数量最多，速度最快
- 集成测试：验证模块协作，数量适中
- E2E 测试：验证核心流程，数量最少

### 4.3 可验证性

- 每个功能都要有验证方法
- 修复 bug 先写测试复现，再修复
- 新功能要有对应的测试用例
- 测试要能自动化运行

## 5. 技术债管理原则

### 5.1 技术债不可怕，可怕的是不记录

- 发现技术债就记录下来
- 评估优先级，排期偿还
- 不要让技术债暗中累积
- 定期回顾债务清单

### 5.2 借债要还，还要付利息

- 技术债是有成本的：维护成本、沟通成本、风险成本
- 能现在还的债不要拖到以后
- 还债时间越晚，成本越高
- 每次开发顺手还一点债

### 5.3 债要分类管理

- P1：必须立即修复（运行时缺陷、安全问题）
- P2：近期修复（影响开发效率、架构错位）
- P3：择机修复（代码风格、小优化）

---

## 6. 记忆系统原则

### 6.1 经验必须沉淀

- 踩过的坑要记录下来
- 好的做法要提炼为最佳实践
- 错误的做法要标记为反模式
- 每次复盘都要更新记忆系统

### 6.2 记忆是阶梯式的

- 从具体经验 → 通用教训 → 方法论 → 原则
- 低层级的记忆多而具体，高层级的少而抽象
- 高层级指导低层级，低层级验证高层级
- 记忆不是静止的，是不断演化的

### 6.3 记忆可验证可证伪

- 每条记忆要有来源
- 每条记忆要有验证状态
- 记忆可以被新的经验推翻
- 被证伪的记忆要及时标记

---

## 7. 协作原则

### 7.1 明确优于模糊

- 有疑问就问清楚，不要猜
- 决策要记录下来，避免反复
- 状态要同步，避免信息差
- 假设要说出来，验证了再确认

### 7.2 对事不对人

- 讨论问题聚焦问题本身
- 用数据和事实说话
- 接受不同意见，追求最优解
- 错了就承认，改了就好
