## BP-001：用 A1 调研法指导调研工作

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-001 |
| **等级** | A（可信级） |
| **验证次数** | 5 次 |
| **来源** | 三屏趋势重构 / 调控系统修复 / L3调度器优化 / 文档统一管理 / 记忆系统设计 |
| **关联文档** | [A1_RESEARCH_METHOD.md](../2-方法论记忆/A1_RESEARCH_METHOD.md) |
| **标签** | 调研, 方法论, 效率 |

### 实践描述

做任何调研工作时，按照 A1 调研方法论的标准流程来：

1. **明确调研目标**：调研什么？为什么调研？调研到什么程度？
2. **文档调研**：先读文档，建立宏观认知
3. **代码调研**：再读代码，从表面层到逻辑层逐步深入
4. **对比校验**：文档和代码对比，发现不一致
5. **总结输出**：写调研报告，有结论有依据

### 为什么有效

- 不会漏东西：按步骤来，覆盖全面
- 效率更高：先文档后代码，先建立整体认知再深入细节
- 产出可复用：调研报告别人也能用
- 容易发现问题：文档代码对比，自然发现技术债

### 适用场景

- 接手新模块
- 修复 bug 前的调研
- 重构前的调研
- 技术债审计
- 任何需要了解陌生代码的场景

## BP-002：用矛盾论找主要矛盾，集中力量解决

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-002 |
| **等级** | A（可信级） |
| **验证次数** | 3 次 |
| **来源** | 技术债治理 / 性能优化 / 架构梳理 |
| **关联文档** | [CONTRADICTION_METHOD.md](../2-方法论记忆/CONTRADICTION_METHOD.md) |
| **标签** | 方法论, 优先级, 矛盾论 |

### 实践描述

面对复杂问题时，用矛盾论分析：

1. **列出所有问题**：把所有现象都列出来
2. **分类归组**：把相似的问题归到一组
3. **找主要矛盾**：找到"牵一发而动全身"的那个问题
4. **找主要方面**：在主要矛盾内部，找到起主导作用的一方
5. **集中力量解决**：把主要精力放在主要矛盾的主要方面上

### 为什么有效

- 不会眉毛胡子一把抓：知道什么最重要
- 效率最高：解决了主要矛盾，很多问题迎刃而解
- 方向明确：知道该往哪使劲
- 避免瞎忙：不会在次要问题上浪费太多精力

### 适用场景

- 技术债治理（先治什么后治什么）
- 性能优化（先优化哪部分）
- 系统重构（从哪里开始）
- 团队效率提升（什么问题最影响效率）
- 任何"问题一大堆，不知道从哪下手"的场景

## BP-003：用 A8 理论实践校验法做文档-代码对齐检查

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-003 |
| **等级** | A（可信级） |
| **验证次数** | 4 次 |
| **来源** | 三屏趋势文档校验 / 调控系统接口校验 / 经典指标索引校验 / 全局文档债梳理 |
| **关联文档** | [A8_THEORY_PRACTICE.md](../2-方法论记忆/A8_THEORY_PRACTICE.md) |
| **标签** | 文档, 校验, 技术债 |

### 实践描述

检查文档和代码是否一致时，按照 A8 方法论来：

1. **明确范围**：校验什么？校验到什么深度？
2. **收集理论**：从文档中提取"断言"（文档说了什么）
3. **收集实践**：从代码中提取"事实"（实际做了什么）
4. **对比校验**：一条一条对比，标记一致/不一致
5. **根因分析**：不一致的原因是什么？
6. **生成债务**：不一致的转化为技术债
7. **修复验证**：修复后重新校验

### 为什么有效

- 系统性强：不会东看一点西看一点
- 结果可量化：一致性比例多少，一目了然
- 可追溯：每条不一致都有记录和根因
- 可复查：下次再校验可以对比进步

### 适用场景

- 子系统文档质量审计
- 接口文档-实现一致性检查
- 技术债排查
- 重构前的现状摸底
- 定期质量巡检

## BP-004：技术债先记录再偿还，定期回顾

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-004 |
| **等级** | A（可信级） |
| **验证次数** | 多次 |
| **来源** | DEBT_INDEX.md 实践 + DOC_DEBT_INDEX.md 实践 |
| **关联文档** | [DEBT_INDEX.md](../../DEBT_INDEX.md) |
| **标签** | 技术债, 管理, 流程 |

### 实践描述

发现技术债时：

1. **立即记录**：发现一个记一个，不要攒着
2. **评估优先级**：P1/P2/P3，排好优先级
3. **定期回顾**：每周/每月回顾债务清单
4. **排期偿还**：根据优先级和资源，安排偿还
5. **关闭确认**：修复后验证，确认修复了再关闭

### 为什么有效

- 不会忘：记下来就不会丢
- 可衡量：知道有多少债，还了多少
- 有计划：不是想起来才还，而是有计划地还
- 有动力：看着债务减少，有成就感

### 记录要素

每条技术债至少记录：
- ID：唯一编号
- 标题：简短描述
- 子系统：属于哪个系统
- 类型：代码债 / 文档债 / 架构债 / 测试债
- 优先级：P1 / P2 / P3
- 描述：详细说明
- 影响：有什么后果
- 修复方案：建议怎么修
- 预计工作量：大概多久

## BP-005：每次工作结束后复盘，沉淀经验到记忆系统

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-005 |
| **等级** | B（待验证） |
| **验证次数** | 刚启动 |
| **来源** | 记忆系统设计理念 |
| **关联文档** | [MEMORY_SYSTEM_ARCHITECTURE.md](../MEMORY_SYSTEM_ARCHITECTURE.md) |
| **标签** | 复盘, 记忆, 持续改进 |

### 实践描述

每次完成一项工作后，花一点时间复盘：

1. **做了什么**：回顾这次的工作内容
2. **学到了什么**：有什么新的发现和认识
3. **踩了什么坑**：遇到了什么问题，怎么解决的
4. **有什么经验**：哪些做法可以复用
5. **沉淀到记忆**：把有价值的经验录入记忆系统

### 为什么有效

- 经验不会丢：做过的事、踩过的坑都记下来
- 持续进步：每次都比上次强一点
- 可复用：好的做法可以推广到其他场景
- 可传承：新人来了也能快速上手

### 复盘频率

| 工作类型 | 复盘频率 |
|---------|---------|
| 小任务（1天内） | 任务结束后简单复盘 |
| 中任务（1周内） | 每个阶段结束复盘 |
| 大项目（1周以上） | 每周复盘 + 项目终复盘 |

## BP-006：小步快跑，每步验证

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-BP-006 |
| **等级** | A（可信级） |
| **验证次数** | 多次 |
| **来源** | 软件工程通用最佳实践 + 项目经验 |
| **标签** | 开发流程, 质量, 风险控制 |

### 实践描述

做开发/改造/重构时：

1. **拆小步骤**：把大任务拆成小步骤
2. **每步验证**：做完一步就验证一步
3. **错了及时回退**：发现问题马上退回去，不要硬着头皮往前走
4. **稳步推进**：一步一步来，不要跳步

### 为什么有效

- 风险可控：每步出错影响范围小
- 容易定位问题：哪一步出的问题，就是那一步的事
- 有成就感：每完成一步都有正反馈
- 质量有保障：每步都验证，问题不会累积

### 对比

| 大干快上 | 小步快跑 |
|---------|---------|
| 一口气全改完 | 拆成小步，逐步推进 |
| 最后才验证 | 每步都验证 |
| 出问题不知道哪错了 | 出问题知道是哪步的事 |
| 容易越改越乱 | 稳步推进，质量可控 |
