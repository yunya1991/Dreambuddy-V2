## TL-001：subprocess + shlex.split 在设置环境变量时会失败

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-001 |
| **等级** | B（待验证） |
| **验证次数** | 1 次 |
| **来源** | L3指挥中心调度器崩溃案例（2026-07-26） |
| **标签** | Python, subprocess, shell, 环境变量 |

### 描述

当使用 `subprocess.run(shlex.split(command))` 执行包含环境变量设置的命令时（如 `PYTHONPATH=. python xxx.py`），会失败。

### 根因

`shlex.split("PYTHONPATH=. python script.py")` 会解析成：
```python
['PYTHONPATH=.', 'python', 'script.py']
```

`subprocess.run` 把第一个元素 `'PYTHONPATH=.'` 当成可执行文件去执行，导致 `FileNotFoundError`。

### 正确做法

```python
# 方案一：用 shell=True（让 shell 解析环境变量）
subprocess.run("PYTHONPATH=. python script.py", shell=True, ...)

# 方案二：用 env 参数（推荐，更安全）
import os
env = os.environ.copy()
env["PYTHONPATH"] = "."
subprocess.run(["python", "script.py"], env=env, ...)
```

### 适用场景

- 使用 subprocess 执行 Python 脚本
- 需要设置环境变量的命令
- 从字符串解析命令并执行

### 相关案例

- L3指挥中心 `phase2_autoreview_trigger.py` 崩溃，导致 launchd 无限重启循环，CPU 持续 99%

## TL-002：launchd 任务 label 要从安装脚本查，不要猜

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-002 |
| **等级** | B（待验证） |
| **验证次数** | 1 次 |
| **来源** | L3调度器CPU优化案例（2026-07-26） |
| **标签** | macOS, launchd, 运维 |

### 描述

查找 launchd 任务时，不要根据功能猜 label，要从安装脚本或 plist 文件中找真实的 label。

### 教训

猜测 label 为 `com.l3.phase2`，结果 `launchctl list | grep` 找不到。实际 label 是 `com.l3.commandcenter.phase2scheduler`，在 `install_l3_launchd.sh` 中定义。

### 正确做法

1. 先找安装脚本（install*.sh）或 plist 文件
2. 从脚本中提取真实的 label
3. 再用真实的 label 去操作

### 适用场景

- 查找已有的 launchd 任务
- 重启/停止 launchd 服务
- 排查后台进程

## TL-003：高 CPU 进程先排查是不是崩溃重启循环

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-003 |
| **等级** | B（待验证） |
| **验证次数** | 1 次 |
| **来源** | L3指挥中心高CPU问题（2026-07-26） |
| **标签** | 性能, 运维, 故障排查 |

### 描述

看到进程持续高 CPU，不要默认就是"计算量大"，先检查是不是崩溃重启循环。

### 崩溃循环的特征

1. PID 频繁变化（进程在反复重启）
2. CPU 持续 90%+，但内存忽高忽低
3. launchd/supervisor 等管理工具配置了 KeepAlive
4. 查看日志，发现反复报错退出

### 排查步骤

1. 看 PID 是不是稳定（隔几秒看一次，变了就是在重启）
2. 看进程的启动时间（`ps -o lstart= -p PID`）
3. 看错误日志，找崩溃原因
4. 修复崩溃原因，而不是优化 CPU 占用

### 典型案例

L3 调度器：subprocess 调用失败 → 进程崩溃 → launchd KeepAlive 立即拉起 → 再崩溃 → 无限循环 → CPU 持续 99%

表面看是"调度太频繁导致 CPU 高"，实际根因是崩溃重启循环。

## TL-004：文档路径不一致是常见的技术债来源

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-004 |
| **等级** | A（可信级） |
| **验证次数** | 3 次 |
| **来源** | 12-三屏趋势系统 / 10-经典指标系统 / 16-调控系统 |
| **标签** | 文档, 技术债, 路径 |

### 描述

文档中的路径引用和实际路径不一致，是高频出现的技术债。包括：
- 引用了错误的目录名
- 引用了已删除/重命名的文件
- 并行目录（同一个东西有两个目录）
- 双索引（同一个文件有两个版本）

### 已知案例

1. **12-三屏趋势系统**：存在 `12-三屏趋势系统/` 和 `trend-system/` 两个并行目录，且 docs/ 下有旧版 ENGINEERING_INDEX
2. **10-经典指标系统**：ENGINEERING_INDEX 引用不存在的 `docs/TECHNICAL_DESIGN.md`，实际是根目录的 `技术文档2.0.md`
3. **多个子系统**：代码中引用 `trend-system/` 路径，实际应该是 `12-三屏趋势系统/`

### 防范方法

1. 重命名/移动文件后，全局搜索旧路径引用
2. 定期用 A8 方法论做文档-代码一致性检查
3. 不要创建并行目录，有迁移就彻底迁移干净

## TL-005：ENGINEERING_INDEX 容易过时，要定期更新

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-005 |
| **等级** | A（可信级） |
| **验证次数** | 2 次 |
| **来源** | 16-调控系统 / 10-经典指标系统 |
| **标签** | 文档, 技术债, ENGINEERING_INDEX |

### 描述

ENGINEERING_INDEX.md 是子系统的工程索引，但代码变化时经常忘记更新，导致严重过时。

### 典型案例

1. **16-调控系统**：文档声称 core/ 只有 `__init__.py`，实际有 19 个核心 Python 文件
2. **10-经典指标系统**：索引断链，引用不存在的文件

### 后果

- 新人接手时被误导
- 排查问题时找错地方
- 文档完全失去参考价值

### 防范方法

1. 新增/删除核心文件时，同步更新 ENGINEERING_INDEX
2. 每季度用 A8 校验法检查一次
3. 在 ENGINEERING_INDEX 头部标注版本号和最后更新日期

## TL-008：修改调度间隔后要重启进程才生效

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-TL-008 |
| **等级** | B（待验证） |
| **验证次数** | 1 次 |
| **来源** | L3调度器优化案例（2026-07-26） |
| **标签** | 运维, 调度, 配置 |

### 描述

修改了调度脚本的间隔参数后，必须重启对应的进程/服务，新配置才会生效。

### 常见场景

- 进程是常驻的，不是每次重新加载配置

### 正确做法

1. 修改配置文件
2. 重启进程/服务
3. 验证新配置是否生效（看日志、看行为）
