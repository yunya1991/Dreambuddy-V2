## 0. 为什么需要理论实践校验？

> **我们核心是解决代码和文档规划不一致问题。**
> **理论（文档）和实践（代码）不一致，是最大的技术债。**

在我们的项目中，这个问题尤其突出：

| 现象 | 后果 |
|------|------|
| 文档说有这个功能，代码里没有 | 新人踩坑，对接失败 |
| 代码里有这个功能，文档没说 | 功能被埋没，没人用 |
| 文档说的是旧版本，代码已经改了 | 按文档做，结果全错 |
| 接口参数文档和实际不一样 | 调用失败，排错困难 |

**本质**：理论（文档）和实践（代码）之间的偏差，就是技术债。

**目标**：让理论指导实践，实践反哺理论，形成闭环。

---

## 1. 核心概念

### 1.1 什么是"理论"？

"理论" = 文档 + 设计 + 规划 + 规范

| 理论类型 | 典型代表 |
|---------|---------|
| 架构理论 | 架构设计文档、系统分层、模块划分 |
| 接口理论 | API_SPEC、接口定义、参数说明 |
| 功能理论 | 需求文档、功能说明、设计文档 |
| 流程理论 | 工作流、开发规范、发布流程 |
| 配置理论 | 配置说明、参数文档、环境变量 |

### 1.2 什么是"实践"？

"实践" = 代码 + 运行数据 + 实际行为

| 实践类型 | 典型代表 |
|---------|---------|
| 代码实践 | 实际的代码实现 |
| 接口实践 | 实际的 API 接口和返回 |
| 运行实践 | 实际运行时的行为和数据 |
| 配置实践 | 实际的配置文件和环境变量 |
| 流程实践 | 实际的工作方式和流程 |

### 1.3 一致 vs 不一致

| 状态 | 说明 | 是技术债吗？ |
|------|------|------------|
| **完全一致** | 文档说的和代码做的一模一样 | ❌ 不是 |
| **文档超前** | 文档规划了，但代码还没实现 | ⚠️ 是（未实现的规划） |
| **代码超前** | 代码实现了，但文档没更新 | ⚠️ 是（未文档化的实现） |
| **相互矛盾** | 文档说东，代码做西 | ❌ 是（严重债务） |
| **双方都缺** | 既没有文档也没有代码 | ⚠️ 是（空白区域） |

## 2. 校验流程

### 第一步：明确校验范围

**动作**：确定校验什么，校验到什么程度。

**校验范围维度**：

| 维度 | 选项 | 说明 |
|------|------|------|
| **校验对象** | 单个模块 / 整个子系统 / 全项目 | 范围越大，工作量越大 |
| **校验深度** | 表面层 / 逻辑层 / 全量 | 越深越准，但越慢 |
| **校验类型** | 接口 / 功能 / 架构 / 配置 | 可以只校验某一类 |

**输出**：校验范围说明

**检查**：
- [ ] 范围是不是明确？
- [ ] 深度要求是不是清楚？
- [ ] 预期工作量是不是可控？

---

### 第二步：收集理论（文档侧）

**动作**：把相关的文档都找出来，整理成"理论清单"。

**文档来源**：

| 文档类型 | 去哪找 |
|---------|--------|
| 系统概览 | README.md、ENGINEERING_INDEX.md |
| 技术设计 | docs/TECHNICAL_DESIGN.md |
| 接口说明 | docs/API_SPEC.md |
| 变更记录 | docs/CHANGELOG.md |
| 配置说明 | 配置文件注释、部署文档 |
| 需求文档 | 需求说明、产品文档 |

**整理方法**：
- 按模块/功能分类整理
- 提取"断言"：文档明确说了什么
- 标注来源：每条断言来自哪个文档哪一页

**输出**：理论清单（文档断言列表）

**示例**：
```
理论-001: auto_exit_system.py 调用 a9_exit_decision.evaluate_position_for_exit()
来源: 16-调控系统/ENGINEERING_INDEX.md v1.2
类型: 接口调用
状态: 待验证
```

**检查**：
- [ ] 相关文档都找全了吗？
- [ ] 是不是提取成了可验证的断言？
- [ ] 每条断言都有来源吗？

---

### 第三步：收集实践（代码侧）

**动作**：读代码，整理出"实践清单"。

**代码调研方法**（参考 A1 调研法）：

| 实践类型 | 怎么查 |
|---------|--------|
| 模块存在性 | 目录结构、文件列表 |
| 接口签名 | 函数定义、类定义 |
| 调用关系 | import 语句、函数调用 |
| 业务逻辑 | 核心代码逻辑 |
| 配置参数 | 配置文件、环境变量读取 |
| 错误处理 | try/except、错误返回 |

**整理方法**：
- 对应理论清单的结构，整理实际情况
- 提取"事实"：代码实际做了什么
- 标注位置：每条事实来自哪个文件哪一行

**输出**：实践清单（代码事实列表）

**示例**：
```
实践-001: auto_exit_system.py 调用的是 a9_exit_decision.a9_exit_decision_handler()
位置: 16-调控系统/scripts/auto_exit_system.py L123
类型: 接口调用
对应理论: 理论-001
```

**检查**：
- [ ] 代码是不是都读到了？
- [ ] 是不是和理论清单一一对应了？
- [ ] 有没有代码有但文档没提的？

---

### 第四步：对比校验

**动作**：把理论清单和实践清单一条一条对比。

**对比结果分类**：

| 结果 | 定义 | 标记 |
|------|------|------|
| ✅ 一致 | 文档说的和代码做的完全一致 | 一致 |
| ❌ 文档超前 | 文档说了，代码没实现 | 文档超前 |
| ❌ 代码超前 | 代码做了，文档没说 | 代码超前 |
| ❌ 相互矛盾 | 文档和代码说的不一样 | 矛盾 |
| ⚠️ 无法验证 | 说不清一致不一致，需要进一步确认 | 待确认 |

**方法**：
- 逐条对比，逐条标记
- 不一致的，记录差异详情
- 待确认的，列出来进一步调研

**输出**：校验结果表

**示例**：
```
| ID | 理论描述 | 实践情况 | 结果 | 差异说明 |
|----|---------|---------|------|---------|
| 001 | 调用 evaluate_position_for_exit | 调用 a9_exit_decision_handler | ❌ 矛盾 | 函数名不一致，参数也不同 |
| 002 | SKILL 名称 dream-research-skill-v2 | 实际是 dream-strategy-research | ❌ 矛盾 | SKILL 注册名不对 |
```

**检查**：
- [ ] 是不是每条都对比了？
- [ ] 不一致的是不是都记清楚了？
- [ ] 有没有遗漏的对比项？

---

### 第五步：根因分析

**动作**：对不一致的项，分析为什么会不一致。

**常见根因分类**：

| 根因类型 | 说明 | 典型例子 |
|---------|------|---------|
| 文档过时 | 代码改了，文档没跟着更新 | 重构后没更新 ENGINEERING_INDEX |
| 实现偏离 | 实现时偏离了设计，没同步改文档 | 开发时改了方案，忘了更新设计文档 |
| 规划未实现 | 文档规划了，但还没做 | API_SPEC 写了接口，但代码还没实现 |
| 理解偏差 | 不同人对同一件事理解不一样 | 文档写得模糊，代码实现偏了 |
| 历史遗留 | 很久以前的债，一直没还 | 从老版本继承来的文档过时 |

**方法**：
- 用 5 问法挖根因
- 看 git history 找变更时间点
- 看 CHANGELOG 找变更记录

**输出**：根因分析表

**检查**：
- [ ] 是真正的根因还是表面原因？
- [ ] 根因分类对吗？
- [ ] 有没有共性的根因？（比如"文档总是忘记更新"是系统性问题）

---

### 第六步：生成债务清单

**动作**：把不一致的项转化为技术债务，录入债务清单。

**债务要素**：

| 要素 | 说明 |
|------|------|
| ID | 债务唯一编号（如 DD-001） |
| 标题 | 简短描述 |
| 子系统 | 属于哪个子系统 |
| 类型 | 文档债 / 代码债 / 设计债 |
| 优先级 | P1 / P2 / P3 |
| 根因 | 根因分析结果 |
| 影响 | 影响范围和程度 |
| 修复方案 | 建议怎么修 |
| 预计工作量 | 大概需要多久 |

**输出**：新增的文档技术债条目

**检查**：
- [ ] 优先级评估合理吗？
- [ ] 修复方案可行吗？
- [ ] 有没有遗漏的债务项？

---

### 第七步：修复与验证

**动作**：修复不一致，然后重新校验。

**修复原则**：

| 情况 | 怎么修 |
|------|--------|
| 文档过时，代码是对的 | 更新文档，对齐代码 |
| 代码错了，文档是对的 | 修改代码，对齐文档 |
| 双方都有问题 | 商量好正确的，然后两边都改 |
| 规划未实现 | 要么实现，要么从文档移除 |

**修复后验证**：
- 重新跑一遍校验
- 确认不一致的项都变成了"一致"
- 确认没有引入新的不一致

## 3. 校验维度

### 3.1 接口校验

| 检查项 | 说明 |
|--------|------|
| 函数/方法存在性 | 文档说的函数，代码里有没有？ |
| 参数列表 | 参数名、参数顺序、参数类型、默认值 |
| 返回值 | 返回值结构、字段、类型 |
| 异常 | 可能抛出什么异常？什么情况下抛？ |
| 调用关系 | 谁调用谁？调用链路对不对？ |

### 3.2 功能校验

| 检查项 | 说明 |
|--------|------|
| 功能存在性 | 文档说的功能，代码里实现了吗？ |
| 业务逻辑 | 核心业务逻辑和文档描述一致吗？ |
| 边界条件 | 文档说的边界处理，代码里有吗？ |
| 配置项 | 文档说的配置参数，代码里支持吗？ |

### 3.3 架构校验

| 检查项 | 说明 |
|--------|------|
| 模块划分 | 实际模块划分和文档说的一致吗？ |
| 分层结构 | 分层架构和文档一致吗？ |
| 依赖关系 | 模块依赖和文档描述一致吗？ |
| 数据流 | 数据流向和文档一致吗？ |

### 3.4 配置校验

| 检查项 | 说明 |
|--------|------|
| 配置项存在性 | 文档说的配置项，实际有吗？ |
| 默认值 | 默认值和文档一致吗？ |
| 取值范围 | 取值范围和文档一致吗？ |
| 环境变量 | 环境变量名和文档一致吗？ |

## 4. 与其他方法论的关系

| 方法论 | 关系 | 结合点 |
|--------|------|--------|
| A1 调研法 | 基础 | 调研是校验的前提，没有充分调研就没法校验 |
| 矛盾论 | 指导 | 用矛盾论分析，找到"理论实践不一致"这个主要矛盾 |
| 技术债治理 | 输出 | 校验发现的不一致，转化为技术债 |
| 文档治理 | 目标 | 持续校验，推动文档质量提升 |

## 6. 常见误区

### 误区一：只看代码，不看文档

> ❌ "代码才是事实，文档都是扯淡，不用看"
> ✅ 文档代表设计意图，代码代表实际实现，两者对比才有意义

**后果**：不知道哪些是设计好的，哪些是偏离的，找不到真正的问题。

---

### 误区二：只看文档，不看代码

> ❌ "文档是权威，按文档来就行"
> ✅ 文档可能过时，代码才是实际情况，两者都要看

**后果**：发现不了文档过时的问题，按文档做结果全错。

---

### 误区三：校验太细，工作量爆炸

> ❌ "要校验就把每个细节都校一遍"
> ✅ 抓重点，先校验核心接口和核心功能，边缘的以后再说

**后果**：工作量太大，做不完，最后不了了之。

**判断标准**：优先校验什么？
- 别人会依赖的接口
- 核心业务逻辑
- 容易出问题的地方
- 最近改动过的地方

---

### 误区四：发现问题不改

> ❌ "校验完了，报告写了，完事了"
> ✅ 校验的目的是修复问题，不是写报告

**后果**：问题还是那些问题，校验白做了。
