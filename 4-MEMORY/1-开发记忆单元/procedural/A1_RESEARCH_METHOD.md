## 0. 为什么要调研？

> **没有调研就没有发言权。**
> **没有调研的改动，就是瞎改。**

在我们的项目中，调研的价值尤其突出：

| 不调研的后果 | 调研的价值 |
|------------|-----------|
| 改了 A 影响了 B，不知道为什么 | 提前知道影响范围，做好预案 |
| 以为是根因，其实是表面现象 | 挖到真正的根因，一次解决彻底 |
| 重新发明轮子，做已有的功能 | 站在已有积累的基础上前进 |
| 文档说的和代码做的不一样，踩坑 | 提前发现不一致，避免踩坑 |

**原则**：
- 系统越大，调研越重要
- 改动越核心，调研越要充分
- 不要求一次解决所有问题，但要求解决彻底
- 解决彻底的前提，是调研充分

---

## 1. 调研的 5 个层次

调研不是随便看看代码，而是有层次、有深度地系统了解。

```
L1 表面层：有什么？ — 目录结构、文件列表、接口清单
    ↓
L2 关系层：怎么连？ — 模块关系、调用链路、依赖图
    ↓
L3 逻辑层：为什么？ — 设计意图、核心逻辑、关键算法
    ↓
L4 历史层：怎么来的？ — 演进历史、决策背景、变更记录
    ↓
L5 问题层：有什么问题？ — 技术债、已知 bug、待优化点
```

越深的层次，调研越充分，改动越有把握。

## 2. 标准调研流程

### 第一步：明确调研目标

**动作**：在调研开始前，明确回答三个问题：

| 问题 | 说明 | 示例 |
|------|------|------|
| **调研什么？** | 调研的范围和对象 | 调研 16-调控系统的 auto_exit 模块 |
| **为什么调研？** | 调研的目的和背景 | 要修复 D048 函数不存在的 bug |
| **调研到什么程度？** | 调研的深度要求 | 搞清楚调用链路和依赖关系 |

**输出**：调研目标说明（一两句话就行）

**检查**：
- [ ] 目标是不是明确？会不会太宽泛？
- [ ] 范围是不是清晰？会不会漏？会不会多？
- [ ] 深度要求是不是明确？L2 够了还是要 L4？

---

### 第二步：文档调研

**动作**：先读文档，建立宏观认知。

**调研清单**：

| 文档类型 | 去哪找 | 看什么 |
|---------|--------|--------|
| 系统 README | 子系统根目录 | 系统定位、功能概览、目录结构 |
| 工程索引 ENGINEERING_INDEX | 子系统根目录 | 模块清单、入口文件、依赖关系 |
| 技术设计 TECHNICAL_DESIGN | docs/ | 设计思路、核心逻辑、架构图 |
| API 说明 API_SPEC | docs/ | 接口定义、参数、返回值 |
| 变更记录 CHANGELOG | docs/ | 历史变更、版本演进 |
| 技术债 DEBT_INDEX | 根目录 / 子系统 | 已知问题、待修复项 |

**方法**：
- 先快速浏览，建立整体印象
- 再重点细读，关注相关部分
- 记下文档中的关键信息和疑问点

**输出**：
- 文档调研笔记：关键信息摘要
- 疑问清单：文档没说清的，或者有疑问的

**检查**：
- [ ] 是不是把相关文档都找全了？
- [ ] 有没有文档说的和预期不一样的地方？
- [ ] 哪些地方文档没覆盖到，需要代码验证？

---

### 第三步：代码调研

**动作**：读代码，验证文档说的对不对，搞清楚实际情况。

**调研路径**：

#### 3.1 表面层（L1）：有什么？

- 目录结构：有哪些文件和文件夹？
- 文件列表：每个文件是干什么的？（从文件名猜）
- 入口文件：程序从哪里开始？
- 核心文件：哪些是核心模块？

**工具**：LS、Glob、文件搜索

#### 3.2 关系层（L2）：怎么连？

- 模块依赖：谁 import 谁？
- 调用链路：从入口到目标，经过哪些函数？
- 数据流：数据从哪来，到哪去？
- 外部依赖：依赖哪些外部库和服务？

**工具**：Grep 搜索 import/调用、SearchCodebase

#### 3.3 逻辑层（L3）：为什么？

- 核心逻辑：关键算法和业务逻辑是什么？
- 设计意图：为什么这么设计？
- 边界条件：有什么特殊处理？异常怎么处理？
- 配置参数：有哪些可配置的参数？

**工具**：Read 核心文件、逐函数分析

#### 3.4 历史层（L4）：怎么来的？（可选）

- 变更记录：CHANGELOG、git log
- 注释信息：代码中的注释和 TODO
- 相关文档：TECHNICAL_DESIGN 中的设计背景

#### 3.5 问题层（L5）：有什么问题？

- TODO/FIXME：代码中标记的待办和修复项
- 已知 bug：DEBT_INDEX 中的债务项
- 异味代码：重复、过长函数、命名混乱等

**输出**：
- 代码结构图：模块关系图（文字或图）
- 关键链路：核心调用链路
- 验证结果：文档说的对不对？哪里不一致？
- 问题清单：发现的问题和疑问

**检查**：
- [ ] 是不是搞清楚了模块关系和调用链路？
- [ ] 文档和代码有没有不一致的地方？
- [ ] 核心逻辑是不是理解了？
- [ ] 有没有发现新的问题？

---

### 第四步：运行调研（可选）

**动作**：实际运行一下，观察行为。

**适用场景**：
- 理解动态行为
- 验证静态分析的结论
- 复现 bug

**方法**：
- 加日志，看运行时的数据流
- 单步调试，跟踪执行路径
- 看监控和指标，了解运行状态

**注意**：
- 生产环境要谨慎
- 做好备份和回滚准备
- 不要影响正常运行

---

### 第五步：总结与验证

**动作**：整理调研结果，验证是否达到目标。

**验证标准**：

| 目标层级 | 验证标准 |
|---------|---------|
| L1 表面层 | 能说清有哪些模块、每个大概是干什么的 |
| L2 关系层 | 能画清楚调用链路和依赖关系 |
| L3 逻辑层 | 能讲明白核心逻辑和设计意图 |
| L4 历史层 | 能说出演进过程和决策背景 |
| L5 问题层 | 能列出主要问题和技术债 |

**输出**：调研报告

**检查**：
- [ ] 调研目标达到了吗？
- [ ] 有没有还没搞清楚的关键问题？
- [ ] 文档和代码的不一致都记下来了吗？
- [ ] 发现的新问题都记录了吗？

---

### 第六步：输出调研报告

**动作**：把调研结果写成结构化的报告。

**报告模板**：见第 4 节

**要求**：
- 结构清晰，便于查阅
- 有结论，有依据
- 有问题，有建议
- 方便后续接手的人快速了解

## 3. 调研与矛盾论的结合

调研和矛盾论是黄金搭档：

```
调研（A1） → 搞清楚现状
    ↓
矛盾分析 → 找到主要矛盾
    ↓
制定方案 → 针对主要矛盾制定解决方案
    ↓
执行验证 → 执行并验证效果
```

**为什么调研在前面？**
- 没有充分的调研，矛盾分析就是瞎猜
- 调研越充分，矛盾分析越准确
- 调研本身就可能发现很多问题

**调研中要带着矛盾论的视角**：
- 这个模块的主要矛盾是什么？
- 主要方面和次要方面是什么？
- 哪些问题是表象，哪些是根因？

## 6. 常见误区

### 误区一：上来就改，从不调研

> ❌ "这么简单，不用调研，直接改就行"
> ✅ 再简单的改动，至少也要 L1 调研确认一下

**后果**：改了才发现影响了别的地方，或者根本改的地方就不对。

---

### 误区二：只看文档，不看代码

> ❌ "文档上是这么写的，应该没错"
> ✅ 文档只能参考，代码才是事实

**后果**：按文档改，改完发现代码根本不是那么回事。

---

### 误区三：只看代码，不看文档

> ❌ "直接读代码就完了，文档都是过时的"
> ✅ 文档能帮你快速建立整体认知，理解设计意图

**后果**：只见树木不见森林，读了半天代码还是懵的。

---

### 误区四：调研无限深入，总不行动

> ❌ "还没完全搞懂，再调研调研"
> ✅ 调研到够用就行，剩下的可以边做边确认

**后果**：永远在调研，永远不行动，效率极低。

**判断标准**：能不能回答"这个改动影响范围有多大？风险在哪里？"，能回答就够了。
