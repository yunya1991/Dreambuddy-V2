## PL-001：改动之前先调研，不要上来就改

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-001 |
| **等级** | A（可信级） |
| **验证次数** | 5+ 次 |
| **来源** | 多次技术债治理和 bug 修复实践 |
| **标签** | 流程, 调研, 最佳实践 |

### 描述

任何代码改动之前，先充分调研现状。搞清楚"现在是什么样"，再决定"怎么改"。

### 反面教材

上来就改的后果：
- 改了 A 影响了 B，不知道为什么
- 以为是根因，其实是表面现象
- 重新发明轮子，做了已有的功能
- 文档说的和代码做的不一样，踩坑

### 正确做法

参考 A1 调研方法论：
1. 明确调研目标和范围
2. 先读文档，建立宏观认知
3. 再读代码，验证文档说法
4. 搞清楚模块关系和调用链路
5. 列出问题和风险
6. 再开始动手

### 适用场景

- 修复 bug 之前
- 新增功能之前
- 重构代码之前
- 优化性能之前
- 任何改动代码的操作之前

### 判断标准

调研到什么程度算够？
- 能说清改动的影响范围
- 能说出有哪些风险
- 知道改哪些文件、哪些函数
- 知道改完怎么验证

## PL-002：运行时缺陷优先级高于文档债

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-002 |
| **等级** | A（可信级） |
| **验证次数** | 1 次（D048/D049 优先修复决策） |
| **来源** | 技术债治理优先级决策（2026-07-25） |
| **标签** | 优先级, 技术债, 运行时 |

### 描述

技术债治理中，运行时缺陷（P1）优先级高于文档类技术债（P2/P3）。

### 原因

1. **影响直接**：运行时缺陷直接导致功能失效、系统崩溃
2. **后果严重**：可能造成资金损失、数据丢失
3. **扩散快**：不修复的话，每次运行都可能出问题
4. **文档债可以累积**：文档债影响的是效率，不是正确性

### 优先级排序建议

| 优先级 | 类型 | 典型例子 |
|--------|------|---------|
| **P0** | 生产事故 | 系统崩溃、资金风险 |
| **P1** | 运行时缺陷 | 函数不存在、接口报错、功能失效 |
| **P2** | 架构/设计债 | 架构错位、模块职责不清 |
| **P3** | 文档债 | 文档过时、索引断链、格式不规范 |
| **P4** | 代码风格 | 命名不规范、注释不够 |

### 注意事项

- 不是说文档债不重要，而是优先级有先后
- 运行时缺陷修复后，要回头补文档
- 文档债累积多了也会拖慢效率，要定期偿还

## PL-003：修复 bug 先复现，再动手

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-003 |
| **等级** | A（可信级） |
| **验证次数** | 多次 |
| **来源** | 软件工程通用最佳实践 + 项目经验 |
| **标签** | 调试, bug修复 |

### 描述

修复 bug 之前，先想办法复现它。复现不了的 bug，很难修好。

### 为什么要先复现？

1. **确认 bug 真实存在**：可能是误报、环境问题、操作错误
2. **定位根因**：复现过程中观察现象，找到触发条件
3. **验证修复**：修好后，用同样的步骤验证是否真的修好了
4. **避免瞎改**：复现不了就改，容易越改越乱

### 复现步骤

1. 收集信息：错误信息、日志、触发条件、环境
2. 还原环境：相同的配置、相同的数据、相同的版本
3. 重现步骤：按照报错的操作步骤走一遍
4. 观察现象：记录每次的现象和变化
5. 缩小范围：找到最小复现代码/步骤

### 复现不了怎么办？

- 加日志，等下次出现时收集更多信息
- 检查代码逻辑，从理论上分析可能的原因
- 写测试用例，尝试各种边界条件
- 记录下来，持续观察

## PL-004：调研要文档和代码两边都看，对比校验

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-004 |
| **等级** | A（可信级） |
| **验证次数** | 3+ 次 |
| **来源** | 多次调研踩坑经验 + A8 方法论实践 |
| **标签** | 调研, 文档, A8 |

### 描述

调研时不能只看文档，也不能只看代码，要两边都看，还要对比校验。

### 只看文档的问题

- 文档可能过时
- 文档可能不完整
- 文档可能有错误
- 不知道实际实现是不是一回事

### 只看代码的问题

- 只见树木不见森林
- 不知道设计意图
- 不知道哪些是故意的，哪些是 bug
- 读了半天还是懵的

### 正确做法（A8 方法论的思路）

1. **先读文档**：建立整体认知，知道"应该是什么样"
2. **再读代码**：了解实际情况，知道"实际是什么样"
3. **对比校验**：把文档说法和代码实现一条一条对比
4. **记录不一致**：不一致的地方就是技术债
5. **以代码为准，但理解设计意图**：代码是事实，但文档告诉你为什么这么设计

### 适用场景

- 接手新项目/新模块
- 调研陌生代码
- 做技术债审计
- 做文档-代码对齐检查

## PL-005：大任务拆小，每步可验证

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-005 |
| **等级** | B（待验证） |
| **验证次数** | 2 次 |
| **来源** | 文档统一管理项目 + 记忆系统项目实践 |
| **标签** | 项目管理, 任务拆分 |

### 描述

大任务要拆成小任务，每个小任务都可以独立验证。

### 好处

1. **进度可见**：知道做了多少，还剩多少
2. **风险可控**：每一步出错影响范围小
3. **可以随时停**：做不完也有阶段性成果
4. **容易验证**：小任务验证起来简单
5. **成就感强**：每完成一个都有正反馈

### 拆分原则

- 每个小任务 1-4 小时能完成
- 每个小任务都有明确的产出物
- 每个小任务都可以独立验证
- 任务之间尽量独立，减少依赖

### 例子

**不好的拆分**：
- "搞定文档统一管理"（太大，不知道什么时候算完）

**好的拆分**：
1. 调研现状（2小时）
2. 设计方案（2小时）
3. 建目录结构（1小时）
4. 写规范文档（2小时）
5. 补5个子系统的文档（每个1小时）
6. 更新索引（1小时）
...每个都有明确产出和验证标准

## PL-006：上线/改动前想好回滚方案

| 属性 | 值 |
|------|-----|
| **ID** | GM-LSN-PL-006 |
| **等级** | B（待验证） |
| **验证次数** | 多次（通用最佳实践） |
| **来源** | 软件工程通用最佳实践 |
| **标签** | 发布, 运维, 风险控制 |

### 描述

任何有风险的改动，上线之前都要想好：出问题了怎么回滚？

### 回滚方案的要素

1. **触发条件**：什么情况下需要回滚？
2. **回滚步骤**：具体怎么操作？
3. **回滚时间**：大概需要多久？
4. **验证标准**：怎么确认回滚成功了？
5. **责任人**：谁来执行回滚？

### 常见回滚方式

| 类型 | 回滚方式 |
|------|---------|
| 代码改动 | git revert / git reset |
| 配置改动 | 备份原配置，改回去 |
| 数据库变更 | 写反向迁移脚本 |
| 服务发布 | 切回旧版本 |
| 数据操作 | 提前备份，出问题恢复 |

### 注意事项

- 不是所有改动都需要复杂的回滚方案，但心里要有数
- 改动越核心、影响越大，回滚方案越要详细
- 回滚方案要在改动之前想，出问题再想就晚了
