## 0. 为什么需要记忆系统？

### 0.1 核心问题

当前项目面临的本质挑战不是功能缺失，而是**积累缺失**：

| 现象 | 根因 |
|------|------|
| 换设备/新环境要从头配置 | 没有系统级记忆，配置散落在各处 |
| 同类bug反复出现 | 教训没有沉淀为可检索的记忆 |
| 文档与代码不同步 | 理论和实践之间没有反馈闭环 |
| 新功能从零开始设计 | 历史决策和架构演进脉络丢失 |
| 子系统各自为战 | 经验无法跨系统复用 |

### 0.2 记忆系统的本质

**记忆系统 = 思维链路的基础设施**

它不是简单的"日志存储"，而是让系统具备**阶梯式积累能力**的核心组件：

```
每次工作 → 产生经验 → 沉淀为记忆 → 指导下次工作 → 再产生新经验
    ↑                                                        │
    └────────────────── 阶梯式上升 ──────────────────────────┘
```

## 1. 设计原则

### 1.1 三原则（项目级）

| 原则 | 在记忆系统中的体现 |
|------|-------------------|
| **工业级标准** | 记忆有类型、有结构、有生命周期、有质量审计 |
| **彻底解决+充分调研** | 每条记忆有源、有验证、有归因，不接受模糊记忆 |
| **理论实践一致性** | 文档记忆 ↔ 代码记忆双向校验，A8 理论实践 SKILL 深度集成 |

### 1.2 记忆系统专属原则

1. **分层不越权** — 总记忆只管索引和全局，应用记忆管具体内容
2. **被动更新** — 总记忆不主动修改应用记忆，只通过索引被动感知
3. **来源可追溯** — 每条记忆必须有来源、有时间、有上下文
4. **蒸馏不复制** — 应用记忆 → 总记忆是蒸馏提炼，不是简单复制
5. **可验证可证伪** — 记忆可以被验证、被推翻、被更新
6. **工具化优先** — 记忆的读写、检索、蒸馏都通过标准化接口

## 2. 总体架构

### 2.1 神经传递架构

借鉴人类神经系统的信息传递机制，总记忆与应用记忆之间不是简单的"上下层包含"，而是**双向突触传递**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    总记忆系统（Global Memory）                    │
│  MU-DEV / MU-TRD / MU-DOC / MU-INF                              │
│  ─────────────────────────────────────                          │
│  程序记忆(S) ←────── 阈值上升 ────── 语义记忆(A)                │
│  "开发必须先调研"      (验证≥3)      "这个模式会失败"           │
└─────────────────────────────────────────────────────────────────┘
              ▲                           │
              │ 蒸馏/上升                  │ 检索/激活
              │ (突触强化)                 │ (指令下发)
              │                           ▼
┌─────────────┴───────────────────────────────────────────────────┐
│                 应用记忆系统（Application Memory）                │
│  L4交易记忆 / 风控记忆 / 运维记忆 ...                             │
│  ─────────────────────────────────────                          │
│  语义记忆(A) ←────── 内部提炼 ────── 情景记忆(B/C)              │
│  "趋势向上LONG胜率高"              "某次BTC交易盈利15%"         │
└─────────────────────────────────────────────────────────────────┘
```

**核心设计**：
- **总记忆不替代应用记忆**：总记忆存"规则摘要"，应用记忆存"原始案例"，层级不同
- **上升需要阈值**：应用记忆中的内容必须达到验证阈值才能上升到总记忆
- **下降是检索激活**：总记忆需要细节时，通过索引查询应用记忆，而非复制数据
- **突触权重动态**：传递强度与验证次数成正比，长期不用则衰减

### 2.1.1 上升路径（应用记忆 → 总记忆）

| 阶段 | 应用记忆层 | 动作 | 总记忆层 | 阈值条件 |
|------|-----------|------|---------|---------|
| 1 | 产生新case/review | 记录事件 | — | — |
| 2 | 内部蒸馏（distill） | 提取模式 | — | — |
| 3 | 模式被验证 | **达到阈值** | 接收为语义记忆 | 验证≥1次 + A8通过 |
| 4 | 规则长期验证 | **再次达到阈值** | 上升为程序记忆 | 验证≥3次 + 无冲突 + 多场景 |

**阈值公式**（详见 §6 证明算法）：
```
confidence = (verify_count × quality_weight × time_decay) / (conflict_count × 2 + 1)
≥ 0.7 → 上升为语义记忆(A)
≥ 0.85 → 上升为程序记忆(S)
```

### 2.1.2 下降路径（总记忆 → 应用记忆）

不是"复制下发"，而是**检索激活**：

```
总记忆查询："趋势向上时怎么交易？"
    │
    ▼
路由到 MU-TRD → MU-TRD-CORE："趋势向上LONG胜率更高"
    │
    ▼
需要详细信息 → 查询 L4 应用记忆接口
    │
    ▼
L4 返回具体 case + review + distill
    │
    ▼
AI 基于"总记忆规则框架" + "应用记忆案例细节" 进行决策
```

**关键约束**：总记忆只存规则摘要和索引路径，不缓存应用记忆的具体数据。

### 2.2 记忆分层体系（含传递路径）

```
L0 元记忆层（Meta-Memory）← 管理整个记忆系统的"神经系统"
    └── 记忆类型定义、记忆单元规范、证明算法参数
        │
        │ 配置/调参（人工维护）
        ▼
L1 总记忆层（Global Memory）← "大脑皮层"：抽象规则 + 全局索引
    ├── MU-DEV：开发程序记忆（S级）+ 语义记忆（A级）
    ├── MU-TRD：交易程序记忆（S级）+ 语义记忆（A级）
    ├── MU-DOC：文档程序记忆（S级）+ 语义记忆（A级）
    └── MU-INF：信息程序记忆（S级）+ 语义记忆（A级）
        │
        │ ↑ 蒸馏/上升（需阈值）
        │ ↓ 检索/激活（实时查询）
        │
L2 应用记忆层（Application Memory）← "感觉/运动皮层"：原始数据
    ├── 交易应用记忆 L4：case / review / distill / stats
    ├── 风控应用记忆：规则库 / 告警历史 / 演化记录
    ├── 运维应用记忆：部署记录 / 监控事件 / 故障复盘
    └── 实验应用记忆：实验设计 / 结果数据 / 参数调优
        │
        │ ↑ 内部提炼（应用层自主）
        │
L3 即时记忆层（Working Memory）← "当前神经冲动"：LLM上下文
    ├── 当前会话注入的 MU-xxx-CORE.md
    ├── 当前检索到的应用记忆片段
    └── 当前任务中间状态
```

**传递规则**：
- **L2 → L1（上升）**：必须达到阈值，详见 §2.1.1
- **L1 → L2（下降）**：检索激活，不复制数据，详见 §2.1.2
- **L2 内部**：应用记忆自主提炼（如 L4 的 distill），无需总记忆干预
- **L0 → L1/L2**：元记忆调整参数（如阈值、容量配额），人工维护

### 2.3 与现有系统的关系

| 现有系统 | 新定位 | 改造方向 |
|---------|--------|---------|
| 4-MEMORY/ | **总记忆系统主体** | 从设计文档升级为可执行的记忆引擎 |
| 11-易经推理系统/memory_l4/ | **交易应用记忆（标杆）** | 规范化接口，纳入总记忆索引 |
| dreamos/core/memory/ | **编排/执行应用记忆** | 合并到总记忆的架构记忆 + 运维记忆 |
| experiments/ab-trading/memory/ | **实验应用记忆** | 规范化，纳入总记忆索引 |
| 0-系统文档管理/ | **文档记忆的一部分** | 总记忆通过索引引用 |

## 3. 总记忆系统（Global Memory）

### 3.1 定位

总记忆系统是**全项目的记忆中枢**，但它是一个"瘦中枢"：

- ✅ **管什么**：全局原则、方法论、架构、通用经验、应用记忆索引
- ❌ **不管什么**：子系统的具体交易案例、具体参数、具体运行数据

### 3.2 核心能力

| 能力 | 说明 |
|------|------|
| **索引服务** | 统一检索入口，路由到对应应用记忆系统 |
| **蒸馏汇聚** | 从各应用记忆中提炼通用经验，上升为总记忆 |
| **原则管理** | 维护项目级工程原则、开发规范、工作流 |
| **方法论库** | 维护矛盾论、A1/A8 等方法论的应用模板 |
| **架构记忆** | 维护系统架构的历史演进和决策脉络 |

### 3.3 记忆类型

#### 3.3.1 原则记忆（Principles Memory）

**来源**：项目决策、架构评审、技术债治理

**内容**：
- 工程原则：代码规范、测试要求、CI/CD 标准
- 开发工作流：需求→调研→设计→实现→验证→发布→复盘
- 质量标准：文档质量、代码质量、测试质量的量化标准
- 安全红线：不可触碰的安全/合规底线

**格式**：结构化 Markdown + 版本号 + 生效日期

#### 3.3.2 方法论记忆（Methodology Memory）

**来源**：A1/A8 等 SKILL 的实践经验蒸馏

**内容**：
- 矛盾论应用模板：如何识别主要矛盾、次要矛盾
- A1 调研方法论：调研步骤、验证标准、输出模板
- A8 理论实践校验法：文档-代码对齐检查清单
- 问题诊断方法论：根因分析 5 问法、故障排查路径

**格式**：方法论模板 + 应用案例索引 + 效果统计

#### 3.3.3 架构记忆（Architecture Memory）

**来源**：架构设计文档 + 架构决策记录（ADR）

**内容**：
- 当前系统架构图
- 架构演进历史（v1.0 → v2.0 → ...）
- 架构决策记录（ADR）：每个决策的背景、选项、决策理由、后果
- 模块依赖图
- 接口契约列表

**格式**：架构图 + ADR 列表 + 依赖图数据

#### 3.3.4 文档记忆（Doc Memory）

**来源**：0-系统文档管理/ 的索引

**内容**：
- 全项目文档索引（与 INDEX.md 同步）
- 文档技术债清单（与 DOC_DEBT_INDEX.md 同步）
- 文档质量审计记录
- 文档-代码对齐状态

**格式**：结构化索引 + 状态标记 + 最后校验时间

#### 3.3.5 通用经验记忆（Lessons Memory）

**来源**：各应用记忆蒸馏的通用教训

**内容**：
- 技术教训：API 踩坑、配置陷阱、性能陷阱
- 流程教训：哪些步骤容易遗漏、哪些环节容易出问题
- 最佳实践：经过验证的高效做法
- 反模式：经过验证的错误做法

**格式**：每条教训 = 描述 + 来源 + 验证次数 + 适用场景

#### 3.3.6 应用记忆索引（App Memory Index）

**来源**：各应用记忆系统注册

**内容**：
- 应用记忆系统列表
- 每个系统的：名称、定位、存储位置、接口、更新频率
- 记忆类型映射：什么类型的查询应该路由到哪个应用记忆
- 健康状态：最后心跳时间、数据新鲜度

**格式**：注册表 + 路由表 + 健康状态

## 4. 应用记忆系统（Application Memory）

### 4.1 定位

应用记忆系统是**子系统专属的记忆仓库**，由各子系统主动维护：

- ✅ **管什么**：本子系统的具体案例、参数、经验、运行数据
- ❌ **不管什么**：跨系统的通用原则、全局架构

### 4.2 统一接口规范

所有应用记忆系统必须实现以下标准接口：

| 接口 | 功能 | 输入 | 输出 |
|------|------|------|------|
| `search(query, filters, memory_type, top_k)` | 检索记忆 | 查询词 + 过滤条件 + 记忆类型 + 返回数量 | 记忆条目列表 |
| `add(memory_entry)` | 添加记忆 | 记忆条目（符合类型规范） | 记忆 ID |
| `update(id, updates)` | 更新记忆 | 记忆 ID + 更新字段 | 成功/失败 |
| `get(id)` | 获取单条 | 记忆 ID | 完整记忆条目 |
| `stats()` | 统计信息 | - | 记忆数量、类型分布、更新频率 |
| `distill_candidates()` | 蒸馏候选 | - | 可上升为总记忆的候选列表 |
| `healthcheck()` | 健康检查 | - | 状态 + 最后更新时间 |

> **注**：`search` 的 `memory_type` 和 `top_k` 参数为可选参数（有默认值），核心输入仍为 `query` 和 `filters`。

#### 接口语义隔离原则

**关键约束：`filters` 的字段语义由各应用记忆系统自行定义，总记忆系统不规定具体字段名。**

这是统一接口不变成领域耦合的关键设计：

| 应用记忆 | filters 示例 | 说明 |
|---------|-------------|------|
| AM-TRD-001 交易记忆 | `{"inst_id": "BTC", "regime": "trending"}` | 交易领域语义 |
| AM-RSK-001 风控记忆 | `{"rule_type": "drawdown", "severity": "critical"}` | 风控领域语义 |
| AM-OPS-001 运维记忆 | `{"alert_type": "cpu", "host": "node-3"}` | 运维领域语义 |
| AM-EXP-001 实验记忆 | `{"experiment_id": "ab-042", "status": "completed"}` | 实验领域语义 |

**规则**：
1. 总记忆系统路由查询时，只传 `query` + `filters` 原文，不解释 `filters` 内部字段
2. 各应用记忆系统自行解析 `filters`，不识别的字段忽略而非报错
3. 标杆实现（AM-TRD-001）中的 `inst_id`、`regime` 等字段**不是**规范要求，而是交易记忆的业务字段
4. 新接入的应用记忆系统应在其文档中声明自己支持的 `filters` 字段集

## 5. 核心机制

### 5.1 索引与路由

```
用户查询 → 总记忆系统
            │
            ├── 匹配总记忆内容？→ 直接返回
            │
            └── 需要应用记忆？→ 查询应用记忆索引
                                    │
                                    ├── 单应用匹配 → 路由到对应应用记忆
                                    ├── 多应用匹配 → 并行查询，聚合结果
                                    └── 无匹配 → 返回总记忆中的相关通用经验
```

### 5.2 蒸馏与上升

```
应用记忆产生新经验
        │
        ▼
  蒸馏候选生成（应用记忆侧）
        │
        ▼
  总记忆系统审核（人工/自动）
        │
        ├── 通过 → 提炼为通用经验，存入总记忆
        ├── 待定 → 标记观察，等更多验证
        └── 驳回 → 保留在应用记忆中，不上报
```

### 5.3 被动更新机制

总记忆系统**不主动修改**应用记忆，更新通过以下方式感知：

1. **心跳上报**：应用记忆定期上报状态和统计数据
2. **蒸馏候选上报**：应用记忆主动提交可上升的经验
3. **索引同步**：应用记忆的结构变化同步更新总记忆的索引
4. **按需拉取**：总记忆在需要时，通过标准接口查询应用记忆

### 5.4 记忆生命周期

```
创建 → 验证 → 活跃 → 衰减 → 归档 → 删除
  │       │       │       │       │
  │       │       │       │       └── 超过保留期，移入归档
  │       │       │       └── 长期未被引用，降低优先级
  │       │       └── 被检索和引用，保持活跃
  │       └── 经过实践验证，标记为可信
  └── 从经验/案例/决策中产生
```

### 5.5 记忆质量分级

| 等级 | 说明 | 验证要求 |
|------|------|---------|
| S（公理级） | 经过大量验证的基本原则 | ≥10 次独立验证 |
| A（可信级） | 经过多次验证的经验 | ≥3 次独立验证 |
| B（待验证） | 有一定证据但需更多验证 | 1-2 次验证 |
| C（假设级） | 初步观察或推测 | 未验证 |
| D（已证伪） | 被证明错误或过时 | 已证伪 |

## 6. 记忆容量与压缩机制

> **借鉴**：Hermes 的 Tier 1 容量限制设计（MEMORY.md ≤ 2,200 字符，80% 时触发 consolidation）
> **核心思想**：架构可以复杂，但核心记忆必须精炼——通过持续优化存储方式，确保最关键的记忆始终在容量内

### 6.1 为什么要限制容量？

| 不限制的问题 | 限制后的好处 |
|------------|------------|
| 记忆无限膨胀，检索变慢 | 检索始终高效 |
| 低价值记忆淹没高价值记忆 | 核心记忆始终可见 |
| 总记忆加载成本持续增长 | 加载成本可控且稳定 |
| 记忆间矛盾累积难发现 | 定期压缩暴露矛盾 |

**本质**：容量限制不是约束，而是**倒逼记忆质量提升的驱动力**。

### 6.2 三级容量架构

借鉴 Hermes 三层设计，适配我们的双层架构：

```
┌──────────────────────────────────────────────────────┐
│  Tier 0：核心记忆（Core Memory）                       │
│  容量：≤ 8,000 字符（约 200 行 Markdown）              │
│  内容：S/A 级原则 + 方法论 + 关键架构决策               │
│  触发：每次会话注入，始终在上下文中                      │
│  压缩：≥ 80% 时触发 consolidation                      │
├──────────────────────────────────────────────────────┤
│  Tier 1：扩展记忆（Extended Memory）                   │
│  容量：≤ 50,000 字符                                   │
│  内容：A/B 级经验教训 + 文档索引 + 应用记忆索引          │
│  触发：按需检索，不常驻上下文                           │
│  压缩：≥ 80% 时触发蒸馏                               │
├──────────────────────────────────────────────────────┤
│  Tier 2：归档记忆（Archive Memory）                    │
│  容量：不限                                            │
│  内容：C/D 级 + 已归档 + 历史版本 + 详细案例            │
│  触发：显式查询才返回                                  │
│  压缩：定期清理超期记忆                                │
└──────────────────────────────────────────────────────┘
```

### 6.3 各 Tier 对应的存储位置

| Tier | 对应目录 | 核心文件 |
|------|---------|---------|
| Tier 0 | `4-MEMORY/CORE.md` | 单文件，≤ 8,000 字符 |
| Tier 1 | `4-MEMORY/1-原则记忆/` ~ `5-通用经验/` | 各分目录下的 Markdown 文件 |
| Tier 2 | `4-MEMORY/archive/` | 归档目录 + 应用记忆原始数据 |

### 6.4 压缩机制（Consolidation）

**触发条件**：Tier 0 或 Tier 1 使用量 ≥ 80% 容量上限

**压缩流程**：

```
检测容量超阈值
    │
    ▼
扫描所有记忆条目
    │
    ├── S/A 级 + 高频引用 → 保留（压缩表达，不删内容）
    ├── B 级 + 有新验证 → 评估是否升级
    ├── B 级 + 长期未验证 → 降级到 Tier 1 或 Tier 2
    ├── C 级 → 蒸馏合并（多条 C 级合并为一条 B 级）
    ├── D 级 → 移入归档（Tier 2）
    ├── 重复/矛盾记忆 → 合并或保留高等级版本
    └── 过时记忆 → 归档
    │
    ▼
执行压缩
    │
    ├── Tier 0 → 重写 CORE.md（保留最精华的 S/A 级内容）
    ├── Tier 1 → 蒸馏低等级记忆，合并相似条目
    └── Tier 2 → 清理超期归档
    │
    ▼
验证压缩后容量 < 60%
```

**压缩原则**：
1. **压缩表达而非删减内容** — "subprocess+shlex.split会失败，用shell=True" 比 "subprocess.run(shlex.split(cmd), env=env) 在设置 PYTHONPATH 等 env 时会解析失败..." 更好
2. **合并相似条目** — 3条关于文档不同步的教训 → 1条"文档必须与代码同步更新"
3. **低等级让位高等级** — C级假设腾出空间给A级经验
4. **保留索引，归档详情** — Tier 0只保留结论，详细案例和验证记录放Tier 2

### 6.5 CORE.md 结构规范

```markdown
# Core Memory — 核心记忆

> 容量: ≤ 8,000 字符 | 上次压缩: YYYY-MM-DD | 当前占用: XX%
> 此文件是系统的常驻记忆，每次会话自动注入

## 工程原则（S级）
- [原则条目，每条一行，简洁表达]

## 方法论要点（A级）
- [方法论核心要点]

## 关键架构决策（A级）
- [架构决策摘要]

## 通用经验 Top 10（A/B级）
- [最常引用的经验教训]

## 当前技术债焦点
- [当前正在处理的关键技术债]
```

### 6.6 Nudge 机制（周期性整理）

借鉴 Hermes 的 periodic nudge，适配我们的场景：

| 触发方式 | 频率 | 动作 |
|---------|------|------|
| 会话开始时 | 每次会话 | 检查 CORE.md 容量，超 80% 触发压缩 |
| 工作完成时 | 每次任务结束 | 检查是否产生新的值得常驻的记忆 |
| 定期审计 | 每周 | 扫描 Tier 1 衰减记忆，评估是否降级或归档 |
| 定期清理 | 每月 | 清理 Tier 2 超期归档 |

### 6.7 容量与质量的闭环

```
容量压力
    │
    ▼
触发压缩 ─────────────────────────────┐
    │                                  │
    ▼                                  │
低质量记忆被压缩/合并/归档              │
    │                                  │
    ▼                                  │
释放空间 ←──────────────────────────────┘
    │                       倒逼
    ▼                      质量提升
新记忆写入 ──→ 需要更高验证等级才能占据核心空间
```

**关键洞察**：容量限制使记忆竞争空间 → 只有高质量记忆能留在核心 → 倒逼每条记忆都被充分验证 → 整体质量持续上升。

## 7. 核心工作流：工程开发闭环模型

> **核心思想**：这是连接“传统文档系统”与“AI记忆系统”的唯一通道，是实现 A8（理论与实践结合）SKILL 的落地方式。

### 7.1 双系统关系

| 系统 | 定位 | 面向对象 | 核心诉求 |
|------|------|---------|---------|
| **传统文档系统** (0-系统文档管理) | **理论知识载体** | 人类开发者 | 工业级标准、完整性、可读性 |
| **AI记忆系统** (4-MEMORY) | **AI上下文索引** | AI Agent | 高效性、结构化、动态性 |

### 7.2 闭环循环流程

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  1. 理论沉淀（蒸馏上行）                                          │
│  ┌──────────────────┐    蒸馏     ┌──────────────────┐            │
│  │  传统工程文档     │ ──────────▶ │  AI 记忆 (CORE)  │            │
│  │  (规范/API/设计)  │   压缩     │  (原则/方法论/索引) │            │
│  └──────────────────┘             └──────────────────┘            │
│                                                                  │
│  2. 实践应用（代码生成）                                          │
│  ┌──────────────────┐   检索文档  ┌──────────────────┐            │
│  │  AI Agent        │ ──────────▶ │  代码实现 (Practice)│           │
│  │  (读取CORE记忆)   │   执行开发  │  (创建/修改文件)   │            │
│  └──────────────────┘             └──────────────────┘            │
│                                                                  │
│  3. 理论更新（反向蒸馏）                                          │
│  ┌──────────────────┐  代码审查   ┌──────────────────┐            │
│  │  代码变更 (实践)   │ ──────────▶│  更新工程文档 (修正)│            │
│  │  (完成开发)       │  A8校验    │  (API_SPEC/CHANGELOG)│           │
│  └──────────────────┘             └──────────────────┘            │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 7.3 关键桥接动作（蒸馏）

| 方向 | 触发时机 | 执行逻辑 |
|------|---------|---------|
| **上行** (文档→记忆) | 人工创建/修改传统文档后 | 提取核心结论、原则、索引，压缩写入 `4-MEMORY` 下对应分目录或直接更新 `CORE.md` |
| **下行** (记忆→文档) | AI Agent 根据记忆找到文档路径时 | 直接读取 `0-系统文档管理` 或子系统下的原始 Markdown 文档作为开发上下文 |
| **反向** (代码→文档) | AI 完成代码编写后 | 必须执行 A8 校验流程：对比新代码与现有 `API_SPEC.md`，如有不一致则更新文档 |

### 7.4 设计原则

1. **单向不冲突**：传统文档是 SSoT (Single Source of Truth)，AI 记忆只是其摘要/索引，不与原文竞争
2. **被动更新**：AI 记忆不需要独立的维护流程，它的内容变化完全依赖于传统文档的变更
3. **动态路由**：AI 记忆中存储的是路径和索引，AI 在需要详细信息时，动态读取完整的传统文档内容

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 记忆膨胀，检索变慢 | 性能下降 | 三级容量架构 + consolidation 压缩 + 定期归档 |

| 应用记忆不配合上报 | 总记忆信息不全 | 接口规范强制执行 + 健康检查 + 激励机制 |
| 维护成本过高 | 资源消耗大 | 自动化工具优先 + 渐进式建设 |
| 与现有系统冲突 | 迁移困难 | 兼容现有接口 + 渐进式迁移 |
