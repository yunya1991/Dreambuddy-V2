# 第一部分：SPEC-33-反思层 v0.2 评审

## 一、Journal-Fit Reviewer（目标适配性）

**适配度**: 4/5。反思层解决的是 REA 当前真实缺口——分析结论质量无系统性检验机制，PoE 门禁只审计产出不改进策略。内外结合设计（内部做梦 + 外部成熟项目路径）与 Dream-RSI 论文形成明确差异点，非简单复刻。

**优点**:
1. 衔接点全部基于已核实的真实接口（DSH_NODE_REGISTRY 8 节点、compute_poe_score、Evidence 结构）
2. FAIL-OPEN 降级设计贯穿始终，不阻断现有能力
3. A8 机制的量化移植（批评准确率≥70%、回滚条件）可证伪

**不足**:
1. **M1（Major）冷启动数据缺失**：SPEC §4.4 验收标准要求『回放模拟器可加载 acceptance_bundles 两个历史包并完成确定性重放』，但经核实验收包内是 wrapup_report.md/fix.diff/acceptance_report.md/run_repro.py 等报告与脚本文件，**不含发现树结构数据**（无节点快照、无执行轨迹、无逐节点评分）。该验收标准当前不可达。
   - **建议**：P1 阶段先定义发现树 Schema（JSON：节点/父指针/证据引用/poe_score/成本），并明确冷启动路径——新分析任务开始记录发现树（增量积累），验收包仅作为初始种子案例（人工转换为最小发现树），删除『加载验收包完成确定性重放』的验收表述或降级为可选目标。

## 二、方法评审（方法论严谨性）

**M2（Major）策略空间未定义**：SPEC §8 声称『分析策略以可执行代码形式存在，需约束重写范围』，但未定义策略空间——REA 当前分析器（python_analyzer/call_chain_tracer 等）是固定代码，哪些参数/分支/编排属于『可变策略』完全未界定。做梦评估循环评估的候选策略从何而来、policy-development agent 重写什么，均无法实施。
- **建议**：明确策略表示为『分析编排配置』（分析器选择/执行顺序/深度参数/停止条件/并行度）而非分析器代码本身，候选策略由配置变换生成；分析器代码保持不变，符合『base agent 不变』原则。

**M3（Major）回放目标函数不可计算**：V = 归一化 hypervolume − λ×并行度惩罚，但 hypervolume 计算需要明确参考点与归一化基准；且单次分析的质量是标量 poe_score，成本是标量调用数，二维 Pareto 前沿在单次任务上退化为单点，hypervolume 无意义。
- **建议**：明确 hypervolume 在『一棵发现树的多个节点（质量,累积成本）点集』上计算，参考点取 (0, 总预算)，归一化到 [0,1]；λ 给出取值方法（如 λ=0.1 起步，观察期调优）。

**Minor 意见**:
- m1: 观察期时长未定义（A8 为 14 天/7 天，反思层应给出对应值，建议改进建议观察 3 个分析任务周期）
- m2: E1 批评准确率验证的『人工标注』成本未评估，建议改为『独立第二分析器交叉验证 + 抽样人工复核』
- m3: 18 采集器 B7 四门禁引用正确，但 rea_mature_project 采集器的 DataRecord 字段映射未定义
- m4: 30 系统三重验证中『截图验证』对外部项目场景不适用（无 UI），应裁剪为网络+内容+交叉三重

## 三、Devil's Advocate

**最高分 4（需让步修改）**：『外部成熟项目的设计决策还原质量依赖 REA 自身分析能力，而 REA 分析能力正是待改进对象——用未验证的能力生成训练数据改进自身，存在自举循环风险。』
- **让步修改**：外部解析树注入前必须过 PoE 门禁 + 30 系统交叉验证（SPEC 已有），另需补充：外部树在回放池中标记 provenance=external，做梦评估时外部树权重初始为 0.5，随验证通过率动态调整。

## 四、7 模式阻断

6/7 通过。需整改：**模式『未定义即使用』**——『发现树』『策略』『做梦』在 SPEC 中首次出现时未给出可计算定义（M1/M2 已覆盖），修订后通过。

# 第二部分：SPEC-33-输出场景-意图系统 v0.2 评审

## 一、Journal-Fit Reviewer（目标适配性）

**适配度**: 5/5。两个输出方向的衔接点全部经代码核实：okr_nodes 的 engineering_okr 通道真实存在且优先消费、rea_cdrive_adapter 的 P4 降级链真实存在、active_training_collector 的 REA Provider 真实注册。闭环设计与 34 系统三种训练机制对接准确。

**优点**:
1. 现有 A/C 层契约零改动，REA 仅作新增供给源，架构风险低
2. 训练闭环的正负样本设计（负样本入库率 100%）符合增量学习最佳实践
3. 闭环自增强失控风险有明确约束机制（观察期/回滚/独立验证）

**不足**:
1. **M1（Major）Spec 增强的生成机制未定义**：s33_rea_spec_enhance 从『成熟项目解析树』到『增强 Spec』的转化是规则拼接还是 LLM 生成？若是 LLM 生成，与 rea_cdrive_adapter 的『零 token』设计哲学关系如何？成本与确定性如何保证？
   - **建议**：明确为两段式——证据提取（规则，零 token：从解析树抽取设计决策/架构约束/ADR）+ Spec 组装（LLM 单次生成，输入含证据包，输出过 PoE 门禁），并给出 token 预算上限。

## 二、方法评审（方法论严谨性）

**M2（Major）E-T1/E-T2 实验设计不完整**：闭环开启 vs 关闭的对比实验未定义周期、样本量与统计方法；训练效果归因存在混杂变量（同期其他改进）。
- **建议**：E-T1 定义为 4 周窗口、按周分桶对比验收通过率，使用比例检验；E-T2 定义回放池规模与 V 值的散点相关性分析，报告相关系数与显著性。

**M3（Major）s33_rea_optimal_path 的触发成本与 C-Drive 延迟预算冲突**：每节点完成后触发策略评估，若评估依赖回放池检索与 V 值计算，单次延迟可能超过 C-Drive 决策预算（现有 P4 适配器为毫秒级规则推导）。
- **建议**：分层触发——轻量层（规则检索，<100ms，对齐 P4 模式）默认触发；重量层（回放池检索+V 值排序）仅在验收失败/低置信度/用户显式调用时触发（SPEC §9 已有触发条件表述，需明确双层延迟预算）。

**Minor 意见**:
- m1: decision_deriver 阈值对接（<0.3 REDO / <0.6 INSERT_BEFORE / >=0.6 CONTINUE）经核实与实际代码一致，无需修改
- m2: 训练案例 Schema 字段已列出但未定义 JSON Schema 与 TDR case_bank 的字段映射
- m3: Q6 依赖 Q5 但 E-T1 需 4 周观察窗口，实施路线应标注 Q6 含 4 周实验期
- m4: 『S 级优先级触发』引用自 run_continual_training v0.5，建议在 SPEC 中注明该机制来源，避免与反思层『S 层』术语混淆

## 三、Devil's Advocate

**最高分 3（需补充说明）**：『闭环的『模型改进→输出质量提升』假设未验证——34 系统训练的是前端模型，其改进是否传导到 REA 输出质量，因果链过长。』
- **让步修改**：E-T1 实验需同时报告中间指标（策略评估命中率）与最终指标（OKR 验收通过率），若中间指标改善而最终指标不动，闭环需重新评估传导链路。

## 四、7 模式阻断

6/7 通过。需整改：**模式『引用即真实』**——训练闭环章节引用的三种训练机制均真实存在（已核实），但『TDR 中央训练数据仓库』的 case_bank_server.store_case 接口契约未在 SPEC 中给出字段映射（m2 已覆盖），修订后通过。
