## 二、逐项明细

### C1. 中文分词方案指定【P0】

- **问题**: L2 倒排索引对中文文本必须分词，SPEC 未指定方案，直接阻塞 P1 实施。
- **解决方案**: 指定 jieba（精确模式）为默认分词器；英文按空白+驼峰拆分；混合文本统一小写归一化。分词器作为 core/chunker.py 的下游组件，接口可替换（预留 HanLP 适配位）。
- **落点**: SPEC §2.2 / §3（core 新增 tokenizer.py）
- **验收**: SPEC 明确分词器选型与归一化规则；分词单测覆盖中英混合用例。

### C2. 索引 schema 版本与迁移策略【P0】

- **问题**: 索引库升级（如 v0.3 新增 chunks 表）无版本管理与兼容策略，升级即重建风险。
- **解决方案**: SQLite 库内建 meta 表记录 schema_version；启动时校验版本，不兼容版本触发自动全量重建（rebuild），兼容版本走增量迁移；重建前保留旧库为 .bak。
- **落点**: SPEC §4.1（新增 meta 表）+ §5.2（status() 返回 schema_version）
- **验收**: 版本不匹配场景有明确行为定义；.bak 保留策略写入文档。

### C3. 并发写入模式定义【P0】

- **问题**: SQLite 单写者限制下，多调用方（前端 API / Agent / 定时任务）并发写索引的行为未定义。
- **解决方案**: 启用 WAL 模式；写操作统一经单写队列串行化（进程内锁 + busy_timeout）；读操作并发无限制；跨进程写通过文件锁互斥。
- **落点**: SPEC §4.1（存储引擎约定）
- **验收**: 并发读写行为、锁策略、超时参数在 SPEC 中有明确定义。

### C4. 增量触发机制决断【P1】

- **问题**: L1 更新频率写『fs 事件或按需』二选一未决，实施时会产生分歧。
- **解决方案**: 决断为『按需 + 定时兜底』——检索前惰性校验（mtime 快速比对）+ 每小时定时全量对账；不引入 fs 事件监听（watchdog 依赖与跨平台成本高于收益）。
- **落点**: SPEC §2.2（L1 更新频率改写）
- **验收**: 触发机制唯一且明确；惰性校验的耗时预算（<10ms/千文件）写入验收标准。

### C5. 权限模型定义【P1】

- **问题**: 『search_api 层按调用方身份过滤』仅一句带过，身份来源与过滤规则未定义。
- **解决方案**: 调用方分两类——前端用户（经 NextAuth 会话，按用户可见范围过滤）与内部 Agent（DSH 链路，全量可见，需内部调用凭证）；过滤在 search_api 入口统一执行，索引层不过滤。
- **落点**: SPEC §5（新增 5.5 权限模型小节）
- **验收**: 两类调用方的身份来源、可见范围、过滤执行位置均有定义。

### C6. 可观测性与测试计划章节【P1】

- **问题**: 无独立章节，仅风险表提及单测。
- **解决方案**: 新增 §可观测性（索引健康度指标：文件数/新鲜度/对账差异/检索耗时 P95，纳入 status() 输出与日志）与 §测试计划（分层：分块/分词/检索单测 + 增量更新/对账集成测试 + 并发场景测试）。
- **落点**: SPEC 新增两章
- **验收**: 指标清单与测试分层矩阵完整；沿用工程 Jest/pytest 体系。

### A1. search_api 部署形态定义【P0】

- **问题**: Python 库直调 vs HTTP 服务未决，影响前端与 7 号中台接入方式。
- **解决方案**: 双形态——默认 Python 库直调（进程内，Agent/脚本场景）；HTTP 形态由 Next.js API Route 封装（前端场景），不独立部署 Python HTTP 服务，避免新增运维面。
- **落点**: SPEC §5.3（改写为部署形态小节）
- **验收**: 两类消费方的接入路径图明确；无独立 HTTP 服务部署项。

### A2. 无标题文档分块兜底策略【P1】

- **问题**: chunker 依赖 markdown 标题结构，代码文件/纯文本无标题时行为未定义。
- **解决方案**: 分块边界优先级——标题层级 > 空行段落 > 固定行数窗口（兜底，256 行）；代码文件按函数/类定义行切分（正则识别 def/class/function/export）。
- **落点**: SPEC §2.2（L2 语义分块要求补充）
- **验收**: 三级兜底策略明确；代码分块规则有正则定义。

### M1. 两段式链路数据对象语义澄清【P0】

- **问题**: 41 索引案例文档（md 文件），案例库精排结构化案例（TDR 记录），两者非同一数据集，『41 召回 → 案例库精排』存在实施歧义。
- **解决方案**: 澄清为**补充注入**语义——CaseBankClient.retrieve 仍为案例库主候选源；41 的 recall() 结果（案例文档命中）作为**补充候选**注入精排池，不替代主链路；两路候选在 Soft Q 打分前合并去重。
- **落点**: SPEC §7.6（改写两段式链路描述）
- **验收**: 主候选源/补充候选源/合并时机三要素明确；无『替代 CaseBankClient』的歧义表述。

### M2. TDR 豁免条款【P0】

- **问题**: §7.8『禁止业务模块自建全文索引』与案例库 solution_case_bank.db 自带检索能力冲突。
- **解决方案**: 增加豁免条款——TDR（solution_case_bank.db）属**结构化业务数据存储**（案例记录的存取与统计），非全文索引，不在禁止范围；禁止范围限定为『对文件系统文档构建第二份全文倒排索引』。
- **落点**: SPEC §7.8（补充豁免定义）
- **验收**: 禁止条款的适用范围有精确定义；TDR 场景明确豁免。
