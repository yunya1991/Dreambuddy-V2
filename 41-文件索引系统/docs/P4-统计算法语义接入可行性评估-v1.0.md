# P4 预研 — 300+ 统计算法语义接入可行性评估

> 日期：2026-11-15  
> 范围：评估 54 方法库的自然语言语义路由，不在 SPEC-41-L1 P4 内实现。  
> 结论：**有条件可行，建议先做高频能力族的两阶段 PoC；不建议把 386 个方法平铺为 386 个顶层 L1 意图。**

## 1. 现状核查

1. [registry.py](../../54-L1架构能力聚合层/l1agg/methods/registry.py) 的目录容量为 core 238、research 149，总计 387；`all_specs()` 可作为后续评估单元的目录来源。
2. [method_audit.json](../../54-L1架构能力聚合层/docs/method_audit.json) 记录已实现 386、审计通过 386、失败 0；但这只证明算法执行实现状态，不等于自然语言路由语料已就绪。
3. `MethodSpec` 当前包含名称、分组、输入类型、样本门禁、输出 schema 和执行函数，没有 `examples` / `examples_zh` 字段；SPEC 子文档中“示例来自 54 注册表”的前提目前不成立，需要补独立语料。
4. 自检覆盖并不完整：总检查覆盖率约 66.15%，determinism 执行率约 36.27%，synthetic 执行率约 27.98%。语义接入不能替代算法本身的统计验证。
5. [capability_manifest.yaml](../../54-L1架构能力聚合层/capability_manifest.yaml) 已把多个 method_id 组织为能力族，并绑定 executor、数据范围和 min_n，例如季节性、相关性、状态转移、条件收益和回撤。

## 2. 路由粒度结论

采用两阶段路由：

```text
用户 query
  → stat_query（现有顶层意图，保持不变）
  → 阶段 A：语义匹配 capability / executor
  → 阶段 B：在能力族候选 method_id 内选方法
  → 54 现有 min_n、quality、deterministic/gated 门禁
```

理由：

- 避免 386 个顶层意图造成向量质心拥挤、正则优先级膨胀和注册表失控。
- 沿用能力 manifest 的 executor 与数据契约，语义层只负责候选选择，不绕过统计门禁。
- 多数方法共享术语但输入前提不同，方法级选择必须受能力族和数据可用性约束。

## 3. 语料与评估单元

建议新增独立 sidecar 语料，而不是把大段示例塞入 `MethodSpec`：

```text
54-L1架构能力聚合层/method_examples/
└── {capability_or_method_id}/
    ├── examples_zh.jsonl
    ├── negatives_zh.jsonl
    └── vector.json
```

每条能力/方法至少覆盖标准术语、中文口语、英文缩写、标的+时间窗口组合和易混淆问法。反例必须包含 OOS、同族近义方法和不同输入类型方法；未知或证据不足时允许 abstain，不能强制 top-1。

复用 41 的向量构建、cosine 检索和 calibration 思路，但阈值、反例集、uplift 和评估报告必须独立，不能复用 L1 中文阈值 0.65 作为统计方法路由的既定阈值。

## 4. 分批实施建议

### 批次 0：高频能力族 PoC

优先选择 manifest 已有且用户问法清晰的能力：`seasonality_query`、`correlation_query`、`conditional_return`、`state_transition`、`drawdown_query`。

- 先验证 query → capability/executor，不直接选 386 方法。
- 为每族建立人工审核正例、跨族反例和 OOS。
- 在能力族内部再评估 method top-1/top-3 与 abstain，比较“正则/显式算法名”“纯语义”“显式名称优先 + 语义兜底”三组。

### 批次 1：真实流量驱动扩展

仅对 PoC 证明有增量且真实 query 覆盖不足的能力族补语料；保留现有显式算法名优先级。低频方法、占位方法和缺少统计自检的方法不因“目录存在”自动上线语义路由。

## 5. 评估指标与建议门禁

- 路由：capability 准确率、method top-1/top-3、abstain 准确率、OOS FPR、族间混淆矩阵。
- 执行：executor 成功率、`insufficient_samples` 正确触发率、输出 schema 合规率。
- 增量：相对现有显式名称/正则链路的准确率 uplift，按能力族分别报告。
- 统计质量：继续沿用 54 的 determinism/synthetic/null/reference 检查，语义命中不得豁免 min_n 或 quality。

建议后续独立 SPEC 将 calibration 门禁设为“TPR≥95%、OOS FPR≤2%”的候选起点，并要求语义相对基线有正 uplift；具体方法级阈值须在真实 stat_query 数据集上重新校准。

## 6. 成本与风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 把 386 实现误当 386 可用语义单元 | 大量方法无示例、无真实查询 | 从能力族和高频方法分批建设 |
| 同义方法混淆 | 选错输入契约或统计口径 | 两阶段路由 + 输入类型约束 + top-k/abstain |
| 训练例与评估例同源 | 准确率虚高 | 按 query 分组 holdout，补真实流量标注 |
| 语义路由绕过门禁 | 小样本产生伪结论 | 继续调用 54 `run_capability` / `registry.run` 门禁 |
| 自检覆盖不足 | 路由正确但算法证据不充分 | 上线清单同时检查语义校准和方法审计覆盖 |

## 7. 决策

- **高频能力族 PoC：建议。** manifest 和执行门禁已具备，可控制改造范围。
- **一次性接入 386 方法：不建议。** 当前缺少示例语料、真实查询分布和完整统计自检证据。
- **P4 交付边界：已完成评估。** 本阶段不修改 54 注册表、不生成方法向量、不上线路由。
