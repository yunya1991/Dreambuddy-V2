# 后续论文三开题报告：从记忆失败到能力获取

> **论文序列**：第四篇（后续论文三），与主论文、记忆治理论文及联合基准论文相互独立  
> **研究题目**：From Memory Failure to Capability Acquisition：长期运行智能体的能力缺口闭环  
> **英文题目**：From Memory Failure to Capability Acquisition: A Capability-Gap Loop for Long-Running LLM Agents  
> **研究对象**：DreamBuddy 现场重建、能力缺口工单与工具增强机制  
> **版本**：v0.1（开题稿）  
> **日期**：2026-11-16  
> **研究阶段**：研究设计与实验协议阶段，尚未形成能力增强收益结论

---

## 摘要

当长期运行智能体无法解决某类问题时，常见做法是将失败过程、答案或案例写入记忆，期望下次检索复用。然而，逐次保存失败案例容易积累过程噪声，且不能解决工具缺失、索引不足、依赖不明或推理链断裂等根本问题。本研究拟提出“记忆失败—能力缺口—工具增强—记忆退出”的闭环：将重复出现的同类求解失败聚合为能力缺口，而非保存为彼此孤立的案例；依据问题类别选择记忆、指针、现场工具或外部调研；对可修复的共性问题实施工具或技能增强；在能力经验证提升后，重新评估原有内容记忆是否仍有保存必要。

研究将通过重复缺陷修复、陌生工程定位、工具链缺失、跨任务泛化和长周期问题复发等任务，对失败案例记忆、规则摘要、能力缺口记录及完整工具增强闭环进行比较。评价重点包括同类问题复发率、未见任务泛化成功率、单位任务求解成本、能力缺口关闭率、记忆规模变化和增强操作的安全性。研究旨在回答“何时应记住答案，何时应记住方法，何时应改进能力”，并明确失败驱动自我进化的边界。

**关键词**：智能体记忆；能力获取；能力缺口；自我进化；现场重建；工具学习；失败归因

## 一、研究背景与问题提出

### 1.1 研究背景

智能体在持续任务中会遇到两类不足：

- **信息不足**：缺少用户偏好、外部状态、历史否决等无法现场推导的信息；
- **能力不足**：无法定位代码、工具不可用、依赖关系无法解析、运行环境无法复现或推理流程不完整。

两类不足需要不同处理方式。信息不足可能需要保存残差记忆，能力不足则更适合改进工具、索引、路由或技能。如果所有失败都通过增加内容记忆解决，系统会出现案例膨胀、检索冲突和对特定实例的过拟合。

### 1.2 工程动机

DreamBuddy 的记忆设计强调“减记忆增能力”：现场重建失败不应自动生成大量失败案例，而应形成按问题类别聚合的能力缺口；同类缺口在重复出现后升级为工具增强任务。记忆树负责定位，REA 等工具负责现场求解，能力缺口负责驱动工具链改进。

这一设计提供了研究机会，但也带来需要实证回答的问题：能力缺口能否比失败案例库带来更好的跨任务泛化？工具增强是否真的能减少内容记忆？增强带来的维护负担和回归风险是否值得？

### 1.3 研究意义

- 区分记忆不足与能力不足，避免将记忆库当作所有失败的统一出口。
- 将失败数据转化为可聚合、可验证的能力改进信号。
- 建立内容记忆、程序性方法和工具能力之间的转换机制。
- 为长期智能体自我进化增加安全验证和成本约束。

## 二、相关研究与比较框架

后续综述拟覆盖以下方向：

| 方向 | 主要思路 | 本研究关注点 |
|---|---|---|
| 经验／案例记忆 | 保存成功或失败案例，后续相似检索 | 案例数量、实例过拟合和过程噪声 |
| 规则与反思蒸馏 | 将多次经验抽象为规则或原则 | 规则可靠性、适用条件和冲突 |
| 技能库 | 将成功过程转化为可复用程序或技能 | 验证门禁、组合泛化和版本维护 |
| 工具学习 | 学习选择、调用或创建工具 | 工具缺口识别和路由能力 |
| 自我修改智能体 | 通过代码或配置修改提升自身能力 | 安全、回滚、回归和权限边界 |
| 元认知与能力评估 | 判断自己是否知道、何时求助 | 失败检测、升级和外部求解路由 |

本研究不将“能力增强”限定为自主改代码，也包括索引补建、工具适配、运行脚本、观测能力和路由表改进。

## 三、核心概念与理论框架

### 3.1 三类失败

| 失败类型 | 典型原因 | 优先处理 |
|---|---|---|
| 信息缺失 | 用户偏好、外部状态或历史否决不可获得 | 保存或更新残差记忆 |
| 定位失败 | 不知道信息位于哪个项目、目录、章节或模块 | 更新记忆树与指针路由 |
| 能力失败 | 找不到入口、依赖不明、无法运行、推理链断裂或工具缺失 | 聚合能力缺口并增强工具链 |

同一任务可能同时包含多类失败，需要保留归因证据，避免笼统归类为“模型不会”。

### 3.2 能力缺口

能力缺口不是原始失败日志，而是对同类失败的可操作抽象，至少包含：

- 问题类别与归一化签名；
- 失败模式；
- 当前工具链及失败位置；
- 缺失工具、索引、观测或技能；
- 可验收的期望能力；
- 复现次数和代表性任务；
- 严重度、成本与适用范围；
- 状态：开放、认领、验证、解决或拒绝。

原始日志作为实验与调试证据保留在运行记录中，不自动转化为长期语义记忆。

### 3.3 记忆—能力决策

```text
任务失败
   ↓
失败归因
   ├─ 缺少不可再推导信息 → 残差记忆
   ├─ 不知道去哪里找     → 指针／记忆树
   ├─ 可现场求解但未执行 → 路由与方法改进
   └─ 工具或能力不足     → 能力缺口
                              ↓
                       同类失败聚合与优先级评估
                              ↓
                       工具／索引／技能增强
                              ↓
                    未见任务验证、回归与安全检查
                              ↓
                 重估旧内容记忆：保留／降级／退出
```

### 3.4 能力增强的净收益

能力增强是否值得实施，可表示为：

\[
G(a)=B_{future}(a)-C_{build}(a)-C_{maintain}(a)-R_{regression}(a)
\]

其中，\(B_{future}\) 是未来任务收益，\(C_{build}\) 是构建成本，\(C_{maintain}\) 是维护成本，\(R_{regression}\) 是回归与错误自动化风险。无法证明净收益时，不应仅因“技术先进”而实施增强。

## 四、研究目标、问题与假设

### 4.1 总体目标

建立一套由失败归因驱动、以能力缺口为中间表示、以工具或技能增强为结果、以泛化和安全验证为门禁的长期智能体能力获取机制。

### 4.2 研究问题与假设

| 研究问题 | 假设 | 验证方法 |
|---|---|---|
| RQ1：能力缺口是否优于逐次失败案例记忆？ | H1：同类失败聚合能够减少记忆规模，并提高未见同类任务的处理能力 | 案例库与缺口聚合对照 |
| RQ2：记忆与能力路由能否改善求解效率？ | H2：按失败类型选择记忆、指针或工具，能够降低无效检索和无效工具调用 | 路由策略消融实验 |
| RQ3：工具增强能否替代部分内容记忆？ | H3：对可重建信息，经验证的工具增强能够在保持任务成功率的同时减少内容记忆依赖 | 增强前后配对实验与删除测试 |
| RQ4：失败驱动增强能否泛化而非记忆实例？ | H4：能力增强的收益可迁移到未见的同类问题，而不仅改善原失败样例 | 时间外与任务外泛化测试 |
| RQ5：能力进化能否保持系统安全？ | H5：沙箱、验证和回滚门禁能够控制增强带来的回归风险 | 故障注入与回归实验 |

## 五、主要研究内容

### 5.1 失败检测与归因

研究如何区分记忆未命中、错误记忆、定位失败、工具失败、环境失败、推理失败和外部不可解问题。超时或工具调用过多只能作为异常信号，不能直接等同于能力缺口。

### 5.2 问题签名与缺口聚合

研究按问题类别、失败位置和缺失能力进行聚类，避免将表面文本相似但根因不同的任务合并，也避免同一问题因措辞差异产生多个缺口。

### 5.3 记忆—指针—工具—外部求解路由

研究何时使用内容记忆、记忆树、现场重建或外部调研，分析路由错误的成本和人工接管条件。路由表保存“问题类别到工具链”的方法，不保存所有具体答案。

### 5.4 工具与技能增强

增强形式包括：

- 新增或修复逆向解析子命令；
- 补建索引和模块入口；
- 提供环境检查与运行脚本；
- 增加观测、日志或评价器；
- 将稳定流程固化为技能；
- 改进工具选择和升级策略。

所有增强均需独立验证，不由失败日志直接触发无审查的生产修改。

### 5.5 增强后的记忆退出

工具能力提升后，对原有内容记忆执行重推、现拆和删除测试，判断其应保留为残差、降级为指针，还是退出检索。研究“能力提高导致记忆需求下降”的真实条件。

## 六、研究方法与实验设计

### 6.1 任务集

| 任务类型 | 失败来源 | 期望学习结果 |
|---|---|---|
| 重复缺陷修复 | 同类问题反复出现 | 从实例答案转向通用诊断能力 |
| 陌生模块定位 | 缺少入口和目录知识 | 记忆树或定位工具增强 |
| 依赖解析失败 | 调用链和依赖关系不明 | 依赖分析能力增强 |
| 环境运行失败 | 环境、配置或运行脚本缺失 | 可复现运行能力增强 |
| 工具能力缺失 | 当前 REA／工具无法处理某类问题 | 新工具或工具适配 |
| 不可推导偏好 | 信息无法从代码或模型得到 | 残差记忆而非工具增强 |
| 外部未知问题 | 当前工程无法提供答案 | 外部求解与能力／树分流 |
| 跨项目同类任务 | 表面不同但能力需求相同 | 未见任务泛化 |

### 6.2 对照方案

1. 无长期记忆、无能力增强；
2. 保存原始失败案例；
3. 保存人工或模型摘要的失败规则；
4. 只记录能力缺口，不实施增强；
5. 实施工具增强，但不进行缺口聚合；
6. 完整的缺口聚合、路由、增强和记忆退出闭环。

### 6.3 消融实验

- 去除失败归因，直接按文本聚类；
- 去除同类缺口聚合；
- 去除问题类别—工具链路由；
- 增强后不做未见任务验证；
- 增强后不执行记忆退出评估；
- 去除回归测试与回滚门禁；
- 将所有失败统一写入记忆。

### 6.4 泛化设计

- 原失败任务与后续测试任务分离；
- 按时间划分，防止未来答案泄漏；
- 按项目或模块划分，测试跨项目迁移；
- 保留未见失败模式，检验系统是否正确升级而非强行套用旧能力；
- 比较原任务修复率与同类新任务成功率，区分实例记忆和能力获取。

### 6.5 指标体系

| 维度 | 指标 |
|---|---|
| 任务效果 | 原任务解决率、同类新任务成功率、问题复发率 |
| 泛化 | 跨时间、跨模块、跨项目成功率 |
| 缺口质量 | 聚合准确率、重复缺口率、错误归因率、缺口关闭率 |
| 路由 | 路由正确率、无效检索率、无效工具调用率、升级及时性 |
| 成本 | Token、延迟、工具调用、构建与维护成本 |
| 记忆 | 内容记忆数量、案例膨胀率、可退出记忆比例 |
| 安全 | 回归率、未经审查修改数、回滚成功率、人工接管率 |

### 6.6 统计与复现

- 固定模型、工具版本、任务初始状态和资源预算；
- 对增强前后相同任务进行配对比较；
- 对未见同类任务独立报告结果；
- 保存失败归因、缺口状态变化和代码／工具版本；
- 报告置信区间、效应量和负面结果；
- 对自动归因和聚合结果进行人工抽样评价。

## 八、预期创新点

1. 将失败案例转化为按能力类别聚合的缺口，而非持续扩张的案例记忆。
2. 建立信息缺失、定位失败和能力失败的分流机制。
3. 将工具增强与内容记忆退出连接，形成记忆—能力双向替代闭环。
4. 以未见同类任务检验能力获取，区分泛化与实例记忆。
5. 将构建、维护、回归和回滚成本纳入自我进化收益评价。

## 九、研究基础与可行性

DreamBuddy 已具备记忆检索、记忆树、REA 现场解析、能力缺口状态机及问题类别—工具链路由等设计基础。研究可复用真实软件工程任务和运行日志，且不需要让模型自主修改生产系统即可完成大部分对照实验。

实施前须核验缺口聚合、工具版本绑定和验证门禁的实际状态。历史失败日志只能作为研究素材，不能直接证明新闭环有效。

## 十二、风险、安全与结论边界

- **错误归因**：将信息缺失误判为能力不足会制造不必要工具，应保留人工复核。
- **错误聚合**：过度合并会掩盖不同根因，过度拆分则退化为案例堆积。
- **自动化回归**：工具增强可能破坏既有链路，必须经过隔离验证、回归和回滚。
- **权限边界**：实验不授权智能体直接修改生产环境，不绕过代码审查。
- **过拟合风险**：仅改善原失败样例不能视为能力获取，必须报告未见任务结果。
- **成本风险**：工具构建和维护可能高于保存少量记忆，应保留负收益结果。
- **领域边界**：初期结论限于软件工程和所选工具链，不外推至高风险自主决策场景。

## 证据边界

本开题报告描述待验证的能力获取机制，不宣称失败聚合、工具增强或记忆退出已经提升系统性能。正式结论须以未见任务、长期任务流、回归测试和完整成本数据为依据。
