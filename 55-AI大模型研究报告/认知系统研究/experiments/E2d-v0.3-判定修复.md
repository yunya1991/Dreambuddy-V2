## 1. 机制：从"符号存在"改为"断言类型"

```text
敏感词（明文）                       → REJECT
残差标记词（偏好/否决/教训…）         → CONTENT
断言类型 = 代码结构（定义/导入/赋值/读取/依赖/继承）
    ├─ 有自包含锚点 → grep/AST → NONE 或 CONTENT
    └─ 无自包含锚点 → CONTENT / PROCEDURE
断言类型 = 运行部署状态 / 组织决策 / 未知 → CONTENT
```

核心变化是**默认拒绝**：只有能归入"代码结构句式"的断言才允许进入探针；其余一律按残差处理。这样"符号能搜到"不再等于"事实可由代码回答"。

判定词表分三组：

| 组 | 作用 | 示例 |
|---|---|---|
| STRUCTURAL | 放行到探针 | 定义、声明、导入、赋值、读取、依赖、继承 |
| RUNTIME | 判为外部状态 | 部署在、跑在、实例、端口、版本、目录在、到期 |
| DECISION | 判为组织决策 | 复核、白名单、默认、只、不再、沿用、冻结、会签、口径、上限 |

REA 兜底也同步收紧：只对"代码结构 + 有符号 + 探针未命中"的候选调用。两个集上都不再触发（0 次）。

## 2. 必须披露的三个问题

### 2.1 词表是在对抗集上调的（过拟合风险）

A-60 的句式与本轮词表高度相关。0% 只能说明"这类构造能被规则覆盖"，不能说明对未见句式同样成立。下一步需要**留出集**：另写 40 条不使用本轮任何词表的对抗样本，重测。

### 2.2 默认拒绝会把"问句形式的代码事实"误存

L1 的可推导样本都由"定义在/被赋值/被读取/被导入"句式构成，因此默认拒绝对它们无影响。但真实写入可能是"`GraphExecutor` 在哪个文件？"这类问句，没有结构谓语，会被判 CONTENT（误存）。本轮没有覆盖这种句式。

建议补 30 条"问句形式的可推导事实"，测误存率。

### 2.3 REA 兜底路径本轮未被验证

v0.3 两个集上 REA 调用为 0，说明测试集里没有"是代码事实但 grep/AST 都失败"的样本。E1b 的 A/B/C 类正是这种，但它们的真值在 HEAD 快照上未重新标注。L2 需要带上这类样本，否则"能力缺口 → REA 兜底"这条链路等于没测。

## 3. 判定分布

| 集合 | NONE | CONTENT | REJECT | PROCEDURE |
|---|---|---|---|---|
| L1-300 | 120 | 120 | 60 | 0 |
| A-60 | 0 | 50 | 10 | 0 |

A-60 的 50 条不可推导项全部落在 CONTENT，原因分布主要是 `decision` 与 `runtime_state`；这符合预期。

## 4. 结论与下一步

- 对抗集漏存已从 56% 降到 0%，**低于 10% 门槛**，L2 可以启动。
- 但 0% 应表述为"在本轮构造的对抗句式上为 0"，论文中必须同时报告留出集结果。
- 进 L2 前建议补两组小样本（各 30–40 条）：问句式可推导事实、未见句式的决策类。两者合计约半天工作量，可避免 L2 结论被判定层的过拟合污染。
