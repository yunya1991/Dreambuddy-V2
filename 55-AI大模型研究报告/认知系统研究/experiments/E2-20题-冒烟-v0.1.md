## 1. 实现了什么

`rmd_mvp.py`（约 250 行，单文件，无外部依赖）：

1. **gate（五值）**
   - 敏感词 → REJECT
   - 无可检索符号 + 步骤语义 → PROCEDURE
   - 无可检索符号 → CONTENT
   - grep 命中任一符号 → NONE（可现场重建）
2. **探针三件套**
   - grep：纯 Python 逐行扫描 258 个 .py
   - AST：符号定义索引 + `os.environ/getenv` 读取点
   - REA trace：调用 `dsh_nodes.S33_rea_trace`（已修 I1 版本）
3. **decode（读时）**
   - 写入时存指针符号；读时与当前问题符号**融合**
   - 按符号稀有度（1/命中文件数）加权排序文件
   - 同一文件内选"命中不同符号最多"的行作为证据
4. **anchor 校验**：证据文件是否覆盖真值文件；主证据行是否可定位

判定规则未使用真值文件路径，只用候选文本与问题文本抽取符号。

## 2. 任务与对照

- **20 题**：沿用 `E1-tasks.jsonl`，全部属"可再推导代码事实"
- **3 条控制项**（仅验证分支，不计入统计）
  - X1 偏好 → CONTENT ✓
  - X2 密码位置 → REJECT ✓
  - X3 双实例排障步骤 → PROCEDURE ✓

控制项证明五值分支可用，尤其敏感域拦截不依赖统计。

---

## 3. 逐题要点

- **20/20 判 NONE**：没有任何一条可再推导事实被误存。
- **17/20** 的 top-3 证据覆盖真值文件。
- **18/20** 的主证据行可以在命中集中定位到（含精确行号）。

### 3.1 三个未命中的原因（均为排序，不是判定）

| 题 | 真值文件 | top-3 实际 | 原因 |
|---|---|---|---|
| B1 | `shared/state.py` | 多个 tests / adapters | `State.update` 与 `self.results` 过于通用，被高频文件压过 |
| D3 | `registry/node_registry.py` | `apps/trading_agent/agent.py`、根 `__init__.py` | 该符号被多处 re-export，权重打平 |
| E2 | `core/sense/intent_engine.py` | `__init__.py`、agent.py、skill_adapter | 候选文本未自包含（只写"仅依赖 shared"），缺主语模块 |

**结论**：gate 没问题，瓶颈在"候选文本必须自包含"与"证据排序需去通用词"。这两点在扩到 300 条前必须先修，否则会把排序失败误算成"解码失败"。

## 5. 本轮显式局限

1. **候选文本取自真值**：真实写入时文本由抽取器生成，可能更短、更不自包含（E2 已暴露该问题）。
2. **控制项是合成样本**：只证明分支，不证明敏感域召回。
3. **单仓库单快照**：`/tmp/e1b_clean`，HEAD `551435b1b9`。
4. **无第二评分者**：锚点判定为机械规则，κ 不可计算。
5. **未做 CONTENT/PROCEDURE 的读时验证**：本轮只验证"该存的确实没被误判为可推导"。

---

## 6. 下一步（按优先级）

1. **修两个工程缺陷**：候选文本自包含检查；证据排序去通用词（`results`、`__init__`、`handler` 等降权）。
2. **REA 短路**：grep 命中即返回 NONE，不再调用 REA；预计单题时延降到 <0.5 s、REA 字节降到 4 题。
3. **扩到 300 条**：120 可推导 + 120 不可推导 + 60 敏感，进入 L1 正式评测。
4. **再决定 PROCEDURE 是否进 MVP**：本轮只做了写入判定，未验证"策略复用能否提升解码成功率"。
