# E4：写入判定单条成本实测 v0.1

> **目的**：为 L2 的成本对比提供分母
> **日期**：2026-11-17
> **样本**：L1-300 + A-60 + H-70 + M-15，共 440 条
> **产物**：`E4-cost.py`、`E4-cost.json`

---

## 0. 结果

| 路径 | 单条时延 | 单条 token | 说明 |
|---|---|---|---|
| 索引构建（一次性） | 604 ms | 0 | 扫 258 文件 + AST 索引 |
| 规则判定（快路） | p50 **0.01 ms**，p95 125 ms | 0 | 290/440 短路；p95 是进入 grep 的那批 |
| 探针 + 解码 | p50 **113 ms**，p95 165 ms，max 465 ms | 0 | 仅 code_fact 候选（150 条） |
| LLM 全量判定（输入） | 未实测（本地无模型） | p50 **289**，p95 301 | 参考提示词 + 候选，tiktoken 代理计数 |

按 p50 折算，LLM 路径单条约 **289 输入 + ~25 输出 ≈ 314 tokens**。

---

## 1. 关键读数

1. **规则路径不是"零成本"，而是"零 token、低时延"**：p95 的 125 ms 来自门槛内部的 grep，真正花钱的是搜索而不是分类。
2. **探针是确定性路径的主要成本**：单条 113 ms，比任何规则都贵两个数量级；但它可本地并行、可缓存，且没有 per-token 费用。
3. **LLM 输入 token 几乎恒定**（289–304）：因为提示词固定，候选文本只有几十字。这使写入成本可预测。
4. **索引 604 ms 是一次性成本**，按进程生命周期摊销；若服务常驻可忽略。

---

## 2. 写入量换算（LLM 全量方案）

| 日写入量 | 日 tokens | 月 tokens（30 天） |
|---|---|---|
| 1,000 | 314,000 | 9.4 M |
| 10,000 | 3.14 M | 94 M |
| 100,000 | 31.4 M | 942 M |

结论：日写入 ≤1 万条时，全量 LLM 判定的 token 量在常规预算内；超过 10 万条则必须回到"规则快路 + 分类器"，LLM 只处理低置信段。

## 3. 未能实测的部分

- **LLM 端到端时延**：本地 ollama 已安装但没有模型（`ollama list` 为空），无法在不下载模型的前提下实测。报告中的时延仅覆盖规则与探针路径。
- **真实 tokenizer**：使用 `cl100k_base` 作代理，与目标模型的分词器有 ±10–15% 偏差。
- **并发与冷启动**：单进程串行测得，未测并发吞吐。

---

## 4. 对 L2 的意义

L2 要比较"内容记忆 / 指针+REA / 指针+grep / RMD 级联"四条件的**正确率与成本**。现在成本侧有三个可比的量：

| 条件 | 主要成本 |
|---|---|
| 内容记忆 | 存储 + 检索时注入的上下文 token |
| 指针+REA | 指针存储 + REA 单次 28 KB（E1b 实测） |
| 指针+grep | 指针存储 + 单次约 113 ms |
| RMD 级联 | 门槛（规则 p50 0.01 ms / 探针 113 ms）+ 解码 |

缺的一项是"检索时注入的上下文 token"（内容记忆条件），需在 L2 任务里按实际注入长度统计。
