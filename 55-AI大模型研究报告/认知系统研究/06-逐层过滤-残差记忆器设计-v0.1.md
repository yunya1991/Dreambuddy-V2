# 逐层过滤的残差记忆器 · 设计 v0.1

> **定位**：把 E2–E5 的实测结论固定成一条可实现的写入/复核流水线
> **上游**：`02-评估方案` §10（三层架构）、`03-阶段结论-v0.2`、`05-残差记忆曲线`（子类与 λ）
> **日期**：2026-11-18
> **状态**：设计稿；所有阈值均来自已跑实验，标注为「实测」或「未测」

---

## 0. 一句话

**写入时逐层过滤，只有付得起证据成本的层才有权说"不用记"；清理时反向复用同一条流水线，用"事实源是否仍成立"替代"时间是否到期"。**

---

## 1. 三条设计不变量

这三条不是风格偏好，每一条都有实验反例。

| # | 不变量 | 反例 |
|---|---|---|
| I1 | **便宜的层只能输出「记」或「转下一层」，不能单独输出「不记」** | v0.2 顺序为"敏感词 → 标记词 → 符号探针"，绕过前两层后退化为"搜到符号即可推导"，对抗集漏存 **56%（28/50）** |
| I2 | **写入判定必须预演一次真实的读时级联** | 若写入说"可重建"而读时重建不出来，该记忆等于不存在；L2d 的 100% 正来自写入与读时共用同一套回退 |
| I3 | **默认只降级，不物理删除** | 删除不可逆；能力回退后再无恢复途径（C6 未验证） |

## 2. 写入流水线 S0–S4

```text
candidate ──S0──► REJECT(硬)
             └──► S1 ──► [policy/decision/runtime] ──► CONTENT
                     └──► [code_structure] ──► S2 ──► NONE
                                                  └──► S3 ──► NONE
                                                            └──► S4 ──► NONE
                                                                      └──► CONTENT
```

| 层 | 做什么 | 允许输出 | 成本 | 实测依据 |
|---|---|---|---|---|
| **S0 敏感屏** | 凭证、私钥、越权路径 | `REJECT`（硬，不做统计让步） | 0 | 60/60（E2c） |
| **S1 断言分型** | 四分：code_structure / runtime / decision / policy | `CONTENT` 或转 S2 | < 1 ms | 误存 0/120、漏存 0/120（E2e，v0.3.1） |
| **S2 本地探针** | grep 精确命中 + AST 定义命中，须带可检索锚点 | `NONE` 或转 S3 | ~200 ms | 单独 80%（L2） |
| **S3 级联重建** | 多符号打分 + 定义优先 + 锚点加权；`top1 < 1.0` 或 `margin < 0.5` 则回退 | `NONE` 或转 S4 | 11.8 tok | 97%（L2b） |
| **S4 LLM 校验** | 对弱证据候选判 yes/no；no 则回退 | `NONE` 或 `CONTENT` | 15.2 tok | 100%（L2d），38/60 题触发 |

**覆盖率**：S0 + S1 覆盖约 70%，S2 再吃掉大部分，真正进 S4 的只有 38/60。逐层过滤的收益是**能在前面结束**，不是更准。

### 2.1 为什么 S1 必须早于 S2

S1 是零成本的分型，它决定"这条有没有资格进探针"。若把 S2 提前，所有决策句/偏好句都会先被 grep 一遍，一旦偶然命中某个符号就会被判为可推导——这正是 v0.2 的失效路径。**分型在前、证据在后**，是不变量 I1 的具体落地。

### 2.2 S2 的判定条件（比 v0.3.1 更严）

原实现是「命中即 NONE」。本设计加一条：

> 命中必须伴随**可检索锚点**（符号名 + 至少一个 `file` 或 `module`），否则降级为 CONTENT。

理由：L2 的 5 个失败全部是"多个合理文件选错"，即命中但定位不唯一。没有锚点的命中只是"存在性"，不是"可恢复性"。

## 3. 记忆条目结构（清理的前提）

现有系统无法按类清理，是因为写入时没打标签。每条记忆至少要有：

| 字段 | 用途 | 缺失后果 |
|---|---|---|
| `id` | 主键 | — |
| `subclass` | `code` / `config` / `runtime` / `D-tech` / `D-policy` | 清理无法选规则 |
| `form` | `POINTER` / `CONTENT` / `PROCEDURE` | 无法决定是否可降级 |
| `source_anchor` | 事实源标识（`file:symbol` / 配置键 / 记录 id） | R1 复核无从跑起 |
| `evidence` | 判定时的证据快照（命中文件、分数、探针版本） | 无法复现判定 |
| `written_at` | 写入时间 | 只用于统计，**不用于清理** |
| `verify_state` | `fresh` / `stale` / `degraded` | 无法表达"已失效但保留" |

`written_at` 存在但**不参与删除决策**，这是与当前 TTL 方案最重要的差别。

## 4. 存量清理 R1–R3

### 4.1 为什么不能用时间过期

| 子类 | λ | TTL 30 天的后果 |
|---|---|---|
| 代码位置 | ≤ 1.4e-4/天（E5-F1，SA 240 样本 0 事件） | 删掉 **99.9% 仍有效**的记忆，纯损失 |
| D-tech 技术决策 | 天级（E5-F3，8 条中 5 条同日被推翻） | TTL 恰好合理 |
| D-policy 偏好/约定/教训 | ≈ 0（**假设，未检验**） | **删掉最不该删的** |

**时间不是失效原因，只是失效的代理。** 用同一条 TTL 覆盖三类，必然对两类出错。

### 4.2 三步复核

| 步骤 | 动作 | 适用对象 | 判定依据 |
|---|---|---|---|
| **R1 复核** | 重跑一次重建；成功→仍为指针，失败→升级为内容 | 全部 `POINTER` | 事实源当前是否仍能解析出该事实 |
| **R2 失效** | 标记 `stale`，**不删除** | 仅 `code` / `config`（可自动验证） | 符号/键是否仍存在；值是否改变 |
| **R3 降级** | 指针 → 内容，或内容 → 指针（仅在删除测试通过后） | 全部 | 重建成功率 + 删除测试 |

### 4.3 三条纪律

1. **D-policy 永不自动删除，也不自动降级。** 它 `p_recon≈0`，删了即永久丢失，且无法从任何事实源验证"用户是否改主意了"。
2. **D-tech 只按"是否被后续记录推翻"失效**，不按时间。依据是 E5-F3：这类事实的失效是事件驱动的，时间只是事件的粗略代理。
3. **物理删除必须过删除测试集**，否则无法区分"清理"与"遗忘"（对应 C6，当前未验证）。

### 4.4 复核频率

不设固定周期，按"事实源是否发生变化"触发：

- `code` / `config`：事实源文件变更时触发（可用 git 事件驱动，成本近零）；
- `D-tech`：新记录与旧记录冲突时触发；
- `D-policy`：仅由用户显式改口触发。

这比"每天扫一遍全库"便宜一到两个数量级，而且不会误伤。

## 5. 防膨胀：级联的副作用

回退是「只升不降」的：判不准就存内容。长期运行会让记忆单调膨胀，把节省的成本吃掉。两个约束：

1. **预算约束**：按子类设配额 `π_c`（§05 §3.2），超额时优先压缩 `code`/`config`（可重建），**不压缩 `D-policy`**。
2. **回退率监控**：回退率 > 60% 说明 S2/S3 召回不足，应改探针而不是继续加大存储——L2d 的 57% 已经接近这条线。

## 7. 落地优先级

| 阶段 | 内容 | 依赖 | 可验证指标 |
|---|---|---|---|
| **P1** | 补 `subclass` + `source_anchor` 两个字段 | 无 | 存量 100% 可分类 |
| **P2** | S2 加锚点校验 | 无 | 误判「命中但定位不唯一」的比例 |
| **P3** | R1 复核（仅 code/config） | P1/P2 | 复核后指针仍有效的比例 |
| **P4** | R3 降级（不删除） | P3 | 降级后读取成功率 |
| **P5** | 删除（需删除测试集） | P4 + C6 | 删除测试通过率 ≥ 95% |

**P1 是硬前置**：没有子类标签，后面每一步都无法选规则。
