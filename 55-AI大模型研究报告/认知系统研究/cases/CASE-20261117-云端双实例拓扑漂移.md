# 案例 CASE-20261117：云端双实例拓扑漂移与记忆形态失效

> **案例类型**：内部工程案例（动机型问题证据，**不是**方案有效性证据）
> **采集日期**：2026-11-17
> **领域**：单机云端部署 / 软件工程智能体
> **关联论文**：01 主论文 RQ1、RQ2、RQ3
> **证据等级**：系统状态、日志、配置可复核（复核命令见附录 A）；无对照实验，不支撑性能主张

---

## 1. 一句话概括

云端前端长期存在两套并存的 systemd 拓扑，而唯一被智能体读取的记忆（Skill 文档）只记录了其中一套；智能体据此反复做出错误判断与不完整修复，直到直接读取事实源才纠正。该案例同时展示了**残差记忆缺失**与**过期内容记忆主动致害**两种失效。

## 3. 核心反差：三个「记忆版本」

| 版本 | 内容 | 性质 | 结果 |
|---|---|---|---|
| M0：Skill 文档 | 「前端服务 `dreambuddy-frontend.service`，端口 3001」 | 内容型记忆（写死结论） | 遗漏 3002 与 Nginx upstream，导致单实例修复 |
| M1：验收结论 | 「3002 与本服务无关」 | 错误内容型记忆 | 掩盖真实依赖，延长故障 |
| D：事实源 | systemd unit、`ss -ltnp`、nginx 配置、进程 cwd | 可现场读取 | 一次读取即纠正全部误判 |

对照主论文判据 \(V(x)=H(x\mid K,D,R)-C(x)\)：

- 「哪两个 unit 在跑、谁占哪个端口、Nginx 挂谁」**完全可以由 D 直接读出**（\(H\) 低），却曾被写成内容型记忆；
- 复制进记忆后与 D 不一致时，没有「事实源优先」仲裁，智能体继续信任 M；
- 正确形态应是指针型记忆（记录「去读哪条命令、校验什么」）而非内容型复制。

## 5. 机制拆解（为什么不是随手一个 bug）

1. **双拓扑并存**：旧单实例 `dreambuddy-frontend.service`（`pnpm start` → `next start -p 3001`）与模板单元 `dreambuddy-frontend@.service`（`next start -p %i`）都指向 3001；单实例 `disabled` 但被手工启动，`@3001` `enabled`，谁先启动谁占用。
2. **无限重启放大器**：模板 unit 为 `Restart=always` + `RestartSec=3`，3.3 次/10s 低于 systemd 默认限流（5 次/10s），确定性端口冲突不会进入 `failed`，而是永久空转。
3. **共用产物**：两实例共用同一份 `.next`，只重启一个会导致新客户端代码与旧服务端进程并存，表现为 400 与骨架屏。
4. **记忆漂移**：文档只写一套拓扑，且没有「与事实源冲突时 D 优先」的校验步骤。

## 7. 边界与反事实

- **「因为服务器小」只成立一半**：单机 4 vCPU / 15.6 GB，无 K8s 与外部负载均衡，手工双进程 + Nginx 是资源受限下的低成本高可用方案；但日请求 10,285 次、峰值 440 次/分钟（≈7.3 rps），说明双实例**不是容量策略**，价值在发布零窗口与单点兜底。论文中不得表述为「为分摊流量」。
- **「独有策略」需要降级表述**：混合拓扑是演化残留（配置漂移），不是设计决策。把漂移包装成策略会削弱可信度；应写成「资源受限环境下的低成本冗余方案，及其配置漂移风险」。
- **反面风险**：本案是「记忆形态错误」，不是「记忆数量过多」，不能反推「记忆越少越好」。
- **可检验反事实**：若当初只记录指针（读 `systemctl list-units 'dreambuddy-frontend*'`、`ss -ltnp`、nginx upstream）而不写死实例名，是否能避免误判？该反事实已可转为阶段二对照任务，见下节。
