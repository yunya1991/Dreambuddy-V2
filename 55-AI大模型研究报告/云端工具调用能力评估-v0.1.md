# 云端大模型工具调用能力评估 v0.1

> **日期**: 2026-11-18 ｜ **范围**: `3.1-FRONTEND` 的 `/api/agent/chat` L2 对话 Agent（云端模型 + MCP/能力工具）
> **方法**: 只读代码审计 + 已有数据统计；**未做线上真实用户会话抽样，未做模型横向压测**
> **一句话**: 「感觉弱」属实，但主因不在模型权重，而在**工具面设计、Agent 循环与门禁、评测缺失**三处；这三处都在 L0–L2 工程层，改造成本低且可量化。**现在直接训练大模型不成立**。

---

## §0 结论（先看这三条）

1. **当前瓶颈是「工具面 + 循环」，不是「模型不会」**。模型实际只有 2 个通用工具（`system_capabilities` / `run_capability`）+ 5 个认知只读工具；22 个业务能力全部藏在 `run_capability` 的一个自由参数里，schema 无 required / enum / example，必须先查目录再猜参数。5 步上限下，一次任务只剩 2–3 次真实调用预算。
2. **现有「步骤评审门禁」会把正常推进误杀成失败**，从外部看就是「模型调工具很弱」。它只看模型自述、不看工具参数与结果，且用正则 `fail|不通过|驳回|不合格|\bno\b` 解析，PASS 文本中出现相关词就会误判 FAIL 并终止后续步骤。
3. **「训练」应排在最后，且第一目标不是大模型**。当前可用工具调用轨迹仅 119 条（其中真实域操作 85 条），且**不含模型侧的 tool_name/args/result**；无多轮工具 golden set，无基线。按 56-H5 的证据门禁，能进训练的 A 级样本目前为 0。闭源云端 API 也无法微调。

## §2 六个可证实的短板（按影响排序）

### P0-1 工具面是「一个万能工具 + 22 个 ID」，模型被迫两跳

- `run_capability` 的入参是 `id: string` + `params: Record<string, unknown>`，没有 `required`、`enum`、字段示例，也没有「id 不存在时怎么纠错」。
- 模型要先调 `system_capabilities` 拿目录，再调 `run_capability` 猜参数；5 步上限里第一步就被目录查询消耗。
- 对比业界成熟做法：一个工具一个 schema，参数在 schema 层强制，模型不需要记忆目录。**工具面越"省事"，模型越难用。**

### P0-2 没有工具使用策略，只有能力目录

- 系统提示给了「该调什么」，没给「先调什么、拿不到怎么办、什么情况不该调、失败几次放弃、引用哪些字段」。
- 规则里写「dsh.technical 必须传 symbol」，但 `run_capability` 的 schema 不强制 `symbol`——**规则与 schema 不同源，模型可绕过**。
- 无 few-shot：对 `deepseek-v4-pro`/`qwen-plus` 这类模型，1–3 个正确的工具调用示例通常比 10 条规则更有效。

### P0-3 步评审门禁会误杀正常工具链

- 评审输入只有标题、摘要、工具名，**没有参数、没有结果、没有错误码**，无法判断「这步是否真的该继续」。
- 用正则 `/fail|不通过|驳回|不合格|\bno\b/i` 解析：模型输出「PASS：无 FAIL 项」也会被判 FAIL。
- 判 FAIL 直接 `stepReviewFailed = true`，后续工具步骤全部停止 → 外部表现就是「调了一两次就不动了」。
- 评审模型未单独配置时复用 `AGENT_MODEL`（同源），独立性不足。

### P0-4 采样参数缺省，工具阶段不稳定

- chat 路由未传 `temperature`，取供应商默认值；工具选择/参数填充通常应在 0–0.2。
- 未设置并行工具调用策略；多维度取数（行情+宏观+情绪）只能串行，进一步挤压 5 步预算。

### P0-5 失败不可学习、不可归因

- 工具失败只回一句 `error` 字符串，没有统一 `error_code`（`invalid / unavailable / not_found / conflict`）、没有 `retryable`、没有「建议下一步」。
- step 事件只存 `title/summary/verdict`，不存 `tool args/result`，**事后无法回答「模型选错了工具，还是参数错了，还是工具本身挂了」**。
- 现有 56-H3 已有 `trace_id/tool_call_id` 影子字段，但 chat 链路没有接。

### P0-6 没有 Agent 级评测，强弱无法证伪

- 45 评测系统的 SPEC 与实现中未检索到 agent / 多轮工具用例定义；56 的 evals 是单轮工具探针；57 的 golden 是意图分类与辩论题。
- 现有"云轨迹"数据：`trajectories_cloud.jsonl` 223 条领域调用，65 条失败（**29%**；`invalid` 32、`unavailable` 17、`not_found` 12、`conflict` 4）——但这是**领域接口调用**，不是模型决策轨迹，不能直接归因给模型。
- 结论：目前任何「优化后变好了」都无法证明，也无法和训练收益分离。

### P1 其他

- **工具可见性靠硬编码名单**：profile 白名单按工具名精确匹配，新增 MCP 工具默认不可见，容易漂移。
- **模型选型未验证**：默认 `qwen-plus` 与本地 `deepseek-v4-pro` 并存，无同集对比数据，云端实际模型未固化在仓库。

## §3 为什么「直接训练」现在不成立

| 必要条件 | 现状 | 判定 |
|---|---|---|
| 足量、可用的工具调用轨迹 | 119 条（真实域操作 85 条，其余 shadow/合成）；无模型侧 name/args/result | ❌ 差 1–2 个数量级 |
| 证据门禁可入训样本 | 56-H5 规定仅 A 级（可复现/人工确认）可入训；当前 A 级工具轨迹 0 条 | ❌ |
| 可微调的模型 | 云端为闭源 API（DeepSeek / DashScope 兼容），无微调接口 | ❌ 只能改开源小模型 |
| 可对比的评测基线 | 无多轮工具 golden set、无基线报告 | ❌ 训练前后无法判定 |
| 稳定的失败模式 | 未做失败归因，当前"弱"是现象不是模式 | ❌ |

**结论**：先修 harness。即便要训练，第一目标也应是**意图→工具路由的小模型/分类器**（可复用 `l1_training` 的 9.6MB 域发现数据），而不是直接 SFT 主模型。

## §4 逐层优化路线（建议按 L0→L4 推进）

| 层 | 动作 | 验收指标 | 成本/收益 | 风险 |
|---|---|---|---|---|
| **L0 可观测** | 全量落 `tool_call{name,args,ok,error_code,latency,step,trace_id}`；固化云端模型名/温度；建 60 题多轮 golden | 100% 调用可 join；基线报告可复跑 | 低 / 决定后续一切 | 日志含参数，需脱敏 |
| **L1 确定性前置** | intent→候选能力 top-3（规则或小分类器）；只注入候选工具；symbol/默认参数前移；统一错误码 + retryable | 候选命中率 ≥90%；参数非法率下降 | 中 / 直接缩小决策面 | 规则覆盖不足会漏召回，需兜底全量 |
| **L2 工具面与循环** | 把 `run_capability` 拆成 4–6 个域工具（market/data/dsh/trading/analysis），各自 schema（required/enum/example/when-not-to-use）；dispatcher 保留兜底；补 3–5 个 few-shot；步评审改确定性校验，仅高风险动作 LLM 复核；步数 5→8；temperature 0.1–0.2 | 工具选择准确率、参数合法率、任务成功率三项同集提升 | 中 / 预计是最大增量 | 工具变多要控总数（47 配额 ≤15/壳、≤10/角色） |
| **L3 模型选型** | 同 golden 集对比 2–3 个模型 × 2 档温度；按成功率/合法率/步数/成本选 | 有显著更优才切换 | 低 / 可能直接解决 | 供应商稳定性与价格波动 |
| **L4 训练（门槛触发）** | 同时满足：①L1–L3 后仍有 ≥50 例同模式稳定失败；②≥2000 条 A 级轨迹；③选定可微调开源模型。先训 router / 参数修复小模型，再评估主模型 SFT | 固定留出集提升且不伤通用能力 | 高 / 最后手段 | 过拟合、评测污染 |

## §5 评测怎么做（最小可用）

**用例结构**（JSONL，一题一行）：

```json
{
  "id": "T001",
  "query": "BTC 现在能不能做多？给我完整研判",
  "expected_tools": ["trading.analysis_pipeline"],
  "required_args": {"symbol": "BTC"},
  "must_have_facts": ["主要矛盾", "失效条件"],
  "forbidden": ["编造价格", "声称已下单"],
  "max_steps": 4
}
```

**指标**：工具选择准确率、参数合法率、任务成功率、平均步数、错误恢复率、p95 延迟、token/CU。
**三臂**：现状 / L1 / L1+L2；每臂 ≥60 题 × 2 次；用 McNemar 或 Wilson 区间判定，不用单次观感。
**产出**：`reports/agent-tool-eval-YYYYMMDD/`（原始 runs、汇总、负例）。

## §6 立即可做的 5 件事（不改业务逻辑）

1. **打开全量 tool_call 日志**（含 args/result/error_code），只加埋点不加行为。
2. **修步评审误杀**：正则改结构化判定；只在「写操作/高风险动作」上允许阻断；评审模型与 worker 异构。
3. **给 `run_capability` 加约束**：`id` 改为候选集合（或动态 enum），`params` 补 required 与示例。
4. **chat 路由显式 `temperature` 0.1–0.2，步数 5→8**（并行工具调用因供应商兼容性未纳入本轮）。
5. **建 60 题 golden 并跑一次基线**，把「感觉弱」变成数字。

### 7.2 基线数字（deepseek-v4-pro，温度 0.15，60 题）

| 口径 | 任务成功 | 工具选择 | 能力命中 | 参数正确 | 平均步数 | 工具失败率 | p95 延迟 |
|---|---|---|---|---|---|---|---|
| 未校准 golden（首跑） | 78.3% | 85.0% | 86.7% | 96.7% | 2.78 | 65.4% | 42.3s |
| 校准后 golden（复跑） | **95.0%** | **98.3%** | **96.7%** | **98.3%** | 2.70 | 68.7% | 37.2s |

**必须一起读的三点**：

1. 首跑 78.3% 的失败里，多数是「输入不足时应先澄清/应拒绝写操作」被 golden 判错；校准只放宽了这类**行为策略**，没有放宽工具选择标准。两跑都保留在 `evals/agent-tool/out/`。
2. **工具失败率 65%–69%** 来自本地 L1/数据服务未启动（`fetch failed`），是环境问题，不是模型选错工具；因此本轮基线只能证明「选得对」，不能证明「查得到」。
3. 真实短板已量化：模型对简单问题**过度调用**（平均 3.6 次工具、多跳题最多 6 个能力），且倾向先查目录再执行；`analysis.data_insight`、`trading.exit_review` 等能力仍会被漏选或参数不全。p95 37–42s 说明工具串行与超时叠加已成体验瓶颈。

### 7.3 下一步（按证据）

1. **L1 路由前置**：intent→候选能力 top-3，直接砍掉「先查目录」这一步与过度调用；预计对平均步数与延迟收益最大。
2. **工具面拆分**：把 `run_capability` 拆成域工具并补 required/enum/example；优先修 `analysis.data_insight` 漏选与 `exit_review` 参数缺失。
3. **数据层可用性**：先把 L1/DSH 服务拉起再复跑同一 golden，才能测出「查得到」的真实成功率。

## §8 结论边界

1. 未抽样线上真实用户会话；`trajectories_cloud` 223 条是领域接口调用，不是模型决策轨迹，29% 失败率不能直接归因模型。
2. 未做模型横向压测，「模型不弱」是相对判断：在工具面与循环修好之前，无法区分模型能力与 harness 缺陷。
3. 基线为单模型、单次运行、本地数据源不可用；golden 在首跑后做过一次「澄清/拒绝」口径校准，复跑数字需与首跑一起读。
4. 57-SPEC 的提示词注册表/宪法与 56-H 的 trace/tool_set 证据门禁已具备基础设施，建议复用，不再新建第二套。
