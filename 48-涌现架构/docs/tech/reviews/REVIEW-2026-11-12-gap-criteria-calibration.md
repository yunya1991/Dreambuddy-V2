## 2. 修订建议 1：architecture_gap 是"改判据"非"关闭缺口"（P1）

**提案表述**（§1.3 预期效果）：
> 11 条中预计大部分可关闭或降级

**问题**：
- 判据校准 ≠ 缺口关闭。把阈值从"模块级重名率 <0.4"改为"call 边假依赖率 <0.35"，**缺口的本质从"命名规范"变成"依赖解析精度"**，是**改判据**而非"达标关闭"。
- 11 条缺口记录的 `gap_type=architecture_gap` 字段含义已变，若直接标 closed 会丢失历史语义。
- 提案 §1.3 提到"根治路径：33-REA 落地 AST 精准解析"，说明真正的修复（AST 消歧）尚未做，当前只是**判据松绑**。

**修订要求**：
- 明确区分三类处置：`closed`（已达标）/ `reclassified`（判据变更，需重测）/ `deferred`（根治依赖 33-REA AST）
- 11 条 architecture_gap 中，按新判据实测达标的标 `reclassified→closed`，不达标的标 `reclassified→open`，依赖 AST 的标 `deferred`
- 在缺口记录的 `notes` 字段写明"判据从 X 改为 Y，原记录的 78-88% 重名率不再适用"

## 3. 修订建议 2：interface_mismatch 抽样仅 17 域，代表性不足（P1）

**提案表述**（§2.1）：
> 17-v4-wave-strategy 抽样：公开函数 25 个，docstring 率 64%

**问题**：
- 仅 1 个域、25 个函数的样本，外推到 13 条 interface_mismatch 缺口（覆盖多个域）**统计代表性不足**
- 17 域可能是 docstring 覆盖率较高的域，存在抽样偏差
- 提案自己也承认"需先统一注解定义"，但未给出定义统一后的全仓重测计划

**修订要求**：
- 至少抽样 3-5 个不同类型的域（如 9 基本面 / 18 数据 / 40 NN / 48 涌现 / 50 决策），每域 ≥ 20 个公开函数
- 先统一定义：L1 = 跨域 import 的公开 API（完整 type hints + docstring）；L2 = 模块内公开函数（docstring）；L3 = 私有函数（豁免）
- 按 L1/L2/L3 分别统计达标率，再决定 13 条缺口的处置

---

## 4. 修订建议 3：doc_debt 需内容门禁，不能只看文件存在（P2）

**提案表述**（§3.2）：
> 域目录 README 覆盖 100%，关键子模块文档覆盖 ≥ 80%

**问题**：
- "有 README.md" ≠ "文档合格"。空 README / 只有一句话的 README 不应算达标
- 缺**内容门禁**：README 应包含哪些最低要素（定位 / 入口 / 数据流 / 依赖 / 运行方式）？
- "关键子模块"由谁定义？无明确标准会导致主观判断

**修订要求**：
- 定义 README 最低内容门禁：定位（1 段）、入口（主要模块/脚本列表）、数据流（1 段或图）、依赖（外部库 + 内部域）、运行方式（关键命令）
- 定义"关键子模块"：被 ≥2 个其他域 import 的模块，或目录下 py 文件 ≥ 5 个的模块
- 不达标 README 标 `doc_debt` open，而非"有文件即关闭"

---

## 5. 修订建议 4：缺决策 SLA 与回填追踪（P2）

**提案表述**（§5 评审请求）：
> 两域裁决后，由 48 域按新判据重测 37 条缺口并回填状态

**问题**：
- 无决策 SLA：33-REA 和 0-系统文档管理域裁决后，48 域多久内完成重测与回填？
- 无回填追踪方案：37 条缺口的状态变更如何记录到 `capability_gaps.jsonl`？是否需要 `reclassified_from` 字段保留旧判据？
- 无回滚机制：若新判据导致大面积"伪关闭"，如何回滚？

**修订要求**：
- 明确 SLA：评审裁决后 5 个工作日内完成重测与回填
- 在 `capability_gaps.jsonl` 增加 `reclassified_from` 字段（旧判据描述）与 `recalibrated_at` 时间戳
- 回滚机制：若某类缺口重测后 closed 比例 > 80%，触发人工抽检 10% 样本
