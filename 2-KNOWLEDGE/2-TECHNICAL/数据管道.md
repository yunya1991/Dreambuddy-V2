# 数据管道

> 从数据源到消费端的完整链路——采集、校验、清洗、存储、消费五阶段，含网络受限下的降级策略。

## 数据源清单

| 数据类别 | 来源 | 状态 | 当前策略 |
|:---|:---|:---:|:---|
| 行情数据 | OKX API | ❌ 网络不通 | 降级到本地session数据 |
| 宏观数据 | Yahoo Finance | ⚠️ 部分可用 | 可用时优先使用 |
| 链上数据 | CoinGecko | ❌ 网络不通 | 降级到本地缓存 |
| 本地数据 | `cron_output/`, `meta.json`, session数据 | ✅ 可用 | 主用数据源 |

参考：Hermes-架构.md（Gateway cron调度架构）、Cron-调度.md（A系列cron任务排程）

## ETL流程

### 1. 采集（Cron定时任务触发）

数据采集由Hermes Gateway cron调度器统一管理（60秒tick），A系列任务按以下排程采集：

| 任务 | 排程 | 输出位置 | 来源 |
|:---|:---:|:---|:---|
| A1 | 01:00 daily | cron_output/ | Cron-调度.md |
| A2 | 02:00 daily | cron_output/ | Cron-调度.md |
| A3 | 03:00 daily | cron_output/ | Cron-调度.md |
| A4 | 每240min | cron_output/ | Cron-调度.md |
| A5 | 每480min | cron_output/ | Cron-调度.md |
| A6 | 每4h | cron_output/ | Cron-调度.md |

采集输出写入 `~/.hermes/cron/output/<job_id>/` 目录（来源：Cron-调度.md）。

### 2. 校验（数据新鲜度检查）

| 新鲜度 | 标记 | 措施 | 来源 |
|:---|:---:|:---|:---|
| ≤3天 | ✅ 正常 | 直接使用 | Screen1/Screen2配置 |
| 3~7天 | ⚠️ 警告 | 输出SOFT_WARN，仍可使用 | Screen1/Screen2配置 |
| >7天 | ❌ 过期 | 标记为不可用，触发降级策略 | Screen1/Screen2配置 |

### 3. 清洗（缺失值处理）

- 前向填充（ffill）：≤3天缺失，用最近有效值替代
- 删除：缺失比例<1%且随机分布
- 标记：无法自动修复的缺失值标记为NaN，上游消费时SKIP

### 4. 存储

- **本地文件**：`cron_output/<job_id>/` 存储每次cron执行结果
- **状态db**：`~/.workbuddy/memory/trading_execution_loop.json` 存储状态机
- **meta.json**：存储源数据元信息（最后更新时间、数据范围等）

### 5. 消费（Screen1/Screen2/Screen3读取）

```
数据管道 → Screen1(七维评分) → Screen2(信号筛选) → Screen3(执行监控)
               ↓                     ↓                     ↓
          方向+Regime         预设价位+强度          持仓状态+离场
```

Screen1读取行情指标与链上/cache数据生成方向判定 → Screen2基于方向约束筛选日线信号 → Screen3消费daily-presets.json执行入场与监控（来源：三屏系统架构）。

## 数据降级策略（V15 4层数据源回退链）

系统当前网络受限，按以下fallback链降级：

```
Layer 1: OKX API / Yahoo Finance / CoinGecko ── (在线优先)
    ↓ 网络不通时
Layer 2: cron_output/ 最新缓存数据 ── (缓存兜底)
    ↓ 缓存过期>3天时
Layer 3: meta.json + session本地历史数据 ── (本地兜底)
    ↓ 完全无数据时
Layer 4: Fail-Closed → SKIP（所有门禁阻断）
```

参考：三屏系统架构（数据流依赖链）、风控体系（Fail-Closed原则）、Cron-调度.md
