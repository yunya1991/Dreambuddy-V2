## 创建审批实例

```bash
lark-cli api POST /open-apis/approval/v4/instances \
  --data '{
    "approval_code": "模板code",
    "open_id": "发起人open_id",
    "form": "[{\"id\":\"widget_id\",\"type\":\"radioV2\",\"value\":\"option_value\"}]",
    "title": "📋 审批标题",
    "node_approver_open_id_list": [{
      "key": "node_id",
      "value": ["ou_xxx"]
    }]
  }'
```

### 关键参数

- `approval_code` — 审批模板code（从管理后台URL获取）
- `form` — JSON字符串数组，每个元素含id/type/value
- `title` — 可选，覆盖模板默认标题
- `node_approver_open_id_list` — 当前节点审批人

### 常见Widget类型

| type | 描述 | value格式 |
|:---|---|:---|
| input | 文本输入 | 字符串 |
| textarea | 多行文本 | 字符串 |
| radioV2 | 单选 | option的value |
| number | 数字 | 数字 |
| fieldList | 明细表格 | []或子字段数组 |

## 超时自动批准规则（详细）

### 规则一：governance — 永不自动

治理审批（索引系统优化、OKR变更、知识库重构等）**绝不自动处理**。|
即使超时12h+，仍然等待人工确认。原因是治理变更影响全系统，不能AI代决。

### 规则二：trading_emergency — 5分钟自动批准

A6情报监控触发紧急审批时（如价格暴跌、费率异常、持仓风险信号）：
1. 每10分钟 `approval-timeout-check` 扫描 PENDING 审批单
2. 检测到 `category=trading_emergency`
3. 检查 `is_emergency=true` flag
4. <5分钟 → 等待（给人工处理窗口）
5. ≥5分钟 → **自动批准** + 推送风控群通知
6. 人工可在飞书审批中心覆盖

### 规则三：trading（非紧急）— 等人

交易进化提案、参数优化等非紧急交易审批，即使超时也不自动批准。

### 规则四：gate_c / a9 — AI评分决策（30分钟超时）

Gate-C 和 A9 有自己的评分逻辑，不算"自动跳过"而是"AI代决"：
- **gate_c**: 基于 composite_confidence、A7评分、Screen1得分、价格漂移
  - 全部达标 → 自动批准
  - 任一低于强制拒绝阈值 → 自动拒绝
  - 灰色地带 → AI保守拒绝 + 建议人工确认
- **a9**: 基于 exit_score
  - ≥65 → 批准离场
  - <40 → 保持持仓
  - 中间区间 → 遵从A9 decision字段

## 超时自动批准

非交易类审批实例超时30分钟后触发AI兜底决策：

1. `approval-timeout-check` cron每10分钟扫描PENDING审批单
2. 超时≥30分钟 → 查询审批详情
3. AI评估是否可自动批准（基于审批类型+表单内容）
4. 自动批准 → 走完审批流程
5. 落地变更：Base记录更新+进展推送

**不自动处理的审批**：涉及资金/仓位/策略变更的交易类审批（需要人工确认）。

## OKR-Base-Knowledge 同步链

审批通过后的自动落地链：

```
审批通过
   ↓
① 飞书Base更新记录（状态字段→已批准）
② OKR进展推送（记录本次审批决策）
③ 知识库更新（涉及规则变更时更新对应文件）
④ Trading-Research群通知变更落地
   ↓
同步完成（回写审批备注：已同步四组件）
```
