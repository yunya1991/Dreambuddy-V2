## 1. RL_Trade_Ensemble_Analysis（纯 numpy RL，P1-4 影子沙盒范式）

### 1.1 工程实现亮点

```
rl_trade/
├── environment.py       # 纯 numpy 交易环境，step() 返回 (s, a, R, s', done) —— 无任何 torch
├── dqn_agent.py         # 1 层隐层 MLP 的 numpy 实现（W 矩阵用 np.random.normal 初始化）
├── replay_buffer.py     # Prioritized ER · 优先级 = |TD-error| + epsilon
└── ensemble_wrapper.py  # 5 个不同 seed DQN 投票，低一致时 WAIT 不交易（反脆弱）
```

### 1.2 与 P1-4 Shadow-RL 的对齐（直接借鉴）

| RL_Trade 元素 | dreambuddy L3 映射 |
|:--|:--|
| `environment.step()` 接口 | Shadow-RL 沙盒包装现有回测引擎（`10-classic-metrics/backtest_strategies.py`），输出同格式 (s,a,R,s') |
| 纯 numpy 无 torch | **项目硬约束**：MVP 不引重型依赖，完全对齐 |
| `ensemble_wrapper` 5 seed 投票一致性 → WAIT | 与项目现有方案 C ElasticGate3L 三权重门控思路一致；可把"RL 投票不一致"作为新增熔断条件 |
| 奖励 = `log_return − 0.001·(手续费 + 滑点)` | P1-5 摩擦模型的最小原型（比 rl-order-execution 简化版，先能跑再升级） |

### 1.3 代码风险

- DQN 目标网络 target_update 频率写死为每 100 步（高频 1h K 线没问题，日线太频繁）
- 经验回放采样是均匀而非 Schaul prioritized（但代码结构支持改成 prioritized）
- **本项目不直接抄代码**（license 合规），而是抄接口结构和沙盒的隔离模式。Shadow-RL 在 Phase 3 启动时单独写，保证零外部依赖。

## 2. genetic-stock-trader（基因编码，P1-2 编码参考）

### 2.1 基因结构与我们 P1-2 的对比

```
   genetic-stock 开源基因结构            vs         dreambuddy P1-2 Schema
┌──────────────────────────────┐          ┌─────────────────────────────────┐
│ CONDITION（阈值比较）          │          │ CONDITION（FUNCTION/THRESHOLD…）│
│   feature_idx: int            │          │   feature_ref: 具体名字符串     │
│   op: ['>','<','==']          │   ≈      │   operator: 标准 op + fallback  │
│   threshold: float            │          │   operand + parameters.range    │
│                              │          │   + required_data_quality       │
│ ACTION（buy/sell/hold×ratio） │    ≈     │   + code_ref（可追溯到原代码 L） │
│   kind: enum                 │          │   ACTION                        │
│   pct: float                 │          │   action_kind × position_ratio  │
│                              │          │   + sl_template/tp_template ±R  │
└──────────────────────────────┘          │   + _sl_tp_constraints（硬约束） │
                                          └─────────────────────────────────┘
```

**dreambuddy 比开源基因多三项关键能力**（这是为什么我们必须自己写，而不能直接替换成开源库的原因）：
1. **code_ref 可追溯审计**（金融合规要求 + 策略拆解来源校验，单测 TR-SG-02 要求 100%）
2. **sl/tp 的模板化与爆仓安全优先级**（§3.2 _sl_tp_constraints — 开源库根本不关心爆仓价）
3. **parameters.range 为 Schluter gmax 预埋轴**（开源库变异是随机扰动，我们沿进化主方向）

### 2.2 锦标赛选择算子可以借鉴

```
父代选择 = 随机抽 7 个策略，取 ESS_score 最高的 2 个作为父母
单点交叉概率 = 0.7，变异概率 = 0.03 × 各参数 gmax 方向分量
```

这个"7抽2"的锦标赛设计（而非轮盘赌）可以在 P1-4 上线时代替随机 gmax 探索，维持多样性。

## 3. rl-order-execution（双尺度摩擦冲击模型，P1-5 直接抄公式）

### 3.1 核心模型：Almgren-Chriss 双尺度市场冲击

```
瞬时冲击（临时）：temporarily_impact =  η · sign(trade_size) · |trade_size/σ_V|^α
持久冲击（永久）：permanent_impact  =  γ · trade_size/V_t + ε

V(s,a) 奖励 = 实现净收益  − κ_temp·临时冲击  − κ_perm·持久冲击
(其中 κ_temp + κ_perm < 0.01 时才允许入场，否则 L3 自动 WAIT)
```

**关键：α 指数在流动性好（BTC）时 ≈ 0.5（平方根定律），流动性差（meme币）时 α → 1.0（线性）。** 这恰好复用 L1 R_reflexivity 的 liquidity_index 子项作为 α 的插值参数——**L1-L4 的天然闭环接口**！

### 3.2 与现有 V9/V15 马丁的关系

现有马丁的"逐级加仓减仓"是仓位管理，不是冲击建模。**同一笔开仓的**内部拆单（比如一次 2000 USDT 的订单拆成 3 笔发）冲击由 rl-order-execution 管，马丁不管。所以 P1-5 的嵌入位置是 A6-执行端前置，而不是 V15 信号层——位置清晰、无耦合冲突。

## 4. evolutionary-trading-strategies（ESS 多样性奖励补充）

4.1 亮点是 **Walk-forward 验证**（不是一次性 train_test_split，而是滚动 70% 训练 + 30% 验证）——这让 ESS 打分的"抗入侵抵抗"是**跨时间片**的，更接近真实市场的非平稳性。

4.2 **多样性奖励**：当进化种群中两个策略的表型向量夹角余弦 < 0.7 时，给 ESS_score 额外 +0.05 奖励。这避免种群"都收敛到同一个有效但拥挤的策略"（和 ESS 抗入侵的初衷完全一致）。

建议 P1-4 上线时一起加入这条多样性奖励（实现简单，效果明显）。

## 5. Deep-RL-Trading-Ensemble（2.3k Star 最大项目）

5.1 强依赖 PyTorch + Ray + 外部 GPU → 直接违反 MVP 重型依赖约束。

5.2 值得借鉴的**非训练部分**：其 **PCA Eigenportfolio 组合层**（P2-3）：
- 对 Top 30 币种收益率矩阵做 PCA，取 PC1 解释率 ≥ 55% 的主成分作为"市场风险因子"
- 所有 L2 选出来的策略组合，再对 PC1 做**中性化**（即组合收益率与 PC1 的 beta ≈ 0）
- 这在 2022 全年 BTC 单边下跌时让组合回撤降低了 18pp

5.3 适配风险高的原因：
- 中性化需要每日再平衡，交易成本高
- dreambuddy 没有专门的组合配置回测沙盒，需要改造 A8
- 所以 P2-3 标记为高风险，先不入主干
