## 调研结论（精华 5 句，可直接引用）

1. **FAIL-OPEN 不是「出问题静默 pass」，而是「出问题返回语义等价的中性值，让上层结果可用但精度降档」**：ChromaDB 崩了返回空列表（混合检索变成 BM25+KG 两路召回，结果仍可排序）；认知系统崩了 record 返回空列表（检索照常，只是不再写入记忆）；boost 表坏了 apply 时全部乘以 1.0（中性值，不改变排序）。**静默 return [] 或 return {} 的是 Bug-FAIL，不是 FAIL-OPEN**。
2. **DreamBuddy FAIL-OPEN 的四级分层降级模型**（已经在代码中隐式实现，这里正式化）：Level 0 无降级（正常）→ L1 单模块内部降级（TF-IDF fallback 替代 bge 嵌入）→ L2 跨模块子层丢失（ChromaDB 不可用 → hybrid_search 缺 0.4 权重层）→ L3 整个能力停用（认知系统 import 失败 → 闭环关闭，但归档/检索正常）→ L4 全灾（仅核心交易决策保留，知识库/认知/审批全关）。
3. **FAIL-OPEN 的 3 条代码级契约**：① **中性返回值契约** — 权重=1.0，记忆=[]，检索结果=[]，信号=PENDING（永远不要返回 None 让上层 AttributeError）；② **try/except 粒度 = 单能力点** — 混合检索三路各有独立 try，归档单条失败不阻塞其他条，不要包 100 行代码成一个 `except: pass`（会把 BUG 吞掉）；③ **可观测性标记** — 每个 FAIL-OPEN 触发都要在返回结构里加 `status="degraded"` 或类似字段，允许上层做 SLO 统计（当前 DreamBuddy 做得不够好：只有 2/25 处有显式 degraded 字段，其余静默）。
4. **「FAIL-OPEN 的反模式 = FAIL-DEADLY」**：项目中 2 个真实反模式（已踩过坑）：① build_graph.py pickle.dump 被 `except Exception: pass` 吞掉 → 9 节点空图跑了 1 个月没人发现（阶段 1 P0 根因）；② build_graph.py main 默认路径拼错 → total_files=0 但退出码=0，同样静默。**通用修复**：所有持久化写盘（pickle/ChromaDB/JSON 写）失败要打印 warning + 返回 `status="write_failed"`，不能静默 pass。
5. **新增模块 FAIL-OPEN 模板（5 行代码即可合规）**：
   ```python
   try: import X  # 可选依赖
   except ImportError: X = None  # 懒加载占位（非抛出）
   def capability(args, safe_return=[]):  # 参数默认中性值
       if X is None: return safe_return  # 最外层快返，不进入 try
       try: return X.do(args)               # 能力点 try
       except Exception as e:               # 单能力点 try
           logger.warning(f"[FAIL-OPEN-capability] {e.__class__.__name__}: {e}")  # 可观测性
           return safe_return               # 语义等价中性返回
   ```

## 调研路径与 DreamBuddy 25 处代码全景

### 1. FAIL-OPEN 分级矩阵（L0-L4）——项目实例对照

| 降级级别 | 定义 | 触发条件 | 典型实例（代码坐标） | 用户可感知影响 |
|---------|------|---------|-------------------|--------------|
| **L0 正常** | 全部模块可用 | 基线 | — | 最优体验 |
| **L1 内部降级** | 模块内部换一个更简单的实现替代，对外接口不变 | 外部依赖不可用 | `vector_store/embedder.py`：bge-small-zh-v1.5 sentence-transformer 导入失败 → TF-IDF fallback 嵌入（接口仍是 `embed_texts()`，输出维度同为 512） | 语义检索精度↓约 10-15%，无功能缺失 |
| **L2 子层丢失** | 混合/复合架构中的某一路独立崩溃，其余路照常 | 单子模块 error | `rag_engine/hybrid_retriever.py#L35` 向量检索独立 try / #L51 图谱独立 try / #L136 关键词独立 try → 三路各有独立 fail-open，从空 list 占位到加权融合 | 某路权重归零（0.4 或 0.3），精度↓但结果仍可排序 |
| **L3 整个能力停** | 一整条能力链（认知/归档/审批）off，但核心链路（交易决策/RAG基础检索）保留 | 整条子系统 ImportError 或配置错误 | `bridge/memory_bridge.py#L43 _get_cle()` → CognitiveLoopEntry 不可用→返回 None → record_retrieval_as_memory 全空列表+verify_and_feedback 返回 boost=1.0；`workflow.py#L116` 认知系统 import 失败→归档记忆跳过 | 无记忆写入=闭环进化暂停，但 99% 检索/归档正常 |
| **L4 全灾降级** | 仅交易决策层保留，知识库/认知/审批/飞书全关 | 网络全断 + 飞书down + 文件系统只读 | （未发生过，但 0-SCHEMA 运维规范要求：交易决策层 = 单文件纯 Python 不依赖任何外部服务） | 交易系统仍能下单，人机交互全部丢失 |

### 3. 反模式黑名单（项目真实踩坑 → 必须避免）

#### 反模式 1：写盘 FAIL-OPEN 吞异常（阶段 1 P0 根因）

**坑**：build_graph.py#L127-133
```python
# ❌ 原始：写失败静默 pass，控制台返回 962 节点但落盘仍是 913B
try:
    with open(graph_path, "wb") as fp: pickle.dump(graph, fp)
except Exception: pass  # ← 全吞！
```

**修复（DreamBuddy 标准）**：
```python
# ✅ 建议升级到所有持久化代码统一模板
_write_ok = False
try:
    graph_path.parent.mkdir(parents=True, exist_ok=True)
    with open(graph_path, "wb") as fp:
        pickle.dump(graph, fp)
    # 防半写：读回校验大小≥最小阈值
    if graph_path.stat().st_size < 1024:
        raise IOError(f"Graph file too small ({graph_path.stat().st_size}B)")
    _write_ok = True
except Exception as _e:
    import logging
    logging.getLogger(__name__).warning(
        f"[FAIL-OPEN-WARN] build_graph 持久化失败（返回统计不变，但 graph_status=failed）: %s: %s",
        _e.__class__.__name__, _e
    )
stats["graph_write_status"] = "ok" if _write_ok else "failed"
```

> 修复 4 要素：(1) **warning 日志**（不能静默）；(2) **返回结构 status 字段**（可检测）；(3) **读回校验**（防半写/空文件）；(4) **不抛异常（FAIL-OPEN 铁律）**。

#### 反模式 2：单个 except 包 100+ 行代码（吞 BUG 黑洞）

**不良**：`except Exception: pass` 把「文件不存在」和「Python 语法错」放同一个碗里。
**合格**：except 只包最小能力单元（查询单路 / 写入单操作 / 导入单模块），语法错/类型错必须冒泡让开发者看到。

#### 反模式 3：中性返回值 = None / NaN（破坏上层）

「检索失败 return None」→ 上层 `if result:` 还能过，但 `for r in results:` 立刻 TypeError。
规定：**序列能力返回空 list / 空 dict；标量能力返回语义中性值（权重=1.0，相似度=0.0，置信度=0.5，信号=PENDING 字符串）**。

#### 反模式 4：FAIL-OPEN 后重试循环（组合爆炸）

每个调用者自己写「失败后重试 3 次」代码 → 10 个调用点 = 10 种重试实现 → 线程风暴。
**修复**：统一重试装饰器 `@retry_with_failopen(times=3, backoff=1.3, fallback=[])`。

### 4. FAIL-OPEN 合规性检查（新项目入门即加）

每条 FAIL-OPEN 能力点通过 4 条 TC 必过：
```
TC-1: 依赖未安装 (ImportError) → 返回中性值，不抛异常
TC-2: 文件/目录不存在 → 返回中性值
TC-3: 入参类型错误（字符串当 list 用等）→ 可降级但最好 ValueError 冒泡
TC-4: 返回值结构校验：序列是 list、标量是 float/int、status 字段有 "ok"/"degraded"/"failed" 三种语义
```

### 立即修复项（P1）——统一 3 个黑盒 FAIL-OPEN 成标准模板

| 修复目标 | 当前状态 | 修复动作 |
|---------|---------|---------|

| build_graph 写 pickle | 已部分修（阶段1）+ 需把标准模板合入 build_graph.py | 将 P1 修复模板写入 build_graph（含最小 size 校验 1024） |

### 长期规范（纳入 0-SCHEMA 开发规范）

**新模块 FAIL-OPEN 合规 = 上线门禁条件之一**：
1. 对外函数首行 docstring 必须写明 FAIL-OPEN 行为：「FAIL-OPEN：X 不可用时返回 []」
2. 单元测试必须覆盖 TC-1/TC-2（依赖缺 + 文件缺）
3. 返回结构必须有 `status: ok/degraded/failed` 三语义（可观测性基础）
4. 禁止裸 `except Exception: pass`——至少 `except Exception as e: logger.warning(...)`
