## §2 TRAIN-BASE SPEC 增量修改（B1/B2/B3/B6）

### 2.1 TB1 PSI 补 K-S 检验（B1）

```python
# TB1 §1.3 drift_detector.py 新增 K-S 检验函数（~20 行）
from scipy.stats import ks_2samp

def ks_test(expected: List[float], actual: List[float], alpha: float = 0.01) -> Tuple[float, bool]:
    """Kolmogorov-Smirnov 两样本检验 — 第二漂移门
    
    - 零假设 H0：expected 和 actual 来自同一分布
    - p-value < alpha → 拒绝 H0 → 显著漂移
    
    Args:
        expected: 历史基线分布
        actual: 当前观测分布
        alpha: 显著性水平（硬编码 0.01，H8 约束）
    
    Returns:
        (statistic, is_drifted): KS 统计量 + 是否漂移
    """
    statistic, p_value = ks_2samp(expected, actual)
    return float(statistic), p_value < alpha


# TB1 §1.3 classify_drift 扩展（三重漂移检测）
def classify_drift(psi_value: float, ks_drifted: bool) -> str:
    """三重漂移检测综合判定
    
    - PSI stable + KS not drifted → "stable"
    - PSI minor 或 KS drifted → "minor_drift"
    - PSI severe 或 (PSI minor + KS drifted) → "severe_drift"
    """
    if psi_value < PSI_STABLE and not ks_drifted:
        return "stable"
    elif psi_value >= PSI_MINOR_DRIFT or (psi_value >= PSI_STABLE and ks_drifted):
        return "severe_drift"
    else:
        return "minor_drift"


# TB1 新增 Kill Switch 链（B6，行业标准分层）
def drift_kill_switch(drift_level: str, context: Dict[str, Any]) -> Dict[str, Any]:
    """Fail-closed 分层 Kill Switch（行业标准）
    
    触发条件链：
      severe_drift → Kill Switch 触发
      - Level 1 Warning: 降低仓位 50%
      - Level 2 Pause: 停止新开仓
      - Level 3 Halt: 强平所有仓位
    
    context: 调用方传入，包含 drift_level 原因和 trace_id
    """
    if drift_level == "stable":
        return {"action": "no_op", "level": 0}
    elif drift_level == "minor_drift":
        return {"action": "log_alert", "level": 1, "reason": context.get("reason")}
    else:  # severe_drift
        return {"action": "kill_switch", "level": 2, "tiers": ["reduce_position_50%", "pause_new", "halt_all"]}
```

**TDD 补 3 条**：

| 用例 | 预期 |
|---|---|
| KS 检验两组明显不同分布 [0-1] vs [4-5] | p-value < 0.01，drifted=True |
| classify_drift(psi=0.15, ks_drifted=True) | "severe_drift"（PSI minor 但 KS drifted → severe） |
| drift_kill_switch("severe_drift", {"reason": "PSI=0.3, KS=p=0.001"}) | action="kill_switch", level=2 |

### 2.2 TB3 AlphaPareto 补过程奖励维度（B2）

```python
# TB3 §3.3 RewardComponents 新增 process_reward component
@dataclass
class RewardComponents:
    """AlphaPareto 四维 → 六维奖励分量（补过程奖励）"""
    p_verify_success: float      # 维度 1：TB2 Beta verify mean
    p_recall_hit: float          # 维度 2：同类事件 recall 命中率
    psi_stability: float         # 维度 3：1 - PSI（三重检测综合）
    citation_diversity: float    # 维度 4：PoE known_gaps 越少奖励越低 + 跨域引用数
    process_reward: float        # 维度 5（新增）：中间 step 奖励（Query→Search→Read→Synthesize 每步的可验证子目标）
    transition_smoothness: float # 维度 6（新增）：相邻 step 的 state 转移平滑度（transition probability matrix 的 entropy）
```

**为什么过程奖励 > 结果奖励**（OpenAI AgentPRM / Meta HiPRAG 实证）：纯结果奖励 credit assignment 困难（哪个 step 好/坏？），过程奖励在每个中间点提供即时梯度信号。我们用贝叶斯 update 替代 PRM 模型训练，但概念一致。

## §3 Oracle 验证层：从 Mandate 门控抽出为独立角色（B5）

### 3.1 Two Sigma 四层分层 → 我们的映射

```
Two Sigma 四层                      → 我们的架构
─────────────────────────────────────────────────
Advisory 建议层（只读）              → 域内 agent 分析层（SPEC-L0-DOMAIN-AGENTS v0.2）
Oracle 验证层（独立 cross-check）  → 【新增】MCP 壳后 Oracle 验证层
Operational 自动化层                → MCP 壳工具面（SPEC-L0-MCP-PACKAGING v0.3）
Agentic 协调层                      → MCP shell orchestration（TECH-L0-MCP v0.1 §2）
```

### 3.2 Oracle 层做什么 vs 不做什么

| 做什么 | 不做什么 | 硬约束 |
|---|---|---|
| 独立 agent 输出做 cross-check（如 REA 做梦结论 → Oracle agent 用不同视角验证） | 修改 agent 输出 | 纯 read-only |
| 标注 `oracle_confidence: float` 在 envelope.meta | 触发 agent 重跑 | FAIL-OPEN（oracle 低置信度只告警，不阻塞主流程） |
| 把 oracle 评分作为 TB3 AlphaPareto 的第 7 个维度 | 绕过 Mandate 门控 | Oracle 输出本身也过 Mandate 门 |

### 3.3 Oracle 层与我们已有模块的关系

- 不替代 COMM-SHADOW 影子模式 —— 影子模式是**旁路观察壳返回体**，Oracle 是**壳后 agent 输出 cross-check**。两者互补：影子看壳层行为，Oracle 看 agent 层行为
- 不替代 PACKAGING Mandate 治理 —— Oracle 是验证层，Mandate 是写入门。Oracle 验证完，要写还得过 Mandate
- 与 TB3 AlphaPareto 集成：oracle_confidence 作为奖励分量之一

**当前阶段决策**：Oracle 层设计文档先写（DOMAIN-AGENTS v0.3 增量），编码等 Phase A-C agent 产出稳定后再加。

## §4 Agent Card 自描述 → MCP 注册表增量（B4）

### 4.1 Google A2A Agent Card 核心概念 → 我们的 mcp_capabilities.yaml

A2A 的 Agent Card 让每个 agent 自描述 shadow/sandbox/trainingHooks 能力。我们可以直接加到 mcp_capabilities.yaml 的 shell 条目里：

```yaml
# mcp_capabilities.yaml schema 1.1 新增字段
shells:
  - shell_id: cognition_mcp
    # ... 现有字段 ...
    capabilities:  # 新增：shell 自描述能力
      shadow_capable: true          # 支持影子模式旁路观察
      sandbox_isolation: null       # 不支持 Docker 沙箱（当前阶段）
      training_hooks: ["on_verify", "on_recall"]  # TB1-TB5 可钩挂点
      oracle_verifiable: true       # Oracle 验证层可 cross-check
```

### 4.2 不做什么

- 不引入完整 A2A 协议层（JSON-RPC + Task 状态机 + Agent Card 发现端点）——适配成本太高，与 MCP JSON-RPC 并存增加复杂度
- 只采纳 Agent Card 的**自描述概念**，加到已有的 mcp_capabilities.yaml schema 里，作为 1.1 版本增量
