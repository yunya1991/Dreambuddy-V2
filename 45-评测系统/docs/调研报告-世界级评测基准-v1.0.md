# 调研报告 — 评测系统世界级基准 v1.0

> 调研日期：2026-11-01
> 调研对象：45-评测系统 SPEC v0.3
> 调研方式：四路并行（AI 评测 / 金融回测与高可用 / 工程门禁与供应链 / 平台工程与统计治理），覆盖 21+ 平台与规范
> 产出用途：支撑 SPEC v1.0 的架构、标准、阈值与实施计划

---

## 0. 结论摘要（先给判断）

1. **最大结构差距不是评测项，而是“可复现实体”缺失**。世界级平台普遍固化 6 个抽象：`Dataset(+version/split)`、`EvalSpec`、`Evaluator`、`Scorer`、`Run`、`Registry`。v0.3 只有 `gateway→dispatcher→judge→reporter` 流程管线，缺 `Run` 与 `Registry`，导致“同一次评测能否复现、两次评测能否比较”无法回答。
2. **门禁必须判置信下界，不能判点估计**。点估计 0.703 与 0.70 阈值的差异没有统计意义；`score`、`n`、`CI` 必须同时落库，否则门禁可被样本波动“刷过”。
3. **LLM 裁判不能直接进硬性项**。必须自带校准凭证（≥200 人工标注、Cohen's κ≥0.6、Krippendorff's α≥0.67），并锁定模型快照、prompt 哈希、temperature=0；A/B 顺序对调消位置偏差。
4. **金融类必须把“回测真实性”升为硬性项**。PBO>0.50、数据泄漏、成本口径缺失属于“结论不可信”，不能用加权分掩盖；`N_trials` 不登记则 DSR 不可计算。
5. **工程类硬性项应收敛到三类**：秘密、可利用漏洞、可追溯性（SBOM+证明）。覆盖率拆为“新增行覆盖率（硬性 0.80）”与“全仓覆盖率（加权 0.60→0.70）”，采用 Sonar「Clean as You Code」避免历史债务卡死门禁。
6. **平台工程在单机 4C16G 上应选 Celery+Redis+PG 状态机**，不选 Temporal/Argo/Dagster；沙箱选 Docker+gVisor；证据链选 Sigstore Bundle + 哈希链 + MinIO WORM，而非强依赖在线 Rekor。

## 2. 分领域发现

### 2.1 AI/ML 评测

**2.1.1 核心抽象**
- OpenAI Evals 用 `<name>.<split>.<version>` 标识评测注册项；lm-evaluation-harness 用 TaskConfig + version；HELM 用 run + leaderboard。三者共同点：**评测定义本身是版本化对象**，不是一次函数调用。
- MLflow/Vertex/Azure/Weave/RAGAS 均采用“evaluator 库化 + 每样本留痕 + 回归抛出异常（RegressionError）”的模式，而不是只给一个总分。
- 启示：45 必须显式建模 `EvalSpec`（数据集@版本、切分、指标、判分器、阈值、seed/温度）与 `Run`（一次不可变执行记录），并把 `run_spec_hash` 写入报告。

**2.1.2 LLM-as-judge 可靠性**
- HELM Safety 采用双裁判取均值；单项裁判在位置偏差、长度偏差、风格偏差下漂移明显。
- 研究显示 `temperature=0` 仍存在边界样本翻转，因此只能承诺“可追溯”，不能承诺“逐位可复现”。
- 启示：裁判必须过校准集并记录 metascore；A/B 顺序对调、不一致记 tie；prompt 哈希 + 模型快照 + 温度全量落库；未过校准的裁判只能进加权项。

**2.1.3 数据集与基准治理**
- lm-evaluation-harness 内置 decontamination；业界常用 n-gram 重叠率作为污染红线。
- 金融/时序场景必须用 purged CV + embargo，按 label horizon 剥离训练/测试边界样本。
- 启示：dataset 需 `content_hash + split_manifest`；污染红线建议 13-gram 重叠 <0.1%；AI 类评测集拆“能力集 / 回归集 / 校准集”三份。

**2.1.4 阈值与回归门禁**
- “Adding Error Bars to Evals” 指出小样本点估计不可用于门禁；应报 CI（Wilson 或 bootstrap）。
- agentic eval 的随机性要求重复 R 次并报 pass^k；flaky 用例应隔离而不是反复重跑到通过。
- promptfoo 的 CI/CD 门禁实践：语义化退出码 + 用例级 threshold 覆盖，支持 fail-on-regression。

### 2.2 金融验收与回测

**2.2.1 高可用验收**
- TCE 白皮书将多副本、探活、故障注入恢复列为硬性门槛；AWS FIS 强调 experiment template / targets / stop conditions 三要素；K8s 探针有 liveness/readiness/startup 三类，阈值需显式声明。
- 启示：故障注入必须是“可复现实验”，不是手工演练；报告需记录注入起止、影响请求数、错误率曲线、恢复耗时、订单零丢失对账。
- 建议 RTO/RPO：订单 RPO=0、RTO≤30s；行情 RTO≤60s；整站切换≤5min。

**2.2.2 回测严谨性**
- DSR/PSR 依赖 `N_trials`；不登记试验次数就无法校正多重检验。
- PBO（CSCV，S=16）是“回测过拟合概率”的直接度量；>0.50 表示结论与随机选择无异。
- 切分应使用 purged k-fold + embargo；CPCV（N=6/k=2）可重建多条路径，适合评估策略稳健性。
- 引擎口径差异是隐性陷阱：qlib 报超额收益且含/不含成本两套；zipline 默认固定滑点与成交量限制；backtrader/vectorbt 默认零成本。
- 启示：回测验收必须“先声明口径，再双引擎复算”，偏差 >10% 需说明；成本×2 稳健性、容量（单笔 ≤10% ADV）纳入加权项。

**2.2.3 模型风险治理**
- 美联储 SR 26-2（新版模型风险管理指引，2026 年发布；引用时以官方生效版本为准）要求模型台账、owner、版本、上次验证日期、持续监控。
- 启示：报告需带 model owner/version/last_validated_at；45 的评测记录本身可作为模型风险台账证据。

### 2.3 工程门禁与供应链

**2.3.1 门禁条件模型**
- SonarQube Quality Gate 的“New Code vs Overall Code”是解决历史债务的关键设计；Clean as You Code 明确新代码定义。
- 启示：覆盖率拆两条；门禁条件应可组合、可版本化，且默认只对新代码生效。

**2.3.2 可追溯性**
- SLSA 1.x 定义构建级别；in-toto/Sigstore 提供证明与签名；SBOM（CycloneDX/SPDX）绑定制品 digest；GitHub Artifact Attestations 原生支持 L2。
- 启示：核心是“三方一致”：`commit_sha ↔ build_digest ↔ SBOM subject digest`，并由签名证明绑定。缺一环即不可追溯。

**2.3.3 防绕过与防 flaky**
- required checks、branch protection、push protection 是前置阻断；但 `|| true`、`--exit-code 0`、skip 标记等旁路痕迹必须被审计。
- flaky 用例允许一次自动重跑并记录 `rerun_pass`；用例级 flaky 率 >1% 进入 quarantine（不计入分子、限期修复）。

### 2.4 平台工程与统计治理

**2.4.1 编排选型（单机 4C16G）**
- Temporal 自托管需独立持久层与多进程，余量不足；Argo 强绑 k8s；Dagster 常驻 webserver+daemon 过重。
- Celery + Redis broker + PostgreSQL 状态机可行：`acks_late` + `eval_id` 唯一键幂等、revoke + DB 取消标志、多队列优先级、指数退避。

**2.4.2 证据与审计**
- Sigstore Bundle（DSSE + in-toto Statement）可作为标准证据容器；逐条 `prev_hash` 链 + 日终 Merkle 根（RFC 6962 思路）可离线验证；MinIO Object Lock（compliance）提供 WORM。
- 不采用在线 Rekor 强依赖：离线可用性差，故障时阻断主流程。

**2.4.3 存储模型**
- 报告二进制落 WORM 桶，库内只存 `uri + sha256`；OpenLineage 的 START/COMPLETE run facet 可登记血缘；41 索引登记报告 URI。

**2.4.4 沙箱**
- Docker + gVisor(runsc) 在单机上性价比最高；Firecracker 需 KVM 与设备运维，收益不抵成本。
- 配额建议：cpu=1、mem=2g、pids=256、超时 kill；rootfs 只读 + tmpfs；非 root + seccomp；`network=none` 仅 allowlist；密钥 `secret_ref` 运行时注入并脱敏。

**2.4.5 人工评测**
- 分层抽样 + Wilson 区间：每层 n≈100（p=0.5、±10%、95%）。
- 双标重叠 10–20%；Krippendorff α 下限 0.67、目标 0.80（ordinal），Cohen's κ≥0.60；α 不足先扩样，不发言。
- 分歧走第三方仲裁 + 校准会，记录仲裁理由。

**2.4.6 阈值治理**
- Wilson 区间 + Beta 后验 + SPRT（α=0.05/β=0.1）监测通过率漂移；灰度误拦截率 ≤1%（看 Wilson 上界）。
- 阈值变更需新版本 + 双人审批 + 7 天 shadow；季度用 golden set 回归基线。

## 4. 采纳与拒绝决策

| 决策点 | 采纳 | 拒绝 | 理由 |
|---|---|---|---|
| 编排 | Celery + Redis + PG 状态机 | Temporal / Argo / Dagster | 单机资源、运维复杂度、k8s 绑定 |
| 证据 | Sigstore Bundle + 哈希链 + Merkle 根 + MinIO WORM | 在线 Rekor 强依赖、自研加密日志 | 离线可用性、标准化、可验证 |
| 沙箱 | Docker + gVisor | Firecracker | 单机收益/成本比 |
| 人工抽样 | 分层 + Wilson + 双标 + 仲裁 | 全量人工、单标 | 成本与一致性可度量 |
| AI 裁判 | 校准后进加权项；硬性项需双裁判+人工对照 | 未校准裁判直接进硬性项 | 可靠性不足 |
| 金融回测 | 硬性真实性 + 加权显著性 | 用加权分掩盖 PBO/泄漏 | 结论可信性优先 |
| 工程门禁 | New Code 门禁 + 三方一致 | 全仓一刀切 | 历史债务会卡死流水线 |
| 阈值 | 版本化 + 双人审批 + shadow | 直接改固定阈值 | 防门禁漂移 |
| 判定 | PASS/BLOCK/INCONCLUSIVE | 仅 PASS/BLOCK | 样本不足时默认不放行 |

## 6. 残余不确定性（需灰度期闭环）

1. AI 类阈值（自动评测 0.75、压测 0.80、人工 0.75）为保守初值，缺少本项目历史分布，必须 P1.5 灰度后用 Wilson CI 复核。
2. 金融类 OOS 净 Sharpe 初值（加密 0.8 / 股票 0.5）与 DSR 判定可能冲突；建议“DSR 为主、Sharpe 为辅”，灰度期双记。
3. 单机 4C16G 下 gVisor 对编译型测试的 CPU 损耗未实测；需 P0 做基准（目标额外开销 ≤20%）。
4. Celery + Redis 的取消语义依赖轮询标志，强杀进程可能留下临时文件；需幂等清理与审计。
5. 人工评测成本与排期未量化；P1.5 需统计每层样本的实际工时。
