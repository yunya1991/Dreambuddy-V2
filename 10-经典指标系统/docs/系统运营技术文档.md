## 0. 运营目标与术语

### 0.1 运营目标（传统金融运维口径）
- 可用性：交易链路可观测、可诊断、可恢复（不追求零故障，追求可控）。
- 可解释性：任何“无信号/无订单/拒单”必须能被口径解释，不允许黑盒化。
- 可回滚：任何改变生产行为的动作必须具备回滚点。
- 可审计：所有关键动作具备 trace_id、证据链与落盘产物，支持回放复盘。
- 低误报：用分位阈值 + 连续命中 + 冷却幂等降低告警风暴。

### 0.2 关键术语
- 生产交易系统（Production）：承担实盘执行、风控、策略运行与生产数据写入的系统。
- AI Agent：负责理解意图、拆解任务、组织证据与建议、调度 Skills、触发沙箱任务与推动审批。
- 沙箱（Sandbox）：回测/稳健性/评估在隔离环境执行；默认禁网、无真实密钥；产物不得自动写入生产。
- 宿主外联（Host Skills）：推特/TG/搜索/GitHub 等外联能力只在宿主侧执行，与生产/沙箱隔离。
- outbox：面向运营的产物落盘队列（告警、审批请求、审计动作、报告等）。
- 卡点：链路未推进的“可解释原因”，例如 gate_fail、approval_pending、queue_full、auth_expired。

## 1. 运营分层架构与职责边界

### 1.1 “四层 + 控制塔”统筹模型
运营采用“四层分工 + 控制塔（Control Tower）”：

1) 监控层（Poll & Detect）
- 责任：按固定节奏轮询关键只读接口与 outbox，生成结构化健康快照与告警。
- 约束：只读；不得直接触发生产写入；不得由外部内容直接拼接命令/URL/工具输入。
- 推荐承载：nanoclaw（定时任务/编排/队列/幂等）。

2) 分析思考层（Explain & Decide）
- 责任：基于 SSoT 文档命中 FAQ/Runbook，形成可解释的根因假设与最小修复建议。
- 输出：triage 报告（证据链、FAQ 命中、修复选项分级、风险与回滚）。

3) 工具调用修复层（Validate & Fix）
- 责任：在权限边界内执行“验证/修复”，优先修复自动化流程本身，再推进业务自动化。
- 约束：默认 tighten-only；任何可能改变生产行为的动作必须走审批与审计。

4) 个人助手（Propose & Approve）
- 责任：把“需要人工审批”的事项整理为一页纸提案（含证据、影响、回滚、验收），并在审批通过后推进放行与通知。

控制塔（Control Tower）
- 不是新增系统组件的强制要求，是运营视角的统一口径：
  - 统一 trace_id/idempotency_key
  - 统一产物（outbox）驱动状态
  - 统一卡点与状态机（RUNNING / PENDING_APPROVAL / BLOCKED / DONE / ROLLED_BACK）

### 1.2 强边界：生产、Agent、沙箱、宿主外联
边界原则以 2.0 文档为准（参见 [交易AI Agent 技术文档2.0.md](file:///Users/zhangjiangtao/ft_userdata/经典指标机器学习系统/交易AI%20Agent%20技术文档2.0.md) 1.4、3.1）：
- 生产：受保护边界，写操作必须受控、可审计、可回滚。
- Agent：调度与思考，不直接改写生产并即时生效。
- 沙箱：隔离执行，默认禁网，不加载真实密钥，不可直写生产。
- 宿主外联：负责对外信息获取与发布，对外发布仅允许来自“已审批/已门禁通过”的事件。

## 2. 权限与风险分级（运营的“红线”）

### 2.1 能力分层（R0–R3）
采用 2.0 文档的 R0–R3（参见 [交易AI Agent 技术文档2.0.md:L1212-L1218](file:///Users/zhangjiangtao/ft_userdata/经典指标机器学习系统/交易AI%20Agent%20技术文档2.0.md#L1212-L1218)）：
- R0：只读观测（默认放开）。
- R1：沙箱验证（默认放开）。
- R2：受控变更（配置/灰度/回滚/受控重启，需要审批与审计）。
- R3：代码变更（严格流程，必须变更包 + 人工审核）。

### 2.2 告警分级（P0–P3）
- P0：资金/执行安全风险或链路不可控（可能扩散）。原则：先止血后复盘。
- P1：关键链路持续异常（信号/订单/门禁/数据新鲜度显著偏离）。
- P2：功能降级或局部异常（可运营绕过或短期容忍）。
- P3：优化建议/边际偏离/一次性告警（进入观察与周会复盘）。

### 2.3 默认策略（强制）
- 默认 tighten-only：修复动作默认“收紧风险、降低暴露、提高门槛、禁开仓”，禁止用“放宽门槛/加仓”掩盖执行或数据问题。
- 任何扩大风险敞口的动作（新增交易对、上新策略、放宽风控阈值）必须走人工审批。

## 3. 运行节奏（Cadence）

### 3.1 10 分钟轮询（轻量）
- 目标：发现异常、输出可回放证据、形成卡点解释，不追求一次覆盖所有深诊断。
- 产物：health_snapshot、alerts（P0/P1 优先）。

### 3.2 每日深检（UTC 凌晨）
- 目标：做链路深检（link_check/triage/backtest/changeset），形成可审批的候选变更包。
- 推荐参数与产物要求见 2.0 文档的清单（参见 [交易AI Agent 技术文档2.0.md:L1048-L1056](file:///Users/zhangjiangtao/ft_userdata/经典指标机器学习系统/交易AI%20Agent%20技术文档2.0.md#L1048-L1056)）。

### 3.3 每周复盘（运营例会）
- 聚焦：P0/P1 事件复盘、误报/漏报、阈值调整、FAQ 补齐、自动化卡点清零。
- 输出：周报（top issues、top reasons、变更清单、下周计划）。

## 4. 监控体系（监控层的“清单化”）

### 4.1 监控原则（降低误报）
分位阈值与去噪建议以 2.0 文档为准（参见 [交易AI Agent 技术文档2.0.md:L1021-L1029](file:///Users/zhangjiangtao/ft_userdata/经典指标机器学习系统/交易AI%20Agent%20技术文档2.0.md#L1021-L1029)）：
- 基线窗口：滚动 30D（不足用 7D），按 5m 粒度聚合；可按 hour-of-day 分桶降低昼夜节律误报。
- 阈值：年龄类看 P99，计数类看 P01，占比类看 P99 或相对中位数倍数，取更保守。
- 连续命中：同一异常连续 N 次命中才升级告警（建议 3 次）。
- 冷却幂等：同一根因 30m 内不重复触发修复（仅更新状态与证据）。

### 4.2 10 分钟轮询清单（建议以“证据 + 卡点”为输出）
下表为最小可用监控清单，推荐直接对齐 2.0 文档的端点与字段口径（参见 [交易AI Agent 技术文档2.0.md:L1030-L1043](file:///Users/zhangjiangtao/ft_userdata/经典指标机器学习系统/交易AI%20Agent%20技术文档2.0.md#L1030-L1043)）：

| 编号 | 监控主题 | 核心信号 | 目标 | 常见卡点（示例） |
| --- | --- | --- | --- | --- |
| M1 | 服务可用性 | /health、/metrics 可达且 ts 递增 | 先保证可观测 | backend_down、proxy_misroute |
| M2 | Strategy 信号新鲜度 | last_signal_age_sec、signals_1h | 避免“沉默失效” | feeders_stalled、data_stale |
| M3 | Gate/Arena 健康 | gating/state 分母漂移、字段缺失率 | 避免门禁黑盒 | model_missing、vote_denominator_drift |
| M4 | 信号→订单链路 | signal_to_order_gap_rate、last_order_age_sec | 避免“信号有但不下单”不可解释 | decision_not_triggered、risk_reject |
| M5 | 拒单结构突变 | top_reason_share、reason_entropy、faq_hits | 识别结构性 bug/参数漂移 | min_notional、venue_constraint |
| M6 | Universe/候选池 | core/shadow/watchlist 长度与更新时间 | 避免候选池空转 | universe_update_stale、pool_empty |
| M7 | Quant 静默异常 | candidates 非空但 orders 长期为 0 | 区分“正常无交易”与故障 | execute_off、preflight_reject |
| M8 | 三屏链路连通 | weekly/daily/5m status_ok | 避免三屏退化不自知 | insufficient_bars、alignment_fail |
| M9 | outbox 堆积/失败 | pending/failed 数量与最旧 age | 避免审批/推送卡死 | approval_backlog、deliver_fail |

输出要求（每次轮询必须落盘）：
- 证据：每条异常必须带 endpoint + 参数快照 + 摘要 hash（避免日志漂移）。
- 解释：必须给出“可能原因 top3 + 下一步最小动作（R0/R1）”。

### 4.3 每日深检清单（建议）
- System Monitor 深检（link_check + triage + backtest + changeset + request_approval）。
- 投票与门禁状态一致性复核（gating/state 快照落盘）。
- Universe 与候选稳定性复核（top candidates 元信息可回放）。
- 执行质量与数据质量告警汇总（audit/alerts/evaluate）。

## 5. 事件处置流程（分析思考层：从“现象”到“可执行结论”）

### 5.1 处置总流程（统一口径）
1) 取证（R0）：抓取 endpoints 摘要 + outbox 相关记录，生成 trace_id。
2) 解释：命中 FAQ/Runbook（优先复用已有排障口径）。
3) 分级：判断 P 级别与影响范围（Strategy/Quant/Carry/ThreeScreen）。
4) 给出选项：按 R0/R1/R2/R3 列出最小动作集合，默认 tighten-only。
5) 验证：R1 沙箱/重放验证（如适用），生成 gate_result 与 baseline_ref。
6) 提案：需要 R2/R3 时生成 proposal，进入审批队列。
7) 放行：审批通过后由受控执行器落地，并记录回执与回滚点。
8) 复盘：补齐 FAQ、阈值与监控卡点映射，避免重复。

### 5.2 P0/P1 快速处置准则（止血优先）
- P0：优先“冻结风险扩张”而非“追求收益修复”。先让链路处于可控、可解释、可回滚状态，再恢复自动化。
- P1：先恢复关键链路连通性（可观测与证据链），再进行参数寻优/策略更替。

## 6. 修复与变更治理（工具调用修复层）

### 6.1 “先修复自动化流程，再修复业务”原则
- 自动化/监控/审批链路一旦卡死，会导致后续任何修复都不可运营。
- 因此修复优先级：
  1) 可观测性与证据链（health/metrics/outbox/审计回放）
  2) 链路连通性（signals→gate→orders→tracker）
  3) 卡点可解释（拒单原因/门禁原因/开关状态能被解释）
  4) 参数/模型/策略层优化

### 6.2 受控变更（R2）标准动作
R2 属于“可能改变生产行为”的动作，必须具备：
- 变更包（proposal/changeset）
- 审批记录（maker-checker）
- 回滚点（配置快照或版本回退）
- 审计落盘（trace_id、执行回执）

R2 常见类别：
- 配置 patch（优先可回滚）
- 灰度与回滚
- 受控重启（仅在具备证据与冷却策略时）

### 6.3 代码变更（R3）准入
R3 必须走严格流程：
- 先以 R0/R1 证明“参数/配置无法修复或存在逻辑缺陷”
- 形成变更包草案（含风险评估与回滚）
- 人工审核通过后才允许落地

### 8.1 目录与环境

### 8.2 产物统一字段（建议最小集合）
所有产物建议具备最小字段集合（便于 UI/审计/回放）：
- kind：产物类型（health_snapshot / alert / triage_report / proposal / approval_request / execution_result / report）
- ts_ms：产出时间
- env：prod/explore/pilot（或等价标识）
- trace_id：一次事件链路的统一追踪 id
- idempotency_key：用于幂等去重（同根因不重复触发修复）
- severity：P0–P3
- summary：人类可读摘要（1–3 行）
- payload：机器可读内容（证据、参数、指标、决策）

### 8.3 状态与卡点字段（运营可扫一眼）
建议统一输出：
- status：RUNNING / BLOCKED / PENDING_APPROVAL / DONE / ROLLED_BACK
- blocked_reason：gate_fail / approval_pending / queue_full / auth_expired / upstream_down
- next_action：推荐下一步最小动作（R0/R1 优先）

## 10. 应急与恢复（Runbook 概览）

### 10.1 典型应急场景
- 后端不可用：先恢复 /health /metrics，再验证前端 proxy 与端口一致性。
- 信号沉默：区分“市场无机会/策略本就低频”与“采集/feeder 停滞/数据陈旧”。
- 信号有但无订单：优先解释 trigger_decision、风控 gate、执行预检与最小名义额约束。
- outbox 堆积：先恢复审批/投递链路（否则任何修复无法运营）。

### 10.2 受控重启与自恢复
